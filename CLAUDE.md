# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MedCEA is a shell-script-based IoT platform deployer targeting a single Ubuntu PC running MicroK8s. It installs and wires together: Kubeflow, Keycloak (SSO), PostgreSQL, Grafana, Node-RED, and OAuth2 Proxy.

**There is no build step, no test suite, and no package manager.** The codebase is bash scripts plus a config file, split into infrastructure (`deploy-infra.sh`) and application content (`deploy-apps.sh` / `apps/`).

## MedCEA Direction

This repo was forked from `pfplatform` (@2032725) as the baseline for the MedCEA PhD prototype. Read [docs/medcea-concept.md](docs/medcea-concept.md) (four pillars, H1–H3, experiments) and [docs/architecture.md](docs/architecture.md) (layer → component mapping, Compliance Plane TODOs) before adding features. Two rules follow from the concept:
- **The Compliance Plane is read-only from the operational layers.** Operational services may append events to it, but never get UPDATE/DELETE on audit, EPCIS or EBR storage.
- **`PROJECT_NAME` (`medcea`) is the one project identifier.** It is the MQTT topic root, and `config.env` derives `NAMESPACE` and `KEYCLOAK_REALM` from it; `deploy-infra.sh` refuses a value that is not `^[a-z][a-z0-9-]{1,30}$`. The database is `medcea_db` with schema `medcea` — a literal, because the schema name is written into the SQL, not templated. `cea` survives only as the domain term "controlled environment agriculture": the table names `cea_unit`/`cea_zone`/`cea_location`, the Python package `schd/cea/` (so `cea.run_agent(...)` is a module call, not a schema), `CEA_*` env vars, `cea-tls`/`cea-ca`, and the `cea-un-<mac6>` hostname of an unregistered board.

## Full Deployment Workflow

All scripts must be run from the repository root; they call each other via relative paths and source `config.env` from the current directory.

```bash
# Everything, in order (infra → apps → health check), with the credentials box last:
./install.sh             # --help lists --configure, --infra-only, --apps-only and the uninstall levels
./install.sh --uninstall-apps [component ...] [--purge-data] | --uninstall-infra | --uninstall-all

# The stages on their own:
# 1. Deploy infrastructure (safe to re-run — bootstrap is skipped if already done).
#    The first run creates config.env from config.env.example by Q&A (infra/configure.sh);
#    later runs ask only for empty required values. Review all: ./deploy-infra.sh --configure
./deploy-infra.sh

# Help text (does not require config.env to be present)
./deploy-infra.sh --help

# 2. Deploy application content (interactive component selector):
./deploy-apps.sh
./deploy-apps.sh --all   # non-interactive

# Recovery only: if Juju charm update resets dex-auth config, re-run:
./patch-dex-keycloak.sh
```

## Script Roles

- **`bootstrap-infra.sh`** — Called by `deploy-infra.sh`. Handles: K3s cleanup, MicroK8s snap install/wipe (interactive prompt, also removes Juju on wipe), MicroK8s addon enablement (dns:8.8.8.8, hostpath-storage, rbac, ingress, helm3, metallb), inotify limit tuning, kubeconfig export, Juju 3.6/stable install, Charmed Kubeflow 1.9 deployment via `juju deploy kubeflow --trust`, dex-auth/oidc-gatekeeper initial configuration, and pod-count readiness wait.
- **`infra/configure.sh`** — Fills `config.env` by Q&A. It is called by `deploy-infra.sh` before logging starts, so answers and generated passwords stay out of `logs/`. `config.env.example` is always the base: on each run the file is rebuilt from the template with existing values carried over line for line, and keys only the old file had are kept at the end. It checks Tailscale on every run, before the early exit for a complete file. `USE_TAILSCALE` records whether `DOMAIN` depends on it: `true` makes a down Tailscale fatal, because the `DOMAIN` expression would quietly fall back to the LAN IP; `false` means LAN-only on purpose and is not raised again. Pressing Enter leaves a line untouched, so expressions like `DOMAIN="$(tailscale ip ...)"` stay expressions. Passwords are limited to `[A-Za-z0-9._~-]` because they are spliced unencoded into YAML, a `postgres://` URL, `helm --set` and a curl form body.
- **`install.sh`** — Single entry point and thin wrapper. It runs `deploy-infra.sh` → `deploy-apps.sh --all` → `health-check.sh`, and the uninstall levels map onto `deploy-apps.sh --uninstall`, `deploy-infra.sh --reset` and `deploy-infra.sh --uninstall` (plus host cleanup that keeps `edge/provisioned/`). It exports `MEDCEA_INSTALLER=1`, so deploy-infra leaves the credentials box for the end, and `MEDCEA_CONFIRMED=1` after its own typed confirmation, so the sub-scripts don't ask a second time.
- **`apps/<component>/uninstall.sh`** — The inverse of that component's `deploy.sh`, discovered by `deploy-apps.sh --uninstall` and run in reverse alphabetical order (so `database` goes last but for `access`, whose `--purge-data` copes with `medcea_db` being gone already). **A new component ships both files.** Uninstall must not break infrastructure: remove patches from infra Deployments before deleting the ConfigMaps they mount (report → Grafana), and leave anything infra mounts (`portal-nginx`). Database data is dropped only with `--purge-data`.
- **`infra/lib-portal.sh`** — `portal_card enable|disable URL`, exact inverses that find a portal card by its URL. App deploys enable their card and uninstalls disable it.
- **`infra/lib-credentials.sh`** — `show_credentials FILE`, which writes to `/dev/tty`; used by deploy-infra (standalone) and install.sh.
- **`k8s/` and `apps/<c>/k8s/`** — Every Kubernetes manifest and Helm values file is a template there, not a bash heredoc. Scripts do `render FILE VAR... | $KUBECTL apply -f -` (or `> "$VALUES"` for Helm). Configs without variables (nginx confs, the Grafana dashboard provider, the MQTT Explorer HTML) are plain files used with `--from-file`. Every oauth2-proxy release shares `k8s/oauth2-proxy/values-common.yaml`. This is the groundwork for a later Argo CD/Flux move (in-cluster layer only).
- **`infra/lib-render.sh`** — `render FILE VAR...` runs `envsubst` with an **explicit** variable list in a subshell. Never bare `envsubst`: the templates contain nginx `$host/$uri/$1`, JupyterHub `$HOME`, `$request_uri` and JavaScript `${…}`, which must survive. When adding `${NEWVAR}` to a template, add it to the `render` call too: an unlisted variable is silently left as literal text. Values over 128 KiB can't go through the environment, so the portal background uses a placeholder plus a python filter.
- **`infra/lib-mk8s.sh`** — `mk8s` / `$MK8S` / `$KUBECTL`: plain `microk8s` when the session has the group, otherwise sudo with an explanatory prompt. Every app script sources it.
- **`infra/lib-prereqs.sh`** — `check_prereqs`: host packages a clean Ubuntu may lack (curl, ca-certificates, openssl, python3, python3-venv, iproute2, snapd), each with a test and an apt package. It is sourced by `configure.sh`, so every `deploy-infra.sh` run checks, and by `deploy-apps.sh`. **When a script starts calling a new host command, add it here**; psql and kubectl don't count, because they run in pods or come from the MicroK8s snap.
- **`infra/lib-lock.sh`** — `medcea_lock`: **one deploy at a time.** Called once, after the `--help` branch, by every script that changes the cluster or `config.env` (install, deploy-infra, configure, bootstrap, deploy-workbench, deploy-apps, each `apps/<c>/deploy.sh`/`uninstall.sh`); `health-check.sh` and `--help` stay unlocked. It is `flock` on fd 9 of `.medcea.lock` (gitignored), so the kernel drops it when the holder dies and there is no stale lock; the PID/command written into the file only explains a refusal. The first locker exports `MEDCEA_LOCK_HELD` and the scripts it runs skip the lock. A new entry script calls it; a new component's scripts already do.
- **`apps/iam/` (access policy)** — `policy/defaults.yaml` is the one source of access rights (roles, levels, resource groups with their route tables, constraints, invariants, help text); `compiler/` is its only reader. `python3 apps/iam/compiler/cli.py check` runs the invariants, `… hosts` shows who each host admits, and `policy_groups HOST_VAR` (`infra/lib-oauth2-proxy.sh`) compiles a host's `allowed_groups` into the values template's `${ALLOWED_GROUPS}` — every oauth2-proxy gate except the User Manager's (admin-only until IAM Phase 2.7) comes from it. **A new host, route, table or role goes into the YAML, not into a values file.** `IAM_GATES=false` renders the pre-policy lists. `tests/test_policy.py` (stdlib unittest) must stay green; it also proves the checker catches 28 kinds of violation (7 of them in `network:`). `cli.py compile routes` (`compiler/routes.py`) compiles every `api` member into the route table: per service, `"METHOD /path"` → group, level(s) and the roles that may call it (`null`, or the constraints that must hold), plus the clients whose tokens it accepts (azp) and `public_routes`. `deploy-infra.sh` writes it to ConfigMap `medcea-iam-lib` together with the check library `apps/iam/lib/medcea_iam.py` and `settings.json` (issuer, audience `medcea-api`, `enforce` = `IAM_ENFORCE`), and publishes the realm's public keys as Secret `medcea-jwks`. The five Python services (scheduler, monitor, dbmgmt, config-ui's platform-api, access) mount both `optional` at `/iam/` and `/jwks/`, load `medcea_iam.py` from the mount on every request (reloaded when it changes, so neither a late ConfigMap nor a new library needs a restart) and call `flask_check(service)` from a `before_request` hook or `http_check(handler, service)` from `parse_request` — access per port: `access-public`, `access`, `access-profile`. **`check()` trusts only a verified token**: `X-Forwarded-Access-Token` (or `Authorization: Bearer`), RS256 against `/jwks/`, iss, aud ∋ `medcea-api`, typ `Bearer`, azp among the clients of the hosts that serve the service; never `X-Forwarded-User/-Groups`, which anything in the cluster can send. The most specific route wins (`/api/runs/active` over `/api/runs/<id>`); a trailing slash is retried without it; a route not in the table is refused; a constraint (own_zone …) is reported, not evaluated (Phase 2). **`IAM_ENFORCE=false` (Phase 1) logs `medcea_iam: would refuse …` to stderr and lets the request through**; true answers 401/403/503. Every proxy with a Python upstream has `pass_access_token = true` (the token as `X-Forwarded-Access-Token`, never as `Authorization`, which PostgREST would try to verify before Phase 2); **Node-RED's stays false on purpose** — its editor runs engineers' code, which could read and replay the token. A new service: mount both, install `pyjwt[crypto]`, copy the `_medcea_iam()` loader and call the wrapper with its route-table name. **Application pods admit only their callers** (Phase 1.4): `network:` in `defaults.yaml` lists, per pod (scheduler, monitor, dbmgmt, config-ui, config-api, access), its selector, the route-table services it `carries` and, per container port, who may connect — `proxy:<HOST>` (`network.proxies`: release name), `pod:<name>`, `ingress` (ingress-nginx) or `node`. `compiler/netpol.py` checks it port by port (every host must reach what it serves, directly or through one pod — config proxy → config-ui → config-api/scheduler; `unproxied` hosts as their own source — the edge wizard as `node`; every proxy but `no_shared_upstreams` must reach `/_account/`) and compiles one NetworkPolicy per pod, `iam-<pod>`, labelled `medcea/iam-netpol=true`; `deploy-infra.sh` applies them with the node's addresses (InternalIP plus Calico's, read at deploy time: host traffic such as kubelet probes and the edge wizard arrives from the InternalIP) and deletes stale ones. **Rollback: `IAM_NETPOL=false` + `./deploy-infra.sh`, or at once `kubectl delete netpol -l medcea/iam-netpol=true`.** NetworkPolicy ports are container ports, not Service ports (access: 8080 public, 8081 admin, 8082 profile). **A new caller of an application pod needs an entry in `network:`**, or Calico drops it (a timeout, not a refusal). Portal, mqtt-explorer, Node-RED, Grafana and the workbench are not covered. `tests/iam-network.sh` (locked) starts a throwaway pod that must time out on every application pod while still reaching Keycloak, and checks the allowed hops. `tests/iam-routes-diff.py` (read-only, no cluster) compares the compiled route table with the routes each service's source serves (`compiler/routes_diff.py`: Flask decorators, the `do_<METHOD>` dispatchers, platform-api's `_resolve` run on probe paths) through `medcea_iam.match()`, so a served route the table lacks — refused once `IAM_ENFORCE=true` — fails; its `REMOVED` (2.6) and `NOT_BUILT` (2.7, 3.5, 4.1) lists name the planned differences and fail once stale. **A new route goes into the YAML and the code together**, and a new service into `SOURCES`. `tests/test_medcea_iam.py` signs tokens with a throwaway key and tests `check()`; `tests/iam-check.sh` (read-only) checks every pod's mounts and sends it a forged request, which must be logged as refused. `tests/iam-signin.sh` (locked) creates one throwaway account per role (`test-<role>-<hex>`, deleted on exit) and `tests/iam_signin_flow.py` signs each in to every gated host the way a browser does — host → Keycloak's form → the proxy's callback — then compares in/refused with the compiled gates (88 sign-ins, the 403 page must explain the refusal); where an account gets in it calls one read-only API per service, and the services' logs must hold `would refuse` for exactly the calls the route table refuses. It needs no proxy change and no test client. The platform CA has no keyUsage extension: Python 3.13's strict verification rejects it (browsers and curl do not), so the flow clears `VERIFY_X509_STRICT` and still verifies chain and host. `tests/iam-schema.sh` (read-only, no lock) checks the ConfigMap and every pod's copy against a fresh compile, migration 008a, its grants and the hash chain. `tests/iam-hosts.sh` (read-only, no lock) checks the running cluster: each compiled host's live `allowed_groups` equals the policy, its pod is newer than its config, Keycloak accepts its sign-in scopes, and some enabled account can open it. The plan is `codeplan/MedCEA_IAM_Implementation_Plan.md` (gitignored).
- **`infra/lib-keycloak-admin.sh`** — who the scripts are to Keycloak's admin API. `_kc_token` in deploy-infra delegates to it: the master-realm client `medcea-deployer` (client credentials, `KC_DEPLOYER_SECRET`), else the break-glass console account `KC_BREAKGLASS_USER` (`kc-breakglass`), else — once, to migrate an older install — the legacy master `ADMIN_USER`, which is then disabled (never deleted). **Realm `master` and realm `medcea` both may have a user called `admin`; they are different accounts** — the platform admin (portal, Change password) lives in `medcea`, the console account in `master`. Login and admin events are on in both realms; impersonation is disabled (`--features-disabled=impersonation`).
- **`deploy-infra.sh`** — Top-level infrastructure orchestrator. Also deploys the AI workbench (`infra/deploy-workbench.sh`, JupyterHub) unless `WORKBENCH_ENABLED=false` — it is a platform service, and infra already owns its Keycloak client, portal card and URL. Validates config (including METALLB_RANGE and KUBEFLOW_IP), prompts for Docker Hub credentials, calls `bootstrap-infra.sh`, then deploys Postgres → Keycloak → Mosquitto → (Node-RED + Grafana + OAuth2 Proxy) via Helm.
- **`deploy-apps.sh`** — Interactive app content installer. Discovers components under `apps/<component>/deploy.sh` and presents a checkbox menu. Use `--all` to skip the prompt.
- **`infra/deploy-workbench.sh`** — JupyterHub, authenticated against Keycloak with `GenericOAuthenticator`. Replaced Charmed Kubeflow, which `bootstrap-infra.sh` used to deploy. Runnable standalone to redeploy just the workbench.
- **`patch-dex-keycloak.sh`** — Recovery script. Re-applies the Keycloak OIDC connector to the `dex-auth` Juju charm via `juju config dex-auth connectors=<yaml>`. Not needed for initial deployment (deploy-infra.sh handles this). Run it when a Juju charm update resets the dex-auth config. There is no ConfigMap to patch — Juju owns the dex-auth config entirely.
- **`apps/access/html/user-menu.js` + `profile.html`** — The user menu on every signed-in page: the person's name (never role, username or e-mail) opening **Profile** and **Sign out**. Pages include `<script src="/_account/user-menu.js" defer>` (and optionally `<div id="user-menu">` to place it; otherwise it pins top-right). `/_account/` is a second upstream of each signed-in host's oauth2-proxy (portal, config, access) routed to `access-profile` (:8082), so the profile acts for whoever *that* proxy signed in — any role, own account only; oauth2-proxy strips a client-sent `X-Forwarded-Preferred-Username`. The profile edits first/last name and `organisation` (a declared user-profile attribute: Keycloak 26 drops undeclared ones) through the service account; **Change password** is a Keycloak application-initiated action (`kc_action=UPDATE_PASSWORD`, themed page, returns to `/_account/` — registered as a redirect URI on each client), so no password passes through our code. A new signed-in host needs: the upstream, `<host>=<client>` in `HOST_CLIENTS` (`apps/access/deploy.sh`), and the script tag. Every web UI now has it (portal, config, access, monitor, scheduler, dbmgmt, mqtt-explorer).
- **`k8s/keycloak/theme/medcea/login/`** — The platform's only login page, as a Keycloak login theme (realm `loginTheme=medcea`, set by `deploy-infra.sh`). `parent=base`, so every secondary Keycloak page (forgot/update password, errors, logout) renders inside our `template.ftl` with none of Keycloak's PatternFly styling. `login.ftl` has two tabs, Sign in (Keycloak's own form) and Request access (posts with `fetch` to `access.$DOMAIN/api/register`, which allows CORS from the Keycloak origin only); `/#register` opens the second tab, and `access.$DOMAIN/register` redirects there. Every proxy has `skip_provider_button = true`, Grafana `GF_AUTH_OAUTH_AUTO_LOGIN` and JupyterHub `auto_login`, so no service shows its own "Sign in with Keycloak" stop. The portal proxy's 403 (signed in, no platform role) is `k8s/portal/error.html`.
- **`infra/lib-oauth2-proxy.sh` + `k8s/oauth2-proxy/values-app.yaml`** — **Every web UI signs in through Keycloak.** `deploy_oauth2_proxy RELEASE CLIENT SECRET COOKIE HOST VALUES` is the one helm call; `values-app.yaml` (rendered with `APP_SERVICE`) is the shared gate: any platform role (`allowed_groups`), the app Service plus the `/_account/` user-menu upstream. Used by config, monitor, scheduler and dbmgmt; the explorer has its own copy with the broker WebSocket upstream. Recipe for a new UI: `_create_client` + cookie secret + upsert + `groups` loop in `deploy-infra.sh`; in the app's deploy.sh delete the app's own Ingress **before** the helm install (the proxy's Ingress owns the host), render `values-app.yaml`, `gate_error_page RELEASE HOST_VAR "$ALLOWED_GROUPS"` (the 403 page: "No access to <service>", the roles that may open it, ask an administrator — ConfigMap `RELEASE-templates`, which `deploy_oauth2_proxy` mounts at `custom_templates_dir`; a direct helm call adds `gate_helm_args`), `deploy_oauth2_proxy`, `wait_for_http` (302 counts as up); `helm3 uninstall` and `delete configmap RELEASE-templates` in uninstall.sh; `HOST_CLIENTS` + script tag for the menu. Keep the Service plain: the Config UI calls the scheduler in-cluster at `scheduler.<ns>.svc` (`/scheduler-api/`). pgAdmin is the exception — it does OAuth2 itself (`PGADMIN_CONFIG_*`, admin role only via `OAUTH2_ADDITIONAL_CLAIMS`).
- **`apps/mqtt-explorer/`** — The browser MQTT tool, moved out of `deploy-infra.sh` because it needs a Keycloak secret like the other app UIs. The page connects to `wss://<MQTTX_DOMAIN>/mqtt`: its oauth2-proxy routes `/mqtt` to Service `mosquitto-ws` (:9001, ClusterIP only — the 31901 NodePort is gone), so the broker's WebSocket is reachable only signed in, same-origin (no mixed content), and the broker still checks the `mqtt-explorer` service account baked into the page at deploy. Ingress read/send timeouts are 3600 s and mqtt.js keepalive 30 s, or ingress-nginx closes an idle socket after 60 s.
- **`k8s/mosquitto/mqtt-auth-sync.py` + `infra/mqtt-passwd.py`** — **The broker admits nobody anonymously.** A sidecar in the Mosquitto pod merges the service accounts (Secret `mosquitto-service-auth`, hashed by deploy-infra: `node-red` read root, `scheduler` read sense / write control, `mqtt-explorer` readwrite root) with `medcea.mqtt_credential` (read as role `mqtt_auth`, SELECT only) into `/mosquitto/auth/{passwd,acl}` every 15 s, writes atomically and SIGHUPs Mosquitto (`shareProcessNamespace`). It keeps the last good device set if the DB is unreachable — the DB is created in the apps stage, after the broker — so only a successful query can shrink the fleet. `mqtt-passwd.py` writes the `$7$101$…` PBKDF2-SHA512 hash `mosquitto_passwd` writes (verified against it); password on stdin only. Hashes are made on the host; the sidecar never hashes.
- **`apps/access/`** — Self-service access requests. One Python process on two ports: `:8080` (Service `access-public`, its own Ingress for `/register` and `/api/register` only) and `:8081` (Service `access-admin`, reachable only as the upstream of `access-oauth2-proxy`, which admits realm role `admin` and supplies `X-Forwarded-Preferred-Username` for the audit trail). **The trust boundary is the port, not a path check**: never route `access-admin` from a public Ingress. Data is in schema `iam` (not `medcea`, which PostgREST exposes to `anon` with full DML), owned by role `access_svc` with no DELETE anywhere; `iam.access_request_history` is written by a SECURITY DEFINER trigger only, and a BEFORE UPDATE trigger makes a decision final. **E-mail is configured in the User Manager, not `config.env`**: the Gmail account in `iam.mail_settings` (one row; the app password is never returned by the API), the four templates in `iam.mail_template` (absent row = the default file `apps/access/templates/<name>.txt`, first line `Subject:`), and every change in the append-only `iam.config_history` (never the password). Saving settings logs in first, then pushes the account to the realm's `smtpServer` and `resetPasswordAllowed` — which is why the service account also holds `manage-realm`, and why `deploy-infra.sh` must never set realm SMTP itself (it would undo the UI on every run). The **Users** tab lists every realm account (service accounts excluded) with its platform role and deactivates/activates it: a deactivation needs a reason, signs the person out of every session (`POST /users/{id}/logout`) and is refused for your own account, for the last enabled admin, and — for activation — for an account whose access request is still pending (that goes through the request). Each change is appended to `iam.user_status_history` (INSERT/SELECT only for `access_svc`) inside the same transaction as the Keycloak change. Keycloak users are always updated read-modify-write (`kc_set_enabled`), never by partial PUT. It also changes an account's role: **one platform role per account**, the new one added before the old ones are removed (a failure in between leaves two roles, never none), a reason required, refused for your own account, for taking `admin` from the last enabled admin, and for pending accounts; recorded as `role_changed` with `from_role`/`to_role` in the same history. It reaches the portal at the next `cookie_refresh` (≤4 min), without a sign-out. In a decision the approver edits the pre-filled e-mail (rendered client-side with the same `$var` rules as `string.Template.safe_substitute`); what was sent is stored in `access_request.email_subject/email_body`. `apps/access/deploy.sh` imports `SMTP_USER`/`SMTP_PASS` from an old `config.env` once, only while the UI settings are empty. Keycloak's side lives in `deploy-infra.sh`: the four realm roles, client `access` (browser login **and** a service account with realm-management `manage-users`/`view-users`/`query-users`/`manage-realm`), and the `groups` client scope (realm roles as the `groups` claim) as a default scope of `portal` and `access`.
- **`edge/flash-device.sh`** — Device onboarding. Flashes MicroPython over USB, asks for a role and a unit/zone slot from the platform database, asks which sensors or relay channels are wired to which GPIO, ships the application, and writes the `medcea.device` row. `--unregistered` keeps the old bench behaviour (no slot, no application, no database).
- **`edge/wizard-daemon.sh`** — The always-on browser front end for the above, behind Keycloak. Linked from the Devices tab.
- **`apps/edge-wizard/`** — Makes the wizard part of the install: builds `edge/.venv` (`ensure_edge_venv` in `edge/lib-venv.sh`, shared with `flash-device.sh`), writes the `cea-edge-wizard` systemd **user** unit from `wizard-daemon.sh --install-unit`, restarts it (a `--reset` gives the Keycloak client a new secret) and enables linger. A host service, not a pod, because flashing is over USB; it sorts before `frontend`, whose deploy checks the wizard answers. Browsers reach it at `https://$ONBOARD_DOMAIN` (`onboard-device.medcea`): a selector-less Service whose Endpoints is the host (`PLATFORM_IP:EDGE_WIZARD_PORT`, the node's InternalIP), behind the usual TLS Ingress. The wizard takes `--allowed-host https://<name>` for a proxied name and builds that redirect_uri with https; the name is in `_SVC_DOMAINS` (certificate SAN) and in the `edge-wizard` client's redirect URIs, so adding it needs a `deploy-infra.sh` run.
- **`edge/templates/<family>-{sense,control}.json`** — **The wizard's questions are data, not code.** Adding a supported sensor is an entry here plus a branch in `edge/src/app/cea_sense.py`; `flash-device.sh` does not change. The file name carries the device family (`esp32-control.json`); `CEA_DEVICE_FAMILY` selects one, default `esp32`.
- **`edge/templates/esp32-gpio.json`** — The GPIO reference for the whole ESP32 family: which pins each of the seven variants has, and what already wants them (SPI flash, PSRAM, strapping, USB-JTAG, UART0, input-only). Sourced from Espressif's per-target ESP-IDF GPIO pages. It drives the form's board selector, its pin reference panel, and validation — one table, so the reference cannot say a pin is free while the validator calls it taken.
- **`edge/src/host/bindings.py`** — How a command reaches equipment: what identifies one channel, what counts as a legal address, and what the field is called in the file the device reads. Driven by the template's `binding` block, so a device family that is not addressed by GPIO is a new template rather than new Python. Also holds `validate_config()`, the structural checks both the renderer and the browser editor apply.
- **`edge/src/host/ui/channelmap.{js,css}`** — The channel-map editor. Inlined into the wizard page by `wizard_server.py` and into the standalone tool by `edge/tools/build-editor.sh` — one implementation, two hosts. It renders whatever `device_template.py channelmap` prints and contains no mention of a GPIO.
- **`edge/tools/build-editor.sh`** — Rebuilds `edge/tools/actuator-config-editor.html`, a serverless copy of the editor for inspecting or hand-correcting a map away from the platform. Re-run it after changing `channelmap.js`, `channelmap.css`, or the CONTROL template.
- **`edge/src/host/platform_db.py`** — Units, zones, free slots and device registration over PostgREST. Reaches `config-api` by ClusterIP (kube-proxy runs on the host, so ClusterIPs are routable); `CEA_CONFIG_API` overrides.
- **`edge/src/host/device_template.py`** — Turns a template into prompts, then prompts into the board's `device_cfg.py` / `actuator_config.json` and the database component rows.
- **`edge/src/app/`** — The MicroPython application, **identical on every board**. Per-device values live only in the generated `device_cfg.py`; `config.py` derives topics and client id from it, `main.py` dispatches on `ROLE`.
- **`apps/<component>/deploy.sh`** — Per-component idempotent deploy script. Each sources `config.env` from the repo root and uses `sudo microk8s kubectl` directly. New components are auto-discovered by `deploy-apps.sh`.
- **`config.env`** — Sourced by all scripts. Not committed (in `.gitignore`). See `config.env.example` for the full variable list.

## Key Architecture Decisions

**Single-pass deployment:** `deploy-infra.sh` deploys everything in one run. After Keycloak is ready, it uses the Admin REST API to create realm `medcea` and confidential clients (`node-red`, `grafana`, `kubeflow`), then writes the generated secrets into `config.env` and re-sources it before deploying the services that need them.

**Charmed Kubeflow 1.9 via Juju:** Kubeflow is deployed as `juju deploy kubeflow --trust --channel=$KF_CHANNEL` into MicroK8s. Juju manages the entire Kubeflow operator lifecycle. This replaces the old approach of manually cloning manifests and running 5 sequential `kubectl apply -k` passes with cert-manager readiness gating.

**MetalLB for Kubeflow ingress:** MicroK8s's MetalLB addon assigns a real LAN IP from `METALLB_RANGE` to Kubeflow's `istio-ingressgateway` LoadBalancer service. `KUBEFLOW_IP` is the first IP from that range and is used for all Dex and oidc-gatekeeper configuration. Kubeflow is accessed at `http://$KUBEFLOW_IP` (not via subdomain).

**Bootstrap fast-exit:** `bootstrap-infra.sh` exits immediately (without prompts) if both MicroK8s and a Juju controller named `k8s-controller` already exist. On wipe, it removes Juju (snap + `~/.local/share/juju`) before removing MicroK8s.

**Device identity comes from the database, not from typing:** a board is a slot — one unit, one zone, one role — and a unit/zone holds one and only one SENSE and one and only one CONTROL. Free slots are read from `medcea.device` on every run — a slot is free when no *active* device of that role points at the zone — so replacing a board is marking the old one inactive. `platform_db.register()` finds the slot's row by `zone_id` + `device_type` (most recent, active or not) and updates it in place, `dns_name` included, so re-onboarding never creates a second row, even after a code was renamed. A board is one row because `serial_number` (the MAC) is unique: when the board just probed is registered in a *different* slot (`platform_db.py board <serial>`), the wizard asks "Move this board from <old> to <unit> / <zone>?" right after the MAC is read and before anything is erased. Yes passes `move_device_id` and its own row moves (an older inactive row in the target slot is renamed `<name>-<id>` to free the name); no stops with nothing written; `--yes` refuses rather than move silently. Every placement is kept in `medcea.device_slot_history` (migration 006): trigger `device_slot_history_trg` on `medcea.device` appends `placed`/`moved`/`renamed`/`replaced`/`removed` with from/to slot, name and serial — whether the change came from the wizard or from the config UI's Edit. It is append-only by the Compliance Plane rule: the trigger function is `SECURITY DEFINER`, and `apps/database/deploy.sh` revokes INSERT/UPDATE/DELETE on it from `anon` **after** its blanket grant (which would otherwise re-grant them on every deploy). No foreign key, so the history outlives a deleted device. Everything derivable from the slot (MQTT host and port, topics, client id) is inferred and never asked.

**Access is requested, not created:** the portal's oauth2-proxy admits only realm roles `operator`/`qa`/`auditor`/`admin` (`allowed_groups`, read from the `groups` claim). A person asks through `access.$DOMAIN/register`, which creates the Keycloak user **disabled** and an `iam.access_request` row; an admin approves (role as requested, or reassigned) or rejects with notes in the User Manager. Approval maps the role and enables the user; rejection deletes the Keycloak account and keeps the row, so the person can apply again. Keycloak is changed inside the open DB transaction that holds the request row `FOR UPDATE`, so a Keycloak failure leaves the request pending, and two admins cannot both decide it. Mail goes out after commit and never undoes a decision; until e-mail is set up in the User Manager it goes to the service log. `deploy-infra.sh` gives the built-in users a role (ADMIN_USER and Grafana admin → `admin`, developer → `operator`, viewer → `auditor`) in the same run that turns the gate on, so nobody is locked out by the upgrade; users created by hand in Keycloak need a role.

**A board's MQTT identity is its name:** onboarding (`flash-device.sh`) mints a fresh password per board on every onboarding, writes `MQTT_USER` (= `dns_name`) / `MQTT_PASS` into `device_cfg.py` and the provisioned record — never into `component.parameters`, which `anon` can read — and registers only the hash through `POST /rpc/register_mqtt_credential` (SECURITY DEFINER, migration 007; `anon` may execute it but cannot read `medcea.mqtt_credential`). The ACL confines a SENSE board to `<topic_base>/sense/#` (write) and a CONTROL board to `…/control/#` (read) + `…/control_setpoint/#` (write). Marking the device inactive (`device.is_active='N'`) revokes it within one sync (≈15 s). A board flashed before credentials existed cannot connect: re-onboard it.

**One name per device — the DHCP hostname:** `lower(unit_code)-<s|c>-lower(zone_code)`, e.g. `unit02-c-zone02` (`platform_db.slot_hostname`). It is the hostname DHCP registers, `medcea.device.dns_name`, `device_dns` in every MQTT payload (the key name is kept for Node-RED, `measurement.device_dns` and the `msg_*` views), what the config UI's Online check pings, and the record file name. Lowercasing is the **only** transformation: a code a hostname cannot hold (underscore, space, leading/trailing hyphen) or a name over 32 characters (MicroPython's hostname buffer) makes the slot "unnamed" — listed with the reason, not offered — and the fix is renaming the code. There is no fallback name. Uniqueness comes from the codes: migration 005 adds case-insensitive unique indexes on `unit_code` and on `(unit_id, zone_code)`, which the config UI reports as "already exists". An unregistered board is `cea-un-<mac6>`. It replaced `UNIT02_CONTROL_ZONE02` (never resolvable; nothing parsed it — topics and payload fields carry unit and zone) and the compressed `u02-c-z02` (which changed whenever another unit was added). Pods resolve the name because cluster DNS forwards to the node's resolver, i.e. the router that holds the DHCP names; the host itself cannot (systemd-resolved keeps single-label names off unicast DNS) and only resolves `<hostname>.local` over mDNS. A board flashed before the change keeps its old names until re-onboarded.

**The access policy's history is a hash chain:** migration 008a creates schemas `iam_policy` (not `iam`, which access `--purge-data` drops) and `medcea_auth`, both owned by the NOLOGIN role `medcea_owner`. `iam_policy.history` stores `prev_hash` and `hash = sha256(history_record(...))`, the canonical JSON of the row in UTC, so writer and verifier share one function and the session's TimeZone cannot change a hash. `append_history(event, payload, reason)` is its only writer (SECURITY DEFINER, advisory lock, READ COMMITTED only, or a snapshot could miss the head and fork the chain); the actor is `db:<login>` until `set_actor()` (Phase 2). Triggers refuse UPDATE, DELETE and TRUNCATE for every role, the owner included, on `history` and `export_log`; `verify_chain()`, which `health-check.sh` runs (check type `iamchain`), catches any edit that does not rebuild the chain — **not** a superuser who disables the triggers and then drops the newest events or re-hashes from the edited one onward; that needs the head anchored outside the database (plan Section 7, not built). `iam.account_decision` and `iam.access_review` (`access_db.sql`) are likewise final once checked or signed off: a trigger lets only the check/sign-off columns be filled, all in the one UPDATE that sets `checked_at`/`signed_off_at`. `medcea.platform_setting` holds `mqtt_topic_root` (= `PROJECT_NAME`), written by `apps/database/deploy.sh`, which revokes `anon`'s blanket grant on it.

**A device family is a template, not a fork:** everything the platform does with a CONTROL device — ask which equipment is fitted, derive the command table, prune branches the chamber cannot perform, validate, render, write the component rows — runs through the template's `binding` block. `binding` names the address field (`pin`), its label (`GPIO`), the map key in the emitted file (`pin_descriptions`), whether an address is an integer or a string, which values are legal, and which carry a warning. `edge/templates/examples/modbus-control.json` is the worked proof: a CONTROL device addressed `3:0001` over Modbus renders and validates correctly through the same `device_template.py` and the same browser editor — labelled "Coil", checked against its own regex — with no Python anywhere for it. What a binding does **not** abstract is provisioning: `flash-device.sh` writes MicroPython over USB, and a device that is not flashed that way needs its own path into the fleet.

**The board is a variant of the binding, not a fork of it:** every ESP32 is addressed by GPIO number, but an S3 has 0-21/26-48 while a C3 stops at 21 and puts its flash on 12-17. Selecting a variant swaps the legal ranges and the per-pin rules and changes nothing else. The form defaults to `esp32s3` and lets the operator change it, because **the wiring question is asked before the board is ever probed** — a slot and a pin map are chosen while the ESP32 is still on the bench. Step 3 is where the two meet: once esptool reports the real chip, `flash-device.sh` re-validates the map against it and refuses if it cannot drive that silicon. Without that check an S3 map on a C3 flashes cleanly and then quietly fails to switch a relay.

**One editor, two hosts, one validator:** the channel map is edited in `edge/src/host/ui/channelmap.js`, which the wizard inlines and `build-editor.sh` bakes into a standalone page. Its structural rules are deliberately mirrored in `bindings.validate_config()` — the browser needs a verdict on every keystroke, and the renderer needs one it can refuse on. **Python is authoritative:** `render()` re-checks and raises rather than writing a table with errors in it, so a hand-crafted POST or a stale page cannot put a broken map on a board that has just been erased. Device-specific rules are not duplicated at all; both sides read them from the template.

**MQTT topic root is `$PROJECT_NAME` (= `medcea`):** SENSE publishes `medcea/<UNIT>/<ZONE>/sense/<tag>`, CONTROL subscribes `medcea/<UNIT>/<ZONE>/control/#` and reports to `.../control_setpoint/...`. Every consumer gets the root at deploy time, never from a literal: Node-RED has `__TOPIC_ROOT__/#` substituted by `apps/node-red/deploy.sh`; the scheduler pod gets `PROJECT_NAME` as env and hands it to `run_recipe.py`/`run_agent.py` through `/installer/.env`; `flash-device.sh` bakes it into each board's `device_cfg.py`. Mosquitto's ACLs are written per device from `topic_base` (`<root>/<UNIT>/<ZONE>`), so the root is in the credential row too. There is no legacy `plantinc/#` subscriber in MedCEA — it is a fresh fleet. Changing `PROJECT_NAME` after boards are flashed means reflashing them.

**Name-based domain (`DOMAIN=medcea`, `LOCAL_DNS=true`):** three pieces work together:
- the `name-dns` Deployment (CoreDNS, `hostNetwork`, bound to `PLATFORM_IP:53` only, so it never collides with systemd-resolved on 127.0.0.53) answers `*.medcea` for tailnet devices once Tailscale split DNS points `medcea` at the server;
- a managed `/etc/hosts` block (`infra/lib-dns.sh`) makes the server resolve the names itself during its first deploy, before anyone has set split DNS;
- `ALIAS_DOMAIN` (the old `<ip>.nip.io`) becomes 301 redirect ingresses labelled `medcea/alias=true`.

Pods need none of this, but only because every back-channel call goes to `*.svc.cluster.local`, and every oauth2-proxy sets `skip_oidc_discovery = true` with explicit internal URLs. Cluster DNS forwards to 8.8.8.8, which resolves `<ip>.nip.io` by luck and `keycloak.medcea` not at all: the config proxy lacked that flag and crash-looped (503) as soon as the domain became a name. SSO stays on one domain on purpose, because Keycloak's `KC_HOSTNAME`, Grafana's `root_url` and JupyterHub's `oauth_callback_url` each take a single URL.

**Helm OCI authentication:** The Bitnami chart registry (`registry-1.docker.io/bitnamicharts/`) requires Docker Hub credentials for Helm chart pulls only. Runtime container images (Keycloak on Quay, Node-RED on GHCR, etc.) are all auth-free. `deploy-infra.sh` injects credentials via MicroK8s's `certs.d/docker.io/hosts.toml` and `helm3 registry login`.

**`grep -c` + `set -e` pitfall:** `grep -c` exits 1 when the match count is 0. Combined with `|| echo 0`, this appends a second `0` to stdout (producing `"0\n0"`), causing `[ "$VAR" -eq 0 ]` to fail with "integer expression expected". All wait-loop counters use `grep -c ... || true` to let grep's own `0` output pass cleanly.

## Common Pitfalls

- **Never add `set -e` before `source config.env`** in a script that has a `--help` flag — the help branch must run before `set -e` and before sourcing so it works without a config file.
- **`microk8s status --wait-ready` exits immediately** on a fresh install before the daemon socket exists. The readiness check uses a retry loop with a deadline, not a one-shot call.
- **Juju controller existence is the skip guard** (not kubeflow namespace or pod count). Re-running bootstrap when `k8s-controller` exists skips the entire Kubeflow install block.
- **bitnami/keycloak image is behind a paywall** since August 28, 2025. Use the official `quay.io/keycloak/keycloak:26.0` image via plain kubectl manifests instead of the Bitnami Helm chart. `bitnami/postgresql` is still free. Health probes use port 9000 (management interface); the main app runs on 8080.
- **Keycloak 26.0 tag exists on quay.io** — use `26.0`, not `26` (which doesn't exist) or `26.x.y` patch tags.
- **schwarzit/node-red chart splits image into registry+repository+tag** — set `image.registry=docker.io`, `image.repository=nodered/node-red`, `image.tag=3.1.9`. Setting `image.repository=ghcr.io/node-red/node-red` causes the chart to prepend `docker.io`, producing the invalid URL `docker.io/ghcr.io/...`.
- **sudo-rs ignores `sudo -E`** (Ubuntu's default sudo since 25.10), and MicroK8s cannot work without it: `run_with_sudo` in the snap's `utils.sh` runs `sudo -E …` for every privileged step — `microk8s start`, addon enables, apiserver restarts — **even when already root**, so `sudo microk8s …` does not avoid it. The steps lose `SNAP_*` and fail (`snapctl … from outside of a snap`; `enable rbac` dying after "No callback tokens file."). A running cluster never takes that path, so the switch is temporary: `classic_sudo_begin` (`infra/lib-sudo.sh`) points the `sudo` alternative at classic `sudo.ws` for the duration of `bootstrap-infra.sh`, and a trap on EXIT/INT/TERM restores the previous setting. Any new script step that runs `microk8s enable|disable|start|stop|reset` must sit inside such a window. By hand: `sudo update-alternatives --set sudo /usr/bin/sudo.ws`, the microk8s command, then `sudo update-alternatives --auto sudo`.
- **Removing the snap does not stop the pods.** Pod processes live in `/sys/fs/cgroup/kubepods`, outside every systemd unit; orphaned calico-node got the next install's containerd SIGKILLed at start. Remove MicroK8s only through `remove_microk8s` (`infra/lib-mk8s-remove.sh`): stop kubelite, `cgroup.kill` the pods, kill MicroK8s's containerd-shims, and only then `snap stop` the rest and `snap remove --purge`, whose hook does the rest. **The order is load-bearing:** if containerd's unit stops with shims still in it ("remains running after unit stopped"), the next install's containerd is SIGKILLed within a millisecond and snapd rolls the install back — every removal that left shims did that, and the one that left none didn't. Bootstrap retries a rolled-back install once for removals made by older code. No `microk8s reset`: it disables every addon one at a time to restore a fresh cluster (minutes), which is pointless when the snap is about to go. `kill_orphan_pods` also runs before every install, so a dirty host from an older removal heals itself.
- **`microk8s enable` chaining** — MicroK8s 1.33+ warns that space-separated addon lists will be deprecated. Enable each addon with a separate `microk8s enable` call.
- **Dex-auth has NO ConfigMap** in Charmed Kubeflow 1.9. It is a Juju-managed StatefulSet. Config is applied via `juju config dex-auth connectors=<yaml>`. The `connectors` value is a YAML string containing a list of Dex connector definitions.
- **dex-auth connector redirectURI** must be `http://${KUBEFLOW_DOMAIN}/dex/callback` — this is Dex's own callback endpoint where Keycloak redirects after authentication. Do NOT use the oidc-gatekeeper callback (`/authservice/oidc/callback`) here. Use KUBEFLOW_DOMAIN (nip.io), NOT KUBEFLOW_IP (LAN IP).
- **dex-auth issuer-url must use KUBEFLOW_DOMAIN** — set via `juju config dex-auth "issuer-url=http://${KUBEFLOW_DOMAIN}/dex"`. This controls `OIDC_PROVIDER` in the oidc-authservice. The authservice constructs its callback URL (`redirect_uri`) using the OIDC_PROVIDER host. If OIDC_PROVIDER uses `192.168.1.200` (MetalLB IP) but users access Kubeflow via the nip.io domain, the CSRF cookie is set for nip.io but the callback goes to `192.168.1.200` — CSRF check fails. Using KUBEFLOW_DOMAIN for issuer-url ensures the full OIDC flow (auth URL, callback) stays on the same nip.io domain.
- **dex-auth connector requires `insecureSkipVerify: true`** — the nginx ingress has a self-signed cert valid for `ingress.local`, not the actual Keycloak hostname. Without this, Dex fails to fetch the OIDC discovery endpoint and exits with code 2.
- **juju status wait loop** — check unit-level juju-status (`grep -A1 "juju-status:" | grep "current:"`), not the first `current:` in the output (which is the workload status and always shows `available`).
- **Keycloak realm "HTTPS required" blocks HTTP callbacks** — production mode defaults to `ssl_required: external`. OAuth2 Proxy and Dex use HTTP callback URIs (no TLS on ingress), so the realm must have `ssl_required: none`. Set via Admin API: `PUT /admin/realms/{realm}` with `{"sslRequired":"none"}` (use kubectl port-forward to reach Keycloak internally).
- **OAuth2 Proxy defaults to `google` provider** — must set `provider = "oidc"` in `configuration.content` values file. Without it, the login button says "Sign in with Google" even with `oidcIssuerUrl` set.
- **PostgREST does not strip quotes from a filter value** — `?dns_name=eq."unit01-s-zone01"` matches nothing (it looks for a value that literally starts with a quote) and returns `[]`, which reads exactly like "no such row". Percent-encode the value instead; do not wrap it in double quotes.
- **A retry on any `23505` is wrong.** The `device`/`component` sequences trail the table because the seed import supplied explicit ids, so a *primary key* collision is worth retrying (each attempt burns one nextval). A collision on `dns_name` is a slot that already has a board, and retrying turns one clear error into thirty requests and a wrong diagnosis. Check which key is named in the error.
- **`while read ...; done < <(cmd)` gives its stdin to the loop BODY too** — so any prompt inside the loop reads from `cmd`'s output instead of the terminal, silently answering the question with the next line of data. Use `for x in "${arr[@]}"` with `IFS=$'\t' read -r ... <<<"$x"`, which redirects only that one `read`.
- **Never echo a password in `deploy-infra.sh` after the `exec > >(tee …)`** — everything on stdout lands in `logs/`. The final summary names users only. Passwords go to `credentials-<ts>.txt` (mode 600, gitignored), and its content is shown through `/dev/tty`, which bypasses the tee. Add any new human-facing password to that file, not to the summary.
- **A fresh group membership is not in the current session.** Bootstrap adds the user to `microk8s`, but the shell that ran it doesn't have the group until the next login. Hardcoded `microk8s kubectl` in the app scripts failed all six components on a clean install. Source `infra/lib-mk8s.sh` and never hardcode it. `install.sh` runs the app stages under `sg microk8s` (`with_mk8s_group`), so the first install needs no sudo for them.
- **Never derive an IP from `DOMAIN`.** `${DOMAIN%.nip.io}` silently becomes `medcea` under a name-based domain; use `PLATFORM_IP`. The MQTT Explorer WebSocket host and the edge-wizard URL used to do exactly this.
- **oauth2-proxy with `allowed_groups` requests the scope `groups`**, and Keycloak refuses a login asking for a scope it does not know (`invalid_scope`). So `groups` is a realm *client scope* carrying the realm-role mapper, a default scope of `portal` and `access` — a mapper on the client alone is not enough.
- **`smtplib.login()` hides Gmail's 535**: after `AUTH PLAIN` is refused it retries `AUTH LOGIN`, Gmail hangs up, and the error becomes "Connection unexpectedly closed". `apps/access` calls `auth('PLAIN', …)` directly so a wrong app password says so.
- **A 403 from oauth2-proxy is not always "no role".** A failed login (provider error, CSRF) is also a 403 but with its own message; `k8s/portal/error.html` says "No access yet" only for the default 403 message.
- **A Keycloak client PUT that omits `serviceAccountsEnabled` turns the service account off and on again**: the service-account user is deleted and recreated with a new id, and every role granted to it is lost (the `access` client's `manage-users`… — the User Manager then gets 403 on everything). `_create_client` therefore always sends the flag (third argument, `true` for `access`). Any manual client update must send it too.
- **Mosquitto refuses to start without its `password_file`**, and the sidecar writes it a moment later: the broker container waits (`until [ -s /mosquitto/auth/passwd ]`) before `exec`ing Mosquitto. A subscription wider than the ACL (`#`) is *accepted* by Mosquitto 2.0 — it filters per message — so a quiet subscriber is not proof of a refused SUBACK.
- **`PGADMIN_CONFIG_*` values are Python literals** (written verbatim into `config_distro.py`): `"['oauth2']"`, `"True"`, quoted strings in the OAuth2 dict. The pgAdmin pod resolves `keycloak.<name-domain>` only through `hostAliases` (→ `PLATFORM_IP`), because authlib reads the issuer's metadata by its public URL. Break-glass: `kubectl set env deployment/pgadmin PGADMIN_CONFIG_AUTHENTICATION_SOURCES="['internal']"`.
- **A freshly onboarded board's first connects are refused for up to ~15 s** — its credential row is registered after it boots and reaches the broker on the sidecar's next sync. `connect_mqtt()` raises, the board restarts and the retry succeeds; not a fault.
- **Only `theme.properties` goes through `render`.** The `.ftl` files are FreeMarker, whose `${...}` must reach Keycloak untouched, and for the same reason their JavaScript cannot use template literals. Deploy-time values (`accessUrl`) are theme properties, read in FTL as `properties.accessUrl`.
- **Keycloak caches themes in production mode** and never re-reads the mount, so a changed theme needs a pod restart: the theme checksum is a pod annotation (`medcea/theme-checksum`). The ConfigMap holds 1 MiB, which is why the background is `apps/portal/bg.jpg` (152 KB) and not the 1.7 MB PNG.
- **A user without a platform role gets a 403 from the portal**, not a login error: oauth2-proxy authenticates them, then `allowed_groups` refuses. The fix is a realm role, not a password reset. The `groups` claim is in the ID token, and oauth2-proxy re-reads it on every `cookie_refresh` (4 min), so granting or removing a role takes effect without a new login.
- **A background job inherits the deploy lock** (fd 9) and holds it after its script has ended, so the next run is refused. Start every `&` job in a locked script with `9>&-` (the kubectl port-forwards do). A run stopped with a plain `kill <pid>` likewise leaves its foreground `helm --wait`/`rollout status` holding it — which is why the refusal message says `kill -- -<pgid>`, and lists any leftover holders by PID.
- **The credentials box can show a password nobody uses any more** — a person may change their own (user menu → Change password) and `_create_kc_user` never overwrites one. The box therefore asks the admin API whether each password is still the one it was created with (`_shown_pass` → `kc_password_status`, comparing the credential's date with the account's) and says "changed by its owner" instead of printing a stale value. It never signs in as the person, so nobody's record gets a login they did not make.
- **`configure.sh` exits early when nothing required is missing**, so a value that is generated rather than asked (QA_INITIAL_PASS, KC_BREAKGLASS_PASS) must be created *before* that exit, or an existing install never gets it.
- **`pkill -f <pattern>` from a shell whose own command line contains the pattern kills that shell.** Match with a bracket (`pgrep -f '[a]ccess-api.py'`) or kill by PID.
- **A rebuilt server leaves the split DNS route behind.** A new machine gets a new Tailscale IP, but the admin console keeps sending `$DOMAIN` to the old one. The server itself still resolves everything (the `/etc/hosts` block), so only other devices fail. `split_dns_target` (`infra/lib-dns.sh`) reads the route from `tailscale dns status`; deploy-infra warns in the `[DNS]` step and prints the edit at the end. There is no CLI to change it — it is an admin-console setting.
- **No wildcard SAN on a one-label domain.** Browsers reject `*.medcea`, so the certificate lists every `*_DOMAIN` explicitly. When adding a service domain, add it to the `_SVC_DOMAINS` list in `deploy-infra.sh` too: the SANs, the hosts block and the alias redirects all come from it.
- **`[ -r file ]` under `/var/snap/microk8s/` is always false for a normal user**, because those directories are root-only. A skip-check built on it never skips: deploy-infra re-wrote `hosts.toml`, restarted containerd (a cluster-wide blip) and stopped at a bare sudo prompt on every run. Check with `sudo grep`, and give `sudo -p` a prompt that says why the password is wanted (the prompt goes to the tty, not the log).
- **`curl … | sh` hides a missing curl** — `sh` reports success on the empty script it receives. Download to a file, check it is non-empty, then run it, and confirm the result exists (`command -v tailscale`) rather than trusting the exit code.
- **`printf -v` into a name the callee also declares `local`** writes the callee's copy, and the caller's variable stays empty. This made `ask_yn` (which called `ask __ans`) loop forever. Give caller variables names the helper doesn't use.
- **`ask()` must die on EOF, not return empty** — a re-asking prompt loop (`menu_ask`) spins forever when stdin is closed (`< /dev/null`, cron, a detached `timeout`).
- **`ujson.dumps()` will not serialise `bytes`** — `ubinascii.hexlify(machine.unique_id())` returns bytes, and putting it straight into a payload raises rather than publishing. `.decode()` it once, in `config.py`. A `str` there also matches `medcea.device.serial_number` exactly.
- **ESP32-P4 flash pins are package pins, not GPIOs** — the P4 datasheet's flash table (FLASH_CK = 32, FLASH_CS = 27 …) lists *package pin* numbers. Mapping those onto GPIO numbers would wrongly blacklist GPIO27-33. The P4's flash is on dedicated pins and its PSRAM is in-package, so unlike every other ESP32 it loses no GPIO to memory at all.
- **Changing the board in the form does not rewrite the map** — it re-checks the same table against different silicon, and the errors that appear are the point. Silently dropping the pins the new chip lacks would hide exactly what the operator needs to see.
- **The browser prompt loop re-renders on every poll** — `renderPrompt()` returns early when `p.id === curId`, and that guard is what keeps the channel-map editor from being re-mounted (and the operator's half-finished edits thrown away) once a second. Any new rich prompt kind must keep it.
- **An edited channel map is authoritative, not a hint** — when the wizard returns a table, `render()` uses it verbatim (`spec["actuator_config"]`) instead of re-deriving from `functions`. Re-deriving would silently discard the edit the operator was just shown and approved.
- **Keycloak has its own database, `keycloak`**, not `medcea_db`. When they were shared, `apps/database/uninstall.sh --purge-data` (`DROP DATABASE medcea_db`) would have wiped every realm, user and client, and an install from before the split still has unused Keycloak tables in `medcea_db.public`. Never point `KC_DB_URL` back at `$POSTGRES_DB`.
- **Bitnami charts with unset resources fall back to the `nano` preset** (192Mi / 150m limits). Always set `resources` explicitly for a Bitnami release: rdbms and the three oauth2-proxies do.
- **Cookie secrets are generated once and kept** (`${OAUTH2_COOKIE_SECRET:-$(openssl rand …)}`). Regenerating them on every deploy logged everybody out.
- **`ALTER ROLE postgres SET search_path TO medcea, public` breaks Keycloak** — Keycloak connects as `postgres` and has its own tables (e.g. `COMPONENT`) in the `public` schema. If `medcea` is first in the search_path, PostgreSQL finds `medcea.component` (our IoT table) instead, causing `column realm_id does not exist` crash-loops. Set `search_path` on the `authenticator` role (PostgREST) only, never on `postgres`.
