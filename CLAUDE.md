# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MedCEA is a shell-script-based IoT platform deployer targeting a single Ubuntu PC running MicroK8s. It installs and wires together: Kubeflow, Keycloak (SSO), PostgreSQL, Grafana, Node-RED, and OAuth2 Proxy.

**There is no build step, no test suite, and no package manager.** The codebase is bash scripts plus a config file, split into infrastructure (`deploy-infra.sh`) and application content (`deploy-apps.sh` / `apps/`).

## MedCEA Direction

This repo was forked from `pfplatform` (@2032725) as the baseline for the MedCEA PhD prototype. Read [docs/medcea-concept.md](docs/medcea-concept.md) (four pillars, H1–H3, experiments) and [docs/architecture.md](docs/architecture.md) (layer → component mapping, Compliance Plane TODOs) before adding features. Two rules follow from the concept:
- **The Compliance Plane is read-only from the operational layers.** Operational services may append events to it, but never get UPDATE/DELETE on audit, EPCIS or EBR storage.
- **Documentation moves with the change.** Any change a user, administrator or auditor would notice (a screen, a role or permission, a command, a switch, a deploy order, what is recorded) updates the platform manual in the same piece of work: the affected `docs/manual/chapters/<key>.html` (HTML fragments in the vocabulary `docs/manual/shell.html` styles), then `python3 docs/manual/build.py` (it refuses dead cross-links, duplicate ids, scripts and inline styles). A human decision goes into the decision record in `chapters/compliance.html`. At the end of each phase bump `EDITION` in `build.py` and add a row to `chapters/revisions.html`. The IAM roadmap page (`codeplan/iam-roadmap.html`) is updated at the end of each plan step. CLAUDE.md stays the developer reference; the manual is for the people who use and run the platform.
- **`PROJECT_NAME` (`medcea`) is the one project identifier.** It is the MQTT topic root, and `config.env` derives `NAMESPACE` and `KEYCLOAK_REALM` from it; `deploy-infra.sh` refuses a value that is not `^[a-z][a-z0-9-]{1,30}$`. The database is `medcea_db` with schema `medcea` — a literal, because the schema name is written into the SQL, not templated. `cea` survives only as the domain term "controlled environment agriculture": the table names `cea_unit`/`cea_zone`/`cea_location`, the Python package `schd/cea/` (so `cea.run_agent(...)` is a module call, not a schema), `CEA_*` env vars, `cea-tls`/`cea-ca`, and the `cea-un-<mac6>` hostname of an unregistered board.

## Full Deployment Workflow

All scripts must be run from the repository root; they call each other via relative paths and source `config.env` from the current directory.

```bash
# Everything, in order (infra → apps → health check), with the credentials box last:
./install.sh             # --help lists --configure, --infra-only, --apps-only and the uninstall levels
./install.sh --uninstall-apps [component ...] [--purge-data] | --uninstall-infra | --uninstall-all

# The stages on their own:
# 1. Deploy infrastructure (safe to re-run — bootstrap is skipped if already done).
#    The first run creates config.env from config.env.example by Q&A (infra/configure.sh);
#    later runs ask only for empty required values. Review all: ./deploy-infra.sh --configure
./deploy-infra.sh

# Help text (does not require config.env to be present)
./deploy-infra.sh --help

# 2. Deploy application content (interactive component selector):
./deploy-apps.sh
./deploy-apps.sh --all   # non-interactive

# Recovery only: if Juju charm update resets dex-auth config, re-run:
./patch-dex-keycloak.sh
```

## Script Roles

- **`bootstrap-infra.sh`** — Called by `deploy-infra.sh`. Handles: K3s cleanup, MicroK8s snap install/wipe (interactive prompt, also removes Juju on wipe), MicroK8s addon enablement (dns:8.8.8.8, hostpath-storage, rbac, ingress, helm3, metallb), inotify limit tuning, kubeconfig export, Juju 3.6/stable install, Charmed Kubeflow 1.9 deployment via `juju deploy kubeflow --trust`, dex-auth/oidc-gatekeeper initial configuration, and pod-count readiness wait.
- **`infra/configure.sh`** — Fills `config.env` by Q&A. It is called by `deploy-infra.sh` before logging starts, so answers and generated passwords stay out of `logs/`. `config.env.example` is always the base: on each run the file is rebuilt from the template with existing values carried over line for line, and keys only the old file had are kept at the end. It checks Tailscale on every run, before the early exit for a complete file. `USE_TAILSCALE` records whether `DOMAIN` depends on it: `true` makes a down Tailscale fatal, because the `DOMAIN` expression would quietly fall back to the LAN IP; `false` means LAN-only on purpose and is not raised again. Pressing Enter leaves a line untouched, so expressions like `DOMAIN="$(tailscale ip ...)"` stay expressions. Passwords are limited to `[A-Za-z0-9._~-]` because they are spliced unencoded into YAML, a `postgres://` URL, `helm --set` and a curl form body.
- **`install.sh`** — Single entry point and thin wrapper. It runs `deploy-infra.sh` → `deploy-apps.sh --all` → `health-check.sh`, and the uninstall levels map onto `deploy-apps.sh --uninstall`, `deploy-infra.sh --reset` and `deploy-infra.sh --uninstall` (plus host cleanup that keeps `edge/provisioned/`). It exports `MEDCEA_INSTALLER=1`, so deploy-infra leaves the credentials box for the end, and `MEDCEA_CONFIRMED=1` after its own typed confirmation, so the sub-scripts don't ask a second time.
- **`guide.sh`** — Interactive Q&A front end to the commands, for a person at the terminal: area menu (install/uninstall, infrastructure, applications, operators and units, IAM switches, health and tests, edge devices, policy) → action → its questions, validated as the target script validates, except that nothing spliced in as a positional argument may start with `-` (unit codes `^[A-Za-z0-9][A-Za-z0-9_-]*$`, usernames likewise, so a "unit code" `--bootstrap` cannot bypass the typed `yes`), uuids, components from `apps/*/{deploy,uninstall}.sh` on disk; `--by` remembered for the session; flash-device's `--unit`/`--zone` match exactly, case included → the command printed with `printf %q`, what it changes, lock, sudo → confirm ([Y/n] read-only, [y/N] change, the word `yes` for an uninstall, `--purge-data`, `--reset`, `--bootstrap`, a board erase; a direct `apps/<c>/uninstall.sh --purge-data` also wants the project name, as deploy-apps asks it) → run as an array with the terminal inherited (no eval; a `&&` element chains commands, e.g. the kept fixture `up && load && apply`), exit code reported. `--ui` is offered only while `EDGE_WIZARD_PORT` is free (the cea-edge-wizard service holds it). IAM switches (and `WORKBENCH_ENABLED`): current value from the one active line (zero or several are refused), the ordered recipe with its preconditions (a checklist confirmed once; e.g. IAM_DB_ROLES enable is refused while IAM_POSTGREST_JWT or IAM_DB_SERVICE_ROLES is not true, a JWT rollback rolls IAM_DB_ROLES back first), then the recipe takes the deploy lock for all its steps (refused while another deploy runs; exports `MEDCEA_LOCK_HELD` so the steps skip theirs), each `set` replaces that one line (backup `config.env.guide-<ts>.bak`, mode 600, gitignored, offered for deletion after a completed recipe and deleted by `install.sh --uninstall-all`; `diff -U0` so neighbouring passwords never print) and each `run` step runs in order, stopping at the first failure — or at Ctrl-C (exit 130) — with how to restore config.env. A switch the recipe's order depends on (IAM_DB_ROLES, IAM_POSTGREST_JWT, IAM_DB_SERVICE_ROLES) must be one literal `true`/`false` line, or the recipe is refused. The catalogue is data in the script: an `a_*` function per action plus one `fn|label|purpose` line in its `AREA_*` array; switch recipes all live in `recipe()`. It never asks for a secret, takes the lock only for a switch recipe (every other command takes its own), reads answers from stdin and dies on EOF (exit 1). The IAM 2.7 rollback is shown, never run. `--dry-run` runs and changes nothing; `MEDCEA_GUIDE_CONFIG=FILE` (dry run only) reads another config. **A new user-facing command or switch gets a guide entry.** Tests: `tests/test_guide.sh` (offline; every case runs a copy in a scratch tree whose scripts are all stubs, so a broken dry-run guard runs stubs, never a deploy: dry runs with piped answers, real switches under the lock, a held lock, Ctrl-C, the `&&` chain).
- **`apps/<component>/uninstall.sh`** — The inverse of that component's `deploy.sh`, discovered by `deploy-apps.sh --uninstall` and run in reverse alphabetical order (so `database` goes last but for `access`, whose `--purge-data` copes with `medcea_db` being gone already). **A new component ships both files.** Uninstall must not break infrastructure: remove patches from infra Deployments before deleting the ConfigMaps they mount (report → Grafana), and leave anything infra mounts (`portal-nginx`). Database data is dropped only with `--purge-data`.
- **`infra/lib-portal.sh`** — `portal_card enable|disable URL`, exact inverses that find a portal card by its URL. App deploys enable their card and uninstalls disable it.
- **`infra/lib-credentials.sh`** — `show_credentials FILE`, which writes to `/dev/tty`; used by deploy-infra (standalone) and install.sh.
- **`k8s/` and `apps/<c>/k8s/`** — Every Kubernetes manifest and Helm values file is a template there, not a bash heredoc. Scripts do `render FILE VAR... | $KUBECTL apply -f -` (or `> "$VALUES"` for Helm). Configs without variables (nginx confs, the Grafana dashboard provider, the MQTT Explorer HTML) are plain files used with `--from-file`. Every oauth2-proxy release shares `k8s/oauth2-proxy/values-common.yaml`. This is the groundwork for a later Argo CD/Flux move (in-cluster layer only).
- **`infra/lib-render.sh`** — `render FILE VAR...` runs `envsubst` with an **explicit** variable list in a subshell. Never bare `envsubst`: the templates contain nginx `$host/$uri/$1`, JupyterHub `$HOME`, `$request_uri` and JavaScript `${…}`, which must survive. When adding `${NEWVAR}` to a template, add it to the `render` call too: an unlisted variable is silently left as literal text. Values over 128 KiB can't go through the environment, so the portal background uses a placeholder plus a python filter.
- **`infra/lib-postgrest.sh` + `apps/frontend/k8s/config-api-jwt.yaml`** — **config-api (PostgREST) verifies the person's token when `IAM_POSTGREST_JWT=true`** (Phase 2b, default false; false renders e97aab6's `config-api.yaml`/`config-ui-nginx.yaml` byte for byte, `tests/golden/`). The JWT template (contract C1, which the database deploy's `IAM_DB_ROLES=true` guard and health-check `postgrest` read): `PGRST_JWT_SECRET` from Secret `medcea-jwks` key `jwks-sig.json` (the realm's RS256 signing keys only, byte-stable, by `infra/jwks-sig.py`; deploy-infra writes it next to `jwks.json`), `PGRST_JWT_AUD=medcea-api`, `PGRST_DB_PRE_REQUEST=medcea_auth.pre_request`, `PGRST_JWT_ROLE_CLAIM_KEY=.medcea_pgrst_role` (a claim nobody issues, so a verified token always starts as `anon`; under `IAM_DB_ROLES=true` `pre_request` picks `rr_<role>`), and authenticator's password `AUTHENTICATOR_DB_PASS` from Secret `db-authenticator` (`AUTHENTICATOR_PASSWORD`, listed first so `$(…)` expands it in `PGRST_DB_URI`). A `secretKeyRef` env is read only at container start, so the pod carries `medcea/jwks-checksum` and `pgrst_roll_if_changed` (deploy-infra, after writing the keys) patches it when the set changed: **after rotating or removing a realm key run `./deploy-infra.sh`**; health-check `postgrest` FAILs on a kid the realm no longer publishes. `pgrst_deploy MODE NS POD DB` is the one switch, called by `apps/frontend/deploy.sh`: preflight (true: the two passwords differ, `jwks-sig.json` valid, `pre_request` exists; false: refused while `IAM_DB_ROLES=true`) → [true: Secret `db-authenticator`] → apply → wait until the new container *started* (a missing Secret key fails here, before the password changes) → `rollout pause` → `ALTER ROLE authenticator` (stdin, `log_statement='none'`) → delete the new revision's unready pod (**PostgREST 12 exits on a refused password** — `password authentication failed` → `postgrest: thread killed` — so that pod is crash-looping in the kubelet's restart back-off; a fresh pod connects at once) → `rollout resume` → `rollout status`. The delete happens only while paused, so the controller cannot scale the old pod down between reading the new pod's readiness and deleting it. **A switch costs config-api up to ~15 s, by design:** the old pod keeps serving on its open connections but dies at its next new one after the ALTER, and nothing serves until the new pod passes its readiness probe (5 s delay, 5 s period, frozen with the legacy manifest); whether the old pod needs a connection in that window is chance, so a switch loses anywhere from 0 to ~70 requests. Both modes log in as `authenticator`, so no order avoids it. Every `pgrst_deploy` resumes after its preflight, since a paused Deployment ignores every later apply; a failure puts the previous password back and runs `rollout undo` only if the apply bumped the generation. The pod also carries `medcea/auth-secret-version` (Secret `db-authenticator`'s resourceVersion, read after the Secret's apply), so a rotated `AUTHENTICATOR_DB_PASS` starts a new pod before the ALTER instead of leaving the running one on the old password. **While config-api runs JWT, the frontend deploy alone owns `db-authenticator` and the role's password**; the database deploy follows the live mode, never config.env alone (`pgrst_db_auth_pass`; it writes the Secret only when it is missing, e.g. after a purge). `pgrst_live_mode` says `rolling` only while two pod templates can be live (observedGeneration behind, or two ReplicaSets with pods); a single unready pod is its template's mode, so a database deploy can recover a config-api whose authenticator a purge dropped. Order by direction: true switches config-api before nginx sends Bearer, false restarts config-ui (subPath conf) before config-api goes back, since a legacy config-api answers Bearer with 500 PGRST300. The JWT nginx (`config-ui-nginx-jwt.yaml`) maps the proxy's `X-Forwarded-Access-Token` to `Authorization: Bearer` in `/api/` only and blanks there `Cookie`, `X-Forwarded-Access-Token/-User/-Email/-Preferred-Username/-Groups`; it relies on oauth2-proxy stripping a client-sent `X-Forwarded-Access-Token` (never set `preserveRequestValue`). With `IAM_DB_ROLES=false` a verified token runs as anon exactly as before, and a write is stamped as the person (source `token`) when azp and a single own role pass, else `db:authenticator`. A forged or expired token is a 401, and the Config UI's `api()` sends the browser through `/oauth2/start` once; this holds because `accessTokenLifespan` is pinned at 300 s in deploy-infra's realm PUT and every proxy's `cookie_refresh` (240 s) stays below it (`tests/test_postgrest.py` checks both, and that no client overrides `access.token.lifespan`). `pre_request` lets an anonymous `GET /` through as anon (config-api's readiness probe; under true anon holds nothing). Its refusals are SQLSTATE 28000, which PostgREST answers 403. A token of a `read_only` network client (`grants.read_only_clients`: `workbench-notebook`, IAM 3.2b review) is refused ("may only read") for any `request.method` but GET/HEAD before the role is taken, and its transaction is `SET LOCAL transaction_read_only = on`. A permission refusal (42501) is 401, not 403, because the request's PostgREST role is anon (`medcea_data.py` and the Config UI read the code, not the status). The only callers of config-api are the Config UI's nginx, the edge wizard and (IAM 3.2b) the workbench's notebooks (`network:` admits `pod:config-ui`, `node` and `client:notebooks`); scheduler, monitor, dbmgmt and Node-RED talk to PostgreSQL. **Enable:** `./deploy-infra.sh`, `IAM_POSTGREST_JWT=true`, `./apps/frontend/deploy.sh`. **Rollback:** `IAM_DB_ROLES=false` + `./infra/deploy-workbench.sh` + `./apps/database/deploy.sh` first if it was true, then `IAM_POSTGREST_JWT=false` + `./apps/frontend/deploy.sh` (under false it closes the notebooks' hops first, `workbench_egress_close`), and only then any `git revert` (a reverted deploy-infra drops `jwks-sig.json`, a reverted database deploy forces `POSTGRES_PASS`; either breaks a config-api still in JWT mode). `apps/database/uninstall.sh --purge-data` warns while config-api is JWT. Tests: `tests/test_postgrest.py` (offline, including `pgrst_live_mode`/`pgrst_db_auth_pass` against a fake kubectl and the switch order), `tests/iam-postgrest.sh` + `iam_postgrest_flow.py` (P1–P17 — P17: a notebook token only reads — and R16 — the nginx's `/scheduler-api/` forwards `X-Forwarded-Access-Token`, checked against an echo stand-in Service `scheduler` — fixture only; `--flip` fails a switch during which config-api served nothing for more than `FLIP_MAX_OUTAGE` (20 s) of its 0.2 s load, or that fails any request once its rollout is done, covers a password rotation in JWT mode and `pgrst_db_auth_pass` per live mode) and the fixture steps `preflight`, `postgrest MODE`, `pgrst-flip`.
- **`infra/lib-db-roles.sh`** — **which PostgreSQL role each database client logs in as** (IAM 2.5, `IAM_DB_SERVICE_ROLES`, default false). `db_client NS ROLE` sets `DBC_USER`/`DBC_PASS`/`DBC_SECRET`/`DBC_SECRET_KEY`: the service's own role only when the flag is true, its password is set, Secret `db-<role>` exists **and** the role can already log in; otherwise postgres (`rdbms-postgresql`/`postgres-password`) with a warning saying why. The clients: scheduler (and the runner, through `/installer/.env`) `svc_scheduler`, monitor `svc_monitor`, dbmgmt `svc_dbexport`, Node-RED `svc_ingest` (apps), Grafana's datasource `svc_grafana` and pgAdmin's server entry `rr_admin_login` (`deploy-infra.sh`). The three pod manifests take `PG_USER` as a value and `PG_PASSWORD` from `${PG_SECRET}`/`${PG_SECRET_KEY}`, never a literal password. Grafana reads its datasource and pgAdmin its `servers.json` at start only, so deploy-infra restarts Grafana when the user changed and pgAdmin carries `medcea/db-user`. `db_clients_live NS` prints each deployed client's user (`?` when unreadable); the database deploy keeps a role able to log in while a live client still uses it, so **infra, apps and database deploy in any order** and nothing is pointed at a role that cannot log in. **A new database client** gets a role with a `db_password` in `defaults.yaml`, a `db_client_role` entry, a reader in `db_clients_live`, and `db_client` in its deploy. iam-api (IAM 3.5) is the client `iam-api` → `iam_svc` and never falls back to postgres (its deploy refuses). pgAdmin on `rr_admin_login` holds only `rr_admin`'s grants (a few master-data and policy tables, `propose_setting`): no DDL, no writes; for those, psql in the PostgreSQL pod. dbmgmt (IAM 2.6) lists the tables and views of `medcea` (`SCHEMAS`; the iam/iam_policy members of the groups stay out by decision) that svc_dbexport may read **and** that are members of the person's X groups (`medcea_iam.exportable()`: routes.json `exports` for the person's `actor_role()`); sequences and types (`pg_catalog`, since `information_schema` hides objects a role holds no privilege on; no rows) are DDL-only for anyone the route admits. An export is one REPEATABLE READ transaction: `set_actor` from the verified token → reads → `iam_policy.log_export(groups, objects)` (objects `schema.name:type:ddl,data=<rows>`; no new export_log columns) → commit, and only then the file (a platform file in `apps/database/exports/`, its own hostPath, never next to the SQL the database deploy runs and never over an existing file: 409; header `export #<id>`, response headers `X-Medcea-Export-Id`/`-Sha256`); an object outside the person's groups refuses the whole export (403, nothing logged), and dbmgmt checks with `enforce=True` whatever IAM_ENFORCE says (503 without the library or with a routes.json from before 2.6). `health-check.sh` `dbclients` WARNs while a client disagrees with the flag. Tests: `tests/test_db_roles.py`, `tests/test_dbmgmt_api.py` (offline), fixture step `services` (logins, each service's statements as its role, `tests/iam-runner.sh --mode false-svc`).
- **`k8s/node-red/` + `infra/lib-node-red.sh`** — Node-RED (IAM 3.3). `values.yaml` is the chart's values template (render list: NAMESPACE KEYCLOAK_DOMAIN KEYCLOAK_REALM NODE_RED_DOMAIN NODE_RED_TZ NR_SETTINGS_CHECKSUM; `TZ` in env, since chart 0.40.0 has no `timezone` value), `settings.js` a plain file in ConfigMap `node-red-settings`, mounted by subPath, so its sha256 is the pod annotation `medcea/settings-checksum` and a change restarts Node-RED. `/data` is a PVC (`microk8s-hostpath`, 1Gi): flows, `flows_cred.json` and its key, palette modules and editor sessions survive a restart; `--reset` deletes it with the namespace. Health-check `noderedflows` (waiver W1's control) runs `apps/node-red/flows_diff.py diff` on `/data/flows.json`: FAIL when a git node is missing or a key git has differs (or no flows at all), WARN on keys or nodes outside git; fields holding a secret placeholder, `credentials` and x/y/w/h are left out, and it never prints a value. `noderedauth` FAILs unless adminAuth is on, `node-red-auth` equals the compile, the pod runs this settings.js, the module is installed and GET /flows without a token is 401. Tests: `tests/test_node_red_flows.py` (offline; settings.js under node when installed).
- **`infra/lib-mk8s.sh`** — `mk8s` / `$MK8S` / `$KUBECTL`: plain `microk8s` when the session has the group, otherwise sudo with an explanatory prompt. Every app script sources it.
- **`infra/lib-prereqs.sh`** — `check_prereqs`: host packages a clean Ubuntu may lack (curl, ca-certificates, openssl, python3, python3-venv, iproute2, util-linux, procps, python3-yaml, snapd), each with a test and an apt package. It is sourced by `configure.sh`, so every `deploy-infra.sh` run checks, and by `deploy-apps.sh`. **When a script starts calling a new host command, add it here**; psql and kubectl don't count, because they run in pods or come from the MicroK8s snap.
- **`infra/lib-lock.sh`** — `medcea_lock`: **one deploy at a time.** Called once, after the `--help` branch, by every script that changes the cluster or `config.env` (install, deploy-infra, configure, bootstrap, deploy-workbench, deploy-apps, each `apps/<c>/deploy.sh`/`uninstall.sh`, `apps/iam/units.sh`; `guide.sh` for the length of a switch recipe); `health-check.sh` and `--help` stay unlocked. It is `flock` on fd 9 of `.medcea.lock` (gitignored), so the kernel drops it when the holder dies and there is no stale lock; the PID/command written into the file only explains a refusal. The first locker exports `MEDCEA_LOCK_HELD` and the scripts it runs skip the lock. A new entry script calls it; a new component's scripts already do.
- **`apps/iam/` (access policy)** — `policy/defaults.yaml` is the one source of access rights (roles, levels, resource groups with their route tables, constraints, invariants, help text); `compiler/` is its only reader. `python3 apps/iam/compiler/cli.py check` runs the invariants, `… hosts` shows who each host admits, and `policy_groups HOST_VAR` (`infra/lib-oauth2-proxy.sh`) compiles a host's `allowed_groups` into the values template's `${ALLOWED_GROUPS}` — every oauth2-proxy gate comes from it (the User Manager's only once every access pod has proved it enforces, IAM 2.7). A tool that signs people in itself gets its role setting from a group's `tool:` block (schema_version 3, checked by `invariants.py`): `compiler/tools.py` maps the group's levels to the tool's settings (first match, unconstrained levels only; the roles given a setting must equal the host's gate, and `reaches` must cover the tool's datasource ceiling), `cli.py compile grafana` prints Grafana's role path (IAM 3.1), `cli.py compile jupyterhub --setting allowed_groups|admin_groups` the AI workbench's lists (IAM 3.2: settings `admin` (K only, `tools.SETTING_LEVELS`) and `user`; no service identity), `cli.py compile node-red` Node-RED adminAuth's `permissions.json` (IAM 3.3: setting `editor`, U only, = `tools.NODE_RED_PERMISSIONS`, every editor scope but `nodes.write`, so palette modules come only from `apps/node-red/packages.txt`; Node-RED's `read` is no setting because GET /flows shows the ingest password; service identity `svc_ingest`), and (IAM 3.4) `cli.py compile edge-wizard` the onboarding wizard's `--required-role` (onboarding's setting `onboard`, C/U, comma list, any one admits: engineer,maintenance) and `cli.py compile pgadmin` pgAdmin's `OAUTH2_ADDITIONAL_CLAIMS` (platform_admin's setting `sign_in`, K only: `{'groups': ['admin']}`), both through `policy_tool edge-wizard|pgadmin` (`infra/lib-policy-tools.sh`; IAM_GATES=false: `EDGE_WIZARD_ROLE` and `{'groups': ['admin']}`; under true a set EDGE_WIZARD_ROLE is ignored with a warning; an empty list never compiles). - **`edge/src/host/edge_auth.py`** — The token holder (stdlib only): `TokenSet`, `fresh()` (refresh under a per-set lock, `invalid_grant` → reauth, keeps a token with >30 s left when Keycloak is down), `Holder` (bind, re-sign-in by the same `sub`, 2-min backoff, keepalive `tick`), `device_login` (RFC 8628, no `offline_access`) and `agent` (the terminal holder; wipes its tokens on EOF/SIGTERM — **never revokes**: Keycloak's revocation endpoint detaches edge-wizard from every session the person has, and its logout would end their whole SSO session, since a device sign-in reuses the browser's). `NET_ERRORS` includes `http.client.HTTPException` (IncompleteRead is no OSError); device polling treats a 5xx or an answer without an OAuth error as the network; `serve()` turns any unexpected exception into `ERR unreachable` rather than ending the channel. Line protocol, one request → `WAIT…`* then `OK exp user name role token` or `ERR code message`: tab-separated, every field non-empty (`-`), every reply one write ≤ 4096 bytes, requests ≤ 512 bytes. `tests/test_edge_auth.py` covers it, the agent and wizard_server's start/callback/logout.
- **`apps/edge-wizard/`** — Makes the wizard part of the install: builds `edge/.venv` (`ensure_edge_venv` in `edge/lib-venv.sh`, shared with `flash-device.sh`), writes the `cea-edge-wizard` systemd **user** unit from `wizard-daemon.sh --install-unit`, restarts it (a `--reset` gives the Keycloak client a new secret) and enables linger. It refuses while a `flash-device.sh` runs in the unit's own control group (the restart would kill it; a run outside the unit does not block), logs the compiled onboarding roles (a policy that does not compile fails before the restart) and warns when the daemon's argv lacks them. A host service, not a pod, because flashing is over USB; it sorts before `frontend`, whose deploy checks the wizard answers. Browsers reach it at `https://$ONBOARD_DOMAIN` (`onboard-device.medcea`): a selector-less Service whose Endpoints is the host (`PLATFORM_IP:EDGE_WIZARD_PORT`, the node's InternalIP), behind the usual TLS Ingress. The wizard takes `--allowed-host https://<name>` for a proxied name and builds that redirect_uri with https; the name is in `_SVC_DOMAINS` (certificate SAN) and in the `edge-wizard` client's redirect URIs, so adding it needs a `deploy-infra.sh` run.
- **`edge/templates/<family>-{sense,control}.json`** — **The wizard's questions are data, not code.** Adding a supported sensor is an entry here plus a branch in `edge/src/app/cea_sense.py`; `flash-device.sh` does not change. The file name carries the device family (`esp32-control.json`); `CEA_DEVICE_FAMILY` selects one, default `esp32`.
- **`edge/templates/esp32-gpio.json`** — The GPIO reference for the whole ESP32 family: which pins each of the seven variants has, and what already wants them (SPI flash, PSRAM, strapping, USB-JTAG, UART0, input-only). Sourced from Espressif's per-target ESP-IDF GPIO pages. It drives the form's board selector, its pin reference panel, and validation — one table, so the reference cannot say a pin is free while the validator calls it taken.
- **`edge/src/host/bindings.py`** — How a command reaches equipment: what identifies one channel, what counts as a legal address, and what the field is called in the file the device reads. Driven by the template's `binding` block, so a device family that is not addressed by GPIO is a new template rather than new Python. Also holds `validate_config()`, the structural checks both the renderer and the browser editor apply.
- **`edge/src/host/ui/channelmap.{js,css}`** — The channel-map editor. Inlined into the wizard page by `wizard_server.py` and into the standalone tool by `edge/tools/build-editor.sh` — one implementation, two hosts. It renders whatever `device_template.py channelmap` prints and contains no mention of a GPIO.
- **`edge/tools/build-editor.sh`** — Rebuilds `edge/tools/actuator-config-editor.html`, a serverless copy of the editor for inspecting or hand-correcting a map away from the platform. Re-run it after changing `channelmap.js`, `channelmap.css`, or the CONTROL template.
- **`edge/src/host/platform_db.py`** — Units, zones, free slots and device registration over PostgREST. Reaches `config-api` by ClusterIP (kube-proxy runs on the host, so ClusterIPs are routable); `CEA_CONFIG_API` overrides. The operator's token arrives on fd 3 only when `PLATFORM_DB_TOKEN_FD=3` is set, and only through `platdb()` in flash-device.sh. Phase 1 sends nothing (no jwt-secret on config-api: Bearer would be PGRST300). `IAM_POSTGREST_JWT=true` (Phase 2b: config.env, then `./apps/frontend/deploy.sh` gives config-api the keys) sends `Authorization: Bearer` and refuses locally without a token; `_phase2_error` turns config-api's refusals into what to do (500 PGRST300 no JWT key, 401 PGRST301/303 expired or refused, 401 PGRST302 anonymous, `pre_request`'s 403 messages). It writes nothing to stderr on success. `tests/test_platform_db_token.py`.
- **`edge/src/host/device_template.py`** — Turns a template into prompts, then prompts into the board's `device_cfg.py` / `actuator_config.json` and the database component rows.
- **`edge/src/app/`** — The MicroPython application, **identical on every board**. Per-device values live only in the generated `device_cfg.py`; `config.py` derives topics and client id from it, `main.py` dispatches on `ROLE`.
- **`apps/<component>/deploy.sh`** — Per-component idempotent deploy script. Each sources `config.env` from the repo root and uses `sudo microk8s kubectl` directly. New components are auto-discovered by `deploy-apps.sh`.
- **`apps/database/deploy.sh` + `lib-db-apply.sh`** — `db_apply NS POD MODE` is the whole database deploy, shared with `tests/iam-db-fixture.sh` so the throwaway instance gets exactly what production gets: role shells (medcea_owner, anon, authenticator, mqtt_auth) → database → DDL → migrations with a nonce that 008b must have committed (`008b:last_nonce`) → `medcea_db_owner.sql` → `medcea_db_008b_data.sql` (one-shot, as medcea_owner) → `medcea_db_008b_index.sql` (CONCURRENTLY, batched backfill, autocommit) → passwords (authenticator's is whatever config-api logs in with *now*: `pgrst_db_auth_pass` — legacy → `POSTGRES_PASS`, jwt → Secret `db-authenticator` (missing: `AUTHENTICATOR_DB_PASS`, and the Secret is written), absent → by the flag; two templates live or an unreadable deployment is a refusal) → the `IAM_DB_ROLES` bundle. psql always runs in the pod with SQL and secrets on stdin and `PGOPTIONS=-c client_min_messages=warning -c lock_timeout=5s` (production's `client_min_messages=error` would hide 008b's WARNING listings; a busy table fails the deploy instead of stalling ingest — re-run). The database name is `$CEA_DB`; SQL files use `current_database()`. Secrets `db-<role>` (label `medcea/db-role=true`, `k8s/db-role-secret.yaml`) carry each role's credentials; nothing mounts them before 2.5. `--purge-data` drops the database, then every role (`purge.sql` with `cli.py db-roles --names` + medcea_owner, authenticator, anon) and the Secrets.
- **`config.env`** — Sourced by all scripts. Not committed (in `.gitignore`). See `config.env.example` for the full variable list.

## Key Architecture Decisions

**Single-pass deployment:** `deploy-infra.sh` deploys everything in one run. After Keycloak is ready, it uses the Admin REST API to create realm `medcea` and confidential clients (`node-red`, `grafana`, `kubeflow`), then writes the generated secrets into `config.env` and re-sources it before deploying the services that need them.

**Charmed Kubeflow 1.9 via Juju:** Kubeflow is deployed as `juju deploy kubeflow --trust --channel=$KF_CHANNEL` into MicroK8s. Juju manages the entire Kubeflow operator lifecycle. This replaces the old approach of manually cloning manifests and running 5 sequential `kubectl apply -k` passes with cert-manager readiness gating.

**MetalLB for Kubeflow ingress:** MicroK8s's MetalLB addon assigns a real LAN IP from `METALLB_RANGE` to Kubeflow's `istio-ingressgateway` LoadBalancer service. `KUBEFLOW_IP` is the first IP from that range and is used for all Dex and oidc-gatekeeper configuration. Kubeflow is accessed at `http://$KUBEFLOW_IP` (not via subdomain).

**Bootstrap fast-exit:** `bootstrap-infra.sh` exits immediately (without prompts) if both MicroK8s and a Juju controller named `k8s-controller` already exist. On wipe, it removes Juju (snap + `~/.local/share/juju`) before removing MicroK8s.

**Device identity comes from the database, not from typing:** a board is a slot — one unit, one zone, one role — and a unit/zone holds one and only one SENSE and one and only one CONTROL. Free slots are read from `medcea.device` on every run — a slot is free when no *active* device of that role points at the zone — so replacing a board is marking the old one inactive. `platform_db.register()` finds the slot's row by `zone_id` + `device_type` (most recent, active or not) and updates it in place, `dns_name` included, so re-onboarding never creates a second row, even after a code was renamed. A board is one row because `serial_number` (the MAC) is unique: when the board just probed is registered in a *different* slot (`platform_db.py board <serial>`), the wizard asks "Move this board from <old> to <unit> / <zone>?" right after the MAC is read and before anything is erased. Yes passes `move_device_id` and its own row moves (an older inactive row in the target slot is renamed `<name>-<id>` to free the name); no stops with nothing written; `--yes` refuses rather than move silently. Every placement is kept in `medcea.device_slot_history` (migration 006): trigger `device_slot_history_trg` on `medcea.device` appends `placed`/`moved`/`renamed`/`replaced`/`removed` with from/to slot, name and serial — whether the change came from the wizard or from the config UI's Edit. It is append-only by the Compliance Plane rule: the trigger function is `SECURITY DEFINER`, and `medcea_db_migrations_down_008b.sql` (the IAM_DB_ROLES=false bundle, the only place the blanket `anon` grant lives) revokes INSERT/UPDATE/DELETE on it from `anon` **after** that grant (which would otherwise re-grant them on every deploy); under true, anon holds nothing. See the `IAM_DB_ROLES` rule below for where a new append-only table's revoke goes. No foreign key, so the history outlives a deleted device. Everything derivable from the slot (MQTT host and port, topics, client id) is inferred and never asked.

**Access is requested, not created:** the portal's oauth2-proxy admits the roles compiled for PORTAL_DOMAIN — all eleven platform roles of `defaults.yaml` (`allowed_groups`, read from the `groups` claim). A person asks through `access.$DOMAIN/register`, which creates the Keycloak user **disabled** and an `iam.access_request` row; an admin approves (role as requested, or reassigned) or rejects with notes in the User Manager. The form and the User Manager offer all eleven roles (IAM 2.6): `ROLES` in `access-api.py` is a copy of `defaults.yaml` `roles:` (label, availability, description, policy order), checked against the policy and `access_db.sql`'s CHECKs by `tests/test_access_api.py`, and deliberately not read from routes.json, whose digest `role_widening()` carries (a wording change never needs a database deploy); `availability: later` (qc, qp) is offered, tagged 'not yet in use'. Approval is an account decision (`grant`, IAM 2.7) that waits for a qa person: the request reads `approved`, but the account stays disabled with no role until qa confirms, which maps the role, enables the user and sends the approval e-mail; rejection (and a grant qa refuses) deletes the Keycloak account and keeps the row, so the person can apply again. Keycloak is changed inside the open DB transaction that holds the request row `FOR UPDATE`, so a Keycloak failure leaves the request pending, and two admins cannot both decide it. Mail goes out after commit and never undoes a decision; until e-mail is set up in the User Manager it goes to the service log. `deploy-infra.sh` gives a built-in user a role only when that run creates the account (ADMIN_USER → `admin`; under `IAM_GATES=false` also the pre-3.1 demo accounts: GRAFANA_ADMIN_USER → `admin`, developer → `operator`, viewer → `auditor`; under true it creates no demo account, retires the `grafana_*` realm roles and leaves existing demo accounts alone) (IAM 2.7: re-granting on every run silently undid applied narrowings); break-glass: with no enabled admin it re-grants `admin` to ADMIN_USER, loudly, and the Decisions tab shows that as drift. Users created by hand in Keycloak need a role.

**A board's MQTT identity is its name:** onboarding (`flash-device.sh`) mints a fresh password per board on every onboarding, writes `MQTT_USER` (= `dns_name`) / `MQTT_PASS` into `device_cfg.py` and the provisioned record — never into `component.parameters`, which `anon` can read — and registers only the hash through `POST /rpc/register_mqtt_credential` (SECURITY DEFINER, migration 007; `anon` may execute it but cannot read `medcea.mqtt_credential`). The ACL confines a SENSE board to `<topic_base>/sense/#` (write) and a CONTROL board to `…/control/#` (read) + `…/control_setpoint/#` (write). Marking the device inactive (`device.is_active='N'`) revokes it within one sync (≈15 s). A board flashed before credentials existed cannot connect: re-onboard it. Under `IAM_MQTT_PERSON=true` the 1883 listener carries boards and services only, and person (Explorer) credentials only the WebSocket listener.

**One name per device — the DHCP hostname:** `lower(unit_code)-<s|c>-lower(zone_code)`, e.g. `unit02-c-zone02` (`platform_db.slot_hostname`). It is the hostname DHCP registers, `medcea.device.dns_name`, `device_dns` in every MQTT payload (the key name is kept for Node-RED, `measurement.device_dns` and the `msg_*` views), what the config UI's Online check pings, and the record file name. Lowercasing is the **only** transformation: a code a hostname cannot hold (underscore, space, leading/trailing hyphen) or a name over 32 characters (MicroPython's hostname buffer) makes the slot "unnamed" — listed with the reason, not offered — and the fix is renaming the code. There is no fallback name. Uniqueness comes from the codes: migration 005 adds case-insensitive unique indexes on `unit_code` and on `(unit_id, zone_code)`, which the config UI reports as "already exists". An unregistered board is `cea-un-<mac6>`. It replaced `UNIT02_CONTROL_ZONE02` (never resolvable; nothing parsed it — topics and payload fields carry unit and zone) and the compressed `u02-c-z02` (which changed whenever another unit was added). Pods resolve the name because cluster DNS forwards to the node's resolver, i.e. the router that holds the DHCP names; the host itself cannot (systemd-resolved keeps single-label names off unicast DNS) and only resolves `<hostname>.local` over mDNS. A board flashed before the change keeps its old names until re-onboarded.

**`IAM_DB_SERVICE_ROLES` (Phase 2.5, default false) moves the services off postgres before anything is enforced.** True: `apps/database/deploy.sh` lets every login role with a password log in (`cli.py db-roles --logins` → `db_apply` `DBA_SERVICE_LOGINS` → `compile grants --mode additive --service-logins`, which also grants `rr_admin` to `rr_admin_login`, INHERIT without SET), while `IAM_DB_ROLES` stays false: no RLS, the policy refusals are still WARNINGs, but a statement a service's grants do not cover is now "permission denied" — that is the point. False: only the roles a live client still uses keep their login. The additive assertions read the catalog (a managed role may log in only if it is a login role; `rr_admin_login` → `rr_admin` only while it may), so `grants --mode verify` needs no parameter. **Enable:** `IAM_DB_SERVICE_ROLES=true`, `./deploy-apps.sh --all` (database first), `./deploy-infra.sh` (Grafana, pgAdmin); `dbclients` OK. **Rollback:** false and the same two deploys, then `./apps/database/deploy.sh` once more to make the roles NOLOGIN. `IAM_DB_ROLES=true` is refused until it is true and every client has moved.

**`IAM_DB_ROLES` (Phase 2a, default false) switches the database between two bundles.** Migration 008b (additive: tables, columns, functions, always-on triggers, ownership) applies on every deploy; then one transaction applies either `medcea_db_migrations_down_008b.sql` + `cli.py compile grants --mode additive` (false: today's grants — anon on the medcea tables — and the per-role grants on NOLOGIN roles nobody uses) or `medcea_db_migrations_008b_enforce.sql` + `--mode enforce` (true: per-role grants, LOGIN, CONNECT, RLS, `iam_*` guard triggers, `log_statement=all` for postgres), the settings, and assertions last (I9/I10/I15: the catalog equals the compiled policy, or the whole bundle rolls back). The flag lives in `medcea.platform_setting.iam_db_roles` (triggers read it through `medcea_auth.enforcing()`, which a session cannot override) and in the database setting `medcea.iam_db_roles` (read only by `pre_request()`, which runs as anon and may read no table; new sessions see it, so PostgREST needs a restart after a flip: `apps/database/deploy.sh` reads the setting before applying and runs `rollout restart deployment/config-api` when it changed). Transitions append `enforcement_enabled`/`enforcement_disabled` to the hash chain. **Rollback: `IAM_DB_ROLES=false`, `./infra/deploy-workbench.sh` (closes the notebooks' hops), then `./apps/database/deploy.sh`** (which also closes them on a running workbench before it applies, `workbench_egress_close`, and refuses if it cannot; it restarts config-api; or the down file by hand, then `kubectl rollout restart deployment/config-api`, which records the flag and the event itself, and sets every `rr_*`/`svc_*`/`iam_svc` role NOLOGIN again — enforce made them LOGIN and the down file hands CONNECT back to PUBLIC). Before a `git revert` of the Phase 2 code, also run the down file with `-v full=1`: it drops 008b's triggers and functions, gives medcea back to postgres, revokes every privilege of the managed roles and parks 008b's tables with their data in schema `medcea_retired_008b` (no grants), where the reverted deploy's blanket anon grant cannot reach the broker's service hashes or the audit tables; the new columns stay, and re-applying 008b moves the tables back. `deploy.sh` refuses true until `IAM_POSTGREST_JWT=true`, config-api runs contract C1 (`PGRST_JWT_SECRET` from `medcea-jwks/jwks-sig.json`, `AUTHENTICATOR_PASSWORD` from `db-authenticator`, `PGRST_JWT_AUD`, `PGRST_DB_PRE_REQUEST`; 2b), `IAM_DB_SERVICE_ROLES=true` and every deployed database client logs in as its own role (2.5, `db_clients_live`) and `AUTHENTICATOR_DB_PASS` is set and differs from `POSTGRES_PASS`. `health-check.sh` WARNs (`iamdbroles`, and `iamenforce` for IAM_ENFORCE) while it is false, so a default install never prints "All checks passed" — on purpose; `iamgrants` runs `grants --mode verify` read-only and FAILs on drift. Under true, `apps/database/deploy.sh` warns (never refuses) when no unit is assigned to anyone: `own_unit` RLS on `measurement`, `recipe_run`, `recipe_line_cycle_run` and `run_release` shows an operator only their units' rows, and the run functions' `assigned_run` check compares the run's unit with `iam_policy.user_unit`, so an operator without a unit sees nothing and starts nothing (`apps/iam/units.sh list`; a unit still waiting for qa is not in effect); the Monitor and the scheduler's run reads apply the same rule (IAM 2.6), already once `IAM_ENFORCE=true`.

**The anon blanket grant lives only in the down file.** A migration re-run on every deploy must never re-grant what enforce revoked (migration 007's `GRANT … TO anon` moved there too). A new medcea table needs three things: `REVOKE ALL … FROM PUBLIC, anon, authenticator` (and on its identity sequence) right after its `CREATE` in the migration (postgres's default ACL gives anon arwd on every new table), an explicit REVOKE in the down file after the blanket grant (and in `grants.LEGACY_ANON_EXCLUDED`), and a member entry in `defaults.yaml` (or I15 refuses the enforce bundle).

**`medcea_owner` owns `medcea`, `medcea_auth`, `iam_policy` and (IAM 2.7) `iam`** (the DDL, `medcea_db_owner.sql` and 008b itself; `iam` only through `medcea_db_owner.sql`), is NOLOGIN and has no members. `access_svc`'s grants are compiled like every other role's (`grants.DEFERRED` is gone). `dba_iam_flag NS POD DB` (`lib-db-apply.sh`; db_apply, health-check `iamgrants`, `tests/iam-db.sh`) decides how `cli.py compile grants` treats schema `iam`: nothing (compiled like the rest), `--without-iam` whenever schema `iam` is absent (no access component, or after a purge; a left-over `access_svc` then holds nothing compiled), exit 3 for a half-present component (schema `iam` without `access_svc` or without `iam.confirm_decision`: "run ./apps/access/deploy.sh first"), exit 1 when it cannot ask — callers abort or FAIL, never default. The three iam histories (`user_status_history`, `access_request_history`, `config_history`) are append-only by trigger (`ENABLE ALWAYS`), the owner and the superuser included. "Only a function may write this" means `current_user = 'medcea_owner'` in a SECURITY INVOKER trigger (the guards, `reject_non_draft_update`, `immutable_row`, `algorithm_state_guard`); a SECURITY DEFINER trigger cannot see the writer, so owner functions also mark their writes in the actor store (`_owner_write`). The guards call no function: the writer (anon, today) executes nothing in medcea. `ALTER DEFAULT PRIVILEGES … REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` for postgres and medcea_owner applies in both modes. **The scheduler runs no DDL**: 008b creates `schedule` and `scheduler_config` (redeploy the scheduler with 2a).

**Attribution and approvals (008b).** `stamp_actor()` overwrites `created_by_*`/`updated_by_*` (sub, person, name, role, source) on the 14 attributed tables; the actor comes from `medcea_auth.set_actor()`/`set_system_actor()` for the current transaction (a temp table `pg_temp.medcea_actor` owned by medcea_owner, checked on every read — a table of that name owned by anyone else raises "spoofed"), or from the verified claims when `session_user = authenticator`; otherwise `db:<login>` (refused while IAM_DB_ROLES=true, superusers excepted). `set_actor` takes only a uuid sub and a platform role, recorded as `person via <login>`. Every change to those tables is also in the append-only `medcea.row_change`, which the approval functions read for not_own_author (status/retired_at-only changes make nobody an author). A non-owner may not set `approved` or leave `retired`; editing an approved recipe, algorithm or parameter set (or a recipe's line) demotes it to draft with a WARNING while false and is refused while true (`draft_only`). Approval needs a token-sourced person holding A who is not among the authors since the last approval and no unattributed change; existing definitions were grandfathered once (`action='grandfather'`). Policy refusals (assigned_run, approved-only, commissioning, retention, digest mismatch) go through `policy_refuse()`: a WARNING while false, 42501 while true; structural ones always raise. `cea_unit.commissioning`, `schedule.retired_at` and `recipe_run.params_id` change only through functions (always); `params_id` on assignments and schedules too while false. **Append-only triggers are `ENABLE ALWAYS`** (008a's included): `session_replication_role=replica` does not bypass them. **Code CHECKs** (`cea_unit_code_chk`, `cea_zone_code_chk`, `[A-Za-z0-9_-]`) are added only once no code violates them; until then each database deploy lists the violators, which stay editable.

**The scheduler and the runner write runs through 008b's functions (2.4).** Every regulated write runs in one transaction with its actor, because the actor lasts one transaction. In `apps/scheduler/scheduler-api.py`, a person-initiated request uses `set_actor(sub, person_id or sub, username, own role)` from the token `check()` verified (`g.medcea_iam.who` only, uuid sub required; the own role is `medcea_iam.actor_role()`, from `role_includes`, which `cli.py compile routes` now emits — the same rule as SQL `_own_role`). A schedule firing, a dead runner and the run-once retire use `set_system_actor('system:scheduler', 'schedule'|'run', id)`, which takes the schedule's creator, or, for a schedule created before attribution, its last editor if that edit came from a token and the editor's role holds C on runs ("…until a person who holds C on runs re-saves it"). **Fallbacks exist only while IAM_DB_ROLES=false and as a superuser** (postgres; on `svc_scheduler`, under `IAM_DB_SERVICE_ROLES`, there are none: a schedule with no person behind it is refused as under true, and the two false-only direct writes — reopening a completed run, saving the log settings — take the true path, `_functions_only()`): plain DML gets no actor, so `stamp_actor` writes the honest `db:postgres`; a function that needs one gets `system:scheduler-unverified` (a request) or `system:scheduler` (a job); each is logged with method, path and reason. Under true a request without a person is 401. The code reads `medcea.iam_db_roles` only to pick its path; it grants nothing. Runs: `POST /api/runs/<id>/execute` and the trigger call `medcea.start_run`, the stop route `set_run_status(F)` before SIGTERM, and the runner gets the run as `RECIPE_RUN_ID` (`schd/run_recipe.py` `run_recipe_by_id`: status must be R, `record_cycle` R → agent → C, `finish`; `RunStopped` (a BaseException) exits with no write; any other error marks the cycle and run F). `schd/cea/actor.py` (`acting(conn, run_id)`) and `cea/runs.py` hold it; without `RECIPE_RUN_ID` the CLI path is unchanged but refuses while 008b enforces. `_spawn` reaps the runner: still R or S after it exits means F; startup recovery also marks F an API-started R run (`executed_by_sub` set) with no pid file. **DELETE `/api/schedules/<id>` retires** (`medcea.retire_schedule`, which checks U on schedules for the actor's role through `policy_refuse` — a WARNING while false; already retired → 200, nothing written), and `schedule_retired_guard_trg` refuses any non-owner UPDATE of a retired schedule, always (T6), so a retired schedule never fires again, even after a rollback. It is its own function and trigger (SECURITY INVOKER, ENABLE ALWAYS) on purpose: the migration file before 2.4 re-creates `guard_control_columns()` on every deploy and would drop a check folded into it. **Under IAM_DB_ROLES=true the scheduler never acts for a person the route table refused** (`_act_person` answers the decision's 403 when `d.allow` is false), even while `IAM_ENFORCE=false` only logs the refusal: svc_scheduler holds the table grants for every scheduler write and the database checks the role only inside some functions, so for plain DML the route decision is the check; under false the write goes on, attributed to that person, with a log line. The deploy-time B4 WARNING lists every schedule `set_system_actor` would refuse (its own predicate: no person creator — `migration:008` or `db:<login>` — and no token/`person via` re-save by a role holding C on runs freely). Lists filter `retired_at IS NULL`. **`params_id` only under true**: while false every run gets `params_id = NULL`, and the algorithm is chosen exactly as before (the execute body, else IF_THEN_ELSE, a schedule's inline settings). Under true the run needs its set (the schedule's, else the assignment's), inline parameters are 400, and a schedule save copies the set's algorithm and params into the inline columns, so a rollback runs what the set says. `_check_run_params(unit, recipe, params, schedule)` lets a schedule's algorithm override the assignment's. `record_cycle` never reopens a cycle in C (22023), and C→S is refused once a `run_release` exists. Under true `PUT /api/config/logs` becomes `propose_setting` (202, pending qa); in both modes a changed value below the database's minimum (compress ≥1, delete ≥30) is 400; a key sent back unchanged is skipped, so a legacy value below it never blocks the other. **IAM 2.6:** `POST /api/logs/compress|delete` and `DELETE /api/units/<id>/algorithm-state[/<algorithm>]` are gone. **Run logs are compressed, never deleted**: the scheduler's own APScheduler job `sys_log_retention` (`apps/scheduler/log_retention.py`, shipped in the `scheduler-api` ConfigMap, daily 03:15 UTC) gzips a `.log` after `log_compress_days` when its run is C/F (attributed by run id and the `_log_path` name) or it is an unattributed legacy log, never one of a run in S/R or running; `log_delete_days` stays a qa-approved setting nothing reads. The Config UI's `api()` shows a 401/403 with code 42501 as a refusal, not a sign-in. **Database passwords** (`SVC_*_DB_PASS`, `IAM_SVC_DB_PASS`, `RR_ADMIN_LOGIN_DB_PASS`, `AUTHENTICATOR_DB_PASS`) are generated by `infra/configure.sh` before its early exit and reach PostgreSQL only as SCRAM verifiers (`infra/pg-scram.py`, password on stdin) in `log_statement='none'` sessions (the access deploy's sessions set it too). The new roles are NOLOGIN while IAM_DB_ROLES=false, except the login roles `IAM_DB_SERVICE_ROLES` lets in (below); authenticator keeps `POSTGRES_PASS` while config-api is legacy; `pgrst_deploy` moves it to `AUTHENTICATOR_DB_PASS` in the same step as config-api's URI (2b). **`grants.py` reads `defaults.yaml`**: a new table, view or function needs a member entry (functions take `level:` — the old `on:` key is read by YAML 1.1 as the boolean true), `service_only` is a list of services, `written_by: functions` means SELECT only for everyone, a function that is a table's only writer lists it in `writes:`, a waiver names its `objects`. Not-yet-built functions go in `grants.NOT_BUILT`. `tests/iam-grants.golden.json` is the compiled privilege list: change it deliberately (`python3 tests/test_policy.py --update-golden`) and review the diff. `tests/iam-db.sh` is read-only by default; `--write-probes` (each probe in `BEGIN … ROLLBACK`, SQLSTATE and message checked after a positive control) runs only against namespace `medcea-iamtest`. `tests/iam-db-fixture.sh run` builds that throwaway instance from production's image digest, loads production's schema, roles and medcea data read-only (under the lock), and covers apply false/true, the cycle, the full down with the previous commit's code, a fresh install, logins, the server log and the purge; it deletes the namespace on exit.

**The access policy's history is a hash chain:** migration 008a creates schemas `iam_policy` (not `iam`, which access `--purge-data` drops) and `medcea_auth`, both owned by the NOLOGIN role `medcea_owner`. `iam_policy.history` stores `prev_hash` and `hash = sha256(history_record(...))`, the canonical JSON of the row in UTC, so writer and verifier share one function and the session's TimeZone cannot change a hash. `append_history(event, payload, reason)` is its only writer (SECURITY DEFINER, advisory lock, READ COMMITTED only, or a snapshot could miss the head and fork the chain); its actor is `medcea_auth.request_actor()` since 008b (`actor_sub` only for a person's uuid; `system:`/`migration:`/`db:<login>` actors in `actor_name`). Triggers refuse UPDATE, DELETE and TRUNCATE for every role, the owner included, on `history` and `export_log`; Unit assignments (`iam_policy.user_unit`, IAM 2.8) are in the chain as `unit_assigned`/`unit_removed` (trigger `user_unit_audit_trg`, `ENABLE ALWAYS`); `iam_policy.user_zone` and its `zone_*` events stay, unused, for the history that names them. `verify_chain()`, which `health-check.sh` runs (check type `iamchain`), catches any edit that does not rebuild the chain — **not** a superuser who disables the triggers and then drops the newest events or re-hashes from the edited one onward; that needs the head anchored outside the database (plan Section 7, not built). `iam.account_decision` and `iam.access_review` (`access_db.sql`) are likewise final once checked or signed off: a trigger lets only the check/sign-off columns be filled, all in the one UPDATE that sets `checked_at`/`signed_off_at`. `medcea.platform_setting` holds `mqtt_topic_root` (= `PROJECT_NAME`), written by `apps/database/deploy.sh` (`lib-db-apply.sh`, the settings block of the mode bundle); `anon`'s blanket grant on it is revoked in `medcea_db_migrations_down_008b.sql`, right after that grant (and listed in `grants.LEGACY_ANON_EXCLUDED`).

**A device family is a template, not a fork:** everything the platform does with a CONTROL device — ask which equipment is fitted, derive the command table, prune branches the chamber cannot perform, validate, render, write the component rows — runs through the template's `binding` block. `binding` names the address field (`pin`), its label (`GPIO`), the map key in the emitted file (`pin_descriptions`), whether an address is an integer or a string, which values are legal, and which carry a warning. `edge/templates/examples/modbus-control.json` is the worked proof: a CONTROL device addressed `3:0001` over Modbus renders and validates correctly through the same `device_template.py` and the same browser editor — labelled "Coil", checked against its own regex — with no Python anywhere for it. What a binding does **not** abstract is provisioning: `flash-device.sh` writes MicroPython over USB, and a device that is not flashed that way needs its own path into the fleet.

**The board is a variant of the binding, not a fork of it:** every ESP32 is addressed by GPIO number, but an S3 has 0-21/26-48 while a C3 stops at 21 and puts its flash on 12-17. Selecting a variant swaps the legal ranges and the per-pin rules and changes nothing else. The form defaults to `esp32s3` and lets the operator change it, because **the wiring question is asked before the board is ever probed** — a slot and a pin map are chosen while the ESP32 is still on the bench. Step 3 is where the two meet: once esptool reports the real chip, `flash-device.sh` re-validates the map against it and refuses if it cannot drive that silicon. Without that check an S3 map on a C3 flashes cleanly and then quietly fails to switch a relay.

**One editor, two hosts, one validator:** the channel map is edited in `edge/src/host/ui/channelmap.js`, which the wizard inlines and `build-editor.sh` bakes into a standalone page. Its structural rules are deliberately mirrored in `bindings.validate_config()` — the browser needs a verdict on every keystroke, and the renderer needs one it can refuse on. **Python is authoritative:** `render()` re-checks and raises rather than writing a table with errors in it, so a hand-crafted POST or a stale page cannot put a broken map on a board that has just been erased. Device-specific rules are not duplicated at all; both sides read them from the template.

**MQTT topic root is `$PROJECT_NAME` (= `medcea`):** SENSE publishes `medcea/<UNIT>/<ZONE>/sense/<tag>`, CONTROL subscribes `medcea/<UNIT>/<ZONE>/control/#` and reports to `.../control_setpoint/...`. Every consumer gets the root at deploy time, never from a literal: Node-RED has `__TOPIC_ROOT__/#` substituted by `apps/node-red/deploy.sh`; the scheduler pod gets `PROJECT_NAME` as env and hands it to `run_recipe.py`/`run_agent.py` through `/installer/.env`; `flash-device.sh` bakes it into each board's `device_cfg.py`. Mosquitto's ACLs are written per device from `topic_base` (`<root>/<UNIT>/<ZONE>`), so the root is in the credential row too. There is no legacy `plantinc/#` subscriber in MedCEA — it is a fresh fleet. Changing `PROJECT_NAME` after boards are flashed means reflashing them.

**Name-based domain (`DOMAIN=medcea`, `LOCAL_DNS=true`):** three pieces work together:
- the `name-dns` Deployment (CoreDNS, `hostNetwork`, bound to `PLATFORM_IP:53` only, so it never collides with systemd-resolved on 127.0.0.53) answers `*.medcea` for tailnet devices once Tailscale split DNS points `medcea` at the server;
- a managed `/etc/hosts` block (`infra/lib-dns.sh`) makes the server resolve the names itself during its first deploy, before anyone has set split DNS;
- `ALIAS_DOMAIN` (the old `<ip>.nip.io`) becomes 301 redirect ingresses labelled `medcea/alias=true`.

Pods need none of this, but only because every back-channel call goes to `*.svc.cluster.local`, and every oauth2-proxy sets `skip_oidc_discovery = true` with explicit internal URLs. Cluster DNS forwards to 8.8.8.8, which resolves `<ip>.nip.io` by luck and `keycloak.medcea` not at all: the config proxy lacked that flag and crash-looped (503) as soon as the domain became a name. SSO stays on one domain on purpose, because Keycloak's `KC_HOSTNAME`, Grafana's `root_url` and JupyterHub's `oauth_callback_url` each take a single URL.

**Helm OCI authentication:** The Bitnami chart registry (`registry-1.docker.io/bitnamicharts/`) requires Docker Hub credentials for Helm chart pulls only. Runtime container images (Keycloak on Quay, Node-RED on GHCR, etc.) are all auth-free. `deploy-infra.sh` injects credentials via MicroK8s's `certs.d/docker.io/hosts.toml` and `helm3 registry login`.

**`grep -c` + `set -e` pitfall:** `grep -c` exits 1 when the match count is 0. Combined with `|| echo 0`, this appends a second `0` to stdout (producing `"0\n0"`), causing `[ "$VAR" -eq 0 ]` to fail with "integer expression expected". All wait-loop counters use `grep -c ... || true` to let grep's own `0` output pass cleanly.

## Common Pitfalls

- **Never add `set -e` before `source config.env`** in a script that has a `--help` flag — the help branch must run before `set -e` and before sourcing so it works without a config file.
- **`microk8s status --wait-ready` exits immediately** on a fresh install before the daemon socket exists. The readiness check uses a retry loop with a deadline, not a one-shot call.
- **Juju controller existence is the skip guard** (not kubeflow namespace or pod count). Re-running bootstrap when `k8s-controller` exists skips the entire Kubeflow install block.
- **bitnami/keycloak image is behind a paywall** since August 28, 2025. Use the official `quay.io/keycloak/keycloak:26.0` image via plain kubectl manifests instead of the Bitnami Helm chart. `bitnami/postgresql` is still free. Health probes use port 9000 (management interface); the main app runs on 8080.
- **Keycloak 26.0 tag exists on quay.io** — use `26.0`, not `26` (which doesn't exist) or `26.x.y` patch tags.
- **schwarzit/node-red chart splits image into registry+repository+tag** — set `image.registry=docker.io`, `image.repository=nodered/node-red`, `image.tag=3.1.9`. Setting `image.repository=ghcr.io/node-red/node-red` causes the chart to prepend `docker.io`, producing the invalid URL `docker.io/ghcr.io/...`.
- **sudo-rs ignores `sudo -E`** (Ubuntu's default sudo since 25.10), and MicroK8s cannot work without it: `run_with_sudo` in the snap's `utils.sh` runs `sudo -E …` for every privileged step — `microk8s start`, addon enables, apiserver restarts — **even when already root**, so `sudo microk8s …` does not avoid it. The steps lose `SNAP_*` and fail (`snapctl … from outside of a snap`; `enable rbac` dying after "No callback tokens file."). A running cluster never takes that path, so the switch is temporary: `classic_sudo_begin` (`infra/lib-sudo.sh`) points the `sudo` alternative at classic `sudo.ws` for the duration of `bootstrap-infra.sh`, and a trap on EXIT/INT/TERM restores the previous setting. Any new script step that runs `microk8s enable|disable|start|stop|reset` must sit inside such a window. By hand: `sudo update-alternatives --set sudo /usr/bin/sudo.ws`, the microk8s command, then `sudo update-alternatives --auto sudo`.
- **Removing the snap does not stop the pods.** Pod processes live in `/sys/fs/cgroup/kubepods`, outside every systemd unit; orphaned calico-node got the next install's containerd SIGKILLed at start. Remove MicroK8s only through `remove_microk8s` (`infra/lib-mk8s-remove.sh`): stop kubelite, `cgroup.kill` the pods, kill MicroK8s's containerd-shims, and only then `snap stop` the rest and `snap remove --purge`, whose hook does the rest. **The order is load-bearing:** if containerd's unit stops with shims still in it ("remains running after unit stopped"), the next install's containerd is SIGKILLed within a millisecond and snapd rolls the install back — every removal that left shims did that, and the one that left none didn't. Bootstrap retries a rolled-back install once for removals made by older code. No `microk8s reset`: it disables every addon one at a time to restore a fresh cluster (minutes), which is pointless when the snap is about to go. `kill_orphan_pods` also runs before every install, so a dirty host from an older removal heals itself.
- **`microk8s enable` chaining** — MicroK8s 1.33+ warns that space-separated addon lists will be deprecated. Enable each addon with a separate `microk8s enable` call.
- **Dex-auth has NO ConfigMap** in Charmed Kubeflow 1.9. It is a Juju-managed StatefulSet. Config is applied via `juju config dex-auth connectors=<yaml>`. The `connectors` value is a YAML string containing a list of Dex connector definitions.
- **dex-auth connector redirectURI** must be `http://${KUBEFLOW_DOMAIN}/dex/callback` — this is Dex's own callback endpoint where Keycloak redirects after authentication. Do NOT use the oidc-gatekeeper callback (`/authservice/oidc/callback`) here. Use KUBEFLOW_DOMAIN (nip.io), NOT KUBEFLOW_IP (LAN IP).
- **dex-auth issuer-url must use KUBEFLOW_DOMAIN** — set via `juju config dex-auth "issuer-url=http://${KUBEFLOW_DOMAIN}/dex"`. This controls `OIDC_PROVIDER` in the oidc-authservice. The authservice constructs its callback URL (`redirect_uri`) using the OIDC_PROVIDER host. If OIDC_PROVIDER uses `192.168.1.200` (MetalLB IP) but users access Kubeflow via the nip.io domain, the CSRF cookie is set for nip.io but the callback goes to `192.168.1.200` — CSRF check fails. Using KUBEFLOW_DOMAIN for issuer-url ensures the full OIDC flow (auth URL, callback) stays on the same nip.io domain.
- **dex-auth connector requires `insecureSkipVerify: true`** — the nginx ingress has a self-signed cert valid for `ingress.local`, not the actual Keycloak hostname. Without this, Dex fails to fetch the OIDC discovery endpoint and exits with code 2.
- **juju status wait loop** — check unit-level juju-status (`grep -A1 "juju-status:" | grep "current:"`), not the first `current:` in the output (which is the workload status and always shows `available`).
- **Keycloak realm "HTTPS required" blocks HTTP callbacks** — production mode defaults to `ssl_required: external`. OAuth2 Proxy and Dex use HTTP callback URIs (no TLS on ingress), so the realm must have `ssl_required: none`. Set via Admin API: `PUT /admin/realms/{realm}` with `{"sslRequired":"none"}` (use kubectl port-forward to reach Keycloak internally).
- **OAuth2 Proxy defaults to `google` provider** — must set `provider = "oidc"` in `configuration.content` values file. Without it, the login button says "Sign in with Google" even with `oidcIssuerUrl` set.
- **PostgREST does not strip quotes from a filter value** — `?dns_name=eq."unit01-s-zone01"` matches nothing (it looks for a value that literally starts with a quote) and returns `[]`, which reads exactly like "no such row". Percent-encode the value instead; do not wrap it in double quotes.
- **A retry on any `23505` is wrong.** The `device`/`component` sequences trail the table because the seed import supplied explicit ids, so a *primary key* collision is worth retrying (each attempt burns one nextval). A collision on `dns_name` is a slot that already has a board, and retrying turns one clear error into thirty requests and a wrong diagnosis. Check which key is named in the error.
- **`while read ...; done < <(cmd)` gives its stdin to the loop BODY too** — so any prompt inside the loop reads from `cmd`'s output instead of the terminal, silently answering the question with the next line of data. Use `for x in "${arr[@]}"` with `IFS=$'\t' read -r ... <<<"$x"`, which redirects only that one `read`.
- **Never echo a password in `deploy-infra.sh` after the `exec > >(tee …)`** — everything on stdout lands in `logs/`. The final summary names users only. Passwords go to `credentials-<ts>.txt` (mode 600, gitignored), and its content is shown through `/dev/tty`, which bypasses the tee. Add any new human-facing password to that file, not to the summary.
- **A fresh group membership is not in the current session.** Bootstrap adds the user to `microk8s`, but the shell that ran it doesn't have the group until the next login. Hardcoded `microk8s kubectl` in the app scripts failed all six components on a clean install. Source `infra/lib-mk8s.sh` and never hardcode it. `install.sh` runs the app stages under `sg microk8s` (`with_mk8s_group`), so the first install needs no sudo for them.
- **Never derive an IP from `DOMAIN`.** `${DOMAIN%.nip.io}` silently becomes `medcea` under a name-based domain; use `PLATFORM_IP`. The MQTT Explorer WebSocket host and the edge-wizard URL used to do exactly this.
- **oauth2-proxy with `allowed_groups` requests the scope `groups`**, and Keycloak refuses a login asking for a scope it does not know (`invalid_scope`). So `groups` is a realm *client scope* carrying the realm-role mapper, a default scope of `portal` and `access` — a mapper on the client alone is not enough.
- **`smtplib.login()` hides Gmail's 535**: after `AUTH PLAIN` is refused it retries `AUTH LOGIN`, Gmail hangs up, and the error becomes "Connection unexpectedly closed". `apps/access` calls `auth('PLAIN', …)` directly so a wrong app password says so.
- **A 403 from oauth2-proxy is not always "no role".** A failed login (provider error, CSRF) is also a 403 but with its own message; `k8s/portal/error.html` says "No access yet" only for the default 403 message.
- **A Keycloak client PUT that omits `serviceAccountsEnabled` turns the service account off and on again**: the service-account user is deleted and recreated with a new id, and every role granted to it is lost (the `access` client's `manage-users`… — the User Manager then gets 403 on everything). `_create_client` therefore always sends the flag (third argument, `true` for `access`). Any manual client update must send it too.
- **Mosquitto refuses to start without its `password_file`**, and the sidecar writes it a moment later: the broker container waits (`until [ -s /mosquitto/auth/passwd ]`, and under `MQTT_PERSON=true` for `passwd-ws` too) before `exec`ing Mosquitto. With `per_listener_settings true` (IAM_MQTT_PERSON) `allow_anonymous`, `password_file` and `acl_file` are per listener and must follow each `listener` line; an empty password file is avoided by the `explorer-none` placeholder (not verified live whether Mosquitto 2.0 accepts one). A subscription wider than the ACL (`#`) is *accepted* by Mosquitto 2.0 — it filters per message — so a quiet subscriber is not proof of a refused SUBACK.
- **`PGADMIN_CONFIG_*` values are Python literals** (written verbatim into `config_distro.py`): `"['oauth2']"`, `"True"`, quoted strings in the OAuth2 dict; `OAUTH2_ADDITIONAL_CLAIMS` is `${PGADMIN_OAUTH2_CLAIMS}`, a compiled literal, so it must stay in the pgAdmin render list. The pgAdmin pod resolves `keycloak.<name-domain>` only through `hostAliases` (→ `PLATFORM_IP`), because authlib reads the issuer's metadata by its public URL. Break-glass: `kubectl set env deployment/pgadmin PGADMIN_CONFIG_AUTHENTICATION_SOURCES="['internal']"`.
- **A freshly onboarded board's first connects are refused for up to ~15 s** — its credential row is registered after it boots and reaches the broker on the sidecar's next sync. `connect_mqtt()` raises, the board restarts and the retry succeeds; not a fault.
- **Only `theme.properties` goes through `render`.** The `.ftl` files are FreeMarker, whose `${...}` must reach Keycloak untouched, and for the same reason their JavaScript cannot use template literals. Deploy-time values (`accessUrl`) are theme properties, read in FTL as `properties.accessUrl`.
- **Keycloak caches themes in production mode** and never re-reads the mount, so a changed theme needs a pod restart: the theme checksum is a pod annotation (`medcea/theme-checksum`). The ConfigMap holds 1 MiB, which is why the background is `apps/portal/bg.jpg` (152 KB) and not the 1.7 MB PNG.
- **A user without a platform role gets a 403 from the portal**, not a login error: oauth2-proxy authenticates them, then `allowed_groups` refuses. The fix is a realm role, not a password reset. The `groups` claim is in the ID token, and oauth2-proxy re-reads it on every `cookie_refresh` (4 min), so granting or removing a role takes effect without a new login.
- **A background job inherits the deploy lock** (fd 9) and holds it after its script has ended, so the next run is refused. Start every `&` job in a locked script with `9>&-` (the kubectl port-forwards do). A run stopped with a plain `kill <pid>` likewise leaves its foreground `helm --wait`/`rollout status` holding it — which is why the refusal message says `kill -- -<pgid>`, and lists any leftover holders by PID.
- **The credentials box can show a password nobody uses any more** — a person may change their own (user menu → Change password) and `_create_kc_user` never overwrites one. The box therefore asks the admin API whether each password is still the one it was created with (`_shown_pass` → `kc_password_status`, comparing the credential's date with the account's) and says "changed by its owner" instead of printing a stale value. It never signs in as the person, so nobody's record gets a login they did not make.
- **OAuthenticator admits `admin_users` whatever `allowed_groups` says**, and with `allow_existing_users` every user already in the hub's database: neither may be set while the workbench's gate is on (`policy_workbench` renders `[]`/false).
- **KubeSpawner's `delete_pvc` defaults to true**: a hub admin's "delete user" deleted the person's home volume until IAM 3.2 set it false.
- **`configure.sh` exits early when nothing required is missing**, so a value that is generated rather than asked (QA_INITIAL_PASS, KC_BREAKGLASS_PASS, GRAFANA_BREAKGLASS_PASS) must be created *before* that exit, or an existing install never gets it.
- **Never pass a secret in argv**: any account on the host can read `/proc/<pid>/cmdline`. The wizard daemon did this with `--client-secret`; secrets now go as `VAR="$VAR" exec …` into one process's environment (config.env exports nothing), which pops them. `infra/lib-keycloak-admin.sh` sends the grant's secret or password to curl on stdin (`--data-urlencode client_secret@-`), the bearer token as a header on a pipe (`-H @<(_kc_bearer …)`) and a request body on stdin (`--data-binary @-`).
- **Node-RED's settings.js is a subPath mount**: a changed ConfigMap reaches the pod only through a restart (the checksum annotation does it); the rights file is a directory mount and needs none. The first deploy onto the new `/data` volume starts with no flows: run `./apps/node-red/deploy.sh` right after `./deploy-infra.sh` (deploy-infra says so when Node-RED runs no flows).
- **`IFS=$'\t' read` merges empty fields** (tab is IFS whitespace), shifting the rest one variable left. A token-protocol field is therefore never empty (`-`).
- **`read -t` keeps partial input when it times out.** The holder writes each reply in one write of at most 4096 bytes, and `token_get` accumulates partial reads.
- **A note on platform_db's stderr breaks its callers**: `board`, `slots` and `register` are read with `2>&1` (an empty `board` means "not registered"). Report-only notes come from the shell.
- **The token goes to platform_db as `3< <(printf …)`, never `3<<<`** (a here-string may be backed by a temporary file), and `exec {fd}>&- 2>/dev/null` would silence the script's stderr for good — a bare `exec`'s redirections are permanent.
- **`pkill -f <pattern>` from a shell whose own command line contains the pattern kills that shell.** Match with a bracket (`pgrep -f '[a]ccess-api.py'`) or kill by PID.
- **A rebuilt server leaves the split DNS route behind.** A new machine gets a new Tailscale IP, but the admin console keeps sending `$DOMAIN` to the old one. The server itself still resolves everything (the `/etc/hosts` block), so only other devices fail. `split_dns_target` (`infra/lib-dns.sh`) reads the route from `tailscale dns status`; deploy-infra warns in the `[DNS]` step and prints the edit at the end. There is no CLI to change it — it is an admin-console setting.
- **No wildcard SAN on a one-label domain.** Browsers reject `*.medcea`, so the certificate lists every `*_DOMAIN` explicitly. When adding a service domain, add it to the `_SVC_DOMAINS` list in `deploy-infra.sh` too: the SANs, the hosts block and the alias redirects all come from it.
- **`[ -r file ]` under `/var/snap/microk8s/` is always false for a normal user**, because those directories are root-only. A skip-check built on it never skips: deploy-infra re-wrote `hosts.toml`, restarted containerd (a cluster-wide blip) and stopped at a bare sudo prompt on every run. Check with `sudo grep`, and give `sudo -p` a prompt that says why the password is wanted (the prompt goes to the tty, not the log).
- **`curl … | sh` hides a missing curl** — `sh` reports success on the empty script it receives. Download to a file, check it is non-empty, then run it, and confirm the result exists (`command -v tailscale`) rather than trusting the exit code.
- **`printf -v` into a name the callee also declares `local`** writes the callee's copy, and the caller's variable stays empty. This made `ask_yn` (which called `ask __ans`) loop forever. Give caller variables names the helper doesn't use.
- **`ask()` must die on EOF, not return empty** — a re-asking prompt loop (`menu_ask`) spins forever when stdin is closed (`< /dev/null`, cron, a detached `timeout`).
- **`ujson.dumps()` will not serialise `bytes`** — `ubinascii.hexlify(machine.unique_id())` returns bytes, and putting it straight into a payload raises rather than publishing. `.decode()` it once, in `config.py`. A `str` there also matches `medcea.device.serial_number` exactly.
- **ESP32-P4 flash pins are package pins, not GPIOs** — the P4 datasheet's flash table (FLASH_CK = 32, FLASH_CS = 27 …) lists *package pin* numbers. Mapping those onto GPIO numbers would wrongly blacklist GPIO27-33. The P4's flash is on dedicated pins and its PSRAM is in-package, so unlike every other ESP32 it loses no GPIO to memory at all.
- **Changing the board in the form does not rewrite the map** — it re-checks the same table against different silicon, and the errors that appear are the point. Silently dropping the pins the new chip lacks would hide exactly what the operator needs to see.
- **The browser prompt loop re-renders on every poll** — `renderPrompt()` returns early when `p.id === curId`, and that guard is what keeps the channel-map editor from being re-mounted (and the operator's half-finished edits thrown away) once a second. Any new rich prompt kind must keep it.
- **An edited channel map is authoritative, not a hint** — when the wizard returns a table, `render()` uses it verbatim (`spec["actuator_config"]`) instead of re-deriving from `functions`. Re-deriving would silently discard the edit the operator was just shown and approved.
- **Keycloak has its own database, `keycloak`**, not `medcea_db`. When they were shared, `apps/database/uninstall.sh --purge-data` (`DROP DATABASE medcea_db`) would have wiped every realm, user and client, and an install from before the split still has unused Keycloak tables in `medcea_db.public`. Never point `KC_DB_URL` back at `$POSTGRES_DB`.
- **Bitnami charts with unset resources fall back to the `nano` preset** (192Mi / 150m limits). Always set `resources` explicitly for a Bitnami release: rdbms and the three oauth2-proxies do.
- **Cookie secrets are generated once and kept** (`${OAUTH2_COOKIE_SECRET:-$(openssl rand …)}`). Regenerating them on every deploy logged everybody out.
- **`schd/` is live production code.** The scheduler pod mounts it by hostPath, so an edit in the main tree changes the runner of the next run (and the wizard runs `edge/` from the tree too). Edit in a `git worktree` and copy in only when `pgrep -af '[r]un_recipe.py'` prints nothing.
- **PGRST300 is HTTP 500, not 401**: a Bearer token sent to a config-api without a jwt-secret (legacy mode) is a server error. That is why the frontend deploy switches nginx and config-api in an order that depends on the direction.
- **A `secretKeyRef` env var is read only at container start.** Rewriting Secret `medcea-jwks` or `db-authenticator` changes nothing in a running config-api; the annotations `medcea/jwks-checksum` (`pgrst_roll_if_changed`) and `medcea/auth-secret-version` (`pgrst_deploy`) restart it. health-check `postgrest` FAILs when either is stale.
- **`ALTER ROLE postgres SET search_path TO medcea, public` breaks Keycloak** — Keycloak connects as `postgres` and has its own tables (e.g. `COMPONENT`) in the `public` schema. If `medcea` is first in the search_path, PostgreSQL finds `medcea.component` (our IoT table) instead, causing `column realm_id does not exist` crash-loops. Set `search_path` on the `authenticator` role (PostgREST) only, never on `postgres`.
- **A unit that is still assigned cannot be deleted** — `iam_policy.user_unit.unit_id` references `medcea.cea_unit` with the default RESTRICT (23503), on purpose: a cascade would drop an operator's assignment without an account decision. Remove it with `apps/iam/units.sh remove <user> <UNIT> --by <your username>` first. A **waiting** assignment has no `user_unit` row and `account_decision.unit_id` no foreign key, so it does not stop the delete; `list` then shows it as `#<id>` and says qa must refuse it (confirm is 22023, and units.sh resolves only existing codes).
- **Moving a zone to another unit moves its telemetry** — `my_zones()` is "every zone of my units" by each zone's *current* unit, not the unit stamped at insert, so an UPDATE of `cea_zone.unit_id` (engineers hold it) hands the zone's whole history to the new unit's operators. It is recorded only in `medcea.row_change`, not as an account decision: a qa_dual_control gap still open after IAM 2.6, deliberately deferred (the Monitor and scheduler filters follow the same current-unit rule); a `cea_zone` move guard is an open question for a later task.
- **`apps/access/uninstall.sh --purge-data` leaves `iam_policy.user_unit` rows without their decisions** — it drops schema `iam` (and with it `account_decision`), while the assignments and their chain events live in `iam_policy`. The units stay in effect, and `--purge-data` warns while `user_unit` has rows; the next `./apps/access/deploy.sh` records each surviving assignment again as a `pending_qa` decision without a maker (`system:deploy (backfill)`), in effect before the check, which qa confirms with the attestation or refuses (removing the unit). Assignments still waiting for qa had no `user_unit` row: they are gone with schema `iam` and must be assigned again.
- **A qa person cannot confirm a change to their own account, and an admin's widening of the only qa account waits for a second qa person.** Every confirmation depends on there being at least one enabled qa person besides the subject; with none at all, set a new `QA_USER` and run `./deploy-infra.sh` (break-glass, outside the decisions).
