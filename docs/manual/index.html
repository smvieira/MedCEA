Platform overview

MedCEA is an open, self-hosted platform for growing medicinal mushrooms and plants in controlled chambers so that the same recipe gives the same result, and so that every step can be shown to an inspector afterwards. This chapter explains what the platform is for, the parts it is built from, how a sensor reading reaches a dashboard and how a recipe ends up switching a relay, the web addresses you use, and the words the rest of this manual relies on.

What MedCEA is

MedCEA stands for Medicinal Controlled Environment Agriculture. It is the prototype built in a Design Science Research PhD project at ISCTE-IUL and Instituto de Telecomunicações, with ESACB (2025 to 2028). The main organism is Hericium erinaceus (lion's mane). The goal of the production is not the largest harvest. It is a reproducible amount of the target bioactive compounds, made in a way a regulator can accept. All custom code is released under the MIT licence.

The project sets the platform four goals, called pillars:

PillarWhat the platform must do
I. Compound-centred controlRun a recipe as a programme of steps, each with its own target ranges for temperature, humidity, CO2 and light, and keep the chamber inside those ranges with a control algorithm, which can be a simple on/off rule or an AI method.
II. Reproducible outcomesFollow the recipe and know the genetic origin of each lot, so that differences between batches can be traced to the environment rather than to chance.
III. Compliance by designBuild the rules of GACP, EU GMP Annex 11, the Novel Food regulation and THMPD into the data model, the access control and the event records, rather than produce them afterwards as reports.
IV. Traceability and auditRecord every event in a lot's life in an audit trail that can be added to but not edited, with access split by role (operator, quality, administrator, auditor).

This is a prototype. Recipe execution, control algorithms, sign-in with eleven roles, changes stamped with the person who made them, approvals recorded in the database and a hash-chained history of access policy changes are built. Batch and lot records, laboratory results, the Electronic Batch Record, GS1 EPCIS event export and a regulator interface are not built yet. Where a later chapter describes a duty that has no screen yet, it says so.

Building blocks

Everything runs on one Ubuntu computer (the host) with MicroK8s, a small Kubernetes. Two scripts install it: ./deploy-infra.sh for the infrastructure and ./deploy-apps.sh for the applications. The administrator runs them on the host; everyone else works in a web browser. See Administration.

Edge boards

The chambers are equipped with ESP32 boards running MicroPython. Each board is onboarded with one of two roles and runs the application for that role:

  • SENSE reads the sensors fitted to it and publishes the readings. The supported sensors are a Sensirion SCD40/SCD41 or SCD30 (CO2, air temperature and air humidity), a DS18B20 substrate temperature probe and an analogue water level probe.
  • CONTROL drives a relay board: grow lights (red, blue, UV), air heater pad, air cooler, humidifier, air flow fan, CO2 fan, CO2 flow steriliser, substrate heater. Which relay drives which equipment is set in the board's channel map during onboarding. It reports back what it actually switched.

Onboarding, replacing and calibrating boards is covered in Devices.

Units, zones and slots

The physical layout is stored as three levels:

  1. A location is a site or room.
  2. A production unit is a chamber in a location, identified by a unit code such as UNIT01.
  3. A zone is a controlled area inside a unit, identified by a zone code such as ZONE01.

Each zone has exactly two slots: one for a SENSE board and one for a CONTROL board. A board's name comes from its slot: the unit code, s or c, and the zone code, in lower case, for example unit01-s-zone01. That name is its network hostname, its MQTT user name and the hostname shown in the Config UI. A board that is not registered yet is called cea-un- followed by the last six characters of its MAC address.

All MQTT traffic for a zone sits under one topic base, medcea/<UNIT>/<ZONE>:

TopicWho publishesWho listensContent
medcea/<UNIT>/<ZONE>/sense/<tag>SENSE boardNode-RED, the run in progressA reading, for example tag co2, air_temperature or air_humidity
medcea/<UNIT>/<ZONE>/control/<tag>The run in progress (Scheduler); an engineer during commissioningCONTROL boardA command for the equipment that affects that reading, or light for the grow lights
medcea/<UNIT>/<ZONE>/control_setpoint/<tag>CONTROL boardNode-REDWhat the board actually switched

The broker enforces this: a SENSE board may only publish to its own sense topics, and a CONTROL board may only read its own control topics and publish to its own control_setpoint topics. Setting a device's Status to Inactive in the Config UI locks it out of the broker within about 15 seconds.

How data flows

From a sensor to a dashboard

  1. The SENSE board in a zone reads its sensors and publishes each value on medcea/<UNIT>/<ZONE>/sense/<tag>, with a timestamp and the board's name.
  2. Mosquitto checks the board's credential and topic, then passes the message on.
  3. Node-RED receives every message under medcea/ and stores it in the database table of measurements.
  4. Grafana dashboards and the Run Monitor read the measurements from the database and show them.

From a recipe to a relay

  1. An engineer writes a recipe in the Config UI: a sequence of steps, each with a number of cycles, light ON and light OFF minutes, a light type (UV, BLUE, RED or DARK), and lower and upper limits for air temperature, humidity, CO2 and (optionally) substrate temperature.
  2. The recipe is allowed on a unit in the Recipe ↔ Unit Permissions panel of the Config UI's Units tab, with a control algorithm and its parameters.
  3. In the Scheduler someone starts a run (Run Now) or creates a schedule that starts it later. The run is recorded with the person who started it, or, for a schedule, the person who created the schedule.
  4. The run goes through the steps in order and repeats each step for its number of cycles. During a cycle it listens to the sense topics of the unit. At present a run follows one zone per unit.
  5. For each reading the control algorithm compares the value with the step's limits and decides UP, DOWN or OFF, and the run publishes that on the matching control topic. Once per pass it also publishes ON or OFF for the grow lights on control/light: ON during the light ON minutes of the cycle, OFF after.
  6. The CONTROL board looks the command up in its channel map and switches the relay of the right equipment, for example the heater for UP on air temperature.
  7. The board publishes what it did on control_setpoint. Node-RED stores that too, so the record shows not only the command but that it reached the hardware.
  8. When the last cycle ends, the run is marked Completed. A stopped or crashed run is marked Failed.

Web addresses

Every application has its own host name under one base domain, and every one is served over HTTPS with a certificate signed by the platform's own certificate authority. Each computer or phone that opens the platform must trust that authority once, or the browser shows "Not secure".

The administrator chooses the base domain at install time:

  • Name-based (medcea): addresses such as https://portal.medcea. The host answers name lookups for the medcea names, and Tailscale split DNS sends every device on the tailnet to it. This needs one setting in the Tailscale admin console, once per tailnet.
  • IP-based (the default): addresses such as https://portal.100.94.119.12.nip.io, which need no DNS setup.
  • A domain in your own DNS.

When the platform moves from the IP-based to the name-based domain, the old addresses (the alias) stay as permanent redirects, so bookmarks keep working. The first time you open a name-based address, type the https://: browsers treat a one-word ending as a search until they have visited it.

Getting access and roles

Every person signs in to MedCEA with one personal account, and every account holds exactly one platform role. You ask for an account on the sign-in page. An administrator reviews the request, and a different person holding qa confirms it before the account can be used. Your role decides which web apps you can open and what you may do in them. This chapter covers how to request access, what each of the eleven roles is for, how to sign in and out, how to manage your profile and password, what happens when your role changes or your account is deactivated, and what to do when a page says you have no access.

Requesting access

The platform has one sign-in page, served by Keycloak in the MedCEA look. It has two tabs: Sign in and Request access. Below the sign-in form there is also a link, "No account yet? Request access". Opening https://access.<domain>/register brings you to the same tab.

  1. Open the sign-in page and choose the Request access tab.
  2. Fill in every field and choose the role you need.
  3. Choose Submit request. The page answers "Request received. You will get an e-mail once an administrator has reviewed it."
  4. Wait for the e-mail. Until then, signing in shows "This account is not active".

The form refuses a request when another request for the same e-mail address is already waiting, or when the username or e-mail address already has an account. One network address can send at most 10 valid requests per hour.

What happens to your request

Submitting creates your account at once, but disabled. It stays disabled until two different people have acted on it:

  1. An administrator opens the request in the User Manager under Requests, and either approves it with a role (the one you asked for or a different one) or rejects it with a note explaining why. The administrator also writes the e-mail you will receive, starting from a prepared text, or unticks Send e-mail to (followed by your address) so that none is sent.
  2. An approval does not enable the account. It becomes an account decision that waits under Decisions until a person holding qa confirms or refuses it. That person must not be the administrator who approved it, and must not be you.
  3. When qa confirms, the account is enabled with the granted role and the e-mail the administrator wrote is sent. If the granted role differs from the one you asked for, the prepared text the administrator starts from says the role was reassigned.

A rejection, or a qa refusal of the approval, deletes the disabled account. You may apply again.

E-mails depend on the platform's mail account, which an administrator sets up in the User Manager under E-mail settings. Without it, the decision is still recorded but no e-mail goes out, so ask an administrator directly.

Your request is stored with every field except the password, which only Keycloak keeps. Each step (submitted, approved, reassigned, rejected) is added to the request's history, with who decided and when. The approval and the qa confirmation are kept as one account decision that names the maker, the checker, both times and any notes, and the e-mail text the administrator wrote is stored with the request.

One platform role per account

An account holds exactly one platform role. To do work that needs another role, ask an administrator to change your role; you do not get a second one. When a role changes, the new role is added before the old one is removed, so a failure in between leaves the account with two roles for a moment, never with none.

Two rules protect the separation between administration and approval:

  • No person may hold an admin account and a qa account at the same time. The User Manager checks this against all of a person's accounts, enabled or not, when a role is changed and again when the change is confirmed.
  • The User Manager refuses to take away the last enabled admin or the last enabled qa.

Operators and their units

An operator works only in the units assigned to them: they see the telemetry, runs and run logs of those units and start or stop runs only there. With no unit assigned they see none of this. The administrator assigns units on the platform host with apps/iam/units.sh, not in the User Manager. Each assignment waits until a qa person other than the administrator confirms it in the User Manager under Decisions; a removal takes effect at once. A production_manager is not limited to assigned units. The Administration chapter describes how assignments are made.

Signing in and out

  1. Open any platform address, for example the service portal. If you are not signed in, you are sent to the sign-in page.
  2. On the Sign in tab, enter your Username or e-mail and your Password. Show displays the password as you type it.

Report-only and enforcing

The Scheduler, the Run Monitor and the Configuration UI's file libraries check every request against the access policy. The switch IAM_ENFORCE in config.env decides what a failed check does:

Database Management and the User Manager always enforce, whatever the switch says. Recipes and steps

A recipe is the growth programme for a crop: a sequence of steps, each with a number of cycles, a light type, the minutes the light is on and off, and lower and upper limits for:

  • air temperature
  • CO2
  • humidity
  • substrate temperature
  1. Open the Recipes tab and click + New Recipe. Enter a Name and click Save.
  2. Click Steps → on the recipe's row.
  3. Click + Add Step. Fill in Step #, Step Name, Cycles, the light settings and the limits, then click Save Step.
  4. Repeat for every step, then click ← Back.

Other actions on a recipe:

  • ⎘ Copy makes a new recipe with the same steps.
  • ↓ Export downloads the recipe as a file.
  • ↑ Import reads a recipe from your computer or from the Platform Recipe Library.

Saving a recipe to the Platform Recipe Library is refused for every role once the services enforce, because the library cannot check the rules that limit who may change a recipe (drafts only for engineers, assignments only for production managers). Downloading a recipe, and the recipes in the database, are not affected.

No role may delete configuration records once the database enforces roles (IAM_DB_ROLES=true), so the Delete buttons are refused. To take a recipe, unit, location or device out of use, set its Status to Inactive.

Assigning recipes to units

The Recipe ↔ Unit Permissions panel on the Units tab is a grid of recipes against units. A tick means the recipe may run on that unit, and a circle means it may not. Under the tick is the algorithm chosen for that pairing. Inactive recipes are faded and inactive units struck through; their cells show a dash and cannot be clicked. This is the production_manager's planning task.

  1. Open the Units tab and scroll to Recipe ↔ Unit Permissions.
  2. Click the circle where the recipe's row meets the unit's column. The cell turns into a tick and Permission Settings opens.
  3. Pick a Default Algorithm (left empty, the system default IF_THEN_ELSE is used), optionally enter Parameter Overrides (JSON), and click Save. To change these later, click the tick.
  4. To withdraw the assignment, click the tick and then Revoke Permission.

Once the database enforces roles, the recipe must be approved before it can be assigned. A run then takes its algorithm and parameters from an approved parameter set: the schedule's, or else the assignment's. The parameter overrides typed here are not used. This release has no screen that creates a parameter set or attaches one to an assignment; the Scheduler lists the sets that exist.

Control Models and learned state

The Control Models tab has two panels.

  • Control Algorithms lists each algorithm with its code, name, description and Default Params (JSON). An algorithm that is not approved shows its status (for example draft) under its code. An engineer may edit the defaults of a draft and click Save.
  • Production Units lists, for each unit, how many recipes are allowed on it and the learned state each learning controller keeps for it. Click the record count to see the state per channel and when it was last updated.

Drafts, approval and the author rule

Recipes (with their steps), control algorithms and parameter sets have a status: draft, approved or retired.

  • A new definition starts as a draft.
  • A qa person approves it. The approval is refused when the approver changed the definition since its last approval. It is also refused when any change since then has no recorded person; such a definition has to be re-created before it can be approved.
  • An approved definition is frozen. While IAM_DB_ROLES is false, editing an approved definition is allowed but turns it back into a draft, and the app shows that as an advisory. While it is true, the edit is refused. Make a copy with ⎘ Copy and have the copy approved instead.
  • A parameter set can only be approved once its algorithm is approved.

While the database enforces roles, only approved recipes may be assigned to units, and a run uses only approved algorithms and parameter sets.

The apps have no approval screen yet. The approval itself is a database function (approve_recipe, approve_algorithm, approve_params) that only a signed-in person holding qa can call. See the compliance chapter for how approvals are checked.

Every change to these definitions records who made it, with which role, and when; it is also kept in the append-only row-change log. Each approval is a row naming the approver, the authors since the last approval and a digest of the approved row.

Retiring a Q-table

A learning controller, such as Q-learning, keeps what it learnt in a Q-table between runs. Starting a unit afresh means retiring that table. Only qa may do it, and nothing is deleted: the next run on that unit starts cold.

  1. Open the Control Models tab and find the unit in Production Units.
  2. On the row of the algorithm whose state you want to retire, click Retire….
  3. Enter the reason. A reason is required and is recorded.
  4. Confirm. The message names the unit and the number of channels retired.

Retiring needs the database to verify your sign-in, which it does only while IAM_POSTGREST_JWT and IAM_DB_ROLES are both true. Without them, nobody can retire a Q-table. Any other role gets the message that retiring learned state needs a qa person signed in.

For each channel retired, the controller-state event log gets a retired event with the unit, the algorithm, the retired state, the reason and the qa person, and the approval record gets a row naming that person. Neither record can be changed afterwards.

Run logs

Click 📋 Log on a current run, or View Log on a completed one, to open the run's log. For a running run, the log follows new lines as they are written.

A role that does not hold read access on run logs sees the run but not its log: the window shows "(your role does not hold R on run logs)", where R means read. This applies to maintenance, qc and qp while IAM_ENFORCE is true. While it is false, the log is shown and the service records a "would withhold" line.

Log Management: compression, never deletion

No person compresses or deletes a run log. The scheduler's own nightly job runs every day at 03:15 UTC. It compresses (gzips) the log of each run that has finished, Completed or Failed, once the log is older than the Compress run logs after setting. It never touches the log of a run that is queued or running, and it never deletes a log. A compressed log still opens from View Log.

The Log Management section shows:

  • the number of run log files, their total size and the oldest one;
  • when the job last ran and how many files it compressed or kept;
  • the smallest values allowed: 1 day for compression and 30 days for the retention value.

Retention setting (not applied) is kept as a value but nothing reads it, because run logs are never deleted.

  1. As admin, change Compress run logs after (in days) and click Propose retention.
  2. While the database enforces roles, the message says the value is proposed and "pending qa approval". The new value applies only after a qa person other than you approves it. There is no approval screen for this in the Scheduler yet. While the database does not enforce roles, the value is saved at once and the message reads "Defaults saved".

A proposed setting is stored as a pending change with its author. The approval records the qa person who confirmed it.

Database Management

Database Management exports database objects as an SQL file, for evidence, for an inspection or for a copy kept outside the platform. Only qa, qp and auditor can open it. It always enforces the policy, whatever IAM_ENFORCE says, because an export takes data out of the platform.

The page lists only the objects in the export groups your role holds, and states them in a line that begins "You may export:".

  • qa and auditor may export master data, devices, device history, recipes, controllers, controller state, runs, schedules, scheduler settings, telemetry and the audit histories.
  • qp may export runs, telemetry and the audit histories.

The page offers only the platform's own data tables and views. The account records, unit assignments and access policy that belong to the same groups are not offered here, and the audit histories offered are the platform's approvals, pending changes and row-change log. Sequences and types hold no rows and are offered as definitions to everyone who can open the page.

  1. In DDL & Data Export, tick DDL (the table definition) and/or Data (the rows) for each object you need. All DDL, All Data and Clear set or clear every box. For views, sequences and types the Data box is disabled; only their definition is exported.
  2. Keep or change the File Name.
  3. Under Save To, choose one destination:
    • Download locally puts the file on your computer.
    • Save to platform (apps/database/exports/) writes it on the platform host. It refuses a name that already exists there.
  4. Click ↓ Export SQL. The result line shows the file name, its size, the export number and the start of its sha256 checksum.

  • the export number
  • when it was generated, in UTC
  • who exported it, and with which role
  • the groups it covers

The row is written before the file is handed over, and nobody can change or delete it afterwards. The full sha256 of the file is written to the Database Management service log; keep the checksum with the file, so you can show later that the file is the one exported.

MQTT Explorer

MQTT Explorer is a browser tool that shows the messages the boards and the platform exchange on the message broker. Only engineer can open it. It is meant for commissioning and fault finding.

  • The left column lists every topic under the platform's topic root (medcea/ by default) that you may read, seen since the page opened, with its last value.
  • Click a topic to see its latest messages; the page keeps the last 100 for each topic.
  • The status at the top reads Connected, Reconnecting, Waiting for the broker to accept your credential, or an error.

How the page connects depends on the switch IAM_MQTT_PERSON (see IAM switches).

With your own credential (IAM_MQTT_PERSON=true). When the page opens it asks the platform for a broker credential that is yours alone, made from your role, and connects with it. You see nothing of this: no password is shown or stored in the browser.

  • The first connection can take up to 15 seconds: the broker picks up a new credential at its next check.
  • The credential lasts 8 hours and is renewed in the background before it ends. Signing out of the platform does not end it at once; deactivating your account or changing your role ends it within about 15 seconds.
  • The Your rights note under the Publish box lists what you may read and where you may send. An engineer reads every unit's sense, control and control_setpoint topics, and may send only to a unit's control topics while that unit is flagged for commissioning and has no run in progress. The broker checks this every 15 seconds: when the flag is cleared or a run starts, sending to that unit stops.
  • No screen can flag a unit for commissioning yet, so in practice the page only reads. Send stays disabled while you have nowhere to send.
  • A message the broker does not allow is dropped silently: the page shows no error, and nobody receives it.
  • If the page says your role has no MQTT rights, or that your access changed since you signed in, reload it after your administrator has sorted out your role.

With the shared account (IAM_MQTT_PERSON=false). The page connects with one shared service account that may read and write every topic under the platform root.

To send a message:

  1. Click a topic, or type one in the Publish box.
  2. Enter the payload, as text or JSON.
  3. Click Send.

With the shared account, a message published to a control topic switches equipment in a live chamber, whatever the unit's state. Publish to control topics only on a unit with no active run. With your own credential the broker refuses it, but a unit flagged for commissioning is still real equipment.

Saving your notebooks to git

Your home folder is kept when your workspace stops, when the administrator removes you from the hub and when your role loses the workbench, but nothing backs it up, and uninstalling the platform deletes it. Keep work that matters in the research repository on GitHub that the administrator set up (WORKBENCH_NOTEBOOK_REPO; a terminal in your workspace prints it with echo "$MEDCEA_NOTEBOOK_REPO"). SAVE_TO_GIT.md has the details.

  1. Once: set your name and e-mail for commits (git config --global user.name and user.email), create a fine-grained personal access token on GitHub for that repository only (Contents: Read and write, with an expiry date), and clone the repository into your home folder from a terminal.   2. Save your notebooks inside the cloned folder.
  3. In the Git panel on the left: stage the changed files (+), write a message, Commit, then Push. Pull brings in your colleagues' work.

Edge devices

The boards in the growing chambers are ESP32 microcontrollers. A SENSE board reads the chamber and publishes measurements. A CONTROL board receives the scheduler's commands and switches equipment through relays. Each board fills one slot: one unit, one zone, one role. A board joins the fleet through onboarding. Someone plugs it into the platform host over USB, signs in, picks a free slot and says what is wired to it. The onboarding run then erases and flashes the board, joins it to WiFi, gives it its own broker credential and registers it in that slot. This chapter covers who may do that, the steps of a run in the browser and in a terminal, how to replace or move a board, how board credentials work, and what the platform records.

SENSE and CONTROL boards

Every board runs the same application. What makes it a SENSE or a CONTROL board is a small configuration file that onboarding writes onto it. That file holds the role, the slot, the broker credential and, for a SENSE board, its sensors and their pins. A CONTROL board also gets a pin map file with the relay channels chosen during the run.

Slots

A unit is a physical chamber and a zone is one area inside it. Both are created in the Units tab of the Configuration UI before any board is onboarded. The onboarding wizard reads units and zones from the database and never creates them.

Each active zone has exactly two slots, one per role:

UNIT01 / ZONE01  ->  unit01-s-zone01   SENSE: reads the chamber
                     unit01-c-zone01   CONTROL: drives the chamber
  • A slot is free when no active device of that role is in the zone. Only free slots are offered.
  • A slot is taken when an active device of that role is in it. The wizard lists taken slots with their board, but you cannot pick them.
  • A slot is not offered when its unit and zone codes cannot make a legal board name. The wizard says why. See Device names.
  • Slots in an inactive unit or an inactive zone are left out.

This rule is read from the live device table on every run. To free a slot, mark its device Inactive in the Devices tab. Onboarding a board into a slot that already has a device record updates that record in place. It never creates a second one.

The one-SENSE, one-CONTROL rule also limits harm. A board can publish only under its own slot's topics, and a second board cannot quietly start driving a chamber that already has a controller.

Device names

A board has one name, built from its slot:

lower(unit code) - s|c - lower(zone code)

UNIT02 + CONTROL + ZONE02  ->  unit02-c-zone02

The same name is the board's DHCP hostname, its Hostname (DHCP) in the Devices tab, the device_dns field in every MQTT message, its broker user name, and the file name of its provisioning record. Lowercasing is the only change made to the codes, so the name stays readable and is the same every time the slot is onboarded. Unit codes are unique ignoring case, and zone codes are unique within their unit ignoring case, so two slots can never get the same name.

The codes must produce a legal hostname:

  • letters, digits and hyphens only, with no hyphen at the start or the end;
  • at most 32 characters, the longest hostname a MicroPython board accepts.

A slot whose codes break either rule is listed as not offered, with the reason, for example a code containing an underscore or a space. There is no fallback name. To use the slot, rename the unit or zone code in the Units tab. After the board boots, the run reads the hostname back from the board and warns if the board kept a different one.

A board onboarded with --unregistered is named cea-un-<mac6>, where <mac6> is the last six hex digits of its MAC address. The un shows at a glance that it has no slot.

The board does not answer .local names: it runs no mDNS responder. Use the IP address printed at the end of the run and kept in the provisioning record. A DHCP reservation on the router keeps that address stable.

The steps of a run

The questions that only the person at the chamber can answer (role, slot, wiring) come first, before the board is touched, so a board is not left half onboarded because someone walked away. Two questions come later: the go-ahead to erase, and the WiFi network, which the board can only scan once it runs MicroPython. The browser page and the terminal ask the same questions in the same order.

  1. Sign in. In the browser you are already signed in. In a terminal, enter the device code. A run that is not registering a board (--unregistered) skips this.
  2. Role. "What is this board for?" Pick SENSE or CONTROL.
  3. Slot. "Which unit and zone is this board going into?" Only free slots of that role are listed, each with the name it will give the board. If there is exactly one, it is chosen for you. If none is free, the run stops and says to mark the existing device Inactive or add a zone.
  4. What is wired. For a SENSE board, "Which sensor is wired to this board?", one sensor at a time, then each sensor's pins, for example the 1-Wire data pin of a DS18B20. Pick Done when every sensor is listed. For a CONTROL board, the run shows the reference wiring, equipment against GPIO pin, and asks "Use this reference wiring?". Answer no to set the pins yourself or to remove equipment the chamber does not have. See The channel-map editor.
  5. Interval. For a SENSE board, the publish interval in seconds (30 by default). A CONTROL board's command poll interval (100 ms) is asked only with --advanced. The run then prints what it inferred without asking: broker address and port, topics and the board's name.
  6. Serial port. Detected automatically. If the account cannot open the port, the run says so and points at the dialout fix.
  7. Board check. The run reads the chip type and MAC address from the board. Two checks happen here, before anything is erased:
    • If this board is already registered in another slot, the run asks the move question. See Moving a board.
    • If the pin map was checked against a different chip than the one plugged in, the run checks it again against the real chip. If the map cannot drive that chip, the run stops and tells you which board type to pick.
  8. Firmware. The newest local image for this chip is the default. Images from micropython.org are offered for download. Only images that match the detected chip are listed.
  9. Erase and flash. "Erase and flash this board?" Yes wipes the whole chip, then writes MicroPython.
  10. WiFi. The board scans the air with its own radio. Pick a network, or enter a hidden one by name, then type the passphrase. A network missing from the list is usually 5 GHz only: these boards hear only 2.4 GHz.
  11. Files. The run generates a WebREPL password for this board only, writes the board's configuration file, its pin map (CONTROL) and the application, then restarts the board and waits for it to report an IP address.
  12. Registration. If the board came online, the run writes its device record, one component record per sensor (or one for the relay board), and the hash of its broker password. If the board never reported an IP address, it is not registered and the slot stays free.
  13. Record and summary. The run writes edge/provisioned/<name>.json and prints the summary.

If a registration is refused, the board is still flashed and running. Fix the cause and onboard the same slot again. The slot's record is updated in place.

The board in download mode: most boards reset themselves for flashing. If the run cannot talk to the board, hold BOOT, tap RESET, release BOOT, and try again.

The channel-map editor and the board check

When you answer no to the reference wiring in the browser, the page shows the channel map itself: a table of relay channels, every command the scheduler can send, and the pin map file being built as you type.

  • Board selector. It defaults to esp32s3, what this fleet runs. ESP32, S2, S3, C3, C6, H2 and P4 are offered. Changing it checks the map you have against that chip, without rewriting it.
  • Pin reference. Opens the table of every GPIO on the selected chip and what else already uses it.
  • Each row shows its pin's type as you type the number. Pins that cannot work (input-only pins, pins used by the SPI flash) are errors. Strapping, PSRAM, USB-JTAG and console pins are warnings.
  • Missing equipment. Clear the equipment the chamber does not have. Every command that needed it is then left out of the board's table, rather than shipped as a command that does nothing and still reports success.
  • Reset to reference wiring puts the reference layout back.

The page refuses to submit a map with errors. The run checks the map again when it gets it, and a third time against the real chip after probing, before the erase. In a terminal the same step asks for one GPIO per piece of equipment. Answer blank or - for equipment the chamber does not have.

The same editor exists as a standalone page for inspecting or correcting a map away from the platform:

./edge/tools/build-editor.sh        # writes edge/tools/actuator-config-editor.html
python3 edge/src/host/device_template.py pins CONTROL esp32c3   # the pin table in a terminal

Replacing a board

Use this when a board fails and a new board takes its place in the same slot. maintenance and engineer may do it.

  1. In the Devices tab, press Edit on the old board, set Status to Inactive and save. The slot becomes free, and within about 15 seconds the broker refuses the old board.
  2. Plug the new board into the platform host and start onboarding.
  3. Pick the same role and the now free slot. Wire it, flash it and let it register as usual.

The registration updates the slot's existing record in place. The record keeps its id, gets the new board's serial number, becomes Active again, and its components are replaced with the ones just chosen. The board gets the same name as before and a new broker password.

To re-flash the same board in its own slot (a firmware update, new pins), onboard it again without deactivating it. The run sees that the board is already in this slot and updates its record in place. The broker password changes.

Replacement is recorded in the slot history as replaced, with the old and the new serial number and the person who did it. Changing the serial number also deactivates the old board's broker credential.

Moving a board

A board's record follows the board, because its serial number (the MAC address) is unique. To move a board to another slot, start onboarding with the board plugged in and pick the new slot. When the run reads the board's MAC address, it finds the existing record and asks:

this board is already registered as unit01-s-zone01 - UNIT01 / ZONE01 (SENSE).
Move this board from unit01-s-zone01 to UNIT01 / ZONE02?
  • Yes moves the record to the new slot. The board takes the new slot's name, its components are replaced, and the old slot becomes free. If the new slot holds an older inactive record with the same name, that record is renamed <name>-<id> and kept inactive.
  • No stops the run before anything is erased or written.

The question comes after the board is probed and before the erase, because that is the first moment both the board and the target slot are known. A run started with -y never moves a board: it stops and asks you to onboard interactively.

maintenance may move a board only into a slot that already has an inactive record. Moving a board into a slot that never had one is an engineer's change.

A move is recorded in the slot history as moved, with the old and new zone, role and name.

MQTT credentials per board

The broker admits nobody anonymously. Each registered board has its own credential:

  • User name: the board's name, for example unit02-c-zone02.
  • Password: a fresh random password minted at every onboarding, so re-flashing a board changes it. The password goes onto the board and into its provisioning record. The platform database stores only its hash.
  • Access by role. The broker lets a SENSE board publish only under its own slot's sense/ topics. It lets a CONTROL board receive only its own slot's control/ topics and publish only its own control_setpoint/ topics.

A sidecar next to the broker rebuilds the broker's password and access files from the database every 15 seconds. Two things follow from that:

  • Deactivation revokes within about 15 seconds. When a device is marked Inactive, or its record is deleted, its credential drops out at the next rebuild. The broker then refuses its next connection and denies its publishes.
  • The first connections of a new board may be refused. The board boots before it is registered. Until the registration lands and the next rebuild picks it up, which takes up to about 15 seconds, the broker refuses the board. The board restarts after 10 seconds and tries again, so this clears by itself.

A board that is not registered (the run was refused, the board had no IP, or --no-register) has a password that the broker does not know, so it cannot publish. Onboard it again once the cause is fixed.

Boards flashed before broker authentication existed have no credential. Re-onboard them.

Boards and the platform's services connect on the broker's LAN port (31883 on the server; 1883 inside the cluster). With IAM_MQTT_PERSON=true that port accepts no person's credential: the MQTT Explorer's personal credentials work only on the broker's WebSocket listener, behind the Explorer's sign-in (see MQTT Explorer). The shared mqtt-explorer account, which the onboarding summary suggests for watching a board from the command line, is refused there too; watch the board in the MQTT Explorer instead.

The WiFi passphrase and the MQTT password sit in plain text on the board's flash. Anyone holding the board can read them. WebREPL also stays on after onboarding: anyone who reaches port 8266 with the board's WebREPL password gets a full Python prompt and the board's files. Treat a lost board as a lost credential and mark it Inactive.

Adding a sensor type

The wizard's questions are data, not code. The SENSE questions come from edge/templates/esp32-sense.json and the CONTROL questions from edge/templates/esp32-control.json. Bench mode

./edge/flash-device.sh --unregistered

This brings a board up on WiFi with no platform identity, for a bench with no platform deployed. It asks no slot, ships no application, writes nothing to the database and needs no sign-in. Access control and records

This chapter is for quality staff (qa, qc, qp), auditors and thesis examiners. It describes the one access policy that says who may do what, the layers that enforce it, the decisions that need a second person, and the records the platform keeps of every change. It ends with the known gaps and the decisions taken for IAM 2.6. It describes IAM 2.6 (commit a9639b7 on branch iam/phase-2). The current value of each switch is shown by ./health-check.sh and in each access review.

The access policy: one source

Every access right on the platform comes from one file, apps/iam/policy/defaults.yaml. A compiler reads it and produces the database grants, the sign-in gate of each web host, the route table every service checks and the network policies. Grafana, the AI workbench, the device onboarding wizard and pgAdmin sign people in themselves; their own sign-in settings are compiled from it too. The compiler refuses to compile a policy that breaks one of its invariants.

The policy is a matrix. Rows are resource groups: a set of tables, API routes, web pages and MQTT topics that belong together, such as "Recipes and recipe-to-unit assignment" or "Telemetry". Columns are the eleven platform roles. A cell lists the access levels a role holds on a group. A role not listed in a row holds nothing there. Every account has exactly one platform role.

Data classes

Each resource group has one class, and the invariants are written against the classes.

  • Personal data: accounts, names, e-mail addresses, unit assignments and access decisions.
  • Configuration: master data, recipes, controllers, schedules, settings, dashboards and tools, changed under the group's approval rule.

How the policy is enforced, in layers

No single check is trusted alone. A request passes five layers, each compiled from the same policy; a message to the broker passes its own, listed last.

  1. Sign-in gate per host. Every web UI signs in through Keycloak. Each gated host admits only the roles that hold some level on a group served there. A signed-in person without such a role sees a "No access" page naming the roles that may open it. For example the policy admits auditor, qa and qp to Database Management, and admin, qa, qp and auditor to the User Manager. python3 apps/iam/compiler/cli.py hosts lists who each host admits. Grafana signs people in itself; its own role setting is compiled from the same policy: engineer is Editor, the other roles holding Read on dashboards are Viewer, and every other role is refused. Grafana Admin is never given through the sign-in. Node-RED's editor signs people in a second time and gives the rights compiled from the policy: engineer may change and deploy flows but not install palette modules, and no other role has any right in it. The AI workbench (JupyterHub) likewise admits exactly the roles the policy admits to its host (admin, bio_scientist, control_scientist, engineer, qa); admin, the only role holding Configure there, is hub administrator without the right to open anyone's workspace (through the hub role workbench-admin; until the fix of 31 October 2026 the platform did not meet this, see the known gaps), and removing a person from the hub keeps their home folder. The device onboarding wizard admits only engineer and maintenance, the roles that may register boards, and checks again at every renewal of the sign-in during a run, so a board is not erased for someone who lost the role. pgAdmin admits only admin, checked at sign-in.
  2. Verified token in every service. The six Python services (scheduler, Monitor, Database Management, the Config UI's platform API, the User Manager and, since IAM 3.5, iam-api, which issues the MQTT Explorer's credentials) check every request against the compiled route table. They trust only a signed access token verified against Keycloak's public keys, never identity headers that anything inside the cluster could send. Each route belongs to one group and needs one level; a route missing from the table is refused.
  3. Network policies. Each of the eight application services (scheduler, Monitor, Database Management, the Config UI, its database API, the User Manager, Node-RED and iam-api, which only the MQTT Explorer's sign-in proxy reaches) accepts connections only from its listed callers, so another program in the cluster or a forged request cannot reach it at all. Since IAM 3.2b the database API (config-api) also accepts the AI workbench's notebooks, which reach nothing else of the platform but Keycloak, and only while IAM_POSTGREST_JWT and IAM_DB_ROLES are true: each request carries the person's own sign-in, and the database applies that person's role and row rules. Both sides of that opening are compiled from the access policy. The portal, MQTT Explorer's page, the message broker, Grafana and the workbench's own hub are not covered.
  4. Database roles and row-level security. While IAM_DB_ROLES is true, a person's requests through the Config UI's database API run as that person's own database role. Each service logs in as its own role. Row-level security (a filter the database applies to every query) limits an operator to the telemetry and runs of their units. Triggers refuse edits to approved definitions and to append-only records. This layer holds even if an application has a bug.
  5. Approvals in the database. Approval functions check the approver's role and that the approver is not an author, using the person from the verified token. A service cannot approve on its own.
  6. Message broker. Every broker client authenticates. Boards and the platform's services use the LAN port; with IAM_MQTT_PERSON=true people use only their own short-lived credential from the MQTT Explorer, accepted only on the WebSocket listener, carrying the topics their role's cells give. A send right exists only for a unit flagged for commissioning without a running run, and the broker's credential sync re-derives it every 15 seconds from the database.

Some constraints are checked only in one layer. assigned_run is checked only by the database's run functions, and own_unit by row-level security and by the Monitor and scheduler reads themselves.

Report-only and enforce

The services can run in two modes, set by IAM_ENFORCE in config.env.

  • Report-only (IAM_ENFORCE=false, the state in which IAM 2.6 was deployed): a request the route table refuses is let through, and the service writes medcea_iam: would refuse … to its log. In the same way the scheduler logs run_logs: would withhold when it shows a run's log to a role that will not see it under enforcement.
  • Enforce (IAM_ENFORCE=true): the service answers 401 (no token or a bad one), 403 (route or role not allowed) or 503 (the service cannot check, for example the route table or keys are missing).

The services enforce since 31 October 2026, 09:54 UTC (IAM_ENFORCE=true; the policy history holds the enforcement_enabled event). Two places always enforce, whatever IAM_ENFORCE says: Database Management (exports) and the User Manager's administration port. The database layer has its own switch, IAM_DB_ROLES, which has been true since 30 October 2026, and the operator unit filter in the Monitor and scheduler applies whenever either switch is true. Only while both are false do those two services log own_unit: would limit … instead of filtering.

The administrator turns enforcement on with ./guide.sh: area "IAM switches (enable / roll back)", the IAM_ENFORCE action, then enable. The guide first lists its preconditions as a checklist the administrator confirms: IAM_DB_ROLES is true, the report-only trial is over, and every operator has a unit in effect. It then takes the deploy lock, runs python3 tests/iam-routes-diff.py --strict, sets the switch in config.env and runs ./deploy-infra.sh, stopping at the first failure. Services read the new value within about a minute without a restart. Rollback sets it back to false and runs ./deploy-infra.sh again.

Every transition of IAM_ENFORCE or IAM_DB_ROLES appends an enforcement_enabled or enforcement_disabled event, naming the switch, to the tamper-evident policy history. ./health-check.sh (check iamenforce) fails when the value the services read differs from config.env, when IAM_ENFORCE is true while IAM_DB_ROLES is false, or when a service's own fallback copy is still false under true. It warns while IAM_ENFORCE is false.

Dual control: the maker is never the checker

Every approval needs two different persons. The platform compares the person_id carried in each verified token, not account names, so one person with two accounts is still one person. person_id is set to the account's own id when it is first enabled; changing it is itself a decision that waits for qa.

An approval function refuses when the approver is the author, submitter, creator or executor of the record, or, for an account decision, its subject; and when the change would widen the approver's own role. For account decisions the accounts are compared as well.

Rule I17 keeps the administrator and the independent approver apart: no person may hold an admin and a qa account at the same time. The User Manager checks this against Keycloak when a role or person_id change is proposed and again when it is confirmed.

Unit assignments

Operators are assigned units, not zones. An operator with no unit in effect sees no telemetry and no runs and can start none. Until the planned Policy UI (Phase 4) brings this into the web interface, units are assigned on the platform host with apps/iam/units.sh, which takes the deploy lock.

./apps/iam/units.sh list
./apps/iam/units.sh assign <username> UNIT01 --by <your username>
./apps/iam/units.sh remove <username> UNIT01 --by <your username>

--by names the person running the command, who is recorded as the maker. An assignment is only proposed: nothing takes effect until a qa person who is neither the maker nor the subject confirms it in the Decisions tab. A refusal applies nothing. A removal acts at once. list shows the units in effect and those still waiting for qa.

The script cannot prove who ran it, since whoever runs it controls the host. So every assignment made by units.sh can be confirmed only after the qa person ticks the box "I did not run units.sh for this assignment." The attestation is stored with the confirmation note.

--bootstrap applies an assignment at once, before any check, and is allowed only while no other enabled qa account could confirm it. The decision still waits for qa; the Decisions tab marks it "in effect before the check", and a refusal removes the unit.

Every unit that takes effect or is removed appends unit_assigned or unit_removed to the hash-chained policy history, with the qa person as actor for a confirmed assignment.

The quarterly access review

The Access review tab of the User Manager holds one review per quarter. A qa person creates it and signs it off; auditor and qp can read it.

  1. Open Access review and choose "Create this quarter's review". The snapshot is taken at that moment and never changes.

Attribution: who did what

The 14 attributed tables (master data, devices, recipes, controllers, runs, schedules and others) carry created_by and updated_by fields: account, person, name, role and source. A database trigger fills them from the verified actor of the transaction and overwrites whatever a client sends. A service acting for a person records that person, with source person via followed by the service's database login; a schedule firing acts as system:scheduler on behalf of the person who created the schedule.

Every change to those tables is also appended to medcea.row_change. The approval functions read it to decide who counts as an author.

The tamper-evident policy history

iam_policy.history is a hash chain: each event stores the hash of the previous one, so a changed or removed event breaks every hash after it. Triggers refuse UPDATE, DELETE and TRUNCATE on it for every role, the owner included. It records:

  • enforcement_enabled and enforcement_disabled, with the switch (IAM_DB_ROLES, IAM_ENFORCE or IAM_MQTT_PERSON);
  • mqtt_credential_issued: every MQTT Explorer credential, with its user name, the person, their role, the topics and the expiry (never the password);
  • unit_assigned and unit_removed;
  • account_decision_confirmed, _refused, _reviewed and _withdrawn;
  • mqtt_credentials_retired: MQTT Explorer credentials ended by ./deploy-infra.sh because the MQTT policy or the IAM_MQTT_PERSON switch changed, with the number and the reason;
  • break_glass_seen: ./deploy-infra.sh found Node-RED running without its own sign-in (NR_ADMIN_AUTH=off) and turned it on again, with the time Node-RED started that way;
  • older zone_assigned and zone_removed events from before units replaced zones.

./health-check.sh runs iam_policy.verify_chain() (check iamchain) and reports "hash chain intact, N event(s)" or the first broken event.

Known limit: the chain catches any edit that does not rebuild it. It does not catch a database superuser who disables the triggers, drops the newest events or re-hashes the chain from an edited event onward. That needs the head of the chain anchored outside the database, which is not built.

Exports and the export log

Database Management lets a person holding X take a copy of tables and views of schema medcea, covering exactly the groups where their role holds X. An object outside those groups refuses the whole export and nothing is logged. A file saved on the platform goes to apps/database/exports/ and never overwrites an existing file.

Each export writes one row to iam_policy.export_log naming who exported which groups and objects (with row counts) and when, before the file is produced. The file header carries the export number; the page shows the export number and the start of the file's SHA-256, and the service log records the full hash. The export log is append-only for every role.

What is never deleted

  • Audit histories: the policy history, export log, approvals, row changes, account status history, access request history and the User Manager's change log are append-only: database triggers refuse changing or deleting their rows for every role, the owner included.
  • Device placement history: every placement, move and removal of a board.
  • Run logs: kept for good. The scheduler's own job sys_log_retention (daily at 03:15 UTC) compresses the log of a finished run after log_compress_days. It never deletes one, and no person can delete or compress logs. log_delete_days remains a setting but nothing reads it.
  • Q-tables: retired, never deleted.
  • Configuration: recipes, schedules and similar records are retired, not deleted. No person holds a DELETE grant on data.

While IAM_ENFORCE is true, a run's log is shown only to roles that hold Read on run logs; maintenance, qc and qp see the run without its log.

Known gaps and single-person controls

  • Zone moves. Telemetry is filtered by the zone's current unit. Moving a zone to another unit, which engineer may do, gives that unit's operators the zone's whole history without an account decision. It is recorded only in medcea.row_change. Deferred.
  • Open AI workbench sessions. The workbench checks a person's role at each sign-in, not continuously. After a role removal or a deactivation, a workbench session and an open notebook keep working until the sign-in runs again, at the latest after an hour. Personal API tokens a person created on the hub keep working until the administrator removes that person from the hub (which keeps their files). Notebooks run code; of the platform's services they reach only Keycloak and the database API, with the person's own sign-in, for reads only, which follows a role change or a deactivation within five minutes (IAM 3.2b).
  • Fixed 31 October 2026: the workbench administrator could open workspaces. Until then a hub administrator held JupyterHub's built-in administrator role, which includes creating a token in any person's name and opening their workspace. The setting the platform relied on to prevent it (admin_access: false) has done nothing since JupyterHub 2.0, and the health check trusted it. The live test tests/iam-workbench.sh found it on 31 October 2026 (step W4: the hub created a token for the test scientist, and the scientist's workspace accepted it; step W3 passed only because the test did not press "Authorize" on the page the hub showed). The fix gives administrators the narrower hub role workbench-admin and nobody the built-in role, and the test now requires the hub to refuse (403) both the token and the authorize step. The database showed no token created by an administrator for another person; deploying the fix removes the built-in role from the accounts that held it (admin and two earlier test administrators).
  • Node-RED editor tokens in the sign-in proxy's log. Node-RED's sign-in returns the editor token in the address it redirects to, and Node-RED's sign-in proxy logs each request's full address, so every editor sign-in since the Phase 3 deploy left its token in that proxy's log (found 31 October 2026). Someone who can read that log and also passes the engineer gate could use another engineer's editor session until it expires (8 hours), and Node-RED's audit log would name the other engineer. Fixed the same day: the proxy no longer logs requests to /, the path that carries the token (exclude_logging_paths), and the logged sessions were ended by clearing Node-RED's session file. Editor sessions survive a Node-RED restart (they are kept on its volume), so ending them takes clearing /data/.sessions.json; see troubleshooting.
  • Telemetry can leave through a notebook. A scientist holds Read on telemetry, not export, but a notebook runs the person's code with internet access (package installs, GitHub). When a notebook is committed to git its outputs are removed automatically (nbstripout, set up in every workspace at each start), and a check behind the filter refuses a commit whose notebooks still hold outputs, also when a repository's own settings turn the filter off or it could not be installed; a person who deliberately skips git's checks (git commit --no-verify) with the filter off is not stopped. Code and text cells, other files in the repository, downloads from the browser and anything a person's code sends elsewhere are not checked. What is read is attributable (each request runs as the person); what leaves afterwards is not recorded. Mitigated by the instructions in the workspace and the manual.
  • Workbench home folders are not backed up. They are kept when a workspace stops, when a person is removed from the hub or loses the workbench, and across every workbench redeploy, but nothing copies them anywhere, and deleting the namespace or MicroK8s (--uninstall-infra, --uninstall-all, ./deploy-infra.sh --reset or --uninstall, or a yes to "Fully wipe MicroK8s and reinstall?") deletes them; those commands list them and say how to keep them before they ask. A backup of the home folders is planned, not built; until then the research repository is the copy.
  • Onboarding into a new slot by maintenance. The onboarding wizard admits maintenance, which may only re-onboard into a slot that already exists, but the wizard does not check this itself. If a maintenance person chooses an empty slot, the board is erased and flashed before the database refuses the registration, and the board is left unregistered. No account on this install holds maintenance today.
  • Onboarding from the host shell without a platform identity. Whoever has a shell on the platform host and serial port access can flash a board without signing in: flash-device.sh --unregistered, declining the sign-in when a terminal run offers to continue unregistered, continuing when the slots cannot be read, and --ui-insecure. None of these registers the board or gives it a credential. They stay as the host operator's break-glass path (see the decision record).
  • Node-RED flows outside the repository. A flow built in the editor is reported by the health check as a warning, not blocked. Code in a flow runs inside Node-RED and can read what Node-RED holds: the ingest database password, the broker account, Node-RED's sign-in secret and the deploy scripts' token. An engineer who means to can therefore get round the rule that palette modules come only from the repository. The audit log and the health check make such use visible; they do not prevent it.
  • Open Grafana sessions. Grafana checks a person's role only at sign-in. A deactivation or a role removal does not end a Grafana session that is already open: the person keeps their Grafana role, and with it every unit's telemetry, for at most one hour: a Grafana session ends an hour after its sign-in, and the next sign-in checks the role again (a deactivated account cannot sign in). A change to who gets which Grafana role restarts Grafana and ends every session at once; a change to one person's role does not.
  • Grafana reads every unit. Grafana is gated by role since Phase 3.1, but its dashboards read telemetry of every unit through Grafana's own database account, which is why operator has no Grafana. A Viewer can send Grafana any query that account may run (master data, measurements and runs); hiding Explore from Viewers is not a boundary.
  • Grafana's local admin. One break-glass account holds Grafana Admin, with its own generated password in config.env and the credentials file. Whoever operates the host can read it; its use is logged only by Grafana.
  • Shared MQTT Explorer account until the switch. Until IAM_MQTT_PERSON is turned on, MQTT Explorer connects with one shared account that reads and writes every topic, also on the LAN port; the per-person credentials (IAM 3.5) are built and wait for the switch.
  • MQTT Explorer credentials outlive a sign-out. Signing out of the platform does not end a credential; it ends after at most 8 hours. Deactivation, a role change, clearing a unit's commissioning flag and a run start take effect at the broker's next check, within about 15 seconds; a connection already open stays open, but each message is checked. If the broker cannot read the credentials from the database, it stops accepting changes to them for at most 30 seconds and then admits no person credential until it can read them again.
  • The broker's WebSocket listener is reachable inside the cluster. No network policy covers the broker yet, so a program in the cluster that holds a leaked Explorer credential could use it directly, not only through the Explorer's sign-in, until the credential expires. Deferred (see the decision record).
  • No commissioning screen. Nothing in the Configuration UI flags a unit for commissioning (the database functions exist: an engineer proposes, qa approves). Until a screen exists, an engineer's MQTT Explorer can only read.
  • Chain head not anchored outside the database (see the policy history).
  • Approvals are records, not electronic signatures. Re-authentication and signature manifestation are not built.
  • Host operator. In the prototype the administrator also operates the host, which is break-glass access to the superuser and the Keycloak console. Statements by the database superuser are logged in full.
  • One qa person may create and sign off the same access review. This is a known single-person control.
  • Recorded self-check. The test account sergio_qa belonged to the same person as the account svieira. It was granted qa, confirmed account decision #3 (unit UNIT02) and was then deactivated. That confirmation is recorded as independent although it was not. It is noted here and was not undone.

Running the platform

This chapter is for the administrator who runs the MedCEA host. It covers installing the platform with ./install.sh, the deploy scripts and the order they run in, the rule that only one deploy runs at a time, and ./guide.sh, the question-and-answer front end to all of these commands. It then explains the six IAM switches in config.env that turn the access controls on step by step (and WORKBENCH_ENABLED, which the guide switches the same way), what the health check reports, which IAM test scripts to run and what a good result looks like, how operators are given units, how to uninstall, how the domain names reach other devices through Tailscale, and the credentials file. It ends with troubleshooting for problems an administrator can meet. Run every command from the repository root on the host.

Installing and updating

./install.sh is the one entry point. It runs three stages in order: the infrastructure (./deploy-infra.sh), every application (./deploy-apps.sh --all), and the health check (./health-check.sh). The same command updates an existing install: finished steps are skipped or updated in place, so it is safe to run again after a pull or after a failure. If a stage fails, the script stops, names the stage and its log file in logs/, and tells you to fix the cause and run it again.

./install.sh --infra-onlyOnly the infrastructure: MicroK8s, PostgreSQL, Keycloak, Grafana, Node-RED, the portal and the AI workbench.
./install.sh --apps-onlyOnly the applications. Needs the infrastructure and config.env.
./install.sh --helpThe options, including the uninstall levels (see Uninstalling).

At the end of an install the script prints the steps for trusting the platform's certificate authority on your devices and then the credentials box (see The credentials file), so the passwords are the last thing on screen.

config.env and the setup questions

All settings live in config.env in the repository root. It is not in git and is readable only by its owner (mode 600), because it holds every platform password. You do not write it by hand: the first run of ./deploy-infra.sh (or ./install.sh) creates it from config.env.example by asking questions. Press Enter to accept the value shown in brackets. Later runs ask only for required values that are still empty. To review every setting, run ./deploy-infra.sh --configure, or ./infra/configure.sh to edit the settings without deploying.

The questions cover:

  • Project name (PROJECT_NAME, default medcea): the MQTT topic root, the Kubernetes namespace and the Keycloak realm. Lowercase, starting with a letter, 2 to 31 characters from a-z 0-9 -. Changing it after boards are flashed means reflashing them.
  • Domain (DOMAIN): every web page is served at <service>.<DOMAIN>. The menu offers a name (for example medcea, so the portal is portal.medcea) when Tailscale is up, the Tailscale or LAN IP with nip.io, or a custom domain you provide DNS for. Changing the domain later means running ./deploy-infra.sh again.
  • The platform administrator: username, a real e-mail address you read (Keycloak password resets go there, and it is the pgAdmin login) and password.
  • The first qa person and the first engineer: username and e-mail for each. The qa person must be someone other than the administrator. Their initial passwords are generated and replaced at their first sign-in.
  • The PostgreSQL superuser password, the database volume size, and your Docker Hub username and access token (needed to pull the Bitnami Helm charts).
  • On a full review only (--configure): the time zone for Node-RED flows and schedules, and whether to deploy the AI workbench.

Some values are generated and never asked: the qa and engineer initial passwords, the Keycloak break-glass console account (kc-breakglass) and its password, and the passwords of the database service roles. Configuration also checks for Tailscale on every run. USE_TAILSCALE records whether the domain depends on it: when it is true, a deploy stops if Tailscale is down, rather than quietly falling back to the LAN address.

Password rules

A password you type must be 8 to 64 characters from A-Z a-z 0-9 . _ ~ - only. Other punctuation breaks the URLs and YAML files the password is written into, so the question asks again. Password input is hidden and typed twice. Pressing Enter generates a 20-character password (or keeps the current one if there is one), shows it once, and lists it in the credentials file.

Configuration runs before the deploy log starts, so your answers and generated passwords never reach logs/. When configuration rebuilds config.env on a newer config.env.example (keeping your values), it saves the previous file as config.env.bak.

One deploy at a time

Every script that changes the cluster or config.env takes the deploy lock first: install.sh, deploy-infra.sh, infra/configure.sh, deploy-apps.sh, each apps/<component>/deploy.sh and uninstall.sh, infra/deploy-workbench.sh, apps/iam/units.sh, tests/iam-signin.sh and the other test scripts that create things, and guide.sh for the length of a switch recipe. health-check.sh, the read-only tests and every --help do not take it. Two deploys side by side would interleave Helm releases, Keycloak clients and rewrites of config.env.

The lock is held by the kernel on the file .medcea.lock in the repository root. It is released the moment the holding process ends, even after kill -9 or a closed terminal, so there is never a stale lock to delete. A script started by another script that holds the lock (for example install.sh running deploy-infra.sh) uses its parent's lock.

Reading a refusal

A refused script prints Another MedCEA deploy is already running: and exits with code 1. What follows tells you who holds it:

  • A running deploy: its PID, start time, terminal and command, then Wait for it to finish, or stop it with: kill -- -<pgid>. Use that group kill, not a plain kill <pid>: a helm --wait or rollout status the run is waiting on would survive and keep the lock.
  • Leftover processes: The run that started it has ended; these leftover processes still hold the lock, with each process and the kill command to stop them.
  • A run as another user, usually under sudo: the holder could not be inspected, and the message suggests sudo fuser -v on the lock file.

guide.sh reports a held lock without exiting: it says another deploy is running and returns you to the menu with nothing changed.

guide.sh, the guided front end

./guide.sh walks you through the platform's commands by question and answer. It is the recommended way to run anything you do not run every day, and the only supported way to change an IAM switch.

  1. Run ./guide.sh, or ./guide.sh --dry-run to see what it would do without running or changing anything. Every question and confirmation is still asked in a dry run.
  2. Pick an area: Install and uninstall; Infrastructure; Applications; Operators and units; IAM switches (enable / roll back); Health and tests; Edge devices; Policy (read-only).
  3. Pick an action and answer its questions. Answers are checked the way the target script checks them (unit codes, usernames, component names that exist on disk), and nothing you type may start with -, so an answer cannot turn into an option.
  4. Read the plan: the exact command, whether it is read-only, changes the platform or is destructive, what it changes, whether it takes the deploy lock, and whether it needs sudo.
  5. Confirm. A read-only command asks [Y/n]; a change asks [y/N]; a destructive one (an uninstall, --purge-data, --reset, --bootstrap, erasing a board) wants the word yes typed in full, and --purge-data also the project name.
  6. The command runs in your terminal, so its own prompts work, and the guide reports its exit code.

The guide never asks for a password or secret: the commands it runs ask for their own. Ctrl+D (end of input) leaves the guide. For units commands it asks for --by, your own Keycloak username, and offers your last answer as the default for the rest of the session.

Switch recipes

For an IAM switch or WORKBENCH_ENABLED, the guide shows the switch's current value, then the recipe for enabling it or rolling it back:

  • Before you start: a checklist of preconditions, which you confirm once. The guide does not test the checklist items for you. Some preconditions it does check itself and refuses the recipe with the reason (for example, enabling IAM_DB_ROLES while IAM_POSTGREST_JWT is not true).
  • Steps, in order: each is either a change to one line of config.env or a command. The recipe takes the deploy lock once for all its steps and stops at the first step that fails, or at Ctrl+C.
  • Notes: what happens afterwards and how to check it.

The switch must be on exactly one active line in config.env; with none or several, the guide refuses and says which lines to fix. A switch that another recipe's order depends on (IAM_DB_ROLES, IAM_POSTGREST_JWT, IAM_DB_SERVICE_ROLES) must be written literally as "true" or "false".

Before the first change, the guide copies config.env to config.env.guide-<timestamp>.bak (mode 600, not in git). It shows only the changed line, never the lines around it, which may be passwords. If a step fails, it tells you whether config.env was already changed and prints the cp -p command that puts the backup back. Restoring the file does not undo the steps that already ran; each step is safe to repeat, so the usual fix is to correct the cause and run the recipe again. After a recipe completes, the guide offers to delete the backup, because it is a full copy with every password. ./install.sh --uninstall-all deletes any backups that are left.

After switching IAM_ENFORCE

The services read the switch on each request from the shared access settings that ./deploy-infra.sh publishes (the medcea-iam-lib ConfigMap), so the change is live within about a minute with no restart. From then on a refused request is answered 401 (no token or a bad one), 403 (the route or role is not allowed) or 503 (the service cannot verify tokens). Each application pod also keeps a copy of the switch from its last deploy, used only if the route-table mount is missing; it stays at the old value until the app is deployed again, and the health check reports iamenforce as FAIL until then. Redeploy the apps with ./deploy-apps.sh --all when no recipe run is active. Then check with tests/iam-check.sh, ./health-check.sh and tests/iam-signin.sh.

A rollback of IAM_ENFORCE returns the services to logging "would refuse" within about a minute.

When IAM_MQTT_PERSON changes, ./deploy-infra.sh appends enforcement_enabled or enforcement_disabled with {switch: IAM_MQTT_PERSON} to the same history, and every credential the Explorer is given is an mqtt_credential_issued event naming the person, the role, the topics and the expiry (never the password). On every switch change, and whenever the MQTT part of the access policy has changed, ./deploy-infra.sh ends the credentials issued before it and records mqtt_credentials_retired with their number; open Explorer pages then ask for a new credential.

When IAM_ENFORCE or IAM_DB_ROLES changes, the deploy appends an enforcement_enabled or enforcement_disabled event to the access policy history, a hash chain in the database that the health check verifies. For IAM_ENFORCE the event carries {switch: IAM_ENFORCE}. Each ./deploy-infra.sh also writes the current values of IAM_GATES, IAM_NETPOL and IAM_POSTGREST_JWT into the route-table settings with the time, which the quarterly access review records.

A git revert of IAM code comes only after the switch is rolled back. A reverted deploy breaks a config-api that is still in token mode, and reverting the database phase also needs a manual database step, which the guide's IAM_DB_ROLES rollback notes name.

DNS and Tailscale

With a name-based domain (DOMAIN="medcea", LOCAL_DNS="true", as on this install), the platform answers DNS for *.medcea itself, on its Tailscale address, port 53. The host resolves the names from a managed block in /etc/hosts. Other devices on your tailnet need one setting in the Tailscale admin console, which no command can make for you:

  1. Open https://login.tailscale.com/admin/dns.
  2. Nameservers, Add nameserver, Custom.
  3. Enter the server's Tailscale IP (PLATFORM_IP), turn on "Restrict to domain" (Split DNS), domain medcea, and save.
  4. Each device needs "Use Tailscale DNS settings" on (the default). On Linux: sudo tailscale set --accept-dns=true.
  5. Test from any device: nslookup portal.medcea must answer the server's IP. Then open https://portal.medcea, typing the https:// the first time, because browsers treat a one-word ending as a search until they have visited it.

Each ./deploy-infra.sh checks this setting at the end and reports when split DNS is active.

A rebuilt or replaced server

A new machine gets a new Tailscale IP, but the admin console keeps sending the domain to the old one. The server itself still resolves everything through /etc/hosts, so only other devices fail. ./deploy-infra.sh warns about this in its DNS step and, at the end, prints the old and new addresses and the edit to make: in the admin console, edit the nameserver restricted to the domain and change the old IP to the new one. If the old server is gone for good, remove it under Machines too.

With an IP-based domain (<ip>.nip.io) no DNS setup is needed. When you move from one domain to another, the old nip.io addresses keep working as permanent redirects (ALIAS_DOMAIN).

Troubleshooting

A person gets a 403 page from the portal

Symptom: the person signs in and sees "No access yet", or another 403 page. Cause: "No access yet" means Keycloak signed them in but their account has no platform role, so the portal's gate refuses them. A 403 with a different message is a failed sign-in (a provider error or an expired sign-in form), not a missing role. A host other than the portal shows "No access to <service>" with the roles that may open it. Fix: for "No access yet", give the account a role in the User Manager (a grant waits for qa to confirm); a password reset does not help. The role takes effect within about four minutes, without a new sign-in. For a failed sign-in, have the person open the portal again.

Grafana says the login was denied

Symptom: after signing in, a person lands on Grafana's own sign-in page with a message that the login was denied. Cause: their role holds nothing on the Grafana dashboards row of the access policy (for example operator, admin or a scientist), or the account has no platform role. Fix: none, if the role is right; Grafana is not for that role. Otherwise change the role in the User Manager. If everyone is refused, run ./health-check.sh: a grafanarole FAIL or a Keycloak scope problem (tests/iam-hosts.sh, sign-in line for Grafana) is the cause.

A person is refused right after switching to another account

Symptom: someone signs out of one account and in with another (for example to test a role), and an app shows "No access", Grafana says the login was denied, or the app still acts with the first account's role. Cause: usually the previous single sign-on session is still active in that browser: Keycloak, or an app that keeps its own session (Grafana, pgAdmin, the AI Workbench, the Node-RED editor), signed them in again as the first account without asking. Fix: sign out from the user menu (the person's name at the top right, or Sign Out on the portal), close the app's tabs and sign in again, or use a private window for the second account. Check the role in the User Manager only if the refusal stays.

The AI Workbench says "No access to AI Workbench"

Symptom: after signing in, a person sees the workbench's error page with "No access to AI Workbench" and the roles that may open it. Cause: their role holds nothing on the AI workbench row of the access policy (for example operator or auditor), or the account has no platform role. Fix: none, if the role is right. Otherwise change the role in the User Manager; the workbench checks it at the next sign-in, at the latest within an hour. If everyone is refused, run ./health-check.sh: an iamworkbench FAIL is the cause, and ./infra/deploy-workbench.sh the fix.

The System Configuration UI fails after a realm key rotation

Symptom: after a signing key was rotated or removed in Keycloak, the System Configuration UI's data calls are refused and the health check shows postgrest FAIL naming key ids the realm no longer publishes. Cause: config-api and the Python services verify tokens against the keys published at the last ./deploy-infra.sh; config-api reads them only when it starts. Fix: run ./deploy-infra.sh. It republishes the keys and restarts config-api when they changed.

The Config UI stops answering for a few seconds during a switch

Symptom: while IAM_POSTGREST_JWT is switched in either direction, the System Configuration UI's requests fail for up to about 15 seconds. Cause: by design. config-api's database password changes in the same step as its mode, and nothing serves until the new pod is ready. Fix: none needed; do the switch when nobody is editing configuration, and reload the page afterwards.

Node-RED stores no telemetry after a deploy

Symptom: the Monitor and Grafana show no new readings, and the health check shows noderedflows FAIL with "Node-RED runs no flows". Cause: Node-RED started on a new, empty volume (the first deploy that gave it one, or a fresh install). Fix: run ./apps/node-red/deploy.sh.

The Node-RED editor keeps reloading or refuses an engineer

Symptom: an engineer passes the platform sign-in, but the Node-RED editor reloads in a loop or shows its own sign-in form that accepts nothing. Cause: Node-RED's own sign-in cannot work, for example its sign-in module could not be installed (noderedauth FAIL) or Keycloak refuses its callback. Fix: run ./deploy-infra.sh. Break-glass, when the editor is needed at once: microk8s kubectl -n <namespace> set env deployment/node-red NR_ADMIN_AUTH=off turns the editor's own sign-in off (only the platform sign-in remains, which admits engineer only). It restarts Node-RED. While it is off, any program on the platform host or inside the cluster that can reach Node-RED can use its admin interface without signing in, so keep it brief. The next ./deploy-infra.sh turns it on again and records a break_glass_seen event in the access policy history with the time Node-RED started without its sign-in; noderedauth FAILs until then.

Ending every Node-RED editor session

Symptom: you need every engineer signed out of the Node-RED editor now, for example after a role removal or when an editor token may have been exposed. Cause: Node-RED keeps editor sessions on its volume (/data/.sessions.json), so a restart alone does not end them; each lasts up to 8 hours. Fix: clear the session file and restart Node-RED. Flows and palette modules are not affected:

microk8s kubectl -n medcea exec deployment/node-red -c node-red -- sh -c ': > /data/.sessions.json'
microk8s kubectl -n medcea rollout restart deployment/node-red

Engineers sign in again on their next visit. Telemetry ingest pauses for the few seconds the restart takes.

A newly onboarded board's first MQTT connections are refused

Symptom: right after onboarding, a board restarts once or twice before it publishes. Cause: its credential is registered after it boots and reaches the broker at the next sync, up to about 15 seconds later. Fix: none; the retry succeeds. A board flashed before the broker required credentials has none, never connects and must be onboarded again.

A change to the sign-in page does not show

Symptom: the login page still looks the same after you changed the theme files. Cause: Keycloak caches themes and never re-reads them while running. Fix: run ./deploy-infra.sh; it restarts Keycloak when the theme changed.

A deploy is refused although nothing is running

Symptom: "Another MedCEA deploy is already running", but the deploy you started earlier has ended. Cause: a background process started by that run, or a helm --wait or rollout status left after a plain kill, still holds the lock. Fix: the refusal lists the leftover processes and the kill command for them. Next time stop a run with the group kill it prints (kill -- -<pgid>). See One deploy at a time.

MicroK8s steps fail on Ubuntu 25.10 or later

Symptom: a MicroK8s start or addon enable fails with snapctl … from outside of a snap, or enable rbac dies after "No callback tokens file." Cause: Ubuntu's default sudo is now sudo-rs, which ignores sudo -E, and MicroK8s needs it for every privileged step. bootstrap-infra.sh switches to classic sudo for its own duration and restores the setting afterwards, so deploys work; a MicroK8s command you run by hand does not get that. Fix: by hand, run sudo update-alternatives --set sudo /usr/bin/sudo.ws, then the microk8s command, then sudo update-alternatives --auto sudo.

Other devices cannot open *.medcea after a server rebuild

Symptom: the host opens every page, laptops and phones on the tailnet do not. Cause: Tailscale split DNS still points at the old server's IP. Fix: change it in the admin console as ./deploy-infra.sh prints (see DNS and Tailscale).

An operator sees an empty Monitor

Symptom: an operator signs in but sees no telemetry or runs and cannot start a run. Cause: no unit is in effect for them, either none assigned or an assignment still waiting for qa. Fix: apps/iam/units.sh list <username>; assign a unit with --by and have a qa person confirm it in the User Manager's Decisions tab.

A qa decision cannot be confirmed

Symptom: a decision about the only qa person's own account, or one they made, waits forever. Cause: the person who checks a decision is never its maker or its subject. Fix: another qa person confirms it. With no enabled qa person at all, set a new QA_USER in config.env and run ./deploy-infra.sh (break-glass, outside the decisions).
