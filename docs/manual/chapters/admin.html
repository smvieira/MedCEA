Running the platform

This chapter is for the administrator who runs the MedCEA host. It covers installing the platform with ./install.sh, the deploy scripts and the order they run in, the rule that only one deploy runs at a time, and ./guide.sh, the question-and-answer front end to all of these commands. It then explains the seven IAM switches in config.env that turn the access controls on step by step (and WORKBENCH_ENABLED, which the guide switches the same way), which of them a fresh install leaves off and how to turn those on, what the health check reports, which IAM test scripts to run and what a good result looks like, how operators are given units, how to uninstall, how the domain names reach other devices through Tailscale, and the credentials file. It ends with troubleshooting for problems an administrator can meet. Run every command from the repository root on the host.

Installing and updating

./install.sh is the one entry point. It runs three stages in order: the infrastructure (./deploy-infra.sh), every application (./deploy-apps.sh --all), and the health check (./health-check.sh). The same command updates an existing install: finished steps are skipped or updated in place, so it is safe to run again after a pull or after a failure. If a stage fails, the script stops, names the stage and its log file in logs/, and tells you to fix the cause and run it again.

CommandWhat it does
./install.shInstall or update everything: infrastructure, applications, health check. Asks for any missing settings first.
./install.sh --configureReview every setting (current values offered as defaults), then install.
./install.sh --infra-onlyOnly the infrastructure: MicroK8s, PostgreSQL, Keycloak, Grafana, Node-RED, the portal and the AI workbench.
./install.sh --apps-onlyOnly the applications. Needs the infrastructure and config.env.
./install.sh --helpThe options, including the uninstall levels (see Uninstalling).

At the end of an install the script prints the steps for trusting the platform's certificate authority on your devices and then the credentials box (see The credentials file). While any IAM switch is still false it then prints one line pointing to ./guide.sh → IAM switches → Bring IAM to full enforcement (see After a fresh install); a fresh install always prints it.

config.env and the setup questions

All settings live in config.env in the repository root. It is not in git and is readable only by its owner (mode 600), because it holds every platform password. You do not write it by hand: the first run of ./deploy-infra.sh (or ./install.sh) creates it from config.env.example by asking questions. Press Enter to accept the value shown in brackets. Later runs ask only for required values that are still empty. To review every setting, run ./deploy-infra.sh --configure, or ./infra/configure.sh to edit the settings without deploying.

The questions cover:

  • Project name (PROJECT_NAME, default medcea): the MQTT topic root, the Kubernetes namespace and the Keycloak realm. Lowercase, starting with a letter, 2 to 31 characters from a-z 0-9 -. Changing it after boards are flashed means reflashing them.
  • Domain (DOMAIN): every web page is served at <service>.<DOMAIN>. The menu offers a name (for example medcea, so the portal is portal.medcea) when Tailscale is up, the Tailscale or LAN IP with nip.io, or a custom domain you provide DNS for. Changing the domain later means running ./deploy-infra.sh again.
  • The platform administrator: username, a real e-mail address you read (Keycloak password resets go there, and it is the pgAdmin login) and password.
  • The first qa person and the first engineer: username and e-mail for each. The qa person must be someone other than the administrator. Their initial passwords are generated and replaced at their first sign-in.
  • The PostgreSQL superuser password, the database volume size, and your Docker Hub username and access token (needed to pull the Bitnami Helm charts).
  • On a full review only (--configure): the time zone for Node-RED flows and schedules, and whether to deploy the AI workbench.

Some values are generated and never asked: the qa and engineer initial passwords, the Keycloak break-glass console account (kc-breakglass) and its password, and the passwords of the database service roles. Configuration also checks for Tailscale on every run. USE_TAILSCALE records whether the domain depends on it: when it is true, a deploy stops if Tailscale is down, rather than quietly falling back to the LAN address.

Password rules

A password you type must be 8 to 64 characters from A-Z a-z 0-9 . _ ~ - only. Other punctuation breaks the URLs and YAML files the password is written into, so the question asks again. Password input is hidden and typed twice. Pressing Enter generates a 20-character password (or keeps the current one if there is one), shows it once, and lists it in the credentials file.

Every command writes its own log in logs/ (readable by the platform user only): deploy-infra-<timestamp>.log, deploy-apps-…, a component deployed on its own app-<component>-deploy-… (or -uninstall-…), app-iam-units-…, deploy-workbench-…, health-check-…, the throwaway database test iam-db-fixture-<command>-… and each live test iam-<name>-…. A command run by another (a component by ./deploy-apps.sh, a test by the fixture) writes into its caller's log. The first line of the output names the file. MEDCEA_NO_LOG=1 turns it off for one run.

Configuration runs before the deploy log starts, so your answers and generated passwords never reach logs/. When configuration rebuilds config.env on a newer config.env.example (keeping your values), it saves the previous file as config.env.bak.

The deploy scripts and their order

install.sh is a thin wrapper. Each stage also works on its own, and after the first install you will usually run the stages directly.

ScriptWhat it deploys
./deploy-infra.shMicroK8s (bootstrapped only on the first run), PostgreSQL, Keycloak with the realm, clients and roles, the MQTT broker, Node-RED, Grafana, pgAdmin, the sign-in proxies, the portal, the AI workbench (unless WORKBENCH_ENABLED=false), the access policy's route table and the realm's public keys. It writes a log to logs/deploy-infra-<timestamp>.log.
./deploy-apps.shA checkbox menu of the application components under apps/. ./deploy-apps.sh --all deploys every component without asking.
./apps/<component>/deploy.shOne component on its own. The components are access, database, edge-wizard, frontend, iam, monitor, mqtt-explorer, node-red, report and scheduler (./deploy-apps.sh --help lists them).
./infra/deploy-workbench.shRedeploys only the AI workbench (JupyterHub, chart 4.4.4: JupyterHub 5.5.4). A workspace that is already running keeps its old setup until it is stopped and started again. Who may sign in and who is hub administrator come from the access policy; if the policy does not compile, the script stops before it changes anything and the running workbench stays as it is.

The order rules are:

  • Infrastructure first. The applications need the cluster, Keycloak and PostgreSQL that deploy-infra.sh creates. ./install.sh --apps-only refuses without config.env.
  • Database before scheduler. deploy-apps.sh runs components in alphabetical order, so database comes before scheduler. When you deploy them one by one, run ./apps/database/deploy.sh first: the scheduler deploy refuses until the database functions it needs exist.
  • Access after infrastructure. Run ./deploy-infra.sh, then ./apps/access/deploy.sh. The access deploy runs the database deploy itself when it needs to. Since 1 November 2026 the order also matters for Sign out: ./deploy-infra.sh registers the AI Workbench's logout address with each app's sign-in, and the access deploy then points Sign out at it. In the other order, Sign out shows Keycloak's "Invalid redirect uri" and ends nothing until ./deploy-infra.sh has run.
  • After a pull of new IAM code: ./deploy-infra.sh (the route table), then ./apps/database/deploy.sh, then ./deploy-apps.sh --all while no recipe run is active. Until all three have run, the health check's iamgrants and tests/iam-schema.sh stay red.
  • iam-api (the iam component, IAM 3.5) after ./apps/database/deploy.sh and ./apps/access/deploy.sh: alphabetical order already does this. While IAM_DB_SERVICE_ROLES is false it is skipped with a warning. Then turn on IAM_MQTT_PERSON (see IAM switches).
  • After rotating or removing a realm key in Keycloak, run ./deploy-infra.sh. It republishes the keys and restarts config-api when they changed.
  • pgAdmin restarts whenever ./deploy-infra.sh changes its sign-in settings (pgAdmin's client secret, the roles it admits, or ADMIN_PASS), which signs everyone out of pgAdmin; a run that changes none of them leaves it running. The first ./deploy-infra.sh after 1 November 2026 restarts it once, when its secrets move into a Kubernetes Secret, and removes the older copies of pgAdmin's deployment that still held them. pgAdmin's client secret was readable in plain text until then, so give it a new one once: in the Keycloak console, realm medcea, Clients, pgadmin, Credentials, Regenerate; then run ./deploy-infra.sh, which reads the new secret and restarts pgAdmin.
  • pgAdmin's IoT Postgres entry is loaded for each account that may sign in to pgAdmin when pgAdmin starts. ./deploy-infra.sh lists the e-mail addresses of the enabled Keycloak accounts holding a role pgAdmin admits (admin) and gives the list to pgAdmin; when the list changed, pgAdmin restarts (everyone is signed out of it) and loads the entry for each address, which can add several minutes to its start. So after giving someone the admin role, or changing an admin's e-mail address, run ./deploy-infra.sh: until then they can sign in to pgAdmin but see no server. An account without an e-mail address, or with one on a reserved test domain such as .invalid, .test or .example (pgAdmin refuses those), gets no entry; the deploy names it in a warning. If Keycloak cannot be read, the deploy keeps the list pgAdmin already has, so nobody loses their entry, and says so; only when pgAdmin has no list yet does it go on with the platform administrator's address alone. Since 1 November 2026 pgAdmin runs version 9.19.0, pinned in k8s/pgadmin/pgadmin.yaml; the first ./deploy-infra.sh after that date restarts it once.
  • Node-RED after ./deploy-infra.sh: when Node-RED's settings changed, the deploy restarts it. Its flows are kept on a volume and survive. The first deploy onto that volume (and a fresh install) starts with no flows; the deploy then says "Node-RED runs no flows" and telemetry is not stored until you run ./apps/node-red/deploy.sh. Do that first deploy while no recipe run is active.

The scheduler runs recipe code straight from the repository (schd/), and the onboarding wizard runs edge/ from it. Do not pull or edit the repository while a recipe run is active: check first that pgrep -af '[r]un_recipe.py' prints nothing.

When your login session is not yet in the microk8s group (for example right after the first install added you to it), the scripts run their microk8s calls through sudo and say why they ask for your password. Log out and back in to stop that.

One deploy at a time

Every script that changes the cluster or config.env takes the deploy lock first: install.sh, deploy-infra.sh, infra/configure.sh, deploy-apps.sh, each apps/<component>/deploy.sh and uninstall.sh, infra/deploy-workbench.sh, apps/iam/units.sh, tests/iam-signin.sh and the other test scripts that create things, and guide.sh for the length of a switch recipe. health-check.sh, the read-only tests and every --help do not take it. Two deploys side by side would interleave Helm releases, Keycloak clients and rewrites of config.env.

The lock is held by the kernel on the file .medcea.lock in the repository root. It is released the moment the holding process ends, even after kill -9 or a closed terminal, so there is never a stale lock to delete. A script started by another script that holds the lock (for example install.sh running deploy-infra.sh) uses its parent's lock.

Reading a refusal

A refused script prints Another MedCEA deploy is already running: and exits with code 1. What follows tells you who holds it:

  • A running deploy: its PID, start time, terminal and command, then Wait for it to finish, or stop it with: kill -- -<pgid>. Use that group kill, not a plain kill <pid>: a helm --wait or rollout status the run is waiting on would survive and keep the lock.
  • Leftover processes: The run that started it has ended; these leftover processes still hold the lock, with each process and the kill command to stop them.
  • A run as another user, usually under sudo: the holder could not be inspected, and the message suggests sudo fuser -v on the lock file.

guide.sh reports a held lock without exiting: it says another deploy is running and returns you to the menu with nothing changed.

guide.sh, the guided front end

./guide.sh walks you through the platform's commands by question and answer. It is the recommended way to run anything you do not run every day, and the only supported way to change an IAM switch.

  1. Run ./guide.sh, or ./guide.sh --dry-run to see what it would do without running or changing anything. Every question and confirmation is still asked in a dry run.
  2. Pick an area: Install and uninstall; Infrastructure; Applications; Operators and units; IAM switches (enable or roll back one switch, or bring every switch still off to full enforcement); Health and tests; Edge devices; Policy (read-only).
  3. Pick an action and answer its questions. Answers are checked the way the target script checks them (unit codes, usernames, component names that exist on disk), and nothing you type may start with -, so an answer cannot turn into an option.
  4. Read the plan: the exact command, whether it is read-only, changes the platform or is destructive, what it changes, whether it takes the deploy lock, and whether it needs sudo.
  5. Confirm. A read-only command asks [Y/n]; a change asks [y/N]; a destructive one (an uninstall, --purge-data, --reset, --bootstrap, erasing a board) wants the word yes typed in full, and --purge-data also the project name.
  6. The command runs in your terminal, so its own prompts work, and the guide reports its exit code.

The guide never asks for a password or secret: the commands it runs ask for their own. Ctrl+D (end of input) leaves the guide. For units commands it asks for --by, your own Keycloak username, and offers your last answer as the default for the rest of the session.

Switch recipes

For an IAM switch or WORKBENCH_ENABLED, the guide shows the switch's current value, then the recipe for enabling it or rolling it back:

  • Before you start: a checklist of preconditions, which you confirm once. The guide does not test the checklist items for you. Some preconditions it does check itself and refuses the recipe with the reason (for example, enabling IAM_DB_ROLES while IAM_POSTGREST_JWT is not true).
  • Steps, in order: each is either a change to one line of config.env or a command. The recipe takes the deploy lock once for all its steps and stops at the first step that fails, or at Ctrl+C.
  • Notes: what happens afterwards and how to check it.

The switch must be on exactly one active line in config.env; with none or several, the guide refuses and says which lines to fix. A switch that another recipe's order depends on (IAM_DB_ROLES, IAM_POSTGREST_JWT, IAM_DB_SERVICE_ROLES) must be written literally as "true" or "false".

Before the first change, the guide copies config.env to config.env.guide-<timestamp>.bak (mode 600, not in git). It shows only the changed line, never the lines around it, which may be passwords. If a step fails, it tells you whether config.env was already changed and prints the cp -p command that puts the backup back. Restoring the file does not undo the steps that already ran; each step is safe to repeat, so the usual fix is to correct the cause and run the recipe again. After a recipe completes, the guide offers to delete the backup, because it is a full copy with every password. ./install.sh --uninstall-all deletes any backups that are left.

IAM switches → Bring IAM to full enforcement runs the enable recipe of every IAM switch still false, in order, under one lock, and stops at the first problem; running it again resumes. See After a fresh install.

The IAM switches

The access controls (IAM) were built in phases. Each phase has a switch in config.env, turned on in order with a recipe in ./guide.sh (IAM switches). A fresh install has the first two on and the rest off (see After a fresh install). Each one can be rolled back the same way.

Order and prerequisites

  1. IAM_GATES and IAM_NETPOL stand on their own. For IAM_NETPOL, every caller of an application pod must be listed under network: in apps/iam/policy/defaults.yaml.
  2. IAM_POSTGREST_JWT needs AUTHENTICATOR_DB_PASS set and different from POSTGRES_PASS (configuration generates it).
  3. IAM_DB_SERVICE_ROLES, then check that the health check shows dbclients OK.
  4. IAM_DB_ROLES: the guide refuses it until IAM_POSTGREST_JWT and IAM_DB_SERVICE_ROLES are both true, and the database deploy refuses it, changing nothing, until every database client has moved to its own role. Before it, every operator needs a unit in effect, confirmed by qa (see Operators and units); an operator without one sees no telemetry or runs and starts none.
  5. IAM_MQTT_PERSON needs ./apps/iam/deploy.sh to have run (it deploys iam-api, which issues the credentials and logs in to the database only as its own role, so IAM_DB_SERVICE_ROLES must be true), ./apps/access/deploy.sh since the IAM 3.5 pull, and IAM_DB_ROLES true (the broker reads the credentials through its compiled grants). Nobody may still use MQTT_EXPLORER_PASS outside the Explorer page: it stops working on both listeners.
  6. IAM_ENFORCE needs IAM_DB_ROLES true: only the database checks that an operator's run belongs to their unit. The guide lists this in its checklist but does not refuse; the health check reports iamenforce FAIL while IAM_ENFORCE is true and IAM_DB_ROLES false. It should follow a report-only trial in which every "would refuse" line from a real person is intended policy, because each becomes a refusal.

After switching IAM_ENFORCE

The services read the switch on each request from the shared access settings that ./deploy-infra.sh publishes (the medcea-iam-lib ConfigMap), so the change is live within about a minute with no restart. From then on a refused request is answered 401 (no token or a bad one), 403 (the route or role is not allowed) or 503 (the service cannot verify tokens). Each application pod also keeps a copy of the switch from its last deploy, used only if the route-table mount is missing; it stays at the old value until the app is deployed again, and the health check reports iamenforce as FAIL until then. Redeploy the apps with ./deploy-apps.sh --all when no recipe run is active. Then check with tests/iam-check.sh, ./health-check.sh and tests/iam-signin.sh.

A rollback of IAM_ENFORCE returns the services to logging "would refuse" within about a minute.

When IAM_MQTT_PERSON changes, ./deploy-infra.sh appends enforcement_enabled or enforcement_disabled with {switch: IAM_MQTT_PERSON} to the same history, and every credential the Explorer is given is an mqtt_credential_issued event naming the person, the role, the topics and the expiry (never the password). On every switch change, and whenever the MQTT part of the access policy has changed, ./deploy-infra.sh ends the credentials issued before it and records mqtt_credentials_retired with their number; open Explorer pages then ask for a new credential.

When IAM_ENFORCE or IAM_DB_ROLES changes, the deploy appends an enforcement_enabled or enforcement_disabled event to the access policy history, a hash chain in the database that the health check verifies. For IAM_ENFORCE the event carries {switch: IAM_ENFORCE}. Each ./deploy-infra.sh also writes the current values of IAM_GATES, IAM_NETPOL and IAM_POSTGREST_JWT into the route-table settings with the time, which the quarterly access review records.

A git revert of IAM code comes only after the switch is rolled back. A reverted deploy breaks a config-api that is still in token mode, and reverting the database phase also needs a manual database step, which the guide's IAM_DB_ROLES rollback notes name.

After a fresh install

Every new config.env is made from config.env.example, and neither ./install.sh nor the setup questions change the IAM switches. A fresh install therefore comes up with the sign-in gates and the network policies on, but without token checks at config-api, database roles, row-level security or service enforcement:

SwitchFresh installWhat it does when true
IAM_GATEStrueEach sign-in gate, Grafana, the AI workbench, the onboarding wizard and pgAdmin admit the roles the access policy compiles for them.
IAM_NETPOLtrueOnly each application pod's listed callers can connect to it.
IAM_POSTGREST_JWTfalseconfig-api verifies the person's sign-in token.
IAM_DB_SERVICE_ROLESfalseEach database client logs in as its own role instead of the superuser.
IAM_DB_ROLESfalseThe database enforces per-role grants, row-level security and guard triggers, including an operator's units.
IAM_ENFORCEfalseThe Python services refuse what the route table does not allow, instead of logging "would refuse".
IAM_MQTT_PERSONfalseThe MQTT Explorer uses a personal, short-lived credential instead of the shared account.

The health check warns while IAM_POSTGREST_JWT, IAM_DB_ROLES, IAM_ENFORCE, IAM_MQTT_PERSON or IAM_GATES is off, so a fresh install never prints "All checks passed". It does not warn for the other two: with IAM_DB_SERVICE_ROLES off the dbclients check is OK as long as every client is on postgres, and no check reads IAM_NETPOL; read those two in config.env. That is deliberate: each switch has its own rollback, and an administrator turns them on in order. Some cannot be on at the very first install:

  • IAM_DB_ROLES needs the scheduler and Node-RED already deployed and logging in to the database as their own roles (IAM_DB_SERVICE_ROLES). On a fresh install the database is deployed before them, so its deploy would refuse.
  • Operators need units assigned and confirmed by a qa person before IAM_DB_ROLES, or they see no telemetry or runs and start none (see Operators and units).

The order is: IAM_POSTGREST_JWT; IAM_DB_SERVICE_ROLES; assign the operators' units with apps/iam/units.sh assign … --by <your username> and have a qa person confirm them in the User Manager; IAM_DB_ROLES; IAM_ENFORCE (after a report-only trial, see The IAM switches); IAM_MQTT_PERSON.

Bring IAM to full enforcement

./guide.sh → IAM switches → Bring IAM to full enforcement runs that order for you. It uses each switch's own enable recipe, the same one the switch's own entry runs, so nothing in it differs from turning the switches on one by one.

  1. It reads every IAM switch from config.env. Each must be on exactly one active line and written literally as "true" or "false"; otherwise it refuses and changes nothing. If every switch is already true, it says so and stops.
  2. It shows the plan: each switch still false, in the order above (IAM_GATES and IAM_NETPOL only if they are false), with its purpose, its checklist, its steps and its notes. You confirm the whole plan once ([y/N]).
  3. It takes the deploy lock once for the whole chain (refused while another deploy runs), then runs the switches in turn. For each, it asks that switch's checklist when its turn comes, because some items only become true after the switches before it.
  4. Before IAM_DB_ROLES it runs apps/iam/units.sh list under its lock. If an enabled operator has no unit in effect, or the list cannot be read, it says what that means and asks whether to go on; answering no stops the chain there.
  5. Each switch's steps run as in its own recipe: one line of config.env changed, with its own backup, and the deploys in order.

On a fresh install, expect a run made soon after the install to stop at IAM_ENFORCE's checklist, whose first item is that a report-only trial is over. Answer no unless the services have already run long enough with "would refuse" lines that are all intended (the trial needs no other switch, so it can run while you work through the earlier ones). Then run the trial (see The IAM switches) and choose the action again: it resumes from IAM_ENFORCE and goes on to IAM_MQTT_PERSON. In the same way, if the operators' units are not yet assigned and confirmed by a qa person, answer no at the question before IAM_DB_ROLES, assign them, and choose the action again.

It stops at the first refused checklist, failed step or Ctrl+C (exit code 130). Ctrl+C while it waits at a question stops it at once, before any step of that switch; during a step it stops once that step's command has ended. It then says which switch stopped and why, which switches are already done, which were not started, and the backups it made. Fix the cause and choose Bring IAM to full enforcement again: switches already true are skipped, so it resumes from the one that stopped. If that switch's own line was already set to true before its steps failed, put its backup back first, using the cp -p command the guide prints (only that switch changes back), or finish it with its own entry in IAM switches. Do not put back an earlier backup: it would turn off switches whose deploys already ran. After a complete chain the guide offers to delete the backups.

./guide.sh --dry-run shows the plan and every command and config.env change, without running anything, changing anything or taking the lock.

The health check

./health-check.sh checks every service and IAM control listed in health-checks.conf and prints one line per check. It is read-only and does not take the deploy lock. Options: --verbose shows detail for passing checks too, --timeout SECS sets the per-check timeout (default 8), --config FILE reads another check list.

ResultMeaning
OKThe check passed.
WARNNot broken, but not in its final state: for example a switch still false, a pod's copy of a setting that is out of date, or a decision waiting a long time.
FAILSomething is wrong or disagrees with config.env. The message names the cause and usually the command that fixes it.
SKIPThe check does not apply yet (for example the component it reads is not installed).

The summary is All N checks passed., or a count of OK, warnings and failures. The script exits 1 if any check failed. Services that are still starting usually pass a minute later.

The checks iamdbroles, postgrest, iamenforce and iammqtt WARN on purpose while their switch is false, so a platform that is not fully enforcing never prints "All checks passed". grafanarole, iamworkbench, onboardroles and pgadminroles WARN while IAM_GATES is false; the proxies' gates and IAM_NETPOL have no health check; test them with tests/iam-hosts.sh and tests/iam-network.sh. On this install every switch is true since 31 October 2026, IAM_MQTT_PERSON included, so these checks should all be OK; the health check passed all 50 checks that evening.

Operators and units

An operator works in the units they are assigned to. Once IAM_DB_ROLES is true (or IAM_ENFORCE), an operator sees the telemetry, runs and run logs of every zone of their units, including zones added later, and starts or stops runs only there. An operator with no unit in effect sees an empty Monitor and can start nothing. Assign units with apps/iam/units.sh, or through ./guide.sh under Operators and units.

CommandWhat it does
apps/iam/units.sh list [<username>]Columns USERNAME, ROLE, ENABLED, UNITS, WAITING_QA. UNITS are in effect (a * marks one in effect before qa checked it, its decision still waiting); WAITING_QA are not in effect yet. Warns about an enabled operator with no unit in effect.
apps/iam/units.sh assign <username> <UNIT>… --by <your username>Proposes the assignment. It waits for a qa person other than you to confirm it in the User Manager's Decisions tab, and is not in effect until then.
apps/iam/units.sh remove <username> <UNIT>… --by <your username>Removes an assigned unit at once, or withdraws an assignment still waiting for qa.
apps/iam/units.sh remove --sub <uuid> <UNIT>… --by <your username>The same for an account Keycloak no longer has; list prints the command.

--by is your own Keycloak username in the platform realm. It is recorded as the person who made the change, so you cannot confirm it yourself. --reason TEXT adds a reason. Unit codes are case-insensitive. The script takes the deploy lock and is not run by deploy-apps.sh. It warns, without refusing, about an account that is not an operator, is disabled or has no person id. Exit code 1 means an unknown user or unit, an SQL failure or a held lock; 2 means a usage error (a missing --by included), a database or access deploy that has not run yet, or Keycloak unreachable.

When the qa person confirms such a decision in the Decisions tab, they must also tick the statement "I did not run units.sh for this assignment.", because --by is a claim the script cannot prove: whoever runs it has the host.

--bootstrap

assign … --bootstrap puts the unit in effect at once, before any check, with its decision still waiting for qa. It is allowed only while Keycloak has no enabled qa account other than yours and the operator's, so nobody else could confirm. Otherwise it is refused with exit code 2, naming who could confirm. A qa person who later refuses that decision removes the unit. ./guide.sh asks for yes before running it.

Each assignment or removal writes one account decision per unit (maker shown as system:deploy (by <username>)). When qa confirms an assignment, a unit_assigned event is added to the access policy history with the qa person as actor; a removal adds unit_removed; a withdrawal adds account_decision_withdrawn.

A unit that is still assigned to someone cannot be deleted in the System Configuration UI. Remove the assignment with units.sh remove first.

--purge-data

./install.sh --uninstall-apps --purge-data (or ./deploy-apps.sh --uninstall --purge-data) also drops the platform database medcea_db with all its data and its database roles. It applies only when database is among the components removed, and asks for the project name to confirm.

--purge-data cannot be undone. It drops every run, recipe, measurement, device record and audit record in medcea_db, including the access policy history. If config-api still verifies tokens, it cannot connect after the purge until ./apps/database/deploy.sh and then ./apps/frontend/deploy.sh have run.

./apps/access/uninstall.sh --purge-data drops the User Manager's data: access requests, account decisions and their histories. Unit assignments in effect survive (the script warns while there are any), and the next ./apps/access/deploy.sh records each one again as a decision waiting for qa. Assignments that were still waiting for qa are lost and must be assigned again.

Keycloak has its own database, so purging medcea_db does not remove realms, users or clients. Those go only with --uninstall-infra or --uninstall-all.

DNS and Tailscale

With a name-based domain (DOMAIN="medcea", LOCAL_DNS="true", as on this install), the platform answers DNS for *.medcea itself, on its Tailscale address, port 53. The host resolves the names from a managed block in /etc/hosts. Other devices on your tailnet need one setting in the Tailscale admin console, which no command can make for you:

  1. Open https://login.tailscale.com/admin/dns.
  2. Nameservers, Add nameserver, Custom.
  3. Enter the server's Tailscale IP (PLATFORM_IP), turn on "Restrict to domain" (Split DNS), domain medcea, and save.
  4. Each device needs "Use Tailscale DNS settings" on (the default). On Linux: sudo tailscale set --accept-dns=true.
  5. Test from any device: nslookup portal.medcea must answer the server's IP. Then open https://portal.medcea, typing the https:// the first time, because browsers treat a one-word ending as a search until they have visited it.

Each ./deploy-infra.sh checks this setting at the end and reports when split DNS is active.

A rebuilt or replaced server

A new machine gets a new Tailscale IP, but the admin console keeps sending the domain to the old one. The server itself still resolves everything through /etc/hosts, so only other devices fail. ./deploy-infra.sh warns about this in its DNS step and, at the end, prints the old and new addresses and the edit to make: in the admin console, edit the nameserver restricted to the domain and change the old IP to the new one. If the old server is gone for good, remove it under Machines too.

With an IP-based domain (<ip>.nip.io) no DNS setup is needed. When you move from one domain to another, the old nip.io addresses keep working as permanent redirects (ALIAS_DOMAIN).

The credentials file

Each ./deploy-infra.sh writes the passwords a person needs to credentials-<timestamp>.txt in the repository root, readable only by you, and shows it in a box on the terminal. The box is written straight to the terminal, never to the deploy log. It lists:

  • the platform admin, the first qa person and the first engineer, with the portal address;
  • the Keycloak admin console break-glass account (realm master), for recovery only; every use is recorded in Keycloak's admin events;
  • the Grafana address, and Grafana's local admin account (the only Grafana Admin, for recovery only, at /login?disableAutoLogin; its password GRAFANA_BREAKGLASS_PASS is not the platform admin's); the demo accounts developer and viewer only while they still exist from an older install;
  • the pgAdmin address (platform admin role only);
  • where the MQTT service account passwords are (MQTT_*_PASS in config.env), that each board has its own credential, and how the MQTT Explorer connects: the shared mqtt-explorer account (MQTT_EXPLORER_PASS) only while IAM_MQTT_PERSON is false, otherwise a personal credential per sign-in, with MQTT_EXPLORER_PASS unused but kept for a rollback;
  • the PostgreSQL superuser.

Save these in a password manager, then delete the file. config.env keeps its own copy, which re-deploys need. A person may change their own password from the user menu; the box then shows "(changed since the account was created; config.env's copy no longer works)" instead of a value nobody uses any more. A first password that must be replaced at first sign-in is marked "temporary".

The platform admin (the username you gave at setup, in the realm named after the project, medcea on this install) and the break-glass console account kc-breakglass in realm master are different accounts. Use the break-glass account only when the platform's own tools cannot do the job.

Troubleshooting

A person gets a 403 page from the portal

Symptom: the person signs in and sees "No access yet", or another 403 page. Cause: "No access yet" means Keycloak signed them in but their account has no platform role, so the portal's gate refuses them. A 403 with a different message is a failed sign-in (a provider error or an expired sign-in form), not a missing role. A host other than the portal shows "No access to <service>" with the roles that may open it. Fix: for "No access yet", give the account a role in the User Manager (a grant waits for qa to confirm); a password reset does not help. The role takes effect within about four minutes, without a new sign-in. For a failed sign-in, have the person open the portal again.

Grafana says the login was denied

Symptom: after signing in, a person lands on Grafana's own sign-in page with a message that the login was denied. Cause: their role holds nothing on the Grafana dashboards row of the access policy (for example operator, admin or a scientist), or the account has no platform role. Fix: none, if the role is right; Grafana is not for that role. Otherwise change the role in the User Manager. If everyone is refused, run ./health-check.sh: a grafanarole FAIL or a Keycloak scope problem (tests/iam-hosts.sh, sign-in line for Grafana) is the cause.

A person is refused right after switching to another account

Symptom: someone signs out of one account and in with another (for example to test a role), and an app shows "No access", Grafana says the login was denied, or the app still acts with the first account's role. Cause: usually the previous single sign-on session is still active in that browser: Keycloak, or an app that keeps its own session (Grafana, pgAdmin, the AI Workbench, the Node-RED editor), signed them in again as the first account without asking. Fix: sign out from the user menu (the person's name at the top right, then Sign out; the Sign Out buttons on the portal page end only the portal's own sign-in, and the portal then signs the first account in again), close the app's tabs and sign in again, or use a private window for the second account. Check the role in the User Manager only if the refusal stays.

The AI Workbench says "No access to AI Workbench"

Symptom: after signing in, a person sees the workbench's error page with "No access to AI Workbench" and the roles that may open it. Cause: their role holds nothing on the AI workbench row of the access policy (for example operator or auditor), or the account has no platform role. Fix: none, if the role is right. Otherwise change the role in the User Manager; the workbench checks it at the next sign-in, at the latest within 5 minutes (an open notebook tab within about 10). If everyone is refused, run ./health-check.sh: an iamworkbench FAIL is the cause, and ./infra/deploy-workbench.sh the fix.

A notebook in the AI Workbench says "The document is taking some time to load"

Symptom: in a workspace, no notebook or file opens, not even those in medcea-examples; JupyterLab shows "The document is taking some time to load" and keeps waiting. Cause: before 1 November 2026 the workspace installed real-time collaboration at the same time as it started, and the first start of a new home folder began before the install had finished. The browser then asked for documents through collaboration, which the workspace did not serve yet. Now the install finishes before the workspace starts, so this should no longer happen once ./infra/deploy-workbench.sh (or ./deploy-infra.sh) has run and the workspace has been started since. Fix: the person restarts their workspace (File → Hub Control Panel, Stop My Server, then Start My Server), or the administrator stops it from the hub's admin page. If it happens on a workspace started after the deploy, the workspace's log shows why: kubectl -n medcea get pods -l component=singleuser-server names the workspace pods, then kubectl -n medcea logs <pod> | grep medcea-home-setup (a line with WARNING names the install that failed; a later start tries again).

pgAdmin's IoT Postgres server fails with "no password supplied", or shows no username

Symptom: an administrator signed in to pgAdmin opens IoT Postgres and gets "no password supplied", the server's properties show an empty Username, or there is no IoT Postgres server at all. Cause: before 1 November 2026 the entry belonged to pgAdmin's built-in user and was shared; pgAdmin does not share a server's username or password file, so everyone else saw it without them. The password file also belonged to the wrong user, so even the built-in user could not use it, and pgAdmin 9.19 reads a password file only from the signed-in person's own storage folder (an absolute path elsewhere, and PGPASSFILE, are ignored). Now each admin gets an entry of their own when pgAdmin starts, with a copy of the password file in their storage folder, but only for the addresses the last ./deploy-infra.sh listed. Fix: run ./deploy-infra.sh, then ./health-check.sh; pgadminroles names any address still without its entry. The account must be enabled, hold admin and have an e-mail address in Keycloak on an ordinary domain (not .invalid, .test, .example or .local). pgAdmin writes one line per address to its log (kubectl -n medcea logs deployment/pgadmin | grep oauth2-servers).

The System Configuration UI fails after a realm key rotation

Symptom: after a signing key was rotated or removed in Keycloak, the System Configuration UI's data calls are refused and the health check shows postgrest FAIL naming key ids the realm no longer publishes. Cause: config-api and the Python services verify tokens against the keys published at the last ./deploy-infra.sh; config-api reads them only when it starts. Fix: run ./deploy-infra.sh. It republishes the keys and restarts config-api when they changed.

The Config UI stops answering for a few seconds during a switch

Symptom: while IAM_POSTGREST_JWT is switched in either direction, the System Configuration UI's requests fail for up to about 15 seconds. Cause: by design. config-api's database password changes in the same step as its mode, and nothing serves until the new pod is ready. Fix: none needed; do the switch when nobody is editing configuration, and reload the page afterwards.

Node-RED stores no telemetry after a deploy

Symptom: the Monitor and Grafana show no new readings, and the health check shows noderedflows FAIL with "Node-RED runs no flows". Cause: Node-RED started on a new, empty volume (the first deploy that gave it one, or a fresh install). Fix: run ./apps/node-red/deploy.sh.

The Node-RED editor keeps reloading or refuses an engineer

Symptom: an engineer passes the platform sign-in, but the Node-RED editor reloads in a loop or shows its own sign-in form that accepts nothing. Cause: Node-RED's own sign-in cannot work, for example its sign-in module could not be installed (noderedauth FAIL) or Keycloak refuses its callback. Fix: run ./deploy-infra.sh. Break-glass, when the editor is needed at once: microk8s kubectl -n <namespace> set env deployment/node-red NR_ADMIN_AUTH=off turns the editor's own sign-in off (only the platform sign-in remains, which admits engineer only). It restarts Node-RED. While it is off, any program on the platform host or inside the cluster that can reach Node-RED can use its admin interface without signing in, so keep it brief. The next ./deploy-infra.sh turns it on again and records a break_glass_seen event in the access policy history with the time Node-RED started without its sign-in; noderedauth FAILs until then.

Ending every Node-RED editor session

Symptom: you need every engineer signed out of the Node-RED editor now, for example after a role removal or when an editor token may have been exposed. Cause: Node-RED keeps editor sessions on its volume (/data/.sessions.json), so a restart alone does not end them; each lasts up to one hour from when it was issued. Sessions issued before 1 November 2026 were set to last a week; at each start Node-RED now drops every stored session longer than the hour, so the restart of that day's ./deploy-infra.sh ended them (its log says how many). Fix: clear the session file and restart Node-RED. Flows and palette modules are not affected:

microk8s kubectl -n medcea exec deployment/node-red -c node-red -- sh -c ': > /data/.sessions.json'
microk8s kubectl -n medcea rollout restart deployment/node-red

Engineers sign in again on their next visit. Telemetry ingest pauses for the few seconds the restart takes.

A newly onboarded board's first MQTT connections are refused

Symptom: right after onboarding, a board restarts once or twice before it publishes. Cause: its credential is registered after it boots and reaches the broker at the next sync, up to about 15 seconds later. Fix: none; the retry succeeds. A board flashed before the broker required credentials has none, never connects and must be onboarded again.

A change to the sign-in page does not show

Symptom: the login page still looks the same after you changed the theme files. Cause: Keycloak caches themes and never re-reads them while running. Fix: run ./deploy-infra.sh; it restarts Keycloak when the theme changed.

A deploy is refused although nothing is running

Symptom: "Another MedCEA deploy is already running", but the deploy you started earlier has ended. Cause: a background process started by that run, or a helm --wait or rollout status left after a plain kill, still holds the lock. Fix: the refusal lists the leftover processes and the kill command for them. Next time stop a run with the group kill it prints (kill -- -<pgid>). See One deploy at a time.

MicroK8s steps fail on Ubuntu 25.10 or later

Symptom: a MicroK8s start or addon enable fails with snapctl … from outside of a snap, or enable rbac dies after "No callback tokens file." Cause: Ubuntu's default sudo is now sudo-rs, which ignores sudo -E, and MicroK8s needs it for every privileged step. bootstrap-infra.sh switches to classic sudo for its own duration and restores the setting afterwards, so deploys work; a MicroK8s command you run by hand does not get that. Fix: by hand, run sudo update-alternatives --set sudo /usr/bin/sudo.ws, then the microk8s command, then sudo update-alternatives --auto sudo.

Other devices cannot open *.medcea after a server rebuild

Symptom: the host opens every page, laptops and phones on the tailnet do not. Cause: Tailscale split DNS still points at the old server's IP. Fix: change it in the admin console as ./deploy-infra.sh prints (see DNS and Tailscale).

An operator sees an empty Monitor

Symptom: an operator signs in but sees no telemetry or runs and cannot start a run. Cause: no unit is in effect for them, either none assigned or an assignment still waiting for qa. Fix: apps/iam/units.sh list <username>; assign a unit with --by and have a qa person confirm it in the User Manager's Decisions tab.

A deploy fails with "metadata.annotations: Too long"

Symptom: an app deploy stops with The ConfigMap "…" is invalid: metadata.annotations: Too long: must have at most 262144 bytes. Cause: kubectl apply keeps a copy of the whole object in an annotation, and annotations hold at most 256 KiB, so a ConfigMap carrying a large page cannot be applied. The Configuration UI's page (apps/frontend/html/index.html, about 254 KB) reached that limit on 31 October 2026. Fix: the frontend and scheduler deploys replace or create their page ConfigMap instead of applying it, so pull and deploy again. A deploy script that still applies a large file needs the same change (kubectl replace when the ConfigMap exists, kubectl create otherwise).

A qa decision cannot be confirmed

Symptom: a decision about the only qa person's own account, or one they made, waits forever. Cause: the person who checks a decision is never its maker or its subject. Fix: another qa person confirms it. With no enabled qa person at all, set a new QA_USER in config.env and run ./deploy-infra.sh (break-glass, outside the decisions).
