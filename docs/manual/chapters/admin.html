Running the platform

This chapter is for the administrator who runs the MedCEA host. It covers installing the platform with ./install.sh, the deploy scripts and the order they run in, the rule that only one deploy runs at a time, and ./medcea.sh, the question-and-answer front end to all of these commands. It then explains the seven IAM switches in config.env that turn the access controls on step by step (and WORKBENCH_ENABLED, which medcea.sh switches the same way), which of them a fresh install leaves off and how to turn those on, what the health check reports, which IAM test scripts to run and what a good result looks like, how operators are given units, how to uninstall, how the domain names reach other devices through Tailscale, and the credentials file. It ends with troubleshooting for problems an administrator can meet. Run every command from the repository root on the host.

Installing and updating

./install.sh is the one entry point. It runs three stages in order: the infrastructure (./deploy-infra.sh), every application (./deploy-apps.sh --all), and the health check (./health-check.sh). While IAM_DB_SERVICE_ROLES is true (a new config.env's default since 8 November 2026) it runs the infrastructure once more between the applications and the health check, and says why ("IAM_DB_SERVICE_ROLES is true: the infrastructure runs once more, so Grafana and pgAdmin move onto their own database roles (svc_grafana, rr_admin_login) now that the database lets them log in."): Grafana and pgAdmin are deployed by the first stage, before the database deploy in the applications stage lets their roles log in. It is the switch's own enable recipe, under the same deploy lock; a failure stops the install like any stage. The same command updates an existing install: finished steps are skipped or updated in place, so it is safe to run again after a pull or after a failure. If a stage fails, the script stops, names the stage and its log file in logs/, and tells you to fix the cause and run it again.

config.env and the setup questions

All settings live in config.env in the repository root. It is not in git and is readable only by its owner (mode 600), because it holds every platform password. You do not write it by hand: the first run of ./deploy-infra.sh (or ./install.sh) creates it from config.env.example by asking questions. Press Enter to accept the value shown in brackets. Later runs ask only for required values that are still empty. To review every setting, run ./deploy-infra.sh --configure, or ./infra/configure.sh to edit the settings without deploying.

The questions cover:

  • Project name (PROJECT_NAME, default medcea): the MQTT topic root, the Kubernetes namespace and the Keycloak realm. Lowercase, starting with a letter, 2 to 31 characters from a-z 0-9 -. Changing it after boards are flashed means reflashing them.
  • Domain (DOMAIN): every web page is served at <service>.<DOMAIN>. The menu offers a name (for example medcea, so the portal is portal.medcea) when Tailscale is up, the Tailscale or LAN IP with nip.io, or a custom domain you provide DNS for. Changing the domain later means running ./deploy-infra.sh again.
  • The platform administrator: username, a real e-mail address you read (Keycloak password resets go there, and it is the pgAdmin login) and password. Addresses on special-use domains (.local, .test, .invalid, .example, .localhost, .arpa, .onion) are refused here and for the qa person and the engineer: pgAdmin will not start with one.
  • The first qa person and the first engineer: username and e-mail for each. The qa person must be someone other than the administrator. Their initial passwords are generated and replaced at their first sign-in.
  • The PostgreSQL superuser password, the database volume size, and your Docker Hub username and access token (needed to pull the Bitnami Helm charts).
  • On the first run (no config.env yet) and on a full review (--configure): the time zone for Node-RED flows and schedules; the backup folder (BACKUP_DIR, an absolute path, default /var/backups/<project>; better on another disk than the data's, and when you cannot write its parent the applications stage asks for sudo once to create it) and the days to keep backups (BACKUP_KEEP_DAYS); and whether to deploy the AI workbench.

Some values are generated and never asked: the qa and engineer initial passwords, the Keycloak break-glass console account (kc-breakglass) and its password, and the passwords of the database service roles. Configuration also checks for Tailscale on every run. USE_TAILSCALE records whether the domain depends on it: when it is true, a deploy stops if Tailscale is down, rather than quietly falling back to the LAN address.

Password rules

A password you type must be 8 to 64 characters from A-Z a-z 0-9 . _ ~ - only. Other punctuation breaks the URLs and YAML files the password is written into, so the question asks again. Password input is hidden and typed twice. Pressing Enter generates a 20-character password (or keeps the current one if there is one), shows it once, and lists it in the credentials file.

Every command writes its own log in logs/ (readable by the platform user only): deploy-infra-<timestamp>.log, deploy-apps-…, a component deployed on its own app-<component>-deploy-… (or -uninstall-…), app-iam-units-…, deploy-workbench-…, health-check-…, the throwaway database test iam-db-fixture-<command>-… and each live test iam-<name>-…. A command run by another (a component by ./deploy-apps.sh, a test by the fixture) writes into its caller's log. The first line of the output names the file. MEDCEA_NO_LOG=1 turns it off for one run.

Configuration runs before the deploy log starts, so your answers and generated passwords never reach logs/. Its host package check is the exception: when a package is missing, what it reports, its question and apt-get's output go to logs/prereqs-<timestamp>.log (your answer and the sudo password do not), so a deploy stopped there still leaves a record. When configuration rebuilds config.env on a newer config.env.example (keeping your values), it saves the previous file as config.env.bak.

The deploy scripts and their order

install.sh is a thin wrapper. Each stage also works on its own, and after the first install you will usually run the stages directly.

The order rules are:

  • Infrastructure first. The applications need the cluster, Keycloak and PostgreSQL that deploy-infra.sh creates. ./install.sh --apps-only refuses without config.env.
  • Database before scheduler. deploy-apps.sh runs components in alphabetical order, so database comes before scheduler. When you deploy them one by one, run ./apps/database/deploy.sh first: the scheduler deploy refuses until the database functions it needs exist.
  • Access after infrastructure. Run ./deploy-infra.sh, then ./apps/access/deploy.sh. The access deploy runs the database deploy itself when it needs to. Since 1 November 2026 the order also matters for Sign out: ./deploy-infra.sh registers the AI Workbench's logout address with each app's sign-in, and the access deploy then points Sign out at it. In the other order, Sign out shows Keycloak's "Invalid redirect uri" and ends nothing until ./deploy-infra.sh has run.
  • After a pull of new IAM code: ./deploy-infra.sh (the route table), then ./apps/database/deploy.sh, then ./deploy-apps.sh --all while no recipe run is active. Until all three have run, the health check's iamgrants and tests/iam-schema.sh stay red.
  • From IAM 4.2a, every deploy that compiles the access policy reads the applied version from PostgreSQL first and refuses while PostgreSQL is not Ready; ./deploy-infra.sh repairs PostgreSQL before it reads the policy, so run it first in that case. A git change that gives access is refused by every deploy (see The skeleton gate).
  • iam-api (the iam component, IAM 3.5) after ./apps/database/deploy.sh and ./apps/access/deploy.sh: alphabetical order already does this. While IAM_DB_SERVICE_ROLES is false (an older config.env) it is skipped with a warning. A new config.env has it true, so a fresh install deploys iam-api and the Access Policy; there, confirming and approving answer "need IAM_POSTGREST_JWT=true and IAM_DB_ROLES=true" until both switches are on. Then turn on IAM_MQTT_PERSON (see IAM switches).
  • After rotating or removing a realm key in Keycloak, run ./deploy-infra.sh. It republishes the keys and restarts config-api when they changed.
  • pgAdmin restarts whenever ./deploy-infra.sh changes its sign-in settings (pgAdmin's client secret, the roles it admits, or ADMIN_PASS), which signs everyone out of pgAdmin; a run that changes none of them leaves it running. Only on an install deployed before 1 November 2026 (not after a fresh install, where the secret never left the Kubernetes Secret): the first ./deploy-infra.sh after that date restarts pgAdmin once, when its secrets move into a Kubernetes Secret, and removes the older copies of pgAdmin's deployment that still held them; pgAdmin's client secret was readable in plain text until then, so give it a new one once: in the Keycloak console, realm medcea, Clients, pgadmin, Credentials, Regenerate; then run ./deploy-infra.sh, which reads the new secret and restarts pgAdmin.
  • pgAdmin's IoT Postgres entry is loaded for each account that may sign in to pgAdmin when pgAdmin starts. ./deploy-infra.sh lists the e-mail addresses of the enabled Keycloak accounts holding a role pgAdmin admits (admin) and gives the list to pgAdmin; when the list changed, pgAdmin restarts (everyone is signed out of it) and loads the entry for each address, which can add several minutes to its start. So after giving someone the admin role, or changing an admin's e-mail address, run ./deploy-infra.sh: until then they can sign in to pgAdmin but see no server. An account without an e-mail address, or with one on a reserved test domain such as .invalid, .test or .example (pgAdmin refuses those), gets no entry; the deploy names it in a warning. If Keycloak cannot be read, the deploy keeps the list pgAdmin already has, so nobody loses their entry, and says so; only when pgAdmin has no list yet does it go on with the platform administrator's address alone. Since 1 November 2026 pgAdmin runs version 9.19.0, pinned in k8s/pgadmin/pgadmin.yaml; on an install from before that date the first ./deploy-infra.sh after it restarts pgAdmin once.
  • Node-RED after ./deploy-infra.sh: when Node-RED's settings changed, the deploy restarts it. Its flows are kept on a volume and survive. The first deploy onto that volume (and a fresh install) starts with no flows; the deploy then says "Node-RED runs no flows" and telemetry is not stored until you run ./apps/node-red/deploy.sh. Do that first deploy while no recipe run is active.

The scheduler runs recipe code straight from the repository (schd/), and the onboarding wizard runs edge/ from it. Do not pull or edit the repository while a recipe run is active: check first that pgrep -af '[r]un_recipe.py' prints nothing.

When your login session is not yet in the microk8s group (for example right after the first install added you to it), the scripts run their microk8s calls through sudo and say why they ask for your password. Log out and back in to stop that.

IAM 4.1: deploying the policy versions schema

Slice 4.1 adds the database side of policy versions (migration 008c), a function the access component installs (iam._changed_since) and every Phase 4 entry of the access policy. Nothing calls them yet. After pulling it, run three deploys in this order, back to back, best through ./medcea.sh → Policy → Deploy IAM 4.1, which holds the deploy lock for all three:

  1. ./apps/access/deploy.sh. It must come first: the database deploy refuses without iam._changed_since ("run ./apps/access/deploy.sh first (IAM 4.1)"), and the health check's iamgrants is red from the pull until this step.
  2. ./apps/database/deploy.sh: migration 008c, the compiled functions and the grants.
  3. ./deploy-infra.sh, at once: the new route table, which the User Manager reads within a minute, and the NetworkPolicies.

From the end of step 2 until the User Manager has read the route table of step 3 (about one to two minutes), the User Manager answers 503 to a grant, an activation, or a role change into qa, qp, admin or auditor: the database and the route table disagree about what such a change widens (the new policy_page row). Do not grant or change roles until all three deploys have finished. A refused decision changed nothing and can simply be repeated. Every other decision and every other service is unaffected.

Between steps 2 and 3 the health check's iamgrants and tests/iam-schema.sh are red; after step 3 and one minute, everything is green. To take slice 4.1 back out, while no policy version exists: run apps/database/medcea_db_migrations_down_008c.sql as postgres in one transaction (the command is in its header), then revert the code, then ./apps/database/deploy.sh and ./deploy-infra.sh; the 503 window opens in reverse. The down file refuses once a version exists.

IAM 4.2a: version 1 and the skeleton gate

Slice 4.2a turns the access policy into numbered versions on this host. The database records version 1 (the factory policy of apps/iam/policy/defaults.yaml, applied at once), every deploy then compiles from the applied version (the host file state/policy-applied.yaml, see Policy source), and every deploy runs the skeleton gate. Nobody's access changes: version 1 compiles to exactly what defaults.yaml compiled to before. After pulling it, check that git status -- apps/iam shows nothing (the bootstrap refuses uncommitted changes there), then run three deploys in this order, back to back, best through ./medcea.sh → Policy → Deploy IAM 4.2a, which asks your username (--by) and holds the deploy lock for all three:

  1. ./apps/database/deploy.sh: the 4.2a database functions (the policy's system actors, the event rules, the filter of the policy history) and the grants. It must come first: the other two record events through these functions.
  2. ./deploy-infra.sh, at once: the route table's digest moves once (it no longer counts the name of the policy file), and the accounts the install seeded are recorded in the policy history (account_seeded, see the policy history).
  3. MEDCEA_POLICY_BOOTSTRAP_BY=<your username> ./apps/iam/deploy.sh: no policy version exists yet, so it runs ./apps/iam/apply.sh --bootstrap --by <you> (without the variable, the platform administrator ADMIN_USER is named). It checks every compile is unchanged, writes version 1 in one database transaction, writes state/policy-applied.yaml, checks the grants, records bootstrap_applied, and restarts iam-api as every iam deploy does.

There is no 503 window: no grant or role changes. Between steps 1 and 2 the health check's iamenforce and tests/iam-schema.sh are red for a few minutes, because the database and the route table disagree about the digest; after step 2 they are green. Step 3 prints [iam] Policy versions..., then the bootstrap's lines (state empty, the tree's commit, the account you named, "version 1 compiles to exactly what defaults.yaml compiles to (N targets): nothing is re-rendered", [policy] state/policy-applied.yaml: version 1 (bootstrap) written, the grants check, the report) and ends "version 1 (bootstrap) applied: nothing was re-rendered". The health check then has two more checks, 54 in all (55 since the Platform manual check of 3 November 2026, 56 since the Superset roles check of 6 November 2026): Access policy version (OK: "version 1 (bootstrap), qa confirms it in the Policy UI once it exists (IAM 4.3)") and Policy artefacts (OK; the Policy UI's host is counted as not deployed). Then run tests/iam-schema.sh and ./apps/iam/apply.sh --status.

If the bootstrap waits (Keycloak not reachable, or a --by that is not an enabled account with a person_id), the iam deploy warns and finishes, and Access policy version FAILs "no applied version: a widening git change is not gated until version 1 exists" until ./apps/iam/deploy.sh runs again. On a fresh install the same happens inside ./install.sh: the iam component bootstraps version 1 in ./deploy-apps.sh --all.

Taking slice 4.2a back out. Version 1 and its events stay in the database, frozen; the down file of 008c refuses while they exist, by design. Under the deploy lock, while the 4.2a code is still there, move the host's policy files aside: bash -c 'source infra/lib-lock.sh && medcea_lock && source infra/lib-policy-source.sh && policy_state_retire rollback' (it moves state/policy-applied.yaml, state/seed-facts.jsonl, state/break-glass/ and the mark state/.policy-versioned into state/retired-<time>-rollback/; the 4.1 code refuses a host file). Then revert the slice in git, run ./apps/database/deploy.sh (the 4.1 functions come back) and ./deploy-infra.sh (the route table's digest moves back once). Applying 4.2a again later finds version 1 and does not bootstrap again.

The applied access policy

From slice 4.2a the access policy in force is the database's applied version, not the file in git. apps/iam/policy/defaults.yaml stays the factory file: version 1 was made from it, and it still holds the platform's skeleton (roles, resource groups and their routes, hosts, the network rules, the invariants: everything but the matrix of who holds which level, and the waivers). The matrix and the waivers come from the applied version.

IAM 4.3: the Policy UI

Slice 4.3 (November 2026) adds the Access Policy at https://policy.<domain>: iam-api serves it on a second port (8083, Service iam-admin) behind its own sign-in proxy (iam-oauth2-proxy, Keycloak client policy). Nobody's access changes and the policy is not changed. Run three deploys in this order, best through ./medcea.sh → Policy → Deploy IAM 4.3 (the Policy UI), which holds the deploy lock for all three:

  1. ./deploy-infra.sh: the Keycloak client policy (with groups, person_id and the medcea-api audience), policy.<domain> in the certificate and the name service, the portal's Access Policy card, and POLICY_DOMAIN, POLICY_CLIENT_SECRET and POLICY_COOKIE_SECRET in config.env.
  2. ./apps/access/deploy.sh: the User Manager's Access Policy link, and Sign out on the new address.
  3. ./apps/iam/deploy.sh: ConfigMap iam-compiler (the policy compiler and the factory file, about 360 KiB, applied server-side), iam-api with its second port, then the sign-in proxy. Like the User Manager's, the proxy admits admin only until every iam-api pod answers on port 8083 that it enforces, then admin, auditor, qa and qp; without that answer the deploy stops with "the Policy UI's gate stays admin-only".

Afterwards the health check has one warning on purpose: Access policy version "version 1 (bootstrap) is not confirmed by qa yet (the Policy UI)", until a qa person confirms it (exercise E16). From then on the check also fails when the Policy UI shows another applied version than the database, and warns when it ships another skeleton than the accepted one (run ./apps/iam/deploy.sh). ./apps/iam/deploy.sh --gate-only re-renders the Policy UI's proxy when it drifted. To remove it: ./apps/iam/uninstall.sh (the proxy, the second port, the compiler ConfigMap and the card); the Keycloak client stays, and a confirmation already recorded stays in the history.

IAM 4.4: drafting and approval

Slice 4.4 (November 2026) lets an admin draft a change to the access policy in the Access Policy and a qa person approve it there, and lets the host operator propose a git skeleton change for the same approval (apply.sh --propose-skeleton, below). Nothing approved is applied in 4.4: applying a version came with slice 4.5 (below). Nobody's access changes, no grant changes and there is no 503 window. Run two deploys in this order, best through ./medcea.sh → Policy → Deploy IAM 4.4 (drafting and approval), which holds the deploy lock for both:

  1. ./apps/database/deploy.sh: the new bodies of the policy's approve and why-not functions (break-glass blocks approvals; a skeleton version needs the attestation, a fresh proposal and an approver whose role it does not widen). No new table, column, function or grant.
  2. ./apps/iam/deploy.sh: iam-api with the write side of the Policy UI, the new page, and ConfigMap iam-compiler with the new diff code (its checksum restarts iam-api).

In the minute between the two the old page still serves and cannot write: harmless. ./deploy-infra.sh and the access deploy are not needed (the route table, the proxies and the clients do not change). Approving needs IAM_POSTGREST_JWT and IAM_DB_ROLES to be true, as confirming does. The health check stays green after the deploy. It WARNs "version N (<kind>) is approved: ./apps/iam/apply.sh N --by <you> applies it" (since slice 4.5; until then "applying it arrives with IAM 4.5") for as long as an approved version waits, "skeleton version N was proposed against skeleton …, the accepted one is now …: return it and propose again" when a deploy accepted a narrowing under a proposal, and, as before, an open version older than 7 days.

Taking slice 4.4 back out.

  1. ./apps/iam/apply.sh --status must show no open change or skeleton version. If one is open, withdraw it: in the Policy UI (an admin, while the 4.4 page still serves), or from the host with ./apps/iam/apply.sh --withdraw-open --by <you> --reason "<why>" (when the page is the reason for the rollback, or after the revert: the 4.3 page has no Withdraw). Last resort, with the 4.4 apply.sh already reverted: SELECT iam_policy._withdraw_open('<reason>') as postgres in the PostgreSQL pod (actor system:apply). An approved 4.4 version must not survive a revert of 4.4: it was approved under 4.4's checks, which the reverted code no longer makes, and slice 4.5 could otherwise apply it.
  2. Revert the slice in git.
  3. The same two deploys.

What stays, by design: the withdrawn and approved versions, their events and their evidence (permanent); a proposed skeleton that was never accepted (harmless). The reverted approve function no longer refuses under break-glass and no longer checks skeleton versions.

IAM 4.5: applying versions

Slice 4.5 (November 2026) applies what a qa person approved: ./apps/iam/apply.sh N --by <you> for a change or skeleton version, ./apps/iam/apply.sh --rollback-to K --by <you> --reason "<why>" to restore an earlier version, and ./apps/iam/apply.sh --audit N to check an applied version afterwards (apply.sh). The deploy itself changes nobody's access, no grant and no gate, and has no 503 window. Run four deploys in this order, best through ./medcea.sh → Policy → Deploy IAM 4.5 (applying versions), which holds the deploy lock for all of them:

  1. ./apps/database/deploy.sh: new_draft refuses a draft while the applied version's last apply event is unfinished (apply_started or partial_apply), whatever events were filed after it.
  2. ./apps/access/deploy.sh: the User Manager reads who approves and who makes account changes from the route table's dual_control, not from a list in its code (proof-gated as before; no access change).
  3. ./apps/iam/deploy.sh: the Access Policy shows the apply states ("applied — rollout incomplete", "approved — a previous apply was reverted") and a rollback's Confirm card; ConfigMap iam-compiler carries the new compiler code, so iam-api restarts.
  4. ./apps/backup/deploy.sh: the nightly backup's MANIFEST names the policy history's head (its id and hash) at the time of the dump.

apply.sh, its checks and health-check.sh run on the host and need no deploy. After the deploy the health check stays green; it WARNs "version N (<kind>) is approved: ./apps/iam/apply.sh N --by <you> applies it" while an approved version waits.

Taking slice 4.5 back out. First ./apps/iam/apply.sh --status: no version may be left apply_started or partial_apply (any outcome: run --resume first), and no open change or skeleton version (withdraw it). Then revert the slice in git and run the same four deploys. The versions applied by 4.5 stay applied and keep their events; the 4.4 code reads them as it reads version 1.

Policy source

Every compile of the policy (every deploy, the health check, the onboarding wizard, flash-device.sh) reads the host file state/policy-applied.yaml when it exists. It is the applied version composed with the accepted skeleton, written by the deploy scripts under the deploy lock: by ./apps/iam/apply.sh after it applies a version, and by every deploy that finds it missing or different from the database. Nobody edits it by hand. state/ is readable by the deploying account only (mode 700, the file 600) and is not in git. Its first two lines say what it is:

# medcea-applied: version=1 kind=bootstrap entries_digest=… skeleton_digest=… git_commit=… written_at=…
# medcea-applied-body: body_digest=… groups=… roles=… dropped=0 keys=…

Every compile checks those lines against the body: a file edited by hand or cut short stops every deploy and the onboarding wizard with "its header does not match its body (edited by hand, or truncated)". Restore it with ./apps/iam/apply.sh --resume --by <you> if an apply was interrupted, or with any deploy, which rewrites it from the database. Health compares the whole body with the database's rows as well (Access policy version).

Before compiling, each deploy reads the applied version from PostgreSQL:

  • No version yet (before the bootstrap, or before migration 008c): the deploy compiles defaults.yaml. A host file at that point is refused: "state/policy-applied.yaml names a version but the database has no policy versions".
  • PostgreSQL not Ready: the deploy refuses and compiles nothing, with or without a host file. ./deploy-infra.sh is the one that repairs PostgreSQL: right after the Kubernetes API answers it only checks the skeleton gate (when the database can be asked; a widening git change stops it there, before anything changes), and it reads the applied policy only after its PostgreSQL step, so run it first. ./deploy-apps.sh asks PostgreSQL once before its first component that compiles the policy and stops the whole run when it is not Ready.
  • A host file without its database (after a restore of an older dump, or a database dropped by hand): restore the database the file belongs to, or move the file aside with policy_state_retire as in Restoring step 2a, only after reading this section. The next deploy then writes it again from the database. apps/database/uninstall.sh --purge-data (after its DROP), ./deploy-infra.sh --reset (after the namespace is gone) and --uninstall (after MicroK8s is removed) do this themselves, under the deploy lock, into state/retired-<time>-<why>/; nothing is deleted.
  • A version was applied here, but the host file is missing: the first host file also writes the mark state/.policy-versioned. While it exists, a compile outside a deploy (the onboarding wizard at its start, flash-device.sh) refuses "state/policy-applied.yaml is absent, but a policy version was applied on this host" instead of falling back to defaults.yaml, which may hold an unreviewed change. The next deploy writes the file again. A restore's step 2a keeps the mark; a deploy that then finds a database with no applied version (a dump older than the bootstrap) moves the mark into state/retired-<time>-no-version/ itself. A purge, a reset and an uninstall move it with the rest.
  • Versions exist but none is applied: refused; see ./apps/iam/apply.sh --status.

What these checks defend against, and what they do not. They stop a widening of access from reaching a deploy through the platform's own tools: a change in git, a variable left exported in a shell, a file edited during a deploy, a stale or hand-edited state/ file, a cold or crashed PostgreSQL, a restore or a purge. They do not stop the account that deploys the platform from going round them on purpose (it can run psql as postgres, edit the scripts, or rewrite the host file with recomputed digests): that is the host operator's break-glass, found afterwards through the policy history, the version audit and the health check, not prevented. A host file forged that way passes the compile's own checks, is found by the health check, and is overwritten by the next deploy; the onboarding wizard can compile it in between (see known gaps).

Two edge cases: flash-device.sh run from another clone of the repository, which has no state/, compiles defaults.yaml (harmless while version 1 equals it; it matters once a later version differs, IAM 4.5). The onboarding wizard compiles once when it starts, so a new applied version reaches it only at its next restart (./apps/edge-wizard/deploy.sh --gate-only restarts it only when its roles changed).

The skeleton gate

Every deploy compares the skeleton in git with the skeleton the platform accepted last. A change that gives access is refused before anything is compiled or changed. It counts as giving access when it adds, for any role: a route, a host, a database privilege or row filter, a tool setting, an MQTT topic or a level; and also, for nobody in particular: a route anyone may call without signing in, an upstream every signed-in host reaches, a host's service or client, a network source allowed into a pod, a host outside the sign-in proxies, a hop or a token client of a calling pod, any privilege or membership of a service identity, any database row filter, and any weakening of the checker's own rules (the invariants, the waivable list, break-glass, the database roles, the levels, the resource types, the classes, the constraints, the schema version). Help texts and descriptions do not count. The deploy stops with:

ERROR: this git change gives access that has not been approved (skeleton <git> over the accepted <accepted>):
  <role>: <n> new: route iam GET /api/… ; …
  anonymous and services: public monitor GET /api/… ; …
This change needs a qa-approved skeleton version: put HEAD back at the accepted skeleton, keep the change as a commit on a branch, and run ./apps/iam/apply.sh --propose-skeleton --by <you> --reason "<why>" --from-git <commit>; once qa approves it, check that commit out and run ./apps/iam/apply.sh <version>.
Break-glass (MEDCEA_POLICY_FILE) does not bypass this check: it changes the matrix, never the skeleton.
Nothing was changed.

The network rules count in full: besides each pod's allowed sources, any change to how a source is resolved (the ingress namespace, a proxy's release name, a pod's or a calling pod's selector, the ports a pod carries, a calling pod's only_rpc list, the hosts that skip the shared upstreams) is a change that gives access, and so is any change to a database role name, a service identity's MQTT login or database password variable, or the MQTT Explorer's credential settings. Removing an allowed source, a rule, a hop, a resource group or a role only narrows. A key the gate does not know yet counts as giving access too (developers classify it in apps/iam/compiler/explain.py; tests/test_policy_source.py fails until they do). The refusal names such a change "section <key> changed".

The way forward for such a change: put HEAD back at the accepted skeleton, keep the change as a commit on a branch, and propose that commit as a skeleton version (./apps/iam/apply.sh --propose-skeleton --by <you> --reason "<why>" --from-git <commit>, since slice 4.4); a qa person approves it in the Access Policy. While the proposal waits, the deploying tree stays at the accepted skeleton; a tree that carries it is refused by every deploy, and the health check FAILs "the git skeleton widens: a deploy refuses it (proposed as version N, <status>: put HEAD back at the accepted skeleton; the proposal waits on its branch)". Once it is approved, check its commit out and run ./apps/iam/apply.sh N --by <you> (since slice 4.5): the gate lets through exactly the approved skeleton, and only when HEAD contains the proposal's commit; the refusal then reads "This skeleton is approved as version N: run ./apps/iam/apply.sh N --by <you> to apply it (deploys refuse it until then)".

Keep the skeleton commit on the deployed branch. Once skeleton version N is applied, the accepted skeleton is that commit's. A checkout that drops it (an older branch, a reset) is a narrowing to the next deploy, which accepts it without asking: the approved access is silently gone. To undo an applied skeleton version on purpose, git revert the skeleton change and deploy (the deploy accepts the narrowing and records it), plus --rollback-to for the matrix if needed. A skeleton version is never reverted automatically.

A change that only narrows access, or changes nothing a person can reach, is checked first: the git skeleton with the applied matrix must pass the policy checker, otherwise the deploy refuses "the git skeleton … with the applied matrix fails the checker; it is not accepted and nothing was changed" (fix the change in git). When it passes, it is accepted by the next deploy and recorded (skeleton_accepted, with the skeleton it replaced, and skeleton_synced); the health check WARNs "the git skeleton narrows: accepted at the next deploy" until then. A change to the matrix: in git is not refused but has no effect: the matrix comes from the applied version (the health check WARNs "git may lag"). ./apps/iam/apply.sh --status shows the accepted and the git skeleton; developers check a change offline with python3 apps/iam/compiler/cli.py skeleton-gate --against-git HEAD --check.

Policy break-glass

When a deploy must compile another matrix than the applied version's (an emergency, before approvals exist), break-glass names a policy file of your own for one run: MEDCEA_POLICY_FILE=<file> MEDCEA_POLICY_BREAK_GLASS="<reason>" ./apps/<component>/deploy.sh (or ./deploy-infra.sh). Without the reason the deploy refuses ("set MEDCEA_POLICY_BREAK_GLASS=<reason>"). For several components at once, export MEDCEA_POLICY_FILE and run ./deploy-apps.sh [--all] --break-glass "<reason>" (asked once, one event naming every selected component that compiles the policy) or ./install.sh --break-glass "<reason>" (asked once, two events: the infrastructure and the applications). Without --break-glass, deploy-apps.sh and install.sh ignore an exported MEDCEA_POLICY_FILE and say so. ./medcea.sh → Policy → How to use policy break-glass shows the same and runs nothing.

  • Break-glass does not bypass the skeleton gate. A git change that gives access is refused under break-glass too, before anything is recorded.
  • It changes only the matrix and the waivers. The file's skeleton must equal the accepted one, and its rows for iam_policy and iam_users must equal the applied version's: break-glass can never change who approves policy or account changes.
  • The deploy prints the file and the reason and asks you to type the word break-glass at the terminal (deploy-apps.sh/install.sh --break-glass ask once for the whole run); without a terminal it refuses.
  • The file is copied to state/break-glass/<time>-<pid>.yaml; that copy is what is compiled, so editing the original afterwards changes nothing. The copy stays as evidence.
  • Before any compile, the deploy records break_glass_seen in the policy history (the copy's SHA-256, the reason, your OS account, the component) and prints in red "BREAK-GLASS: compiling … recorded as event N".
  • The health check's Access policy version FAILs while it is open. It ends per component: that component's next successful deploy without MEDCEA_POLICY_FILE records break_glass_ended as its last step (a deploy that fails leaves it open). ./deploy-infra.sh (infrastructure and, when enabled, the AI workbench) and ./deploy-apps.sh --all end it everywhere. The onboarding wizard's component ends only on a machine with a user session (its deploy skips otherwise).
  • Write the reason and the decision in your operations log.

One deploy at a time

Every script that changes the cluster or config.env takes the deploy lock first: install.sh, deploy-infra.sh, infra/configure.sh, deploy-apps.sh, each apps/<component>/deploy.sh and uninstall.sh, infra/deploy-workbench.sh, apps/iam/units.sh, tests/iam-signin.sh and the other test scripts that create things, and medcea.sh for the length of a switch recipe. health-check.sh, the read-only tests and every --help do not take it. Two deploys side by side would interleave Helm releases, Keycloak clients and rewrites of config.env.

The lock is held by the kernel on the file .medcea.lock in the repository root. It is released the moment the holding process ends, even after kill -9 or a closed terminal, so there is never a stale lock to delete. A script started by another script that holds the lock (for example install.sh running deploy-infra.sh) uses its parent's lock.

Reading a refusal

A refused script prints Another MedCEA deploy is already running: and exits with code 1. What follows tells you who holds it:

  • A running deploy: its PID, start time, terminal and command, then Wait for it to finish, or stop it with: kill -- -<pgid>. Use that group kill, not a plain kill <pid>: a helm --wait or rollout status the run is waiting on would survive and keep the lock.
  • Leftover processes: The run that started it has ended; these leftover processes still hold the lock, with each process and the kill command to stop them.
  • A run as another user, usually under sudo: the holder could not be inspected, and the message suggests sudo fuser -v on the lock file.

medcea.sh reports a held lock without exiting: it says another deploy is running and returns you to the menu with nothing changed.

medcea.sh, the MedCEA menus

./medcea.sh walks you through the platform's commands by question and answer. It is the recommended way to run anything you do not run every day, and the only supported way to change an IAM switch.

The name. Until 9 November 2026 this was ./guide.sh. It is named after the platform, MedCEA, not after your installation's project name: an install whose PROJECT_NAME is something else still runs ./medcea.sh. The old name still works for now: ./guide.sh prints "guide.sh is now ./medcea.sh (this name will be removed in a later release)" and runs ./medcea.sh with the same options. Change scripts, notes and habits to ./medcea.sh: the old name will be removed in a later release.

  1. Run ./medcea.sh, or ./medcea.sh --dry-run to see what it would do without running or changing anything. Every question and confirmation is still asked in a dry run.
  2. Pick an area: Install and uninstall; Infrastructure; Applications; Operators and units; IAM switches (enable or roll back one switch, or bring every switch still off to full enforcement); Health and tests; Edge devices; Policy (read-only views; the IAM 4.1 and 4.2a deploys; policy versions: status, would version 1 bootstrap, bootstrap by hand, finish an interrupted apply, print the applied policy; how to use policy break-glass, shown and never run); Backups.
  3. Pick an action and answer its questions. Answers are checked the way the target script checks them (unit codes, usernames, component names that exist on disk), and nothing you type may start with -, so an answer cannot turn into an option.
  4. Read the plan: the exact command, whether it is read-only, changes the platform or is destructive, what it changes, whether it takes the deploy lock, and whether it needs sudo.
  5. Confirm. A read-only command asks [Y/n]; a change asks [y/N]; a destructive one (an uninstall, --purge-data, --reset, --bootstrap, erasing a board) wants the word yes typed in full, and --purge-data also the project name.

  7. At a terminal these steps are dialog boxes (see Dialog boxes and the status header); ./medcea.sh --plain keeps the numbered questions.

medcea.sh never asks for a password or secret: the commands it runs ask for their own. Ctrl+D (end of input) leaves medcea.sh. For units and policy commands it asks for --by, your own Keycloak username, and offers your last answer as the default for the rest of the session.

Switch recipes

For an IAM switch or WORKBENCH_ENABLED, medcea.sh shows the switch's current value, then the recipe for enabling it or rolling it back:

  • Before you start: a checklist of preconditions, which you confirm once. medcea.sh does not test the checklist items for you. Some preconditions it does check itself and refuses the recipe with the reason (for example, enabling IAM_DB_ROLES while IAM_POSTGREST_JWT is not true).
  • Steps, in order: each is either a change to one line of config.env or a command. The recipe takes the deploy lock once for all its steps and stops at the first step that fails, or at Ctrl+C.
  • Notes: what happens afterwards and how to check it.

The switch must be on exactly one active line in config.env; with none or several, medcea.sh refuses and says which lines to fix. A switch that another recipe's order depends on (IAM_DB_ROLES, IAM_POSTGREST_JWT, IAM_DB_SERVICE_ROLES) must be written literally as "true" or "false".

Before the first change, medcea.sh copies config.env to config.env.guide-<timestamp>.bak (mode 600, not in git). It shows only the changed line, never the lines around it, which may be passwords. If a step fails, it tells you whether config.env was already changed and prints the cp -p command that puts the backup back. Restoring the file does not undo the steps that already ran; each step is safe to repeat, so the usual fix is to correct the cause and run the recipe again. After a recipe completes, medcea.sh offers to delete the backup, because it is a full copy with every password. ./install.sh --uninstall-all deletes any backups that are left.

IAM switches → Bring IAM to full enforcement runs the enable recipe of every IAM switch still false, in order, under one lock, and stops at the first problem; running it again resumes. See After a fresh install.

After switching IAM_ENFORCE

The services read the switch on each request from the shared access settings that ./deploy-infra.sh publishes (the medcea-iam-lib ConfigMap), so the change is live within about a minute with no restart. From then on a refused request is answered 401 (no token or a bad one), 403 (the route or role is not allowed) or 503 (the service cannot verify tokens). Each application pod also keeps a copy of the switch from its last deploy, used only if the route-table mount is missing; it stays at the old value until the app is deployed again, and the health check reports iamenforce as FAIL until then. Redeploy the apps with ./deploy-apps.sh --all when no recipe run is active (Bring IAM to full enforcement asks for this at its end). Then check with tests/iam-check.sh, ./health-check.sh and tests/iam-signin.sh.

A rollback of IAM_ENFORCE returns the services to logging "would refuse" within about a minute.

When IAM_MQTT_PERSON changes, ./deploy-infra.sh appends enforcement_enabled or enforcement_disabled with {switch: IAM_MQTT_PERSON} to the same history, and every credential the Explorer is given is an mqtt_credential_issued event naming the person, the role, the topics and the expiry (never the password). Each ./deploy-infra.sh also writes the current values of IAM_GATES, IAM_NETPOL and IAM_POSTGREST_JWT into the route-table settings with the time, which the quarterly access review records.

The services' own database roles from the start

Since 8 November 2026 a new config.env has IAM_DB_SERVICE_ROLES="true", so that Superset, whose data connection is never the database superuser, installs with everything else (decision "Superset installed by default" in the decision record). What that means on a fresh install:

  • ./install.sh runs ./deploy-infra.sh a second time after the applications, so Grafana and pgAdmin move onto svc_grafana and rr_admin_login; afterwards dbclients is OK.
  • pgAdmin holds rr_admin's grants only: it can change no table structure and write no data. For those, use psql in the PostgreSQL pod.
  • The scheduler's log settings become proposals that a qa person approves in the Configuration UI's Approvals tab, which reaches the database through config-api; until IAM_POSTGREST_JWT is on, config-api serves every request as anonymous and the approval is refused, so a proposal waits.
  • iam-api and the Access Policy are deployed; confirming version 1 and approving versions there answer "need IAM_POSTGREST_JWT=true and IAM_DB_ROLES=true" (503) until both are on.
  • Superset is installed when the iam deploy has applied version 1. Its first install downloads three packages from pypi.org (from a pod), besides the images every install pulls; a firewall that blocks PyPI stops it there.

An install that keeps an older config.env (a reinstall that kept it, or an install from before that date) keeps its value: with "false" the infrastructure runs once, Superset is skipped and the install ends with "Still to do: Superset was skipped, it needs IAM_DB_SERVICE_ROLES=true." A config.env with no line for the switch (from before Phase 2.5) is given "false" by the setup, which says so once. Turning it on is the owner's choice: ./medcea.sh → IAM switches → IAM_DB_SERVICE_ROLES, then ./apps/superset/deploy.sh.

The order is: IAM_POSTGREST_JWT; IAM_DB_SERVICE_ROLES (already on, on a new install); assign the operators' units in the User Manager (or with apps/iam/units.sh assign … --by <your username> on the host) and have a qa person confirm them; IAM_DB_ROLES; IAM_ENFORCE (after a report-only trial, see The IAM switches); IAM_MQTT_PERSON; then, with no recipe run active, ./deploy-apps.sh --all, so every app pod's copy of IAM_ENFORCE is true. Until that redeploy ./health-check.sh reports iamenforce FAIL ("pod IAM_ENFORCE copy still false"); after it the IAM checks are OK.

Bring IAM to full enforcement

./medcea.sh → IAM switches → Bring IAM to full enforcement runs that order for you. It uses each switch's own enable recipe, the same one the switch's own entry runs, so nothing in it differs from turning the switches on one by one.

  1. It reads every IAM switch from config.env. Each must be on exactly one active line and written literally as "true" or "false"; otherwise it refuses and changes nothing. If every switch is already true, it says so and stops.
  2. It shows the plan: each switch still false, in the order above (IAM_GATES and IAM_NETPOL only if they are false), with its purpose, its checklist, its steps and its notes. You confirm the whole plan once ([y/N]).
  3. It takes the deploy lock once for the whole chain (refused while another deploy runs), then runs the switches in turn. For each, it asks that switch's checklist when its turn comes, because some items only become true after the switches before it.
  4. Before IAM_DB_ROLES it runs apps/iam/units.sh list under its lock. If an enabled operator has no unit in effect, or the list cannot be read, it says what that means and asks whether to go on; answering no stops the chain there.
  5. Each switch's steps run as in its own recipe: one line of config.env changed, with its own backup, and the deploys in order.
  6. When IAM_ENFORCE was one of the switches, it then asks "No run is active: redeploy the apps now?" ([y/N]) and, on yes, runs ./deploy-apps.sh --all under the same lock, so every app pod carries IAM_ENFORCE="true". On a fresh install no run is active: answer yes. If you answer no, or the redeploy fails, it says that every switch is true but the apps are still to be redeployed, and ./health-check.sh reports iamenforce FAIL until you run ./deploy-apps.sh --all.

On a fresh install, expect a run made soon after the install to stop at IAM_ENFORCE's checklist, whose first item is that a report-only trial is over. Answer no unless the services have already run long enough with "would refuse" lines that are all intended (the trial needs no other switch, so it can run while you work through the earlier ones). Then run the trial (see The IAM switches) and choose the action again: it resumes from IAM_ENFORCE and goes on to IAM_MQTT_PERSON. In the same way, if the operators' units are not yet assigned and confirmed by a qa person, answer no at the question before IAM_DB_ROLES, assign them, and choose the action again.

It stops at the first refused checklist, failed step or Ctrl+C (exit code 130). Ctrl+C while it waits at a question stops it at once, before any step of that switch; during a step it stops once that step's command has ended. It then says which switch stopped and why, which switches are already done, which were not started, and the backups it made. Fix the cause and choose Bring IAM to full enforcement again: switches already true are skipped, so it resumes from the one that stopped. If that switch's own line was already set to true before its steps failed, put its backup back first, using the cp -p command medcea.sh prints (only that switch changes back), or finish it with its own entry in IAM switches. Do not put back an earlier backup: it would turn off switches whose deploys already ran. After a complete chain medcea.sh offers to delete the backups.

./medcea.sh --dry-run shows the plan and every command and config.env change, without running anything, changing anything or taking the lock.

The health check

./health-check.sh checks every service and IAM control listed in health-checks.conf and prints one line per check. It is read-only and does not take the deploy lock. Options: --verbose shows detail for passing checks too, --timeout SECS sets the per-check timeout (default 8), --config FILE reads another check list.

ResultMeaning
OKThe check passed.
WARNNot broken, but not in its final state: for example a switch still false, a pod's copy of a setting that is out of date, or a decision waiting a long time.

Operators and units

An operator works in the units they are assigned to. Once IAM_DB_ROLES is true (or IAM_ENFORCE), an operator sees the telemetry, runs and run logs of every zone of their units, including zones added later, and starts or stops runs only there. An operator with no unit in effect sees an empty Monitor and can start nothing.

Since 12 November 2026 an administrator assigns units in the User Manager. apps/iam/units.sh stays as the path on the platform host: for --bootstrap, for an account Keycloak no longer has, and as break-glass when the User Manager cannot be used.

In the User Manager

  1. Open Users and select the operator's account. The Units section lists the units Assigned (a unit tagged "in effect before the check" still has a decision waiting for qa) and those Waiting for qa (not in effect yet), with the decision number, who made it and when.
  2. Write a Reason. Every action needs one.
  3. To assign, choose the unit under Assign a unit and click Assign (waits for qa). The page says "Recorded as decision #N — waiting for a qa person." Nothing takes effect until a qa person other than you confirms it under Decisions.
  4. To take a unit away, click Remove beside it: it applies at once. Withdraw beside a waiting assignment withdraws it, and nothing it proposed is applied.

The section is not shown for your own account or an account still awaiting approval. The User Manager refuses to assign a unit to an account that is disabled, does not hold the operator role (a production_manager counts, as it includes operator) or has no person_id, and says which. The same rule is checked again when qa confirms an assignment made here: if the account was disabled, lost the operator role or its person_id meanwhile, Confirm is refused with the reason and qa refuses the decision instead. Removing a unit is allowed for any account, so a leftover assignment can always be cleared. Other refusals are shown as the database gives them, for example "decision #N is no longer waiting" when someone confirmed or withdrew it a moment before. A unit decision is not withdrawn in the Decisions tab: that page says to withdraw it in the account's Units section.

qa and auditor may read an account's units (the policy gives them R on the route), but the Users tab is an administrator's tab, so in the User Manager they follow unit assignments in the Decisions tab.

A decision made in the User Manager names the administrator as its maker, from their sign-in, so the qa person confirms it without the attestation that a units.sh row needs.

Each assignment or removal writes one account decision (unit_assign or unit_remove) with the reason and the administrator as maker; a withdrawal writes no new decision: it closes the waiting unit_assign as withdrawn, with your name and reason. When qa confirms an assignment, a unit_assigned event is added to the access policy history with the qa person as actor; a removal adds unit_removed; a withdrawal adds account_decision_withdrawn.

The two new User Manager routes widen the access policy's skeleton (admin gains the assign route; admin, qa and auditor the read route; the access service the new database function), so the change ships as a skeleton version in two commits:

  2. Propose the second commit (the routes, the API and the page): ./apps/iam/apply.sh --propose-skeleton --by <you> --reason "<why>" --from-git <commit>. Until it is applied, every deploy of that commit is refused by the skeleton gate.

OKWritten last. A folder without it is a run that failed or is still running; nothing treats it as a backup.

Not copied: PostgreSQL's own volume (the dumps are its consistent copy), the broker's persistence (retained messages, which the boards publish again) and the hub's database (the AI workbench rebuilds it as people sign in). config.env, the platform CA .ca/ and edge/provisioned/ are files in the repository folder, not in the cluster: keep your own copy of them, which a full restore after a reinstall needs.

The backups hold secrets: Keycloak's password hashes and client secrets, pgAdmin's stored files inside the platform database, people's homes with their git tokens. ./apps/backup/deploy.sh creates BACKUP_DIR with mode 700 for the account that runs it (with sudo when the parent folder is not writable), and the job hands every folder to that account, mode 700. Copy them only to storage that is as well protected.

Settings and the job

  • BACKUP_DIR: an absolute path. On the same disk as the data (the deploy warns when it is), a disk failure takes both; point it at another disk, or copy the folders off the host. Changing it takes effect at the next ./apps/backup/deploy.sh; the old folder stays where it is.
  • BACKUP_KEEP_DAYS (14): after a good run, folders older than this are deleted, complete or not. The newest complete folder is never deleted, so a host that was off for weeks keeps its last good backup. Only folder names of the form 20261102-023000Z are ever deleted.
  • The job runs in a pod from the same image as PostgreSQL, so pg_dump has the server's version. The postgres password reaches it only from the Kubernetes Secret rdbms-postgresql, never on a command line or in its log. It reads the volumes' directory (/var/snap/microk8s/common/default-storage) read-only, as a whole rather than volume by volume, because a person's workbench home appears at their first start and the job must find it without a redeploy. It runs as root inside the pod to read every person's files, with no other privilege, no access to the Kubernetes API and a read-only image.
  • A host that was off at 02:30 runs the night's backup when it is back within 6 hours. A failed run is not retried; the health check shows it and the next night runs again.
  • Grafana's and Node-RED's files are copied while they run. A save during the copy (unlikely at 02:30) can leave that copy inconsistent; the next night's is not.

Restoring

The restore is shown, not run: it stops services and drops databases, and only you can decide what to put back. Restore only the parts you need. Check the folder first with ./apps/backup/backups.sh verify FOLDER. In the commands below, F is the folder (for example /var/backups/medcea/20261102-023000Z); restore-help prints them with the real path. psql and pg_restore run in the PostgreSQL pod and read the password there; the dump goes in on standard input.

After a reinstall, restore once ./install.sh has finished, with the old config.env if you kept it, and within BACKUP_KEEP_DAYS: the new install's first nightly run deletes the older folders (except the newest complete one). To be safe, copy the folder you will restore from out of BACKUP_DIR first.

A backup or a restore writes nothing into the platform's records. The manual in the portal

The portal serves this manual at https://portal.<domain>/manual/, linked by the Platform manual card on its main page (see the platform manual in the portal). Everyone the portal admits may read it; there is no access policy change behind it, because the portal's gate covers every path of its address. The decision is in the decision record ("The manual in the platform", 3 November 2026).

What is served is always built from docs/manual/chapters/ at the moment of publishing, never the committed docs/manual/index.html, which may be older: docs/manual/build.py --out <temporary file> --standalone, so publishing never changes the working tree. The page is stored gzipped (about 160 KiB for 570 KiB) in the Kubernetes ConfigMap portal-manual, with the page's sha256 and the commit it came from as annotations, and the portal's nginx sends it compressed.

After a change to the manual (a chapter edited, then python3 docs/manual/build.py and a commit), publish it:

  1. ./medcea.sh → Infrastructure → Publish the manual to the portal (it runs ./infra/publish-manual.sh, which takes the deploy lock and writes logs/publish-manual-<time>.log; it publishes the manual and nothing else).
  2. It prints the page's size, the size in the ConfigMap, the sha256 and the commit, restarts the portal (a few seconds) and ends "the portal serves it at /manual/". On an install whose portal is older than the manual (deployed before 3 November 2026), it only stores the manual and says the portal is not set up to serve it yet, without restarting it: run ./deploy-infra.sh once, which adds the /manual/ route, the mount and the card.
  3. ./health-check.sh: Platform manual is OK.

./deploy-infra.sh publishes the manual too, every run, before it updates the portal page. Both refuse, and the portal keeps the copy it has, when build.py refuses the chapters (a dead link, a duplicate id, a script; the message names the chapter) or when the compressed page would not fit in a ConfigMap (1 MiB at most; the limit used is 1,000,000 bytes). deploy-infra.sh stops there with an error, before the portal changes: fix the chapter and run it again.

The health check's Platform manual (type manual) rebuilds the page into a temporary file and compares it with what the ConfigMap holds. OK when they are the same; WARN when the portal serves an older build ("the portal serves the manual of <commit> …, the repository builds …", with the medcea.sh entry to run), when nothing is published yet, or when the portal does not mount the manual (run ./deploy-infra.sh); FAIL when build.py refuses the chapters, or when the ConfigMap's content is not the page its annotation names (someone changed it by hand: publish again); SKIP before the portal exists.

The ConfigMap is the portal's, like the portal's web server configuration (k8s/portal/nginx.conf, ConfigMap portal-nginx); ./apps/frontend/deploy.sh adds only the background image's folder to the portal. ./deploy-infra.sh --reset removes them with the namespace, and the next ./deploy-infra.sh publishes again.

Superset

Apache Superset 6.1.0 (apps/superset/) is the data analysis tool decided on 4 November 2026 (see Superset for what people see). Its code arrived on 6 November 2026 (stage B) without its access policy. Stage C (7 and 8 November 2026) added the policy: Superset's host, its resource group analysis and its database account svc_superset as a skeleton version (version 15 on the previous install), and the cells for its builders and viewers as a change version (version 16), both approved by qa and applied with ./apps/iam/apply.sh; Superset was installed on 8 November 2026 (decision record "Superset stage C", exercise E27). The factory file carries both, so a fresh install's version 1 has Superset, and since 8 November 2026 a fresh install installs it (decision record "Superset installed by default", exercise E28).

The first part of stage C, the wiring around Superset, was deployed before the policy and stays off wherever the applied policy gives no role a Superset setting. Every ./deploy-infra.sh creates the Keycloak client superset (callback https://superset.<domain>/oauth-authorized/keycloak, the groups scope, the two sign-out return addresses below) and writes its secret into config.env as SUPERSET_CLIENT_SECRET (read back from Keycloak, never rotated, never on a command line), and superset.<domain> joins the platform certificate, the server's hosts block and the alias redirects. A client no deployed app uses is inert.

When it is skipped. There is no switch of its own to turn Superset on. ./deploy-apps.sh --all (and so ./install.sh) runs ./apps/superset/deploy.sh on every install, and it installs nothing, prints one line and exits 0 while:

  • the applied access policy has no Superset tool, or has it but gives no role a setting yet (between the skeleton version and the change version of stage C): [superset] skipped: Superset is not in the applied access policy, or no role is given a setting;
  • IAM_GATES is false: "skipped: IAM_GATES=false, and Superset has no pre-policy sign-in" (Superset has no sign-in from before the access policy);
  • IAM_DB_SERVICE_ROLES is not true, as with a config.env from before 8 November 2026 (a new one has it true): [superset] skipped: Superset needs IAM_DB_SERVICE_ROLES=true (its data connection is svc_superset). Superset's data connection logs in only as svc_superset, never as the database superuser, and that account can log in only under this switch. ./install.sh then ends with "Still to do: Superset was skipped, it needs IAM_DB_SERVICE_ROLES=true." and names the medcea.sh entry that turns it on; afterwards run ./apps/superset/deploy.sh;
  • no version of the access policy is applied yet (since 8 November 2026; the full deploy only): [superset] skipped: no version of the access policy is applied yet (state empty), and Superset deploys only from an applied one: run ./apps/superset/deploy.sh once ./apps/iam/deploy.sh has applied version 1 (./apps/iam/apply.sh --status). On a fresh install the iam deploy, which runs before it, applies version 1; this skip shows only when that bootstrap waited (the iam deploy warns why). Nothing deploys Superset again after a later bootstrap, so ./install.sh ends with "Still to do: Superset was skipped, no version of the access policy is applied yet. Once ./apps/iam/deploy.sh has applied version 1 (./apps/iam/apply.sh --status), run ./apps/superset/deploy.sh." A policy state that cannot be read, or any other state, stops the deploy (exit 1) instead.

In each case a Superset that is running is stopped: its Deployment is deleted, its portal card greyed out, and its database, Secret and ConfigMap are kept. With IAM_DB_SERVICE_ROLES true but svc_superset unable to log in (no password, no Secret db-svc-superset: ./apps/database/deploy.sh has not run since the skeleton version) the deploy is not skipped: it stops with an error. A policy that does not compile also stops it (exit 1), and any option other than --gate-only is refused (exit 2). Exercise E24 checks the skip.

Once the policy gives roles a setting, the same command installs it, in this order:

  1. The wheel cache (SUPERSET_WHEEL_DIR, below): any of the three pinned packages missing there is downloaded first, before anything the running Superset reads changes, so a failed download leaves it as it was.
  2. Superset's own database superset, owned by the login role superset_meta, created in the PostgreSQL pod (the password goes in only as a verifier, on standard input, in a session that logs no statement). It is outside the platform database medcea_db, as Keycloak's is, and the database deploy never compiles it.
  3. The Kubernetes Secret superset-secrets (the secret key, superset_meta's password, Superset's Keycloak client secret and the compiled role mapping) and the ConfigMap superset-config (Superset's settings and the MedCEA sign-in code).
  4. A one-off Job superset-init: Superset's own schema, its built-in roles, the role "MedCEA Viewer" and the connection MedCEA, logged in as svc_superset, with data changes, table creation, file upload and impersonation stated off and checked after saving. The deploy refuses unless the connection would log in as svc_superset (that needs IAM_DB_SERVICE_ROLES=true and ./apps/database/deploy.sh); it never uses the database superuser.
  5. The web Deployment superset, its Service and its address https://superset.<domain> (SUPERSET_DOMAIN), then the portal card is turned on.

The wheel cache. The Superset image is pinned by digest. It lacks the PostgreSQL driver and the sign-in library, so at every start an init container installs exactly three packages (psycopg2-binary, Authlib, joserfc), each checked against the SHA-256 in apps/superset/requirements.txt. Since stage C (decision N10) they come from a folder on the host, SUPERSET_WHEEL_DIR in config.env (empty: /var/lib/<project>/superset-wheels), mounted read-only, with no package index: a restart, by apply.sh's rollout, a reboot or an eviction, needs no internet. Since 8 November 2026 ./deploy-infra.sh creates the folder after the MicroK8s bootstrap and the Docker Hub registry setup, just before the Helm registry login ("Superset's wheel cache folder..."): mode 700, owned by the deploying account, with one sudo prompt that says why ("[sudo] password for <you> (to create … for Superset's wheels):") when the parent is not writable, so the applications stage, and an unattended ./deploy-apps.sh, need no sudo for it. It checks the folder against the volumes' directory with the same code the Superset deploy uses and stops on a folder inside or around it; run as root it creates nothing and says so; it creates the folder whether or not Superset is installed (an empty folder). The full Superset deploy still creates the folder when it is missing (asking for sudo itself) and refuses one owned by another account or by root, one inside or around the volumes' directory, and a run as root; when a package is missing it runs a one-off Job superset-wheels, which downloads it from PyPI (pip download --require-hashes, binary packages only) and is deleted once the cache is complete. A changed pin in requirements.txt therefore needs a full deploy with PyPI reachable, and so does the first install: the pods must reach pypi.org, not only the image registries. ./apps/superset/uninstall.sh keeps the folder; ./install.sh --uninstall-all removes it (see Uninstalling).

There is no Redis and no background worker: SQL Lab runs queries directly, and alerts, reports and thumbnails are off. A pod restart ends nobody's session; sessions last 5 minutes idle and at most one hour.

Sign-out. Superset's Logout ends Superset's session and sends the person to Keycloak's end-session, which returns to the AI Workbench's /hub/logout when WORKBENCH_ENABLED is true and to the portal's sign-out otherwise (decision N4; the pod's MEDCEA_LOGOUT_RETURN, an https address or Superset does not start). ./deploy-infra.sh registers both addresses on the client whatever WORKBENCH_ENABLED says.

./apps/superset/deploy.sh --gate-only checks only who may sign in, and never downloads:

  • not deployed while Superset does not run;
  • unchanged when the Secret holds the compiled role mapping and every running pod was started with the Secret and ConfigMap as they are now (the pods read the mapping only at start, so a Secret rewritten by a re-render that did not finish counts as drift);
  • re-rendered (role mapping): the Secret and ConfigMap are rewritten and Superset restarts from the wheel cache;
  • re-rendered (stopped, …): the applied policy no longer gives any role a setting, IAM_GATES is false or IAM_DB_SERVICE_ROLES is not true; Superset is stopped and its card greyed out, as in the full deploy;
  • deferred, exit 4, when the mapping drifted while the wheel cache is incomplete and the running Superset admits only roles the policy still gives, in the same way (the policy only adds roles): Superset keeps its old mapping, apply.sh records apply_deferred ("Superset's wheel cache is incomplete"), and you run ./apps/superset/deploy.sh (it fills the cache), then ./apps/iam/apply.sh --resume --by <you>. Any other drift with an incomplete cache (a narrowing, a role mapped differently, a pod on another configuration) stops Superset instead: a mapping that would narrow is never deferred.

Either way Superset is closed, never left open, and the next ./deploy-infra.sh leaves a stopped Superset's card grey. apply.sh runs ./apps/superset/deploy.sh --gate-only in the rollout of every version from stage C's wiring on, whatever the version; it prints not deployed until Superset is installed.

Settings. ./infra/configure.sh generates three values once, before it checks for missing settings, and never asks or shows them: SUPERSET_SECRET_KEY (64 hex characters; it signs Superset's session cookies and encrypts the stored connection password, so changing it signs everyone out and the next deploy writes the connection again), SUPERSET_META_DB_PASS and SVC_SUPERSET_DB_PASS (it reaches the database, and Secret db-svc-superset, with the first ./apps/database/deploy.sh after the skeleton version that adds svc_superset). SUPERSET_CLIENT_SECRET is written by ./deploy-infra.sh (above). A rotated SVC_SUPERSET_DB_PASS needs ./apps/database/deploy.sh and then the full ./apps/superset/deploy.sh; a new SUPERSET_CLIENT_SECRET (regenerated in Keycloak, then ./deploy-infra.sh) needs the full deploy too: --gate-only compares the running Superset with the cluster's Secret, not with config.env.

Stage C, in order, as it was done on the previous install on 7 and 8 November 2026 (an install whose applied policy predates Superset follows the same path). Best through ./medcea.sh, which holds the deploy lock for each group of commands (exercise E27 walks through it):

  1. The wiring: ./deploy-infra.sh (client superset, the certificate name; run it with no onboarding or run active, since the certificate change reloads the ingress), ./apps/iam/deploy.sh (iam-api restarts: its compiler changed), ./deploy-apps.sh --all (Superset skipped), ./health-check.sh (Superset roles SKIP).
  2. The skeleton version: ./apps/iam/apply.sh --propose-skeleton --by <you> --reason "<why>" --from-git <commit>, approved by a qa person with the attestation, then git checkout <commit> and ./apps/iam/apply.sh N --by <you>. Between that checkout and the end of the apply every deploy that compiles the policy exits 2 (the skeleton gate): run nothing else in between. Its rollout prints Superset not deployed.
  3. ./medcea.sh → Policy → Superset stage C: after the skeleton version: ./apps/database/deploy.sh (svc_superset's password and Secret), ./apps/iam/deploy.sh (the Access Policy then ships the new skeleton), the health check.   4. The change version with the cells: drafted by an admin in the Access Policy, approved by qa, applied with ./apps/iam/apply.sh N --by <you>; its rollout still prints not deployed.
  5. ./medcea.sh → Policy → Superset stage C: install Superset: ./apps/superset/deploy.sh (the first install: the image, the wheels, the init Job), the health check, tests/iam-hosts.sh, tests/iam-network.sh, tests/iam-signin.sh and a backup (backups.sh now, then verify, which lists db/superset.dump).

Taking stage C back out.

  • The wiring (commit A): revert it in git, then ./deploy-infra.sh and ./apps/iam/deploy.sh. The Keycloak client superset stays behind, inert, since no deployed app uses it.
  • The skeleton version, proposed or approved but not applied: withdraw it (./apps/iam/apply.sh --withdraw-open, or qa returns it) and check out the wiring's commit again.
  • The skeleton version, applied: never reverted. Without the change version Superset never deploys.
  • The change version, applied: ./apps/iam/apply.sh --rollback-to <skeleton version> --by <you> --reason "…", then qa confirms it. Its rollout's --gate-only stops Superset and greys out its card, without needing PyPI; Superset's database is kept.
  • An IAM_DB_SERVICE_ROLES rollback stops Superset too (the deploy and --gate-only); no Superset pod ever runs on the database superuser.
  • Retiring Superset for good: a change version without the cells, then a commit that removes the group analysis and the host (a narrowing, which the next deploy accepts), then ./apps/superset/uninstall.sh. Leave svc_superset and Superset's network policy in place: removing either is a widening and would need its own skeleton version.

Superset users left by the sign-in test. Each sign-in creates a Superset user. tests/iam-signin.sh deactivates the ones its own run made (test-<role>-<run>) when it ends, in Superset's database as the database superuser, and does not delete them (decision N7). A run that was killed leaves its users active, though their Keycloak accounts are gone, so they cannot sign in. A username used again later finds its old Superset user, with what it owned.

Removing it. ./apps/superset/uninstall.sh greys out the card and removes everything labelled app=superset (Deployment, Jobs, Service, Ingress, Secret, ConfigMaps, a leftover superset-wheels Job included) and keeps the database superset and the wheel cache. ./apps/superset/uninstall.sh --purge-data also drops the database and the role superset_meta: every dashboard, chart, saved query and Superset account is gone. That flag is the only way to drop it. Neither touches svc_superset (the database deploy's) nor the platform database.

The deploy and uninstall write logs/app-superset-deploy-<time>.log and logs/app-superset-uninstall-<time>.log. Superset keeps its own log of sign-ins and actions in its database; Keycloak records each sign-in (login events of realm medcea). The health check's supersetroles (The health check) compares the running sign-in with the policy, and the running pods with the live Secret and ConfigMap; it is one of the nine checks apply.sh runs before and after an apply. Once Superset runs, tests/iam-hosts.sh checks its secrets, gate, running configuration, sign-in and reach, tests/iam-network.sh that no pod reaches it directly, and tests/iam-signin.sh who gets in.

DNS and Tailscale

With a name-based domain (DOMAIN="medcea", LOCAL_DNS="true", as on this install), the platform answers DNS for *.medcea itself, on its Tailscale address, port 53. The host resolves the names from a managed block in /etc/hosts. Other devices on your tailnet need one setting in the Tailscale admin console, which no command can make for you:

  1. Open https://login.tailscale.com/admin/dns.
  2. Nameservers, Add nameserver, Custom.
  3. Enter the server's Tailscale IP (PLATFORM_IP), turn on "Restrict to domain" (Split DNS), domain medcea, and save.
  4. Each device needs "Use Tailscale DNS settings" on (the default). On Linux: sudo tailscale set --accept-dns=true.
  5. Test from any device: nslookup portal.medcea must answer the server's IP. Then open https://portal.medcea, typing the https:// the first time, because browsers treat a one-word ending as a search until they have visited it.

Each ./deploy-infra.sh checks this setting at the end and reports when split DNS is active.

A rebuilt or replaced server

A new machine gets a new Tailscale IP, but the admin console keeps sending the domain to the old one. The server itself still resolves everything through /etc/hosts, so only other devices fail. ./deploy-infra.sh warns about this in its DNS step and, at the end, prints the old and new addresses and the edit to make: in the admin console, edit the nameserver restricted to the domain and change the old IP to the new one. If the old server is gone for good, remove it under Machines too.

With an IP-based domain (<ip>.nip.io) no DNS setup is needed. When you move from one domain to another, the old nip.io addresses keep working as permanent redirects (ALIAS_DOMAIN).

Troubleshooting

After a kernel update nothing starts

Symptom: after the host reboots into a newer kernel, PostgreSQL never becomes ready (its log stops after "redo done", connections get no answer, and the pod is restarted again and again), Keycloak, Superset and the proxies follow, Mosquitto cannot read its configuration, and ./install.sh stops at PostgreSQL's helm --wait. The data is not damaged. Cause: from Ubuntu kernel 7.0.0-41 on (seen on this host with 7.0.0-42 and 7.0.0-43 on 8 November 2026), Ubuntu's default kernel.apparmor_restrict_unprivileged_unconfined=1 gives every process in a container the stacked AppArmor label cri-containerd.apparmor.d//&unconfined. MicroK8s's container profile does not name that label, so processes in the same container may no longer signal each other: PostgreSQL's internal wake-ups, nginx's reload and Go's scheduler are refused. Through the same stack, a host profile shipped by Ubuntu's apparmor package for a program by its path (/etc/apparmor.d/mosquitto) attaches to that program inside its container. A containerd fix is proposed upstream (containerd issue 14485), not released.

The fix, installed by ./deploy-infra.sh (step "AppArmor rules for the cluster's containers...", one sudo prompt that says why, only when something changes): a root-owned script /usr/local/lib/<project>-apparmor/reapply and the systemd units <project>-containerd-apparmor.service and .path. MicroK8s copies its own profile over /etc/apparmor.d/cri-containerd.apparmor.d each time its containerd starts; the path unit sees that and the script writes MicroK8s's profile back with four added rules (signals and process inspection between processes of a container, with the plain and with the stacked label), loads it, and turns off the host profile mosquitto while the host has no /usr/sbin/mosquitto of its own (listed in disabled-profiles next to the script). A loaded profile applies to running containers at once: nothing is restarted. The kernel setting stays as Ubuntu sets it, and containers stay confined. ./install.sh --uninstall-all (./deploy-infra.sh --uninstall) removes the units and the script once MicroK8s is gone and turns the host profile back on; --uninstall-infra keeps MicroK8s and so keeps them.

Fix, on an install from before 8 November 2026: boot the older kernel first if PostgreSQL is stuck (GRUB menu → Advanced options; this host was held on 7.0.0-38 that day), then run ./deploy-infra.sh and ./health-check.sh (Container AppArmor OK). Then boot the newer kernel once from the GRUB menu and run exercise E29; only after it passes, make the newer kernel the default again and remove the hold. If PostgreSQL was killed during recovery under the broken kernel and still does not start on a good one, recover it in single-user mode (the data directory is intact; take a copy first).

Some refused signals are normal on a good kernel too, before the rules are loaded: processes that Kubernetes starts in an existing container (probes, start-up hooks, kubectl exec) already carried the stacked label under 7.0.0-38, and the probe program check-status was refused a few dozen times per boot. They stop once the rules are loaded, which the check counts from.

A person gets a 403 page from the portal

Symptom: the person signs in and sees "No access yet", or another 403 page. Cause: "No access yet" means Keycloak signed them in but their account has no platform role, so the portal's gate refuses them. A 403 with a different message is a failed sign-in (a provider error or an expired sign-in form), not a missing role. A host other than the portal shows "No access to <service>" with the roles that may open it. Fix: for "No access yet", give the account a role in the User Manager (a grant waits for qa to confirm); a password reset does not help. The role takes effect within about four minutes, without a new sign-in. For a failed sign-in, have the person open the portal again.

Grafana says the login was denied

Symptom: after signing in, a person lands on Grafana's own sign-in page with a message that the login was denied. Cause: their role holds nothing on the Grafana dashboards row of the access policy (for example operator, admin or a scientist), or the account has no platform role. Fix: none, if the role is right; Grafana is not for that role. Otherwise change the role in the User Manager. If everyone is refused, run ./health-check.sh: a grafanarole FAIL or a Keycloak scope problem (tests/iam-hosts.sh, sign-in line for Grafana) is the cause.

A person is refused right after switching to another account

Symptom: someone signs out of one account and in with another (for example to test a role), and an app shows "No access", Grafana says the login was denied, or the app still acts with the first account's role. Cause: usually the previous single sign-on session is still active in that browser: Keycloak, or an app that keeps its own session (Grafana, pgAdmin, the AI Workbench, the Node-RED editor), signed them in again as the first account without asking. Fix: sign out from the user menu (the person's name at the top right, then Sign out; the Sign Out buttons on the portal page end only the portal's own sign-in, and the portal then signs the first account in again), close the app's tabs and sign in again, or use a private window for the second account. Check the role in the User Manager only if the refusal stays.

The AI Workbench says "No access to AI Workbench"

Symptom: after signing in, a person sees the workbench's error page with "No access to AI Workbench" and the roles that may open it. Cause: their role holds nothing on the AI workbench row of the access policy (for example operator or auditor), or the account has no platform role. Fix: none, if the role is right. A notebook in the AI Workbench says "The document is taking some time to load"

Symptom: in a workspace, no notebook or file opens, not even those in medcea-examples; JupyterLab shows "The document is taking some time to load" and keeps waiting. Cause: before 1 November 2026 the workspace installed real-time collaboration at the same time as it started, and the first start of a new home folder began before the install had finished. The browser then asked for documents through collaboration, which the workspace did not serve yet. Now the install finishes before the workspace starts, so this should no longer happen once ./infra/deploy-workbench.sh (or ./deploy-infra.sh) has run and the workspace has been started since. pgAdmin's IoT Postgres server fails with "no password supplied", or shows no username

Symptom: an administrator signed in to pgAdmin opens IoT Postgres and gets "no password supplied", the server's properties show an empty Username, or there is no IoT Postgres server at all. Cause: before 1 November 2026 the entry belonged to pgAdmin's built-in user and was shared; pgAdmin does not share a server's username or password file, so everyone else saw it without them. The password file also belonged to the wrong user, so even the built-in user could not use it, and pgAdmin 9.19 reads a password file only from the signed-in person's own storage folder (an absolute path elsewhere, and PGPASSFILE, are ignored). Now each admin gets an entry of their own when pgAdmin starts, with a copy of the password file in their storage folder, but only for the addresses the last ./deploy-infra.sh listed. Fix: run ./deploy-infra.sh, then ./health-check.sh; pgadminroles names any address still without its entry. The account must be enabled, hold admin and have an e-mail address in Keycloak on an ordinary domain (not .invalid, .test, .example or .local). pgAdmin writes one line per address to its log (kubectl -n medcea logs deployment/pgadmin | grep oauth2-servers).

The System Configuration UI fails after a realm key rotation

Symptom: after a signing key was rotated or removed in Keycloak, the System Configuration UI's data calls are refused and the health check shows jwks (Realm signing keys) FAIL naming key ids the realm no longer publishes, or a key id the realm signs with that the Secret lacks. Cause: config-api and the Python services verify tokens against the keys published at the last ./deploy-infra.sh; config-api reads them only when it starts. Fix: run ./deploy-infra.sh. It republishes the keys and restarts config-api when they changed.

The Config UI stops answering for a few seconds during a switch

Symptom: while IAM_POSTGREST_JWT is switched in either direction, the System Configuration UI's requests fail for up to about 15 seconds. Cause: by design. config-api's database password changes in the same step as its mode, and nothing serves until the new pod is ready. Fix: none needed; do the switch when nobody is editing configuration, and reload the page afterwards.

Node-RED stores no telemetry after a deploy

Symptom: the Monitor and Grafana show no new readings, and the health check shows noderedflows FAIL with "Node-RED runs no flows". Cause: Node-RED started on a new, empty volume (the first deploy that gave it one, or a fresh install). Fix: run ./apps/node-red/deploy.sh.

The Node-RED editor keeps reloading or refuses an engineer

Symptom: an engineer passes the platform sign-in, but the Node-RED editor reloads in a loop or shows its own sign-in form that accepts nothing. Cause: Node-RED's own sign-in cannot work, for example its sign-in module could not be installed (noderedauth FAIL) or Keycloak refuses its callback. Fix: run ./deploy-infra.sh. Break-glass, when the editor is needed at once: microk8s kubectl -n <namespace> set env deployment/node-red NR_ADMIN_AUTH=off turns the editor's own sign-in off (only the platform sign-in remains, which admits engineer only). It restarts Node-RED. While it is off, any program on the platform host or inside the cluster that can reach Node-RED can use its admin interface without signing in, so keep it brief. The next ./deploy-infra.sh turns it on again and records a break_glass_seen event in the access policy history with the time Node-RED started without its sign-in; noderedauth FAILs until then.

Ending every Node-RED editor session

Symptom: you need every engineer signed out of the Node-RED editor now, for example after a role removal or when an editor token may have been exposed. Cause: Node-RED keeps editor sessions on its volume (/data/.sessions.json), so a restart alone does not end them; each lasts up to one hour from when it was issued. Sessions issued before 1 November 2026 were set to last a week; at each start Node-RED now drops every stored session longer than the hour, so the restart of that day's ./deploy-infra.sh ended them (its log says how many). Fix: clear the session file and restart Node-RED. Flows and palette modules are not affected:

microk8s kubectl -n medcea exec deployment/node-red -c node-red -- sh -c ': > /data/.sessions.json'
microk8s kubectl -n medcea rollout restart deployment/node-red

Engineers sign in again on their next visit. Telemetry ingest pauses for the few seconds the restart takes.

A newly onboarded board's first MQTT connections are refused

Symptom: right after onboarding, a board restarts once or twice before it publishes. Cause: its credential is registered after it boots and reaches the broker at the next sync, up to about 15 seconds later. Fix: none; the retry succeeds. A board flashed before the broker required credentials has none, never connects and must be onboarded again.

A change to the sign-in page does not show

Symptom: the login page still looks the same after you changed the theme files. Cause: Keycloak caches themes and never re-reads them while running. Fix: run ./deploy-infra.sh; it restarts Keycloak when the theme changed.

A deploy is refused although nothing is running

Symptom: "Another MedCEA deploy is already running", but the deploy you started earlier has ended. Cause: a background process started by that run, or a helm --wait or rollout status left after a plain kill, still holds the lock. Fix: the refusal lists the leftover processes and the kill command for them. Next time stop a run with the group kill it prints (kill -- -<pgid>). See One deploy at a time.

MicroK8s steps fail on Ubuntu 25.10 or later

Symptom: a MicroK8s start or addon enable fails with snapctl … from outside of a snap, or enable rbac dies after "No callback tokens file." Cause: Ubuntu's default sudo is now sudo-rs, which ignores sudo -E, and MicroK8s needs it for every privileged step. bootstrap-infra.sh switches to classic sudo for its own duration and restores the setting afterwards, so deploys work; a MicroK8s command you run by hand does not get that. Fix: by hand, run sudo update-alternatives --set sudo /usr/bin/sudo.ws, then the microk8s command, then sudo update-alternatives --auto sudo.

Other devices cannot open *.medcea after a server rebuild

Symptom: the host opens every page, laptops and phones on the tailnet do not. Cause: Tailscale split DNS still points at the old server's IP. Fix: change it in the admin console as ./deploy-infra.sh prints (see DNS and Tailscale).

An operator sees an empty Monitor

A deploy fails with "metadata.annotations: Too long"

Symptom: an app deploy stops with The ConfigMap "…" is invalid: metadata.annotations: Too long: must have at most 262144 bytes. The health check FAILs Account drift

Symptom: Account drift (iamdrift) FAILs with "N platform role(s) no confirmed decision or signed-off review explains" or "N failed compensation(s)". Cause: Keycloak gives an account a role the account record does not (a role set in Keycloak's console, a seeded account given a role other than the one its seed fact records, or a decision whose undo in Keycloak failed). The health check FAILs History chain anchor

Symptom: History chain anchor (iamanchor) FAILs: the event the newest backup recorded is missing, or its hash differs. Cause: the access policy history was cut or rewritten after that backup, or the platform database was restored from an older backup. Fix: if you restored from an older backup, nothing: it clears at the next nightly backup. (A backup left from an earlier install or a purged database is no FAIL: the check sees that it predates the history's first event and WARNs.) Otherwise treat it as tampering: do not deploy, keep the backup folder, and compare the history with the newest backup's dump (Restoring, last step, shows the read-only query); Access policy history shows whether the chain itself still verifies.

The health check FAILs Database catalog

Symptom: Database catalog (iamcatalog) FAILs naming objects not owned by medcea_owner, triggers not ENABLE ALWAYS, or views without security_invoker. Cause: someone with superuser rights changed the catalog (for example ALTER TABLE … ENABLE TRIGGER, which turns ENABLE ALWAYS back to the default, or a table created as postgres in one of the platform's schemas); also an extension installed into those schemas by another owner. Fix: first find who made the change (PostgreSQL's log, the deploy logs in logs/). Then run ./apps/database/deploy.sh (and ./apps/access/deploy.sh for a trigger of schema iam): their migrations set ENABLE ALWAYS on the protective triggers, security_invoker on the platform's views and medcea_owner on the objects they create, and run ./health-check.sh again. A deploy does not fix an object its migrations do not create (a table made by hand, an extension's function): decide whether it belongs there, then drop it or change its owner by hand, in a session as postgres.

A qa decision cannot be confirmed

Symptom: a decision about the only qa person's own account, or one they made, waits forever. Cause: the person who checks a decision is never its maker or its subject.
