Training: hands-on exercises

An exercise is a task you carry out on the platform from start to end, with the accounts and screens a real person would use. It has two purposes. A new person learns a task by doing it once under guidance. After a change to the platform, running the exercise shows that the screens, the database rules and the records still work together. This chapter says how to run an exercise safely, where to read what it recorded, the fixed form every exercise follows, the exercises themselves, and how to add a new one.

Running an exercise safely

  • Use test accounts. Every account on this install is a test account of one person (see test accounts). Several exercises need roles no account holds yet (production_manager, operator, qp): make them with E1 first, with a username that says it is a test account, for example qp_test, and add each one to the test accounts table.
  • Give each account its own browser session. All the web apps share one sign-in. If you sign in as a second account in another tab of the same window, the first account is replaced everywhere, and the screens then act for whoever signed in last. Use a normal window for one account, a private window for a second, and another browser or browser profile for a third. Private windows of the same browser share one session with each other, so two private windows are still one account.
  • Every exercise leaves permanent records. Approvals, returns, decisions, releases and the policy history can be added to but never changed or deleted; the policy history is hash-chained, so a removed or edited event would show. That is what the exercises are meant to prove. Never try to clean up a record afterwards. An approved test item can be retired, a test account deactivated, a unit removed; each of those is a new record too.
  • Real equipment is real. A unit in test mode drives its chamber. Do not send commands to a unit with plants in it unless that is the point of the exercise.

How every exercise is written

Each exercise has the same parts, in this order:

  1. Goal: what you learn and what the exercise proves.
  2. Accounts and roles: which accounts take part, and which separation of duties the exercise shows.
  3. Before you start: what must be true first.
  4. Steps: numbered; who does what, with the screen, tab, button and field names as the page shows them.
  5. What you should see: the result on the screen.
  6. What is recorded and where to check it: the records, and the screen or file that shows them.
  7. Refusals worth trying: what the platform must refuse, and the message it shows.
  8. Afterwards: how to leave the platform as you found it.
  9. Last done: the date and result, or "not yet".

E1 Request access and grant a role

Goal. Make a new account the way every person gets one, and see that an approved request gives no access until a second person confirms it.

Accounts and roles. A new applicant (no account yet), admin (admin) and svieira (qa). The administrator approves; a qa person who is neither the administrator nor the applicant confirms. Rule I17: no person may hold an admin and a qa account at once (see dual control).

Before you start. A username and an e-mail address that have no account yet. If e-mail is not set up in the User Manager, no e-mail goes out; the decision is still recorded.

Steps.

  1. Applicant, in a window of its own: open https://access.<domain>/register. The sign-in page opens on the Request access tab. Fill in every field, choose the Role you need and a Business justification (20 characters or more), and choose Submit request.
  2. Applicant: try to sign in with the new username and password.
  3. admin: User Manager, Requests, tab Pending. Select the request. Under Decision choose Approve, check Role to grant, write Notes, untick Send e-mail to if the address is not real, click Approve as <role> (waits for qa) and confirm the dialog.
  4. admin: open Decisions and select the new decision.
  5. qa: User Manager, Decisions, tab Waiting for qa. Select the decision. Read the effect, the access it adds and the list of existing admin and qa accounts. Write an optional note and click Confirm.
  6. Applicant: sign in again.

What you should see. After step 1: "Request received. You will get an e-mail once an administrator has reviewed it." In step 2: "This account is not active". After step 3 the request reads approved, but the account stays disabled with no role. In step 4 the administrator reads the decision but cannot check it. After step 6 the applicant signs in with the granted role.

The request and its history (submitted, approved, reassigned if the role changed) are under Requests, tab All. The grant is one account decision naming the maker, the checker, both times and the notes: Decisions, tab All. The confirmation is also appended to the hash-chained policy history (iamchain). iamdecisions warns if a grant waits more than 7 days.

Refusals worth trying.

  • admin opens the waiting decision (step 4): it shows no Confirm, Refuse or Mark reviewed, because only qa holds A on account decisions. The administrator never confirms.
  • A qa person opens a decision they made, or one about their own account: "You cannot check this decision:" followed by the reason, for example "not_own_author: you are its subject". The rule compares persons, not account names.
  • Submitting a second request with the same e-mail address while the first waits, or with a username that already has an account: the form refuses it.
  • qa clicks Refuse with an empty note: "A refusal needs a note."
  • I17: giving a qa account the person_id of an admin account, or the reverse, is refused before anything is recorded, with "person … would hold both an admin account (…) and a qa account (…) (I17)".

Afterwards. The account stays. Add it to the test accounts table. When it is no longer needed, deactivate it (E7); it is never deleted. A refused grant deletes the pending account, so the applicant may apply again.

Last done. Not recorded here.

E2 Assign a unit to an operator

Goal. Give an operator a unit and see that the operator sees nothing of it until qa confirms.

Accounts and roles. The person who runs units.sh on the host (recorded as maker with --by), a qa person who did not run it (svieira), and an operator account (from E1). The script cannot prove who ran it, so qa attests that they did not.

Before you start. An enabled operator account; the unit exists in the Units tab; a shell on the platform host in the repository folder. units.sh takes the deploy lock, so no deploy may be running.

Steps.

  1. Operator: open the Scheduler and the Run Monitor. Note what you see.
  2. Host: run ./apps/iam/units.sh assign <operator username> UNIT01 --by <your username>. For --by, name an account that is not the qa person who will confirm.
  3. Host: run ./apps/iam/units.sh list. The unit is listed under WAITING_QA.
  4. Operator: reload the Scheduler. Still nothing.
  5. qa: User Manager, Decisions, Waiting for qa. Select the unit assignment. Read the note that units.sh recorded its maker but cannot verify it. Tick "I did not run units.sh for this assignment.", write an optional note and click Confirm.
  6. Host: ./apps/iam/units.sh list again. Operator: reload the Scheduler and the Run Monitor.

What you should see. Before the confirmation the operator sees no runs and no telemetry and can start nothing. After it, the operator sees UNIT01's runs, cycles and logs in the Scheduler and its telemetry in the Run Monitor, and list shows the unit under UNITS.

One account decision per unit, with the maker as "system:deploy (by <username>)", the checker, the note with the attestation, and the times: Decisions, tab All. The unit taking effect appends unit_assigned to the policy history, with the qa person as actor (iamchain). The command's output is in logs/app-iam-units-<timestamp>.log.

Refusals worth trying.

  • Confirm stays off until the attestation box is ticked.
  • Run the assignment with --by naming the qa account, then open it as that account: "You cannot check this decision:" with the reason that you made it. Refuse it from another qa account or remove it with units.sh remove.
  • units.sh assign without --by is a usage error (exit 2) and records nothing.

Afterwards. Keep the assignment if the operator is needed for E6. Otherwise run ./apps/iam/units.sh remove <operator username> UNIT01 --by <your username>: a removal acts at once and qa marks it reviewed under To review. See unit assignments.

Last done. 31 October 2026: an assignment of UNIT01 confirmed by svieira at 22:13 (decision 14). The operator's view (steps 1, 4 and 6) was not checked: no operator account was enabled.

E3 Draft and approve a parameter set

Goal. Make a parameter set the way every configuration item is made: an engineer drafts, a different person approves, and the approved set is frozen.

Accounts and roles. eng (engineer) writes the draft; svieira (qa) approves. The approval is refused when the approver is the same person as anyone who changed the item since its last approval.

Before you start. The algorithm the set is for is approved (its status shows under its code in Control Algorithms). The database enforces roles (IAM_DB_ROLES=true), so the Approvals tab is shown.

Steps.

  1. engineer: Configuration UI, Control Models, panel Parameter Sets, + New Parameter Set. Enter the Name, choose the Algorithm and the Unit, adjust Params (JSON object) and click Save draft.
  2. engineer: open the Approvals tab. The draft is under My proposals and drafts, waiting for qa.
  3. qa: Approvals, panel Waiting for approval, Review… on the parameter set. Read What you approve and the list of changes (for a new set: Never approved: N change(s) since creation). Type a Note and click Approve.
  4. engineer: open the set again in Parameter Sets.

What you should see. After step 3 the message names the approval record ("Approved: … (approval #N)"). The set's status reads approved; it opens read-only with ⎘ Copy to a new draft and Retire…. A schedule can now choose it.

Every save is stamped with who made it and kept in the row-change log. The approval is a row naming the approver, role and source, the authors, a digest of the content and the note: Approval history, filter Parameter sets, or History of this item.

Refusals worth trying.

  • The author cannot approve. With separate roles, eng has no Approve at all and sees the draft only under My proposals and drafts. The person rule shows when the approver's account and an author's carry the same person_id: "You changed this item (or one of its steps) since its last approval. Another qa person must approve it." (database code not_own_author).
  • An approved set cannot be edited: the screen offers no Edit, and the database refuses an edit from any other client with draft_only: … is approved, not a draft; a change starts a new draft. Use ⎘ Copy to a new draft.
  • A set whose algorithm is still a draft cannot be approved: the row says "Approve its control algorithm first." and Approve is off. This can be tried only while some algorithm is a draft.

Afterwards. The approved set stays. If it should not be used, Retire… it (it asks you to confirm; nothing is deleted).

Last done. 31 October 2026: q_test (#1), created and edited by eng, approved by svieira at 21:59:54 UTC (approval #6).

E4 Return and withdraw

Goal. Send work back with a reason, change it and send it again; and take back a proposal of your own.

Accounts and roles. eng (engineer) as author and proposer; svieira (qa) returns. Only qa returns; only the proposer withdraws.

Before you start. A draft parameter set by eng (as in E3, up to step 2). For the withdrawal, a unit with no run running or scheduled.

Steps.

  1. qa: Approvals, Review… on the draft. Type the reason in the note field and click Return…, then confirm.
  2. engineer: Approvals, My proposals and drafts. The draft reads Returned by qa, with qa's reason, and "Change the draft to send it back".
  3. engineer: Control Models, Parameter Sets, Edit on the draft, change it, Save draft.
  4. qa: the draft is back in Waiting for approval and may be approved.
  5. engineer: Units tab, Flag for commissioning… on the unit, a reason, Propose. Then Withdraw… (in the unit's cell or under My proposals and drafts), with an optional reason.

What you should see. After step 1: "Returned: … (record #N)"; the draft stays an editable draft, marked returned in the queue until its author changes it. After step 5 the proposal reads withdrawn and never applies.

A return and a withdrawal are rows in the approval record (actions return and withdraw) with the reason; no approval rule counts them as approvals. Read them in Approval history (filter Parameter sets for the return, Settings and commissioning for the withdrawal) and the unit's History.

Refusals worth trying.

  • A draft returned and not changed since cannot be returned again: Return… is not offered, and the database refuses it with "Already returned; it has not changed since."
  • Someone else's proposal cannot be withdrawn: another engineer's proposal shows without buttons, and the database refuses with "Only the person who proposed it can withdraw it." This needs a second engineer account.
  • qa clicks Return… with an empty note: "Give the reason for returning it in the note field".

Afterwards. Approve or retire the test draft. A withdrawn proposal is closed; nothing to undo.

Last done. Not yet on production; only probed on the throwaway test database.

E5 Test mode and the MQTT Explorer

Goal. Put a unit in test mode (commissioning), send a command from the MQTT Explorer, and end test mode, seeing the broker follow each change.

Accounts and roles. eng (engineer) proposes, sends and ends; svieira (qa) approves and reviews. Turning test mode on opens command rights, so it waits for qa; ending it narrows them, so it acts at once and is reviewed afterwards.

Before you start. The unit (here UNIT01) has no run running or scheduled; its Commissioning cell reads Off; IAM_MQTT_PERSON=true.

A message on a control topic reaches the unit's CONTROL board. Use a tag that no channel in the board's channel map uses, such as test, unless you mean to switch equipment.

Steps.

  1. engineer: Configuration UI, Units, in UNIT01's Commissioning cell Flag for commissioning…. Type the Reason and click Propose.
  2. qa: Approvals, Review… on the proposal. Read the proposer, time and reason, type an optional note and click Approve and apply.
  3. engineer: open the MQTT Explorer. Wait until the status reads Connected (up to 15 seconds for a new credential). Read Your rights: its topics are patterns.
  4. engineer: in the Publish box type one concrete topic, medcea/UNIT01/ZONE01/control/test, a payload, and click Send.
  5. engineer: send the same to a unit that is not in test mode, for example medcea/UNIT02/ZONE01/control/test.
  6. engineer: Units, End commissioning…, a reason, End commissioning. After about 15 seconds send step 4 again.
  7. qa: Approvals, Review… on the ended commissioning, Mark reviewed.

What you should see. After step 1 the cell reads "Waiting for qa: flag on … (your proposal)". After step 2 it reads Commissioning and the message names the approval record. In step 4 the message arrives on that topic. In step 5 nothing happens and no error is shown: the broker drops a message you may not send. Step 6 applies at once; the cell reads Off with an end waiting for review, and the resend in step 6 is dropped in the same silent way.

Each proposal is a pending change with the proposer and reason; each approval, review and withdrawal a row in the approval record: Approval history, filter Settings and commissioning, and the unit's History. The policy history gets commissioning_enabled and commissioning_disabled with the unit, actor and reason, and mqtt_credential_issued for the engineer's credential (iamchain). iampending warns if a proposal or an end waits for qa more than 7 days.

Refusals worth trying.

  • A topic with + or #, such as the pattern medcea/+/+/control/# copied from Your rights: "Not sent: + and # only match topics; send to one, e.g. medcea/UNIT01/ZONE01/control/<tag>".
  • While the unit has a run running or scheduled, Flag for commissioning… is off, with "Run #N is running" (or "is scheduled"); the database refuses the proposal and the approval too. The other way round, no run can be scheduled on a flagged unit.
  • A second proposal for a unit whose proposal already waits: refused until it is approved, returned or withdrawn.
  • qa cannot propose test mode: there is no Flag for commissioning… for them; only an engineer proposes. In the Units cell, Review… is off for the proposer's own change.

Afterwards. Every unit's cell reads Off, nothing waits in Waiting for approval, and ./health-check.sh passes iampending and iamchain. See commissioning a unit and MQTT Explorer.

Last done. 31 October 2026: two full cycles on UNIT01 (pending changes #1 to #4, approvals #7 and #8 for the first cycle, the second approved at 22:40:18 and reviewed at 22:43:18, policy history events commissioning_enabled and commissioning_disabled); sending from the Explorer verified. The same evening found that a wildcard topic made the broker close the Explorer's connection; fixed that day (see known gaps).

E6 Release a completed run

Goal. Take a run from preparation to release, and see that the release can only come from a person who had no hand in the run.

Accounts and roles. A production_manager prepares the run; the same production manager, or an operator assigned to the unit, starts it; a qp person who neither created, changed nor executed it releases it. None of these roles is held by an account on this install yet: make them with E1, and assign the operator with E2.

Before you start.

  • An approved recipe allowed on UNIT01 in Recipe ↔ Unit Permissions. A short one (one step, one cycle of a few minutes) keeps the exercise short; eng drafts it and svieira approves it as in E3.
  • An approved parameter set for the unit, for example q_test.
  • UNIT01 is not in test mode and has no active run.

Steps.

  1. production_manager: Configuration UI, Units, Recipe ↔ Unit Permissions. If the recipe has no tick for UNIT01, click the circle, choose the Default Algorithm and click Save.
  2. production_manager: Scheduler, New Schedule. Choose UNIT01 and the recipe, Frequency Run Once with a time (UTC), the approved Parameter set, and click Save.
  3. Let the schedule start the run, or the production manager clicks ▶ Run Now on it in Scheduled Jobs. An operator of UNIT01 may click ▶ Execute on a Queued run the production manager prepared.
  4. Follow it in Current Runs or the Run Monitor until it is Completed.
  5. qp: Configuration UI, Approvals, Review… on the Completed run row "Run #<id> (<recipe> on UNIT01)". Read What you release: recipe and parameter set with their approvals, creator, executors, attempts, cycles, start and end, and whether you may release it.
  6. qp: type an optional Release note, click Release and confirm.
  7. Any role that reads runs: Scheduler, Completed Runs.

What you should see. The confirmation says a release is final. The message reads "Released: … (approval #N)" and the row leaves the queue. In the Scheduler the run shows a Released badge; hovering over it shows who released it and when (UTC).

The run records who created and who executed it, with their roles. The release is a run-release row (one per run, never changed) and an approval row with action release, the note, and the persons who created, changed or executed the run: Approval history, filter Run releases. See releasing a completed run.

Refusals worth trying.

  • A person who created, changed (for example rescheduled) or executed the run cannot release it: "You created, changed or executed this run (one of its attempts). Another qp person must release it." With separate accounts per role this shows only when the qp account carries the same person_id as one of them.
  • A run with no recorded person behind its creation or start is listed with "No recorded person created or started this run: …" and is never released.
  • A run already released is not offered again; if it was released meanwhile: "Already released meanwhile; the list was refreshed."
  • qp clicks View Log on the run in the Scheduler: "(your role does not hold R on run logs)". The release is decided on the summary, not the log.
  • Setting a released run back for a retry is refused.

Afterwards. Nothing to undo: a release is final. Retire the Run Once schedule if it is still listed.

Last done. Not yet. It needs a completed run and a qp account.

E7 Deactivate and reactivate an account

Goal. Take an account out of use and bring it back, and see that removing access acts at once while giving it back waits for a second person.

Accounts and roles. admin (admin) deactivates and proposes the activation; svieira (qa) reviews the deactivation and confirms the activation. The subject is a test account that is not needed for anything else.

Before you start. The account is enabled and is not the last enabled admin or qa. For an operator, remove its units first with units.sh remove if they should not come back with it.

Steps.

  1. admin: User Manager, Users, tab Active. Select the account, write the Reason and click Deactivate account.
  2. Subject: try to keep working, then sign in again.
  3. qa: Decisions, tab To review. Select the deactivation and click Mark reviewed.
  4. admin: Users, tab Inactive. Select the account and click Activate (waits for qa).
  5. qa: Decisions, Waiting for qa, select the activation, Confirm.

What you should see. Step 1 applies at once: the person is signed out everywhere and their MQTT credentials are revoked; data, role and history are kept. In step 2 sign-in shows "This account is not active". After step 4 the account is still disabled; after step 5 it signs in again with its role.

Both changes are account decisions with maker, subject, reason, checker and note: Decisions, tab All. Status changes are kept in the append-only account status history; the review and the confirmation are appended to the policy history (iamchain).

Refusals worth trying.

  • The administrator selects their own account: "This is your own account — another administrator would have to change it."
  • The administrator deactivates svieira, today the only enabled qa account: refused with "this is the last enabled qa person", before anything is recorded. The same holds for the last enabled administrator.
  • While an activation waits for qa, the account's role and person cannot be changed until it is decided or withdrawn with Withdraw decision.

Afterwards. Leave the account as it should be: reactivated if still needed, otherwise deactivated. See when your account is deactivated.

E8 Quarterly access review

Goal. Review who holds which role and unit, sign it off, and read it as an auditor.

Accounts and roles. svieira (qa) creates and signs off; viewer (auditor) reads. One qa person may create and sign off the same review: a known single-person control.

Before you start. The tab holds one review per quarter, and its snapshot never changes. Creating it is this quarter's review, not practice: run this exercise when the review is due.

Steps.

  1. qa: User Manager, Access review, Create this quarter's review.
  2. qa: read the snapshot: accounts with role, state, person_id and last login; units; Unexplained at the time of the review; decisions waiting and made since the last review; waivers; the IAM switches; the policy version and hash-chain verdict. Compare the accounts with the test accounts table.
  3. qa: write an optional note and click Sign off.
  4. auditor: User Manager, Access review.

What you should see. The signed-off review with its snapshot, note and signer. The auditor reads it but has no create or sign-off button.

The review, its snapshot and its sign-off are kept in the User Manager's Access review tab, readable by qa, qp and auditor. See the quarterly access review.

Refusals worth trying.

  • auditor and qp cannot create or sign off a review.
  • A signed-off review cannot be undone or changed.

Signing off a review that lists unexplained roles accepts them: the drift banner in the Decisions tab stops showing them until a later change to that account. Explain or correct them first.

Afterwards. Nothing to undo.

E9 Open an example notebook in a new workbench home

Goal. Start an AI Workbench workspace for the first time and open an example notebook at once, without a restart. The exercise proves that the workspace's installs finish before it starts (before 1 November 2026 a new home folder opened no document until its workspace was restarted) and that the workspace shows the person: the terminal prompt and the git author name are the person's username, not the container's account jovyan.

Accounts and roles. A test account that has never started a workspace, holding a role the workbench admits, for example a new bio_test (bio_scientist) made with E1 and added to the test accounts table. admin (admin, hub administrator) watches from the hub's admin page and can stop the workspace afterwards; the administrator cannot open it.

Before you start. ./infra/deploy-workbench.sh (or ./deploy-infra.sh) has run since 1 November 2026, and ./health-check.sh shows iamworkbench OK. The account must be new to the workbench: a home folder already set up by an earlier start proves nothing about a first start. Use a browser session of its own (see running an exercise safely).

Steps.

  1. Test account: on the portal, click the JupyterHub card and sign in.
  2. Wait on the start page until JupyterLab opens. The first start takes a few minutes.
  3. In the file browser, open medcea-examples, then 01-connect.ipynb.
  4. Open a terminal (File → New → Terminal), read the prompt, then run git config --global user.name.
  5. admin: on the hub's admin page, find the test account's workspace and its start time.

What you should see. In step 3 the notebook opens with its cells; it never stays on "The document is taking some time to load". In step 4 the prompt reads bio_test@workbench:~$, the terminal tab's title names bio_test, and git config --global user.name prints bio_test. The workspace's log lists its set-up steps before the notebook server starts.

Nothing is recorded in the platform's database: the exercise changes no right and no record. Evidence is the workspace's log on the host, which the host operator reads: kubectl -n medcea get pods -l component=singleuser-server names the workspace's pod (jupyter-…, the username with special characters escaped), then kubectl -n medcea logs <pod> | grep -E "medcea-home-setup|is running at". Every medcea-home-setup: line, ending with medcea-home-setup: done, comes before the line saying the Jupyter Server is running, and no line holds WARNING. The hub's admin page shows when the workspace started.

Refusals worth trying.

  • admin: follow the link to the test account's workspace from the admin page. The hub answers "403 Forbidden"; the administrator cannot open the workspace or its notebooks.
  • Test account: in the terminal, run touch ~/medcea-examples/x. It answers touch: cannot touch '/home/jovyan/medcea-examples/x': Read-only file system, because the folder is mounted read-only. Then change a cell of 01-connect.ipynb and save it (Ctrl+S). The save is refused: JupyterLab may show a "File Save Error for 01-connect.ipynb" dialog naming the read-only file system or "Permission denied", or, with real-time collaboration on, show nothing at all. Either way, close the notebook and open it again: your change is gone. Copy the notebook into your home folder to change it.

E10 Sign out and switch accounts

Goal. Sign out as one account and sign in as another in the same browser window, and see each app follow the new person. The exercise proves the decision of 1 November 2026 ("short sessions and one-hop sign-out"). Sign out ends the app it is chosen in, the platform sign-in and the AI Workbench's own session. The AI Workbench follows the person signed in now within 5 minutes, and so does a Grafana tab that is not in use. Nobody is shown another person's workspace. Before that day the workbench still served the previous person after a sign-out.

Accounts and roles. Two test accounts used one after the other in one browser window. Account A is eng (engineer), which may open the AI Workbench, Grafana (Editor) and the Node-RED editor. Account B is admin (admin), which may open the AI Workbench and pgAdmin, but not Grafana or the Node-RED editor. The exercise shows that two people never share an identity through one browser.

Before you start. ./deploy-infra.sh, then ./apps/access/deploy.sh, then ./health-check.sh have run, in that order, since the review of 1 November 2026, and the AI Workbench is installed (WORKBENCH_ENABLED=true). Contrary to the usual advice (see running an exercise safely), use one private window for both accounts. Sharing one window is the point of this exercise. Do not tick Remember me. Have a watch at hand.

Steps.

  1. A: in a new private window, open the portal and sign in as eng.
  2. A: open the AI Workbench from the portal and wait until JupyterLab shows. Note the address, …/user/eng/lab. Leave the tab open.
  3. A: open Grafana from the portal and open the IoT Environmental Monitoring dashboard. Grafana's profile menu (top right) names eng. Set auto-refresh to Off next to the time range, so the tab is not in use. Leave the tab open and do not touch it.
  4. A: open the Node-RED editor from the portal. Leave the tab open.
  5. A: on the portal tab, open the user menu (your name, top right) and choose Sign out. Note the time.
  6. A: on the page "Do you want to log out?", choose Logout.
  7. B: on the sign-in page you land on, sign in as admin.
  8. B: open the AI Workbench from the portal.
  9. B: open pgAdmin from the Platform Management page.
  10. B: in the tab of step 2, try to save the notebook or open a file, then reload the tab.
  11. B: when at least 5 minutes have passed since step 3, reload the Grafana tab of step 3.
  12. B: then, at least 5 minutes after step 6, reload the Node-RED tab of step 4.

What you should see.

  • Step 5 shows "Do you want to log out?" (the portal has signed you out of itself first).
  • Step 6 passes through the AI Workbench's address and lands on the portal's sign-in page.
  • Step 8 opens …/user/admin/lab. File → Hub Control Panel names admin, and nothing shows eng.
  • Step 9 goes to pgAdmin's browser tree without a MedCEA sign-in button.
  • In step 10, before the reload, the save may still work: the old tab keeps eng's token for about 5 to 10 minutes. After the reload the workbench answers "403 Forbidden" for eng's workspace.
  • In step 11 the Grafana tab goes through the sign-in and shows Grafana's sign-in page saying the login was denied, because admin has no Grafana role. It does not show eng's dashboards as eng.
  • Step 12 shows the page "No access to Node-RED".

Nothing is recorded in the platform's database: the exercise changes no right and no record. The host operator can read the evidence:

  • The hub's log has a line User logged out: eng at the time of step 6, if step 6 came within 5 minutes of step 2. Read it with kubectl -n medcea logs deploy/hub | grep "logged out".
  • In the Keycloak admin console, Users → eng → Sessions lists no session after step 6.
  • Grafana's log has a refused sign-in for admin after step 11.

Write the times of steps 5, 6 and 11 under Last done.

Refusals worth trying.

  • B: type the address of A's workspace (https://ai-workbench.<domain>/user/eng/lab). The workbench answers "403 Forbidden".
  • A, in a second run: on the "Do you want to log out?" page, close the tab instead of confirming. The portal signed A out of itself, but the platform sign-in stays: opening the portal signs A in again without a password, and the AI Workbench still shows A. This is why the page must be confirmed.

Known gaps you may see (see switching accounts in one browser):

  • Reloading the Node-RED tab less than 4 minutes after step 6 may still open the editor as eng: its gate checks the platform sign-in every 4 minutes. If B were another engineer, whom the gate admits, the editor would keep acting as eng for up to an hour after step 4.
  • pgAdmin opened by A, if A could open it, would stay A's for up to an hour.
  • A Grafana tab that stays in use, for example a dashboard with auto-refresh, keeps eng's Grafana session for up to an hour after step 3, so in step 11 it may still show eng. The hour is the bound; 5 minutes would drop unsaved panel edits.
  • If the AI Workbench does not answer, step 6 stops on its error page. The platform sign-in has already ended; only the workbench's own session is left, for up to 5 minutes.

Afterwards. B: Sign out, then close the private window. Stop both workspaces if they are not needed (admin, from the hub's admin page).

Adding an exercise

Every change a user would notice gets an exercise in this chapter, in the same piece of work as the change: a new screen, button, rule or refusal. Extend an exercise when the change belongs to it; add a new one (E9, E10 and so on) when it does not.

  1. Write it in the form of How every exercise is written, all nine parts. Take the screen, tab, button and field names and the refusal texts from the code, not from memory.
  2. Add its row to Exercises at a glance: exercise, roles, what it proves, last done ("Not yet").
  3. After the change is deployed, run the exercise on the platform.
  4. Write the date and the result under Last done and in the summary row, with the record numbers the screens showed (approval, decision, pending change). Never write a number you did not see.
  5. When the exercise is evidence that a control works, record it in the decision record as well, and list anything it found in known gaps.
