Using the web apps

The platform is a set of web apps, each on its own address under the platform domain, all signed in through the same platform account. This chapter takes them one at a time: what each app is for, which roles can open it, and the main tasks as step lists. It also says what each action records. The access policy decides who may do what. An app that your role may not open answers with an error page that names the roles that may open it. In most apps a button your role may not use stays on the screen; once the policy is enforced, the action is refused with a message that names the reason.

Every app sits behind a sign-in gate that admits only the roles the access policy compiles for that address. The table shows the gates at this release. Inside an app, the policy then limits each action further, as the sections below explain.

Report-only and enforcing

The Scheduler, the Run Monitor and the Configuration UI's file libraries check every request against the access policy. The switch IAM_ENFORCE in config.env decides what a failed check does:

  • While it is false (report-only), the request goes through and the service writes a "would refuse", "would limit" or "would withhold" line to its log.
  • While it is true, the request is refused: 401 when the app cannot tell who you are, 403 when your role does not hold the right, and 503 when the service cannot load the policy.

Database Management and the User Manager always enforce, whatever the switch says. The changes you save in the Configuration UI go straight to the database, which adds its own checks once IAM_DB_ROLES is true. Each app section notes where the two modes differ. The switches themselves are explained in the administration chapter.

The user menu

Every signed-in app except Grafana, the AI Workbench, Node-RED and pgAdmin shows your name at the top right. It opens a menu with two entries:

  • Profile: your personal details and your password.
  • Sign out: ends your session on the platform, not only in that app.

Portal

The portal is the start page. It lists the apps as cards; clicking a card opens that app in a new browser tab. Every platform role can open the portal. An account without a platform role gets the page No access yet, which explains that an administrator still has to approve the access request.

The main page, MedCEA Platform, shows three cards:

  • Grafana: the MedCEA Dashboard.
  • JupyterHub: the AI Workbench.
  • Administration: opens the Platform Management page.

Platform Management holds the cards for these apps:

  • Node-RED
  • Database Management
  • MQTT Explorer
  • Configuration
  • Scheduling (Recipe Schedule Manager)
  • Operations (Run Monitor)
  • User Manager

The portal shows every card to every role. A card for an app your role may not open still opens it, and the app's gate answers with an error page. When an administrator uninstalls an app, its card stays on the page, greyed out and not clickable, and it comes back when the app is deployed again.

  1. Open https://portal.<domain> and sign in with your platform account.
  2. Click a card. For the apps under Platform Management, click Administration first.
  3. Use Back to return to the main page, or the user menu to sign out.

Configuration UI

The Configuration UI, titled System Configuration, holds the definitions the platform runs on:

  • the physical plant: locations, units, zones and devices
  • the control algorithms and the learned state of learning controllers
  • the recipes, which recipe may run on which unit, and the steps of each recipe

Every role can open it. What you may change depends on your role:

The page has five tabs: Locations, Units, Devices, Control Models and Recipes. The Portal link at the top left returns to the portal.

Locations

A location is a site, for example a building. Each one has a name, an address, a contact, coordinates, a description and a status (Active or Inactive).

  1. Open the Locations tab.
  2. Click + New Location, or Edit on an existing row.
  3. Fill in at least Name, then click Save Location.

↑ Import loads locations from a file on your computer or from the Platform Location Library. ↓ Export All and the row's ↓ Export save them to your computer or to the library. Once the services enforce, only an engineer may save to the library.

Units and zones

A unit is one cultivation chamber at a location; a zone is a part of a unit. Telemetry, runs and device names all carry the unit and zone codes.

  1. Open the Units tab and click + New Unit, or Edit on a row.
  2. Enter the Unit Code, choose the Unit Type (Greens, Mushrooms or Other) and the Location. + New beside the location creates one without leaving the form.
  3. Click Save Unit.
  4. To add a zone, open the unit with Edit, click + Add Zone, enter the Zone Code and click Save Zone.

Unit codes and zone codes are unique regardless of case. A duplicate is reported as "already exists". A code becomes part of each board's network name, so choose codes of letters, digits, _ and - only; the devices chapter explains why.

Devices

The Devices tab lists every board with its hostname, type, unit and zone, model, serial number and status. The Online column checks whether the board answers on the network: click the icon in a row to check that board, or the icon in the column header to check all of them. Edit opens a device, and its components can be added with + Add Component.

Boards are normally added with the onboarding wizard, not typed in here. That procedure, and the rule that maintenance may only re-onboard into an existing slot, are in the devices chapter.

Recipes and steps

A recipe is the growth programme for a crop: a sequence of steps, each with a number of cycles, a light type, the minutes the light is on and off, and lower and upper limits for:

  • air temperature
  • CO2
  • humidity
  • substrate temperature
  1. Open the Recipes tab and click + New Recipe. Enter a Name and click Save.
  2. Click Steps → on the recipe's row.
  3. Click + Add Step. Fill in Step #, Step Name, Cycles, the light settings and the limits, then click Save Step.
  4. Repeat for every step, then click ← Back.

Other actions on a recipe:

  • ⎘ Copy makes a new recipe with the same steps.
  • ↓ Export downloads the recipe as a file.
  • ↑ Import reads a recipe from your computer or from the Platform Recipe Library.

Saving a recipe to the Platform Recipe Library is refused for every role once the services enforce, because the library cannot check the rules that limit who may change a recipe (drafts only for engineers, assignments only for production managers). Downloading a recipe, and the recipes in the database, are not affected.

No role may delete configuration records once the database enforces roles (IAM_DB_ROLES=true), so the Delete buttons are refused. To take a recipe, unit, location or device out of use, set its Status to Inactive.

Assigning recipes to units

The Recipe ↔ Unit Permissions panel on the Units tab is a grid of recipes against units. A tick means the recipe may run on that unit, and a circle means it may not. Under the tick is the algorithm chosen for that pairing. Inactive recipes are faded and inactive units struck through; their cells show a dash and cannot be clicked. This is the production_manager's planning task.

  1. Open the Units tab and scroll to Recipe ↔ Unit Permissions.
  2. Click the circle where the recipe's row meets the unit's column. The cell turns into a tick and Permission Settings opens.
  3. Pick a Default Algorithm (left empty, the system default IF_THEN_ELSE is used), optionally enter Parameter Overrides (JSON), and click Save. To change these later, click the tick.
  4. To withdraw the assignment, click the tick and then Revoke Permission.

Once the database enforces roles, the recipe must be approved before it can be assigned. A run then takes its algorithm and parameters from an approved parameter set: the schedule's, or else the assignment's. The parameter overrides typed here are not used. This release has no screen that creates a parameter set or attaches one to an assignment; the Scheduler lists the sets that exist.

Control Models and learned state

The Control Models tab has two panels.

  • Control Algorithms lists each algorithm with its code, name, description and Default Params (JSON). An algorithm that is not approved shows its status (for example draft) under its code. An engineer may edit the defaults of a draft and click Save.
  • Production Units lists, for each unit, how many recipes are allowed on it and the learned state each learning controller keeps for it. Click the record count to see the state per channel and when it was last updated.

Drafts, approval and the author rule

Recipes (with their steps), control algorithms and parameter sets have a status: draft, approved or retired.

  • A new definition starts as a draft.
  • A qa person approves it. The approval is refused when the approver changed the definition since its last approval. It is also refused when any change since then has no recorded person; such a definition has to be re-created before it can be approved.
  • An approved definition is frozen. While IAM_DB_ROLES is false, editing an approved definition is allowed but turns it back into a draft, and the app shows that as an advisory. While it is true, the edit is refused. Make a copy with ⎘ Copy and have the copy approved instead.
  • A parameter set can only be approved once its algorithm is approved.

While the database enforces roles, only approved recipes may be assigned to units, and a run uses only approved algorithms and parameter sets.

The apps have no approval screen yet. The approval itself is a database function (approve_recipe, approve_algorithm, approve_params) that only a signed-in person holding qa can call. See the compliance chapter for how approvals are checked.

Every change to these definitions records who made it, with which role, and when; it is also kept in the append-only row-change log. Each approval is a row naming the approver, the authors since the last approval and a digest of the approved row.

Retiring a Q-table

A learning controller, such as Q-learning, keeps what it learnt in a Q-table between runs. Starting a unit afresh means retiring that table. Only qa may do it, and nothing is deleted: the next run on that unit starts cold.

  1. Open the Control Models tab and find the unit in Production Units.
  2. On the row of the algorithm whose state you want to retire, click Retire….
  3. Enter the reason. A reason is required and is recorded.
  4. Confirm. The message names the unit and the number of channels retired.

Retiring needs the database to verify your sign-in, which it does only while IAM_POSTGREST_JWT and IAM_DB_ROLES are both true. Without them, nobody can retire a Q-table. Any other role gets the message that retiring learned state needs a qa person signed in.

For each channel retired, the controller-state event log gets a retired event with the unit, the algorithm, the retired state, the reason and the qa person, and the approval record gets a row naming that person. Neither record can be changed afterwards.

Scheduler

The Scheduler, titled Recipe Schedule Manager, is where runs are started, stopped and followed, and where recurring schedules are kept. A run is one execution of a recipe on a unit. Every role can open the page and sees all four sections. Once the services enforce, the Scheduler refuses the data and actions your role does not hold, as the table shows.

The page has four sections: Current Runs, Scheduled Jobs, Completed Runs and Log Management. A run's status is one of:

  • Queued: created, not yet started.
  • Running
  • Completed
  • Failed: the run failed or was stopped.

Starting a run now

  1. Click Run Now at the top right.
  2. Choose the Production Unit, then a Recipe. The list offers only the recipes allowed on that unit. If the unit already has an active run, a warning asks you to finish or cancel it first, and a new run is refused.
  3. Optionally choose an Algorithm and enter Param Overrides (JSON). Once the database enforces roles, leave these empty: the run uses the approved parameter set of the recipe's assignment, and typed parameters are refused.
  4. Click Start Run. The run is created and executed in one go and appears under Current Runs.

If the run is created but cannot start, the message begins "Run created but not started", and the run waits as Queued.

Executing, stopping and retrying

Each row in Current Runs shows the buttons that fit its status:

  • ▶ Execute on a Queued run.
  • ■ Stop on a Running run. Stopping marks the run Failed, then ends the process.
  • ↺ Retry on a Failed run. Retrying sets the run back to Queued and executes it again, optionally with another algorithm.
  • 📋 Log on every run.

The arrow at the left of a row expands the cycles of the run, with each cycle's step, start and end times, status and parameters.

An operator may execute, stop or retry a run only when both of these hold:

  • a different person holding production_manager created it, or a schedule such a person created started it;
  • its unit is one of the operator's units.

This keeps preparing a run separate from starting it.

A run records who created it and who executed it, with their roles. Each cycle is recorded as the runner completes it. A run started by a schedule is recorded with the actor system:scheduler, on behalf of the person who created the schedule.

Schedules

  1. Click New Schedule.
  2. Choose the Production Unit and the Recipe.
  3. Pick a Frequency: Daily, Weekly, Monthly, Hourly or Run Once. Set the days, the date and the time. All times are UTC. Generated Schedule shows the result.
  4. Choose the Parameter set. While the database enforces roles, you must choose an approved set, and the schedule runs that set's algorithm and parameters. Otherwise the list is for information only, and the schedule runs the Algorithm and Param Overrides (JSON) fields below it.
  5. Optionally add a Description, leave Enabled on, and click Save.

In Scheduled Jobs, each schedule has three buttons:

  • ▶ Run Now starts the schedule's recipe at once.
  • Edit changes the schedule.
  • Retire stops the schedule from firing.

A schedule is retired, never deleted. A retired schedule stays in the record and cannot be edited or enabled again. Create a new schedule instead.

Run logs

Click 📋 Log on a current run, or View Log on a completed one, to open the run's log. For a running run, the log follows new lines as they are written.

A role that does not hold read access on run logs sees the run but not its log: the window shows "(your role does not hold R on run logs)", where R means read. This applies to maintenance, qc and qp while IAM_ENFORCE is true. While it is false, the log is shown and the service records a "would withhold" line.

Log Management: compression, never deletion

No person compresses or deletes a run log. The scheduler's own nightly job runs every day at 03:15 UTC. It compresses (gzips) the log of each run that has finished, Completed or Failed, once the log is older than the Compress run logs after setting. It never touches the log of a run that is queued or running, and it never deletes a log. A compressed log still opens from View Log.

The Log Management section shows:

  • the number of run log files, their total size and the oldest one;
  • when the job last ran and how many files it compressed or kept;
  • the smallest values allowed: 1 day for compression and 30 days for the retention value.

Retention setting (not applied) is kept as a value but nothing reads it, because run logs are never deleted.

  1. As admin, change Compress run logs after (in days) and click Propose retention.
  2. While the database enforces roles, the message says the value is proposed and "pending qa approval". The new value applies only after a qa person other than you approves it. There is no approval screen for this in the Scheduler yet. While the database does not enforce roles, the value is saved at once and the message reads "Defaults saved".

A proposed setting is stored as a pending change with its author. The approval records the qa person who confirmed it.

Operators see only their own units

An operator sees only the runs, cycles and logs of the units assigned to them. A run in another unit looks the same as a run that does not exist. The filter applies while IAM_ENFORCE or IAM_DB_ROLES is true. An operator with no unit assigned sees no runs and can start none. Units are assigned with apps/iam/units.sh and confirmed by qa in the User Manager's Decisions tab, as described in the administration chapter.

Run Monitor

The Run Monitor is a live view of every run that has not completed: running, queued (shown as Scheduled) and failed runs. Each run gets its own card. The Monitor is for watching. It has no buttons that change anything.

The roles admitted are operator, production_manager, maintenance, qc, qa, qp, engineer and auditor, and since IAM 3.2b bio_scientist and control_scientist, who may read telemetry but not runs: the Monitor lists runs, so for them it shows "No active runs at this time." or a refusal, and they read telemetry in the AI Workbench instead. An operator sees only the units assigned to them, under the same rule as in the Scheduler: runs, readings and actions of other units are not shown, and a reading that carries no zone is never shown to an operator.

Each card shows the unit code and type, the run number, the recipe, the status and the start time, with three panels:

  • Steps: each step of the recipe, its status and the cycles completed out of the total. The current step is highlighted.
  • Live Measurements: the latest value of each sensor reading for the unit. Air Temp, CO2, Humidity and Substrate Temp are drawn as bars against the current step's limits, which are shown in brackets. A bar marks whether the value is inside or outside the limits, and "no limits set" means the step has none for that reading.
  • Actions: the latest command sent to each actuator, for example a light or a fan, with its time.

The page refreshes itself every 30 seconds. Click ↻ Refresh to refresh at once. "No active runs at this time." means that no run you may see is open.

Database Management

Database Management exports database objects as an SQL file, for evidence, for an inspection or for a copy kept outside the platform. Only qa, qp and auditor can open it. It always enforces the policy, whatever IAM_ENFORCE says, because an export takes data out of the platform.

The page lists only the objects in the export groups your role holds, and states them in a line that begins "You may export:".

  • qa and auditor may export master data, devices, device history, recipes, controllers, controller state, runs, schedules, scheduler settings, telemetry and the audit histories.
  • qp may export runs, telemetry and the audit histories.

The page offers only the platform's own data tables and views. The account records, unit assignments and access policy that belong to the same groups are not offered here, and the audit histories offered are the platform's approvals, pending changes and row-change log. Sequences and types hold no rows and are offered as definitions to everyone who can open the page.

  1. In DDL & Data Export, tick DDL (the table definition) and/or Data (the rows) for each object you need. All DDL, All Data and Clear set or clear every box. For views, sequences and types the Data box is disabled; only their definition is exported.
  2. Keep or change the File Name.
  3. Under Save To, choose one destination:
    • Download locally puts the file on your computer.
    • Save to platform (apps/database/exports/) writes it on the platform host. It refuses a name that already exists there.
  4. Click ↓ Export SQL. The result line shows the file name, its size, the export number and the start of its sha256 checksum.

The file begins with a header naming:

  • the export number
  • when it was generated, in UTC
  • who exported it, and with which role
  • the groups it covers

If one selected object is outside your groups, the whole export is refused and nothing is logged.

Every export writes one row to the export log (iam_policy.export_log). The row holds the time, the person, the groups, and each object with whether its DDL or how many rows were exported. The row is written before the file is handed over, and nobody can change or delete it afterwards. The full sha256 of the file is written to the Database Management service log; keep the checksum with the file, so you can show later that the file is the one exported.

The full access process, including what the applicant sees, is in the access chapter; dual control and the review are explained in the compliance chapter. The main tasks are below.

Deciding an access request (admin)

  1. Open Requests, tab Pending, and select a request.
  2. Under Decision, choose Approve or Reject. For an approval, check Role to grant. It starts as the requested role, and you may reassign it.
  3. Write a note. A rejection needs one. Check the e-mail to the applicant, which is pre-filled from the template; untick Send e-mail to the applicant's address to send nothing.
  4. Confirm. An approved request waits for qa: the account stays disabled, with no role, until a qa person confirms the decision, and the approval e-mail goes out only then. A rejection takes effect at once: the e-mail goes out, and the pending account is deleted so the person may apply again. The request record keeps who asked, for what, and why it was refused.

Changing an account (admin)

In Users, select an account. Deactivating, changing the role, proposing a person and withdrawing a decision each need a reason; for an activation the reason is optional. The reason is recorded with the decision. You cannot change your own account.

  • Deactivate account acts at once. The person is signed out everywhere and their MQTT credentials are revoked. Their data, role and history are kept.
  • Activate (waits for qa) waits for confirmation, also for an account with no role.
  • Change role acts at once when the new role holds less, a narrowing; it takes effect within a few minutes, without signing the person out. When the new role adds any right, the button reads Change (waits for qa) and the page lists the rights it adds.
  • Person: enter the New person_id the account belongs to and click Propose (waits for qa). This always waits for qa.
  • While a decision about the account waits for qa, the role and the person cannot be changed until it is decided or withdrawn with Withdraw decision. Deactivating the account is always possible and withdraws the waiting decision.

Confirming decisions (qa)

  1. Open Decisions, tab Waiting for qa, and select a decision. The detail lists the effect and the access it adds. For a new applicant it also lists the existing admin and qa accounts, flagging any that may be the same person.
  2. Write a note (required to refuse) and click Confirm or Refuse.
  3. Decisions that acted at once (deactivations, narrowings) appear under To review. Click Mark reviewed after checking them.

You cannot check a decision that you made, or one about your own account. The page says why when that is the case.

E-mail settings and templates (admin)

Until e-mail is set up, a banner at the top says that nothing is sent and messages go to the service log.

  1. In E-mail settings, enter the Gmail address, the App password and the Sender name. The panel beside the form explains how to get an app password. Use Another mail server for a different SMTP host.
  2. Click Verify and propose (waits for qa). The login is checked first. The change is used only after a qa person confirms it, because the same account sends the password-reset e-mails.
  3. Send test e-mail to me checks the current account.

In Templates, select a template, edit it and click Save template, or Reset to default. A template change applies at once.

Every request, decision, confirmation, refusal and review is kept in append-only histories with who and when. Mail settings and template changes are listed in the Change log (when, what, change, by).

The quarterly access review (qa)

  1. Open Access review and click Create this quarter's review. The page takes a snapshot of:
    • accounts, roles and units
    • decisions waiting and decisions made since the last review
    • waivers and switches
    The snapshot never changes afterwards.
  2. Read the review, including Unexplained at the time of the review.
  3. Optionally write a note and click Sign off. Signing off cannot be undone, and it accepts any unexplained roles listed.

MQTT Explorer

MQTT Explorer is a browser tool that shows the messages the boards and the platform exchange on the message broker. Only engineer can open it. It is meant for commissioning and fault finding.

  • The left column lists every topic under the platform's topic root (medcea/ by default) that you may read, seen since the page opened, with its last value.
  • Click a topic to see its latest messages; the page keeps the last 100 for each topic.
  • The status at the top reads Connected, Reconnecting, Waiting for the broker to accept your credential, or an error.

How the page connects depends on the switch IAM_MQTT_PERSON (see IAM switches).

With your own credential (IAM_MQTT_PERSON=true). When the page opens it asks the platform for a broker credential that is yours alone, made from your role, and connects with it. You see nothing of this: no password is shown or stored in the browser.

  • The first connection can take up to 15 seconds: the broker picks up a new credential at its next check.
  • The credential lasts 8 hours and is renewed in the background before it ends. Signing out of the platform does not end it at once; deactivating your account or changing your role ends it within about 15 seconds.
  • The Your rights note under the Publish box lists what you may read and where you may send. An engineer reads every unit's sense, control and control_setpoint topics, and may send only to a unit's control topics while that unit is flagged for commissioning and has no run in progress. The broker checks this every 15 seconds: when the flag is cleared or a run starts, sending to that unit stops.
  • No screen can flag a unit for commissioning yet, so in practice the page only reads. Send stays disabled while you have nowhere to send.
  • A message the broker does not allow is dropped silently: the page shows no error, and nobody receives it.
  • If the page says your role has no MQTT rights, or that your access changed since you signed in, reload it after your administrator has sorted out your role.

With the shared account (IAM_MQTT_PERSON=false). The page connects with one shared service account that may read and write every topic under the platform root.

To send a message:

  1. Click a topic, or type one in the Publish box.
  2. Enter the payload, as text or JSON.
  3. Click Send.

With the shared account, a message published to a control topic switches equipment in a live chamber, whatever the unit's state. Publish to control topics only on a unit with no active run. With your own credential the broker refuses it, but a unit flagged for commissioning is still real equipment.

Node-RED

Node-RED runs the flow that receives telemetry from the broker and writes it to the database. Its editor is where that flow, and any other integration flow, is changed. Only engineer can open it.

After the platform sign-in, the editor signs you in a second time with the same account. You normally see no form: the page reloads once and the editor opens. Your rights in the editor come from the access policy. engineer may change and deploy flows, use inject and debug, and edit context and the library. Nobody installs palette modules from the editor: the modules the platform needs are listed in the repository and installed by ./apps/node-red/deploy.sh. Every deploy you make is logged with your username.

The editor session lasts a working day (8 hours). If your role changes, your editor rights change at your next editor sign-in; if your account is deactivated, the platform sign-in ends your access within about four minutes.

The flows in the repository are the reference. The health check compares the flows Node-RED runs with them every time it runs: a flow from the repository that was changed or deleted in the editor shows as a failure, and a flow built only in the editor shows as a warning. To make an editor change permanent, export the flow and commit it to the repository; to undo an editor change, run ./apps/node-red/deploy.sh.

The flows connect to the message broker as the node-red service account, which reads every topic under the platform root, and to the database with the ingest login svc_ingest, which may read master data and insert telemetry rows. Code in a flow runs with both. A broken or deleted ingest flow stops telemetry from being stored. Export a copy of the flow before you change it. The flow kept in the repository is apps/node-red/flows/message-processing.json.

Grafana

Grafana shows telemetry as dashboards. The portal's Grafana card opens it, and you are signed in with your platform account without a further prompt. The provided dashboard, IoT Environmental Monitoring, has these panels:

  • live readings of air temperature, relative humidity and CO2
  • historical trends of the same readings
  • a summary of the latest readings by zone and device

Grafana gives each person one of its own roles, from the access policy's Grafana dashboards row:

  • Editor, for engineer: edits dashboards and opens Explore;
  • Viewer, for production_manager, maintenance, qc, qa, qp, auditor: views dashboards;
  • no sign-in for every other role (operator, admin, bio_scientist, control_scientist) and for an account without a platform role.

A person Grafana refuses sees Grafana's own sign-in page with a message that the login was denied, not the platform's "No access" page. Nobody gets Grafana Admin through the platform sign-in: only Grafana's local break-glass account holds it (see Credentials).

A Grafana session lasts one hour from sign-in. Then Grafana sends you through the platform sign-in again, usually without asking for your password, and your role is checked again; a tab left open may need a reload.

The platform's dashboards change only through the repository (apps/report/dashboards/) and the report deploy. An Editor who changes one of them in the browser cannot save it. An Editor can still create a new dashboard, or copy one with "Save as"; such a dashboard is visible to other Grafana users until Grafana restarts, then it is gone. It is not part of the record: put a dashboard that should stay in the repository.

Dashboards read through Grafana's own database account, so a viewer sees telemetry of every unit; that is why an operator, who sees only their own units in the Run Monitor, has no Grafana. A viewer can also send Grafana any query that account may run, even though the Explore screen is hidden from Viewers: what limits a viewer is the database account's read access (master data, measurements and runs), not the dashboards.

AI Workbench (JupyterHub)

The AI Workbench is JupyterHub: notebooks for data analysis and for developing control algorithms. It is meant for bio_scientist and control_scientist work.

  • Each person gets their own workspace with persistent storage (a home folder of its own). It starts when you sign in and is stopped after an hour without activity; your files are kept. Nothing backs them up: see Saving your notebooks to git.
  • The workspace opens in JupyterLab, and VS Code is available inside it.
  • The first start of a workspace takes longer, because it installs VS Code into your home folder.
  1. Click the JupyterHub card on the portal. You go straight to the platform sign-in.
  2. Wait while your workspace starts, then work in JupyterLab.

Who may sign in comes from the access policy: admin, bio_scientist, control_scientist, engineer, qa. Anyone else sees the workbench's "No access to AI Workbench" page. Every person admitted gets a full workspace that runs code; the workbench has no read-only mode.

The administrator (admin) is the hub's administrator, through a hub role made for this (workbench-admin), not JupyterHub's built-in administrator. From the hub's admin page the administrator can list the people and their workspaces, start and stop workspaces and remove a person from the hub. The administrator cannot open your workspace or your notebooks, cannot create a token in your name, cannot share your workspace with anyone and cannot change your hub account. If the administrator follows a link to your workspace, the hub answers "403 Forbidden"; it never offers an "Authorize" button for someone else's workspace. Removing a person from the hub, or a role that no longer includes the workbench, keeps your home folder: your files come back if access is restored.

A workspace you are signed in to lasts an hour at most before the sign-in runs again. If your role changes meanwhile, a tab left open longer may ask you to reload.

Reading platform data from a notebook

Every workspace has a read-only folder medcea-examples in its home folder, kept up to date by the platform. If you do not see it, your workspace was started before the folder was added: choose File → Hub Control Panel, Stop My Server, then Start My Server.

  • 01-connect.ipynb: signs you in and lists the units and zones your role may see.
  • 02-air-temperature.ipynb: a line chart of one zone's air temperature over the last minutes. The unit, the zone and the number of minutes are set at the top.
  • SAVE_TO_GIT.md: how to keep your notebooks in the research repository (below).
  • medcea_data.py: the small library the notebooks use (import medcea_data as md works in any notebook).
  • nb_output_guard.py: the check git runs before each commit (see Saving your notebooks to git); you do not run it yourself.

To change a notebook, copy it into your home folder first (right-click, Copy, then Paste in your folder, or File > Save Notebook As).

  1. Open 01-connect.ipynb and run the first cell. It shows a link and a short code.
  2. Open the link in a browser tab, sign in if asked, and confirm the code. The cell finishes once you have; the code is valid for about ten minutes.
  3. Run the other cells. md.units(), md.zones() and md.measurements(unit, zone, tag="air_temperature", minutes=60) return tables (pandas DataFrames). md.measurements returns at most 50,000 readings, the most recent ones; when the window holds more, it warns, and the chart's title says "latest N readings". Shorten the minutes, or pass a larger limit=.

The notebook reads as you: every request carries your own sign-in, and the database applies your role and its row rules. You read exactly what your role may read in the database, nothing more: bio_scientist and control_scientist read master data, recipes, controllers and telemetry (no runs, no export). A notebook only reads: the database refuses any change made with a notebook sign-in ("may only read"), whatever your role may change in the Configuration UI. A refusal because your role may not read a table says so ("your role may not read this"); signing in again does not change it. The sign-in lives only in the notebook's memory; it is renewed while you work and is gone when the kernel stops or your platform session ends (deactivation ends it within five minutes). Then run md.sign_in() again. Nothing in your workspace holds a platform password.

The notebooks reach the platform only while the platform verifies each person's sign-in at the database (IAM_POSTGREST_JWT and IAM_DB_ROLES both true). Otherwise md.sign_in() says it cannot reach the platform. A workspace started before the administrator turned this on must be stopped and started again (File > Hub Control Panel).

Telemetry is regulated data, and the scientist roles may read it, not export it. Keep it on the platform: do not copy values into a code or text cell, a file you download, or a message. When you commit a notebook to git, its outputs are removed automatically (below); code and text cells are not checked.

Saving your notebooks to git

Your home folder is kept when your workspace stops, when the administrator removes you from the hub and when your role loses the workbench, but nothing backs it up, and uninstalling the platform deletes it. Keep work that matters in the research repository on GitHub that the administrator set up (WORKBENCH_NOTEBOOK_REPO; a terminal in your workspace prints it with echo "$MEDCEA_NOTEBOOK_REPO"). SAVE_TO_GIT.md has the details.

  1. Once: set your name and e-mail for commits (git config --global user.name and user.email), create a fine-grained personal access token on GitHub for that repository only (Contents: Read and write, with an expiry date), and clone the repository into your home folder from a terminal. Git asks for your GitHub username and the token, and keeps the token in your home folder only (~/.git-credentials).
  2. Save your notebooks inside the cloned folder.
  3. In the Git panel on the left: stage the changed files (+), write a message, Commit, then Push. Pull brings in your colleagues' work.

Each workspace has nbstripout set up as a git filter at every start: a committed notebook keeps its code and text but none of its outputs (tables, charts, printed values), while the notebook on disk keeps them. If nbstripout could not be installed, git refuses to commit a notebook rather than store its outputs. Behind the filter, a check runs before every commit and refuses it while a notebook still holds outputs (for example in a repository whose own settings turn the filter off): the commit fails with "Commit refused" and the file names. Clear the outputs (Edit > Clear Outputs of All Cells), save, stage the file again and commit. If you set your own git hooks folder (core.hooksPath), the workspace leaves it alone and this check does not run. Commits carry your own name and GitHub account; the platform holds no GitHub credential.

pgAdmin

pgAdmin is a database browser for the administrator, who uses it to see the database schema and the configuration. Only accounts holding admin can sign in, through the MedCEA sign-in button; the access policy decides this. Anyone else is sent back to pgAdmin's login page with a message that they are not authorized. pgAdmin checks the role only at sign-in. Open it from the pgAdmin card on the portal's Platform Management page (every role sees the card; only admin gets in), or at https://pgadmin.<domain>.

pgAdmin uses one of two database logins:

  • While the services use their own database roles (IAM_DB_SERVICE_ROLES=true), it connects as rr_admin_login. That login owns nothing and reads only what the admin role may read. It cannot change regulated data or the histories.
  • While that switch is false, it connects as the database superuser.

Do not change the database schema here. Schema changes are applied by the database deploy, as described in the administration chapter.
