Reference

Lookup tables for everyday use: the web addresses and who may open them, the roles each application admits, the access levels and resource groups of the access policy, the settings an administrator may change, the scripts on the platform host, the health checks, and the abbreviations used in this manual. The tables describe the platform as of IAM 2.6, deployed report-only on 31 October 2026, with the access policy at its default version.

Access levels

Every cell of the access policy holds zero or more of these levels. A level that "includes" others gives them too.

LetterNameIncludesMeaning
NNoneNo access. The role does not see the resource at all. The default for every cell.
RReadSee the resource, change nothing.
XRead and exportRRead, and take a copy out of the platform through the Database Management export. Each export is recorded with who exported which objects and when.
CCreateRAdd new records; never change existing ones. Used for appending to regulated data and audit trails.
UUpdateC, RCreate and change records, within the group's constraint. On recipes and controllers only while the record is a draft. Removing a configuration record means setting it to "retired", never deleting it. Never given to a person on regulated or history data.
AApproveRApprove or release another person's work. The approver must be a different person from the author. In this version an approval is an attributable, time-stamped record, not a 21 CFR Part 11 electronic signature.
OOperateRStart, stop or trigger a process (execute a run, stop it, trigger a schedule) without changing its definition.
KConfigureAdminister the tool without the content it holds. On accounts it means reading and changing account records, which are personal data. Held only by admin.
DDeleteRemove platform components and releases on the host. Never data. Held only by admin.

Access policy versions (IAM 4.1 to 4.5)

Since slice 4.1 the database holds everything Phase 4 needs to keep the access policy as numbered versions (migration 008c). Since slice 4.2a version 1 exists (the factory policy, applied by ./apps/iam/apply.sh --bootstrap inside the iam deploy), every deploy compiles from the applied version, and every deploy runs the skeleton gate (see The applied access policy). Since slice 4.3 the Access Policy shows the versions, and since slice 4.4 an admin drafts change versions there and a qa person approves them; applying an approved version is slice 4.5.

ObjectWhat it is
iam_policy.versionOne row per version: kind (bootstrap, change, skeleton, rollback), status (draft, submitted, approved, applied, superseded, withdrawn), who drafted, submitted, approved, applied, confirmed or disputed it, and its digests. At most one change or skeleton version is open at a time (one_open).
iam_policy.entryThe matrix of a version, one row per role, group and level, with the constraint that narrows that level.
iam_policy.waiverThe version's waivers, with the objects each one covers.
iam_policy.skeletonPlatform skeletons (everything of the policy but the matrix and waivers) by digest; the one this host accepted last is in force.
iam_policy.version_diffFor a skeleton version, the diff the host computed, shown to qa byte for byte.
iam_policy.approval_evidenceThe signed token behind every approve, return, confirm and dispute. Readable by the database owner only.

The six tables are written only by the policy's own database functions. A trigger refuses anything else, for every role, the database owner included: no update without the function's mark, no delete (except replacing a cell of a draft), no truncate, one step of the state machine per update, and every status change written to the policy history (status_changed).

The route table (routes.json) gains dual_control: the roles that may approve and the roles that make changes on iam_policy and on iam_users (today qa and admin for both). Since IAM 4.5 the User Manager (who may confirm an account decision, I17) and apply.sh (who may approve a version, who is a maker) read it from there; without the key the User Manager keeps today's roles (qa approves, admin makes) and logs it once.

What a policy apply compiles (IAM 4.5). The database transaction of apply.sh N compiles the grants and the policy's functions from version N itself, not from the host file of the version before: apply.sh stages N's host file in its own mode-700 directory, binds it to the database rows (the entries digest recomputed in SQL and in Python, the body recomputed from the rows) and passes it with its SHA-256 to the database deploy's bundle, which compiles it with cli.py --staged FILE. --staged reads the file with every check of a host file and refuses (exit 2) unless its SHA-256 equals the one apply.sh pinned, and the bundle honours it only under the run's own verified deploy lock: a variable exported in a shell compiles nothing. It is not --file: an unchecked YAML file is never accepted.

python3 apps/iam/compiler/cli.py audit-version --record F (run by apply.sh --audit N, read-only) reproduces an applied version from its record: the compiler of the commit its apply_started names (git archive; its digest must be the recorded one), the version's rows composed with the skeleton it was applied under, the checker, the approval token against the jwk recorded at apply, and every artefact digest against the applied event. It prints one line per check (OK, FAIL, CANNOT) and exits 0 reproduced, 1 a mismatch, 2 cannot reproduce.

Since 4.2a the route table's digest no longer counts its source (the name of the policy it was compiled from) or applied_version: both are still in routes.json, but the same policy gives the same digest whatever it was read from. The digest moved once, at the first ./deploy-infra.sh of slice 4.2a. The configuration API's admission of the policy host's client is checked whether IAM_DB_ROLES is true or false.

The approval diff

What a qa person approves. For a change iam-api computes it from the applied version and the submitted one, both with the skeleton it ships; for a skeleton version apply.sh --propose-skeleton computes it on the host and the database stores it (iam_policy.version_diff).

{"schema": 1, "kind": "change"|"skeleton", "version": N, "against": <applied version>,
 "entries_digest": "<64 hex>",
 "skeleton": null | {"from": "<accepted digest>", "to": "<proposed digest>", "sections": [...]},
 "cells":   [{"group": g, "role": r, "before": {L: constraint|null}, "after": {...}}, ...],
 "waivers": {"added": [...], "removed": [...]},
 "roles":   {role: {"added": [tuple, ...], "removed": [tuple, ...]}, ...},
 "system":  {"added": [...], "removed": [...]}}

Only cells that differ are listed, sorted by the bytes of group and role; roles lists only roles whose reach changes; a tuple is one thing a role or service can reach (a database privilege, a route, a host, an MQTT topic, a tool setting, a level). The document carries no time, commit or compiler version. Its canonical form is JSON with sorted keys, no spaces (, and : as separators) and non-ASCII characters written as themselves, encoded as UTF-8; diff_digest is the SHA-256 of those bytes in lower-case hex. iam-api serves exactly those bytes with the headers X-Medcea-Skeleton-Digest and X-Medcea-Diff-Digest, and the browser hashes what it received before showing it.

The host policy file

state/policy-applied.yaml (mode 600 in a mode-700 state/, not in git, written only by the scripts under the deploy lock):

# medcea-applied: version=N kind=bootstrap|change|skeleton|rollback entries_digest=<64 hex> skeleton_digest=<64 hex> git_commit=<40 hex>[-dirty]|unknown written_at=<UTC>
# medcea-applied-body: body_digest=<64 hex> groups=<n> roles=<n> dropped=<n> keys=<64 hex>
# Written by infra/lib-policy-source.sh (or apps/iam/apply.sh) under the deploy lock …
<the policy: the accepted skeleton with the applied version's matrix and waivers>

entries_digest is the applied version's; skeleton_digest the accepted skeleton's, checked against the body; body_digest covers the matrix and waivers; groups and roles count the version's keys and keys is their digest; dropped counts rows the skeleton no longer has a group or role for. A rewrite happens only when the version, kind, a digest or the second line differs, or the body differs from the database; a new written_at or commit alone is not a difference. state/seed-facts.jsonl (account facts waiting for the history), state/break-glass/ (break-glass copies) and state/retired-<time>-<why>/ (files moved aside) live next to it.

IAM switches

Change these with ./guide.sh (IAM switches), which checks each switch's preconditions and runs its enable or rollback steps. After a fresh install, IAM switches → Bring IAM to full enforcement turns on every switch still false, in order (see After a fresh install).

NameDefaultMeaning
IAM_GATEStrueEach signed-in host admits the roles compiled from the access policy. false falls back to the pre-policy list (operator, qa, auditor, admin), and every deploy prints a warning.
IAM_NETPOLtrueOne network policy per application pod, so only its sign-in proxy and the listed services can connect to it. false removes them.
IAM_ENFORCEfalsefalse (report-only): every service checks each request against the route table but only logs "would refuse". true: the services answer 401, 403 or 503 to what the route table refuses. The administration side of the User Manager and Database Management refuse in both modes. Takes effect about a minute after ./deploy-infra.sh, without a restart.
IAM_POSTGREST_JWTfalsetrue: the configuration API verifies each person's sign-in token, so writes are attributed to the person and an expired or forged token is refused.
IAM_DB_SERVICE_ROLESfalsetrue: each service connects to the database under its own role instead of the database superuser. pgAdmin then has limited rights: it can no longer change table structure or write data.
IAM_DB_ROLESfalsetrue: the database itself enforces each role's rights, limits operators to their own units and refuses changes to locked records. Refused until IAM_POSTGREST_JWT and IAM_DB_SERVICE_ROLES are on. Operators need units assigned first (apps/iam/units.sh).
IAM_MQTT_PERSONfalsetrue: the MQTT Explorer connects with a short-lived personal credential made from the person's role, accepted only on the broker's WebSocket listener, false: one sign-in check for both listeners, and the Explorer has no credential (its page says it needs true); the shared mqtt-explorer account was removed on 1 November 2026. Needs iam-api (./apps/iam/deploy.sh) and IAM_DB_ROLES=true.

Changes of IAM_DB_ROLES are recorded in the access policy history; so are changes of IAM_MQTT_PERSON, by ./deploy-infra.sh, and every MQTT Explorer credential issued. When ./deploy-infra.sh applies a changed IAM_ENFORCE, it records an enforcement_enabled or enforcement_disabled event there.

Secrets

config.env also holds passwords, client secrets and cookie secrets. ./infra/configure.sh asks you for three of them: ADMIN_PASS, POSTGRES_PASS and the Docker Hub access token DOCKERHUB_PAT. The others are generated by ./infra/configure.sh or ./deploy-infra.sh and must not be edited by hand (./deploy-infra.sh writes its values without them reaching any program's command line): the initial passwords QA_INITIAL_PASS and ENGINEER_INITIAL_PASS (replaced at first sign-in), KC_BREAKGLASS_PASS, GRAFANA_BREAKGLASS_PASS (Grafana's local admin), KC_DEPLOYER_SECRET, one Keycloak client secret and one cookie secret per signed-in host, the database role passwords (SVC_*_DB_PASS, IAM_SVC_DB_PASS, RR_ADMIN_LOGIN_DB_PASS, AUTHENTICATOR_DB_PASS; SVC_SUPERSET_DB_PASS since 6 November 2026), Superset's SUPERSET_SECRET_KEY and SUPERSET_META_DB_PASS (since 6 November 2026; Superset's client secret SUPERSET_CLIENT_SECRET, written by ./deploy-infra.sh from stage C's wiring on) and the MQTT service passwords (MQTT_*_PASS). MQTT_EXPLORER_PASS, the password of the MQTT Explorer's removed shared account, is no longer used: if an older config.env still has it, ./infra/configure.sh says so in one line and it is ignored; you can delete the line.

On the cluster, secrets are kept in Kubernetes Secrets, never as plain values in a deployment, which anyone allowed to read deployments could see. pgAdmin's client secret and its first-start password (the platform admin's, ADMIN_PASS) are in the Secret pgadmin-config since 1 November 2026; before that they were plain values in the pgAdmin deployment. Kubernetes also keeps older copies of a deployment (ReplicaSets) that anyone allowed to read deployments may read too, so pgAdmin's deployment keeps none. If that change is ever reverted, ./deploy-infra.sh puts the plain values back and leaves the Secret unused; it does no harm and can be deleted by hand. Superset keeps all of its secrets and its role mapping in the Secret superset-secrets and its settings in the ConfigMap superset-config; the health check fails if a Superset deployment or ReplicaSet holds a secret as a plain value.

config.env and its backups (config.env.guide-<timestamp>.bak) hold every password. Keep them on the host only. E-mail settings are not in config.env: set them in the User Manager under E-mail settings.
