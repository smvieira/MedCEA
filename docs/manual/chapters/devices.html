Edge devices

The boards in the growing chambers are ESP32 microcontrollers. A SENSE board reads the chamber and publishes measurements. A CONTROL board receives the scheduler's commands and switches equipment through relays. Each board fills one slot: one unit, one zone, one role. A board joins the fleet through onboarding. Someone plugs it into the platform host over USB, signs in, picks a free slot and says what is wired to it. The onboarding run then erases and flashes the board, joins it to WiFi, gives it its own broker credential and registers it in that slot. This chapter covers who may do that, the steps of a run in the browser and in a terminal, how a SENSE board's wiring is drawn on screen, the health and test messages a board sends, how to replace or move a board, how board credentials work, and what the platform records.

SENSE and CONTROL boards

Every board runs the same application. What makes it a SENSE or a CONTROL board is a small configuration file that onboarding writes onto it. That file holds the role, the slot, the broker credential and, for a SENSE board, its sensors and their pins. A CONTROL board also gets a pin map file with the relay channels chosen during the run.

RoleWhat it doesMQTT topics
SENSEReads its sensors at a fixed interval (30 seconds by default) and publishes one message per measurement tag. A SENSE board may carry several sensors.Publishes to medcea/<UNIT>/<ZONE>/sense/<tag>/<sensor>
CONTROLDrives a relay board. It receives the scheduler's commands for its zone, switches the relay channels and reports what it actually did.Receives medcea/<UNIT>/<ZONE>/control/#; reports on medcea/<UNIT>/<ZONE>/control_setpoint/...

The topic root is the platform's project name, medcea. The unit and zone segments are the codes as the Units tab shows them.

The sensor in the topic (since 13 November 2026, feedback control Phase 1). A reading's last topic level names the sensor that took it: its id on the wiring screen (sht45_1, scd30_1), or, for a board set up through the questions, its driver (scd30; a second sensor of the same driver at position 3 is scd30_3). The message carries it too, as "sensor". So two sensors may publish one tag, for example an SHT45 and an SCD30 both on air_temperature, and they stay two series: the Run Monitor shows one value per sensor and Grafana one line per sensor (see Run Monitor and Grafana), and the zone's control loops say which one a loop controls on (Control loops of a zone). A board flashed before then ends its reading topics at <tag>, one level shorter; the platform still accepts that form and calls its sensor default, which is why no sensor may have the id default. Re-onboard such a board to give its readings their sensor names. The health and test messages keep their topics (…/sense/_health, …/sense/_test) and carry no sensor.

The wiring screen also offers the TCA9548A I2C hub (eight channels, address 0x70 to 0x77). Besides its readings, every board sends a test message at start-up, and a SENSE board a health message; see Health and test messages.

The CONTROL template describes an 8 or 16 channel relay board. Its equipment is the red, blue and UV grow lights, the air heater pad, the air cooler, the humidifier, the air flow fan, the CO2 fan, the CO2 flow steriliser and the substrate heater.

Slots

A unit is a physical chamber and a zone is one area inside it. Both are created in the Units tab of the Configuration UI before any board is onboarded. The onboarding wizard reads units and zones from the database and never creates them.

Each active zone has exactly two slots, one per role:

UNIT01 / ZONE01  ->  unit01-s-zone01   SENSE: reads the chamber
                     unit01-c-zone01   CONTROL: drives the chamber
  • A slot is free when no active device of that role is in the zone. Only free slots are offered.
  • A slot is taken when an active device of that role is in it. The wizard lists taken slots with their board, but you cannot pick them.
  • A slot is not offered when its unit and zone codes cannot make a legal board name. The wizard says why. See Device names.
  • Slots in an inactive unit or an inactive zone are left out.

This rule is read from the live device table on every run. To free a slot, mark its device Inactive in the Devices tab. Onboarding a board into a slot that already has a device record updates that record in place. It never creates a second one.

The one-SENSE, one-CONTROL rule also limits harm. A board can publish only under its own slot's topics, and a second board cannot quietly start driving a chamber that already has a controller.

Device names

A board has one name, built from its slot:

lower(unit code) - s|c - lower(zone code)

UNIT02 + CONTROL + ZONE02  ->  unit02-c-zone02

The same name is the board's DHCP hostname, its Hostname (DHCP) in the Devices tab, the device_dns field in every MQTT message, its broker user name, and the file name of its provisioning record. Lowercasing is the only change made to the codes, so the name stays readable and is the same every time the slot is onboarded. Unit codes are unique ignoring case, and zone codes are unique within their unit ignoring case, so two slots can never get the same name.

The codes must produce a legal hostname:

  • letters, digits and hyphens only, with no hyphen at the start or the end;
  • at most 32 characters, the longest hostname a MicroPython board accepts.

A slot whose codes break either rule is listed as not offered, with the reason, for example a code containing an underscore or a space. There is no fallback name. To use the slot, rename the unit or zone code in the Units tab. After the board boots, the run reads the hostname back from the board and warns if the board kept a different one.

A board onboarded with --unregistered is named cea-un-<mac6>, where <mac6> is the last six hex digits of its MAC address. The un shows at a glance that it has no slot.

The board does not answer .local names: it runs no mDNS responder. Use the IP address printed at the end of the run and kept in the provisioning record. A DHCP reservation on the router keeps that address stable.

Before the first onboarding

These are one-time tasks for the administrator of the platform host.

  1. Serial port access. The account that runs the wizard must be in the dialout group. ./deploy-infra.sh adds it, as its last step. The wizard service keeps its old group list until its user service manager restarts, and that restart closes every desktop program of the account, so ./deploy-infra.sh restarts it only when it runs over SSH or on a text console with no desktop session of the account open. On a desktop it says so instead, and ./install.sh repeats it at the end: reboot the host once after the install. To do it all by hand, signed out of the desktop (from SSH or a text console): 
    sudo usermod -aG dialout "$USER"
sudo systemctl restart "user@$(id -u)"
    Logging out of the desktop is not enough: the wizard service keeps the user service manager running (linger). Confirm with id -nG in a new login.
  2. The wizard service. ./install.sh and ./deploy-apps.sh --all run ./apps/edge-wizard/deploy.sh. It installs the cea-edge-wizard service on the host and publishes it at https://onboard-device.<domain>. If the service is not running, the Onboard Device button gives a connection error. ./health-check.sh checks that it answers. It restarts the service, so it refuses while an onboarding run started from the wizard is in progress; run it again when the run has finished. It prints the roles the wizard admits.
  3. Sign-in. ./deploy-infra.sh creates the Keycloak client edge-wizard and writes EDGE_WIZARD_SECRET into config.env. Without it the wizard cannot sign anyone in.
  4. Units and zones. Create them in the Units tab, with codes that make legal names.
  5. Firmware. Nothing to do. edge/firmware/ may start empty: the run offers MicroPython images for the detected chip and downloads one on request.

The same tasks are in ./medcea.sh under Edge devices: flash and register a board, send a test message as a board (see Sending a test message), show flash-device.sh's options, install or update the browser wizard service, and (since 13 November 2026) Choose a zone's control loops, which runs ./edge/flash-device.sh --loops-only (see Control loops of a zone).

The provisioning records in edge/provisioned/ hold each board's WiFi passphrase, WebREPL password and MQTT password in plain text. The files are readable by their owner only and are not in git. Keep them that way, and include the folder in host backups only if the backup is protected.

Onboarding from the browser

This is the normal way. Onboarding always happens over USB on the platform host: the cable proves the board is in your hands, and the sign-in says who you are.

  1. Plug the board into a USB port of the machine that runs the platform.
  2. Open the Configuration UI at https://config.<domain>, go to the Devices tab and press Onboard Device. It opens https://onboard-device.<domain> in a new tab.
  3. Sign in with your platform account.
  4. The page "Onboard a device" shows one tile per device type. Pick ESP32 / ESP32-S3. Tiles marked planned or unavailable cannot be started.
  5. Answer each question as the page shows it. The page also shows the live log and the current step. The questions are described in The steps of a run.
  6. At the end, read the summary card: IP address, hostname, unit and zone, role, broker, topics, and whether the device record was written. Copy the WebREPL password if you need it. Below it, Send test message sends one test message as the new board; see Sending a test message.
  7. Return to the Devices tab. The new board appears under its unit and zone.

sign out, next to your name at the top of the wizard page, signs you out of the whole platform, like Sign out in the user menu: the sign-in page asks "Do you want to log out?", and when you confirm you pass through the AI Workbench (when it is installed) and land on the portal's sign-in page. Until 6 November 2026 it ended your platform sign-in but not the portal's own session, so the portal stayed open for up to 4 minutes.

The service runs one onboarding at a time. A second start while a run is in progress is refused with "a device is already being provisioned".

Do not use the Add Record button to add a board. It creates an inventory entry only, with no flash, no slot check and no broker credential.

Onboarding from a terminal

The same run works in a terminal on the platform host, for example over SSH:

./edge/flash-device.sh

Before it reads the free slots, the script shows a sign-in box:

This run reads and writes the platform database as you.
On any device with a browser open:  https://keycloak.<domain>/realms/medcea/device
and enter the code   XXXX-XXXX

Open that address on any phone or computer, sign in, and enter the code. The code expires after about ten minutes. Once you are signed in, the script prints "signed in as <name> (<user>, <role>)" and every database call in the run acts as you. Press Ctrl+C while it waits to stop without writing anything. The device code appears only in the terminal and is never shown on a web page.

Only an account holding engineer or maintenance may onboard. Any other account is refused right after the sign-in with a message naming those roles, and nothing is touched.

Useful options (./edge/flash-device.sh --help lists all of them):

The steps of a run

The questions that only the person at the chamber can answer (role, slot, wiring) come first, before the board is touched, so a board is not left half onboarded because someone walked away. Two questions come later: the go-ahead to erase, and the WiFi network, which the board can only scan once it runs MicroPython. The browser page and the terminal ask the same questions in the same order.

  1. Sign in. In the browser you are already signed in. In a terminal, enter the device code. A run that is not registering a board (--unregistered) skips this.
  2. Role. "What is this board for?" Pick SENSE or CONTROL.
  3. Slot. "Which unit and zone is this board going into?" Only free slots of that role are listed, each with the name it will give the board. If there is exactly one, it is chosen for you. If none is free, the run stops and says to mark the existing device Inactive or add a zone.
  4. What is wired. For a SENSE board in the browser, "How is this board wired?": Wire the sensors on screen, one Start from a saved board: <title> per board template that is valid, or Answer one sensor at a time (questions). The screen is described in Wiring a SENSE board on screen. The questions (and a terminal run without --wiring or --board-template) ask "Which sensor is wired to this board?", one sensor at a time, then each sensor's pins, for example the 1-Wire data pin of a DS18B20. Pick Done when every sensor is listed. For a CONTROL board, the run shows the reference wiring, equipment against GPIO pin, and asks "Use this reference wiring?". Answer no to set the pins yourself or to remove equipment the chamber does not have. See The channel-map editor.
  5. Control loops. When the zone will have both a SENSE and a CONTROL board once this board is in, and your role may change control loops, the run shows the zone's control loops: which sensor each recipe quantity is controlled on, and which actuator it drives. See Control loops of a zone. Nothing is saved at this point; the loops are saved right after the registration.
  6. Interval. For a SENSE board, the publish interval in seconds (30 by default). A CONTROL board's command poll interval (100 ms) is asked only with --advanced. The run then prints what it inferred without asking: broker address and port, topics and the board's name.
  7. Serial port. Detected automatically. If the account cannot open the port, the run says so and points at the dialout fix.
  8. Board check. The run reads the chip type and MAC address from the board. Two checks happen here, before anything is erased:
    • If this board is already registered in another slot, the run asks the move question. See Moving a board.
    • If the pin map (CONTROL) or the wiring (SENSE) was checked against a different chip than the one plugged in, the run checks it again against the real chip. If it cannot work on that chip, the run stops and says what to do instead.
  9. Firmware. The newest local image for this chip is the default. Images from micropython.org are offered for download. Only images that match the detected chip are listed.
  10. Erase and flash. "Erase and flash this board?" Yes wipes the whole chip, then writes MicroPython.
  11. WiFi. The board scans the air with its own radio. Pick a network, or enter a hidden one by name, then type the passphrase. Show next to the field reveals what you typed, in your browser only. A network missing from the list is usually 5 GHz only: these boards hear only 2.4 GHz. The board then tries the network at once. If it gets an address, the run says "joined" with that address and goes on. If not, the run says why ("refused the board": a wrong passphrase, or an access point that gave up on the handshake; the network is not visible; or no address within 20 seconds) and asks what next: type the passphrase again, choose another network, or continue anyway. If you continue anyway, the board is still checked after its restart, and it is not registered without an address.
  12. Files. The run generates a WebREPL password for this board only, writes the board's configuration file, its pin map (CONTROL), the platform's certificate authority (for the broker's certificate) and the application, boot.py last, then restarts the board and waits for it to report an IP address. A file that fails to copy is tried up to three times; the log says "on attempt 2" when a retry was needed, and shows the copy tool's own error when all three fail.
  13. Registration. If the board came online, the run writes its device record, one component record per sensor (or one for the relay board), and the hash of its broker password. If the board never reported an IP address, it is not registered and the slot stays free.
  14. Record and summary. The run writes edge/provisioned/<name>.json and prints the summary.

Back and Cancel (since 5 November 2026). The questions asked before the board is touched (what the board is for, its slot, what is wired to it, and since 13 November 2026 the zone's control loops) have a Back button: it returns to the previous of these questions, and the answers of that part are asked again. On WiFi, Back from the passphrase or from a hand-typed network name returns to the network list. Questions after the board is touched have no Back. Cancel onboarding, shown while a run is active, stops the run at its next question or step; only the person who started it can cancel it. A flash write in progress finishes first, because a write stopped half-way leaves a board that must be flashed again. Once the board's files are written, Cancel is no longer offered: the run checks and registers the board, so the new passwords now on it are kept in its record. The log then says "cancelled" and what was left: nothing changed, if the board had not been erased yet; otherwise a board that must be onboarded again. A cancelled run has registered nothing. In a terminal, type < at one of these questions to go back.

If a registration is refused, the board is still flashed and running. Fix the cause and onboard the same slot again. The slot's record is updated in place.

The board in download mode: most boards reset themselves for flashing. If the run cannot talk to the board, hold BOOT, tap RESET, release BOOT, and try again.

The channel-map editor and the board check

When you answer no to the reference wiring in the browser, the page shows the channel map itself: a table of relay channels, every command the scheduler can send, and the pin map file being built as you type.

  • Board selector. It defaults to esp32s3, what this fleet runs. ESP32, S2, S3, C3, C6, H2 and P4 are offered. Changing it checks the map you have against that chip, without rewriting it.
  • Pin reference. Opens the table of every GPIO on the selected chip and what else already uses it.
  • Each row shows its pin's type as you type the number. Pins that cannot work (input-only pins, pins used by the SPI flash) are errors. Strapping, PSRAM, USB-JTAG and console pins are warnings.
  • Missing equipment. Clear the equipment the chamber does not have. Every command that needed it is then left out of the board's table, rather than shipped as a command that does nothing and still reports success.
  • Reset to reference wiring puts the reference layout back.

The page refuses to submit a map with errors. The run checks the map again when it gets it, and a third time against the real chip after probing, before the erase. In a terminal the same step asks for one GPIO per piece of equipment. Answer blank or - for equipment the chamber does not have.

The same editor exists as a standalone page for inspecting or correcting a map away from the platform:

./edge/tools/build-editor.sh        # writes edge/tools/actuator-config-editor.html
python3 edge/src/host/device_template.py pins CONTROL esp32c3   # the pin table in a terminal

Wiring a SENSE board on screen

Since 6 November 2026 a SENSE board's sensors can be wired on screen in the onboarding wizard. At "How is this board wired?" choose Wire the sensors on screen, or Start from a saved board: <title> to open the same screen with that board already drawn. The screen draws the board, its I2C buses, an optional hub and the sensors as pictures, and you connect them with wires, as on the bench. Every change is checked at once, with the same rules the run applies again afterwards.

Part of the screenWhat it does
Board chipThe chip the wiring is checked against. Only the ESP32-S3 (the ESP32-S3-DevKitC-1) can be chosen so far; the other chips are listed greyed out. For another chip see "A board that is not an ESP32-S3" below.
Start fromKeep the current drawing, start from an empty board, or load a board template. A template that does not fit is listed with its first error.
AddOne button per part: + Sensirion SHT45, + Sensirion SCD30, + DFRobot SEN0562 (IP68 ambient light), + TCA9548A I2C hub and + I2C bus.

The panel of the selected partBoard: per bus its SDA and SCL pins, Clock, Driver (software or hardware I2C; the board gives either a 250 ms timeout for the SCD30's clock stretching, set on software I2C too, but only hardware I2C was bench-tested: choose hardware for an SCD30) and Pull-ups; Remove this bus. Tags and renaming. Each reading is published under a tag and the sensor's id, the last two parts of its topic (medcea/<UNIT>/<ZONE>/sense/<tag>/<sensor id>). The defaults are the platform's usual names (air_temperature, air_humidity, co2, light_intensity). Two sensors may publish the same tag (since 13 November 2026): an SHT45 and an SCD30 both on air_temperature stay two series, told apart by the sensor id, and the zone's control loops say which one a loop controls on. Rename a tag only when the reading means something else, for example a second SHT45 at the top of the chamber as air_temperature_top; a control loop reads only the four tags of Control loops of a zone. A sensor id may not be default. A tag is a lower-case letter followed by up to 47 lower-case letters, digits or _; names starting with _ are kept for the board's own messages (_health, _test). A reading switched off is not published; a sensor with every reading off stays on the board and in its device record, since the hardware is fitted.

What the checks refuse (errors) and what they only warn about:

  • A pin the chip does not have, or one that cannot work (the SPI flash pins, an input-only pin for SDA or SCL); a pin used twice.
  • Two parts that answer the same address on one segment of a bus, for example "sht45_2 answers 0x44, like sht45_1 on the same segment." A segment is one hub channel plus whatever sits directly on the bus. The same address behind two different channels, or behind two different hubs, is allowed: that is what a hub is for.
  • One sensor publishing two of its readings on one tag: "scd30_1 already publishes temperature as air_temperature: one sensor cannot publish two readings on one tag." Two different sensors on one tag are allowed since 13 November 2026 (until then this was refused too).
  • A sensor with the id default: "default is reserved: the platform calls the sensor of a reading that names none "default". Give this sensor another id."
  • A sensor with no wire ("drag a wire from the board or hub to it"), an address the part cannot take, a clock faster than a part on the bus allows, and a board on which no sensor publishes anything.
  • Warnings: pins with another use (strapping, USB-JTAG, the octal PSRAM, the console), no or internal pull-ups ("fit 2.2 kΩ to 3V3"), a hub nothing is wired to, a sensor with every reading off, and a part to be powered from 5 V rather than the board's 3V3.

Continue sends the wiring to the run, which checks it again and stops before the erase if it finds an error. When Save as a board template is ticked, the run then saves the template under the name of the person signed in. A refused save (a name taken without Replace, a name that is a shipped template) is a warning and the run goes on.

Board templates. A board template is a named wiring. The platform ships two, both an ESP32-S3-DevKitC-1 with one hardware I2C bus on GPIO 8 (SDA) and GPIO 9 (SCL) at 100 kHz with external pull-ups and a TCA9548A hub at 0x70 (on the bench, a SparkFun Qwiic Mux, BOB-16784):

  • Sense board as bench-tested 6 Nov 2026: hub + SHT45 ch7 + SCD30 ch6: the wiring the owner's I2C hub bench test passed on, the SHT45 on hub channel 7, the SCD30 on channel 6 (CO2, and since 13 November 2026 its temperature and humidity too), channels 0 to 5 empty and no light sensor. Start from this one for the bench board.
  • Sense board, chamber design map: hub + SHT45 ch0 + SCD30 ch1 + SEN0562 ch2: the channel map of the Edge Layer note for the chamber build. The SEN0562 has not been bench-tested yet.

Whichever is used, the channels on screen must be the ports the cables are in: a sensor on another port reports "ok":false in its health message ("ENODEV") and the others carry on. Shipped templates are in edge/templates/boards/; saved ones in edge/board-templates/, which is kept in git so a saved board can be reviewed and shared. A template is checked again whenever it is listed or used. To list them on the host: python3 edge/src/host/device_template.py board-templates SENSE.

Check the wiring before onboarding. edge/tools/i2c_hub_test.py is the I2C hub bench test the bench template comes from. It runs on the board itself and changes nothing on the platform. Set the lines of its CONFIG block (SHT45_CH, SCD30_CH, LUX_CH, the pins) to the ports the cables are in, then run it with Thonny (F5) or mpremote connect <port> run edge/tools/i2c_hub_test.py. It checks that only the hub answers on the root bus, that each sensor answers on its own channel and on no other (a cable in the wrong port prints a hint naming the port it found), reads the SHT45 and the SCD30, and runs 20 hub-switching cycles; it ends with ALL PASS or a list of failures. Use the same channels on the wiring screen. The test sets the SCD30 to measure every 2 s, as the board firmware does. A test file in the repository (tests/test_i2c_hub_test.py) keeps the script's channels and pins equal to the bench template's.

Onboarding a slot again. When the slot's board was onboarded on screen before, the screen opens with the wiring its provisioning record holds.

The questions instead. Answer one sensor at a time (questions) keeps the older way, one sensor and its pins at a time. It offers the sensors that sit on their own pins (SCD40/41, SCD30, DS18B20, water level), not the SHT45, the SEN0562 or the hub. Boards onboarded that way keep working unchanged.

In a terminal. --wiring FILE takes the wiring from a document (or a board template file) and --board-template NAME from a template, with no questions; both are checked before the board is touched. Without either, a terminal run asks the questions.

A board that is not an ESP32-S3. The screen's pin table is the ESP32-S3's, and the reference pins GPIO 8 and 9 are the SPI flash pins of an original ESP32 ("GPIO8 is wired to the module's SPI flash. Driving it crashes the board."). When the plugged-in chip differs from the one the wiring was checked against, the run checks it again against the real chip after probing, and stops before the erase if it cannot work there. For such a board choose Answer one sensor at a time (questions), or give --wiring FILE with board.variant set to the chip (for example esp32c3) and no board.part.

The accepted wiring goes into the provisioning record ("wiring"), and each sensor becomes one component record of the device, with its driver, address, bus pins, hub and channel, and the tags it publishes. A saved board template records who saved it and when (saved_by, saved_at, and replaced_at when it replaced one).

On the board, all sensors on one bus share it; a hub channel is opened before each sensor is read, and any channel open on another hub of the same bus is closed first, so only one channel is ever on the wire. A sensor that fails does not stop the board: see the health message below.

Control loops of a zone

A recipe run controls each zone through its control loops (since 13 November 2026, feedback control Phases 1 and 2). A loop reads one reading of the zone, compares it with the current recipe step's limits, and drives one actuator of the zone's CONTROL board. Which sensor a loop reads is always the choice of the person who onboards (owner decision Q20): when several sensors publish the same reading, the platform never picks one by itself.

LoopReading (tag)Recipe limits it uses
Air temperature (air_temperature)air_temperatureAir temperature lower and upper limit
Air humidity (air_humidity)air_humidityRelative humidity lower and upper limit (hr_lower_limit, hr_upper_limit)
CO2 (co2)co2CO2 lower and upper limit. It drives the fans, so its commands are mapped: when the algorithm says DOWN (too much CO2) the fans go UP; UP and OFF switch them OFF. This map is fixed.
Substrate temperature (substrate_temperature)ground_temperatureSubstrate temperature lower and upper limit

Where you choose them

  • During onboarding, as the step Control loops after the wiring and before the board is touched (The steps of a run). It is shown only when the zone will have both boards once this one is in: the board being onboarded counts with the sensors or relay channels just chosen. Back returns to the wiring.
  • On its own, with no board and no USB: the tile Control loops of a zone on the wizard's "Onboard a device" page; ./edge/flash-device.sh --loops-only (with --unit and --zone to skip the question) in a terminal; or ./medcea.sh → Edge devices → Choose a zone's control loops. Each signs you in, asks the zone (any active zone, also one whose slots are taken), shows the picker and saves.

The picker

The picker heads with the zone ("Zone UNIT01 / ZONE01 — the sensors of the board you are onboarding") and shows one row per loop (a loop the zone has no reading or no suitable actuator for cannot be ticked, and the row says why), in the columns Control (the tick), Quantity, Sensor, Max age (s), Actuator and Mode.

  • One sensor publishes the reading: it is chosen for you ("on one sensor").
  • Several sensors publish it: nothing is chosen, and the row stays in error until you decide, for example "air_temperature has 2 sensors (scd30_1, sht45_1): choose the one it controls on, or mean/min/max, or mark it not controlled". Choose on one sensor and the reference sensor, optionally with a fallback (another of the sensors, used while the reference has no fresh reading); or mean of the ticked, lowest of the ticked or highest of the ticked; or untick the row, and the quantity is not controlled.
  • Max age (s): how old a reading may be and still count, a whole number of seconds from 1 to 3600 (90 when left empty).
  • Actuator: one of the zone's CONTROL board actuators that takes every command the loop sends; one loop per actuator. Mode is command (UP, DOWN, OFF) in this release; levels need the PWM outputs of a later phase.
  • The note under the zone says what saving does. A zone with no loops yet: "This zone has no control loops yet, so it runs on the default map: a tag with one sensor uses it, a tag with several gets no data and an alarm." A zone with loops: "Saving replaces this zone's loops with the ticked rows: a loop you untick is stopped."
  • Decide later saves nothing: the zone keeps what it has. It is a choice of this run only and writes nothing to the database.
  • Stop all loops (only when the zone has loops) first asks "Stop every control loop of zone ZONE01? The zone goes back to the default map …"; confirmed, it saves the zone with no loops.
  • The findings list below says what is wrong, in plain words; the page does not continue while there is an error. Warnings name, for example, a board that publishes without sensor names ("… flashed before Phase 1: re-onboard this SENSE board so its readings carry the sensor name; until then it is no loop's source").
  • Onboarding a board again never deletes a loop silently. A saved loop whose sensor or actuator the new board takes away is reported in the run's log ("control loop … reads …, which zone … will no longer have") and stays in the picker in error until you choose again or stop it.

In a terminal the same choice is one menu per reading that has several sensors, then the fallback. A run with --yes and no terminal chooses nothing (decided later). The run checks the answer again, and the database checks it a third time when it saves. During onboarding the loops are saved right after the registration, with your sign-in; a save that is refused never undoes the onboarding, the run says why and how to choose them later.

What a run does with them

  • A zone with saved loops runs on them; a reading you did not tick is not controlled.
  • A zone with no saved loops runs on the default map, decided zone by zone: for each loop, a reading with exactly one sensor that reports in time uses it; with several, the loop gets no data and the run log shows ALARM ambiguous_source naming them ("choose the reference in onboarding"). The health check warns about such zones (Control loops).
  • When the reference sensor has nothing fresh, the fallback takes over, with an alarm (fallback_in_use). When no source is fresh, the loop holds its last command and the run log shows ALARM no_fresh_data; it never switches the fans off for lack of data.
  • A recipe step without a limit for a loop leaves that loop inactive for the step, with a warning in the run log.
  • A run reads its loops once, at its start. The loops cannot be changed while the unit has a run running or scheduled.

The run log, the alarms and the administrator's view are in Control loops.

Who may change them

  • Only engineer, and only with IAM_DB_ROLES=true, when the database acts as each person. Otherwise the run says "control loops can be chosen only with IAM_DB_ROLES=true" and goes on without the picker.
  • maintenance may re-onboard a board, but gets no picker: "maintenance does not choose control loops: an engineer does (./edge/flash-device.sh --loops-only --unit … --zone …)". The run goes on.
  • Every other role is refused by the wizard's sign-in, as for onboarding.
  • While the unit has a run running (R) or scheduled (S), nothing is offered: "Unit … has run … The loops of … change only while no run is running or scheduled, so this goes on and leaves them as they are." The database refuses any change in that state, whoever asks.

Each loop is a row of medcea.control_loop, written only through the database function medcea.save_zone_loops with the person's own sign-in, stamped with who created and last changed it (account, person, name, role), and every change is appended to medcea.row_change. A stopped loop is deactivated, never deleted. The provisioning record of an onboarding carries what the run chose ("control_loops"). Every cycle of a run records the loops it ran with in its run parameters (control_loops, and control_loops_source: table, default or mixed), and the run log holds each alarm.

Health and test messages

Besides its readings, a board sends two kinds of message of its own. Both carry the fields of a reading but its sensor (unit_code, zone_code, msg_type, timestamp, device_id, device_dns, tag), plus the board's network address ip and its MAC address mac (each null when the board cannot read it), and no value or unit.

MessageTopicStored asWhenExtra fields
Healthmedcea/<UNIT>/<ZONE>/sense/_healthHBA SENSE board, at start-up and whenever a sensor goes down or comes back.sensors: one entry per sensor, {"id", "ok", "err"}; err is the reason in at most 80 characters, or null.
Test…/sense/_test (SENSE), …/control_setpoint/_test (CONTROL)TSEvery board once at start-up, right after it first connects to the broker; and from the host on request (Sending a test message).source: board-boot, wizard or cli; firmware: the MicroPython release, for example 1.29.0. A test sent from the host also carries "sent_from": "host".

A CONTROL board sends no health message: it may publish only under its control_setpoint topics, which is also why its test message goes there.

A sensor that fails no longer restarts the board (since 6 November 2026; before, a SENSE board on which no sensor answered restarted every 15 seconds and never connected). The board connects, says in its health message which sensor is down and why, keeps publishing the others, reads a sensor that stopped answering again at every cycle, and sets up one that failed at start-up again every 10 minutes. Only the broker restarts it: unreachable when the board starts, or refusing ten publish cycles in a row. An SCD30 is given its first minute to warm up before "no reading yet" counts as down. A cycle with nothing to publish keeps the connection alive with a ping.

How the type is set. The ingest flow in Node-RED takes the type from the topic, not from the message: exactly <root>/<UNIT>/<ZONE>/sense/_health is stored as HB, and exactly …/sense/_test or …/control_setpoint/_test as TS, whatever type the message names. So a test message can never be stored as a reading. A message on any other topic that names HB or TS is dropped, with the line dropped: TS is not allowed on <topic> in Node-RED's log. A CONTROL board's pin report is one topic level longer, so a pin labelled _test is still stored as a report (SP).

Where to find them.

  • MQTT Explorer (engineer): under the slot's topic, the tags _health and _test, as they arrive.
  • The database: medcea.measurement, with msg_type HB or TS and the whole message in msg. The Run Monitor, the Grafana dashboards and the measurement views read readings (AP), commands (CT) and reports (SP) only, so neither type appears there. An engineer can look with Grafana's Explore, for example SELECT measure_timestamp, device_dns, msg->>'source' AS source, msg->>'sent_from' AS sent_from FROM medcea.measurement WHERE msg_type = 'TS' ORDER BY measure_timestamp DESC LIMIT 20; qa, qp and auditor through a Database Management export of the telemetry.

Both types are stored once ./apps/database/deploy.sh (migration 009) and ./apps/node-red/deploy.sh have run. Before that the database refuses them, as it did every _health message until 6 November 2026, and Node-RED logs the refused insert.

Sending a test message

A test message sent from the host, as the board, proves the board's path to the platform without touching the board: its broker credential, its topic rights, the broker's TLS name and the ingest flow together. It connects with the board's own credential, read from its provisioning record, over the boards' TLS port, and publishes one TS message on the topic the board itself uses. The password never appears on the command line, on screen or in a log.

  • In the wizard. After a run that registered a board, the page shows Send test message. Only the person who started the run may use it; their onboarding role is checked again first. The wizard takes the board from the run, never from the page. It answers "Sent at <time> on <topic>; look for tag _test in the MQTT Explorer.", or "Not sent: <reason>" (for example not authorised, the broker's answer to a credential it does not know: a board marked Inactive or onboarded again since). One message every 5 seconds: "One test message every 5 seconds — try again in a moment." A run that did not register a board offers no button. A --ui run's page stops a few seconds after the run ends; use the command below instead.
  • In a terminal on the platform host: ./edge/flash-device.sh --send-test unit02-s-zone01. No USB and no sign-in; it needs the board's record edge/provisioned/<name>.json, the platform's certificate authority .ca/ca.crt, and the broker address and name from config.env (or --mqtt-host, --mqtt-port, --mqtt-tls-name, the only options it takes with it). It prints one line such as {"ok":true,"topic":"medcea/UNIT02/ZONE01/sense/_test",…} and exits 0 when sent, 1 when the network or the broker refused, 2 when the record cannot be used (no record, a board onboarded with --unregistered, no broker credential, or a record the board left behind: when a board is moved to another slot or onboarded again under another name, its old record stays in edge/provisioned/ but its old credential is retired, so the command refuses it and names the board's later record, for example "this record is superseded: the same board was onboarded later as unit01-s-zone01 … Send as unit01-s-zone01.").
  • In medcea.sh: ./medcea.sh → Edge devices → Send a test message as a board lists the registered boards that have a record, only the latest record of each board (by its MAC address), and runs the command above.

"Sent" means the broker accepted the message. The broker also acknowledges a message its access rules refuse, and drops it silently, so look for tag _test in the MQTT Explorer, or the TS row in the database, to see it arrived.

Each test message is a TS row in medcea.measurement; one sent from the host says "sent_from": "host" and "source": "wizard" or "cli". The wizard's log names the board and the person who sent it, never a credential. Engineers sending a test message from the MQTT Explorer is planned and needs an approved change of the access policy first (see the decision record).

Testing a CONTROL board: commissioning

After a CONTROL board is onboarded, an engineer can check its wiring by sending commands to it by hand from the MQTT Explorer. The broker allows that only while the board's unit is flagged for commissioning (test mode) and has no run in progress:

  1. Make sure no run is running or scheduled on the unit; flagging is refused while one is.
  2. In the Configuration UI's Units tab, click Flag for commissioning… on the unit, give the reason (for example "relay test of the new CONTROL board in zone 2") and click Propose.
  3. Ask a qa person to approve it. Within about 15 seconds of the approval, the broker accepts your messages to the unit's control topics. The MQTT Explorer's Your rights note does not change: it lists your role's pattern, medcea/+/+/control/#, for every unit.
  4. Send the test commands to one concrete topic, for example medcea/UNIT01/ZONE01/control/<actuator> (never the pattern itself: the page refuses + and #), and watch the board's control_setpoint reports. Clicking the topic in the left-hand list shows your message as the broker delivered it.
  5. Click End commissioning… on the unit when you are done. It applies at once; runs can start on the unit again, and qa reviews it afterwards.

The full procedure, the refusals and who sees what are in commissioning a unit.

Replacing a board

Use this when a board fails and a new board takes its place in the same slot. maintenance and engineer may do it.

  1. In the Devices tab, press Edit on the old board, set Status to Inactive and save. The slot becomes free, and within about 15 seconds the broker refuses the old board.
  2. Plug the new board into the platform host and start onboarding.
  3. Pick the same role and the now free slot. Wire it, flash it and let it register as usual.

The registration updates the slot's existing record in place. The record keeps its id, gets the new board's serial number, becomes Active again, and its components are replaced with the ones just chosen. The board gets the same name as before and a new broker password.

To re-flash the same board in its own slot (a firmware update, new pins), onboard it again without deactivating it. The run sees that the board is already in this slot and updates its record in place. The broker password changes.

Replacement is recorded in the slot history as replaced, with the old and the new serial number and the person who did it. Changing the serial number also deactivates the old board's broker credential.

Moving a board

A board's record follows the board, because its serial number (the MAC address) is unique. To move a board to another slot, start onboarding with the board plugged in and pick the new slot. When the run reads the board's MAC address, it finds the existing record and asks:

this board is already registered as unit01-s-zone01 - UNIT01 / ZONE01 (SENSE).
Move this board from unit01-s-zone01 to UNIT01 / ZONE02?
  • Yes moves the record to the new slot. The board takes the new slot's name, its components are replaced, and the old slot becomes free. If the new slot holds an older inactive record with the same name, that record is renamed <name>-<id> and kept inactive.
  • No stops the run before anything is erased or written.

The question comes after the board is probed and before the erase, because that is the first moment both the board and the target slot are known. A run started with -y never moves a board: it stops and asks you to onboard interactively.

maintenance may move a board only into a slot that already has an inactive record. Moving a board into a slot that never had one is an engineer's change.

A move is recorded in the slot history as moved, with the old and new zone, role and name.

MQTT credentials per board

The broker admits nobody anonymously. Each registered board has its own credential:

  • User name: the board's name, for example unit02-c-zone02.
  • Password: a fresh random password minted at every onboarding, so re-flashing a board changes it. The password goes onto the board and into its provisioning record. The platform database stores only its hash.
  • Access by role. The broker lets a SENSE board publish only under its own slot's sense/ topics. It lets a CONTROL board receive only its own slot's control/ topics and publish only its own control_setpoint/ topics.

A sidecar next to the broker rebuilds the broker's password and access files from the database every 15 seconds. Two things follow from that:

  • Deactivation revokes within about 15 seconds. When a device is marked Inactive (devices are retired, never deleted), its credential drops out at the next rebuild. The broker then refuses its next connection and denies its publishes.
  • The first connections of a new board may be refused. The board boots before it is registered. Until the registration lands and the next rebuild picks it up, which takes up to about 15 seconds, the broker refuses the board. The board restarts after 10 seconds and tries again, so this clears by itself.

A board that is not registered (the run was refused, the board had no IP, or --no-register) has a password that the broker does not know, so it cannot publish. Onboard it again once the cause is fixed.

Boards flashed before broker authentication existed have no credential. Re-onboard them.

Boards connect over TLS only (since 5 November 2026), on the broker's LAN port 31884. The board checks the broker's certificate before it sends its password: it must be signed by the platform's own certificate authority, which onboarding copies to the board, and carry the name mqtt.<domain>. So the password never crosses the network in clear, and a machine that pretends to be the broker is refused. The certificate's dates are checked too: a board whose clock is not set yet (no answer from the internet time server at start-up) asks for the time once more and otherwise restarts and tries again. The plain port 31883 is closed, so a board onboarded before that date cannot connect until it is onboarded again. The platform's own services connect inside the cluster on port 1883. With IAM_MQTT_PERSON=true that port accepts no person's credential: the MQTT Explorer's personal credentials work only on the broker's WebSocket listener, behind the Explorer's sign-in (see MQTT Explorer). The shared mqtt-explorer account was removed on 1 November 2026 and is refused on both ports. Watch the board in the MQTT Explorer instead (the onboarding summary says so while IAM_MQTT_PERSON is true).

TLS protects the connection, not the board. The WiFi passphrase and the MQTT password sit in plain text on the board's flash. Anyone holding the board can read them. WebREPL also stays on after onboarding: anyone who reaches port 8266 with the board's WebREPL password gets a full Python prompt and the board's files. Treat a lost board as a lost credential and mark it Inactive.

Slot history and what gets recorded

The database keeps an append-only history of where every board has been. A database trigger writes it on every change to a device record, whoever makes the change: onboarding, the Devices tab or a direct database change. Nobody can edit or delete the history, and it outlives a deleted device record.

EventWhen
placedA device record was created.
movedIts zone or role changed.
renamedOnly its name changed, for example after a unit or zone code was renamed and the slot re-onboarded.
replacedA different board (serial number) took over the record.
removedThe record was deleted.

Each event holds the board's serial number, the zone, role and name before and after, the time, and who made the change: their account, person id, name, platform role and source. A re-flash in place with no change of slot, name or board adds no event.

For each onboarding the platform records: the device record and its components, stamped with the person whose sign-in the run used; the slot history event; the board's credential hash; and on the host, edge/provisioned/<name>.json with the MAC address, chip, firmware file and its SHA-256, MicroPython version, tool versions, the IP at onboarding, the host login that flashed it, the Keycloak account that registered it and, for a SENSE board wired on screen or with --wiring/--board-template, its wiring; and the zone's control loops as the run left them ("control_loops": saved, decided later, or why not chosen). Every stored measurement is stamped with the zone its board was in when the reading arrived.

maintenance and engineer may read the slot history. auditor and qa may read it and export it from Database Management.

Adding a sensor type

The wizard's questions are data, not code. The SENSE questions come from edge/templates/esp32-sense.json and the CONTROL questions from edge/templates/esp32-control.json. Each sensor entry gives its name, the tags it publishes, and the parameters to ask, with the reference build's wiring as defaults. Neither flash-device.sh nor the wizard page changes when an entry is added.

A sensor also needs code on the board to read it: a reading function in the board application (edge/src/app/cea_sensors.py). If that function already exists, the template entry is all that is needed. A new kind of sensor needs a new reading function, which is a developer's change made through the normal review.

A sensor offered on the wiring screen has, in its template entry, a bus block (its addresses and fastest clock), its power rails, the quantities it measures with their default tags, and the name of its picture in edge/templates/parts/; on the board it needs a set-up and a read function in edge/src/app/cea_sense.py. The pictures of the Adafruit boards come from Adafruit's Fritzing library (CC BY-SA 3.0, listed in edge/templates/parts/ATTRIBUTION.md), converted with edge/tools/import-fritzing.py.

New device types in the onboarding page work the same way. Each tile is an entry in edge/catalog.json. An entry whose script is missing or not executable is shown as unavailable.

Bench mode

./edge/flash-device.sh --unregistered

This brings a board up on WiFi with no platform identity, for a bench with no platform deployed. It asks no slot, ships no application, writes nothing to the database and needs no sign-in. The board is named cea-un-<mac6> and has no MQTT credential, so it cannot connect to the broker. It joins WiFi and keeps WebREPL open, so the warning in MQTT credentials per board applies to it too. To give it a slot later, onboard it normally. Nothing has to be undone.

A registered run also offers to continue unregistered when the platform database does not answer or no sign-in is possible. If you accept, the board ends up the same as with --unregistered.

--no-register is different: it flashes the board for a slot with its application and pins, but does not write the device record. The slot still reads as free, and the broker refuses the board until it is onboarded again with registration.
