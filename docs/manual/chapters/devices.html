Edge devices

The boards in the growing chambers are ESP32 microcontrollers. A SENSE board reads the chamber and publishes measurements. A CONTROL board receives the scheduler's commands and switches equipment through relays. Each board fills one slot: one unit, one zone, one role. A board joins the fleet through onboarding. Someone plugs it into the platform host over USB, signs in, picks a free slot and says what is wired to it. The onboarding run then erases and flashes the board, joins it to WiFi, gives it its own broker credential and registers it in that slot. This chapter covers who may do that, the steps of a run in the browser and in a terminal, how to replace or move a board, how board credentials work, and what the platform records.

SENSE and CONTROL boards

Every board runs the same application. What makes it a SENSE or a CONTROL board is a small configuration file that onboarding writes onto it. That file holds the role, the slot, the broker credential and, for a SENSE board, its sensors and their pins. A CONTROL board also gets a pin map file with the relay channels chosen during the run.

RoleWhat it doesMQTT topics
SENSEReads its sensors at a fixed interval (30 seconds by default) and publishes one message per measurement tag. A SENSE board may carry several sensors.Publishes to medcea/<UNIT>/<ZONE>/sense/<tag>
CONTROLDrives a relay board. It receives the scheduler's commands for its zone, switches the relay channels and reports what it actually did.Receives medcea/<UNIT>/<ZONE>/control/#; reports on medcea/<UNIT>/<ZONE>/control_setpoint/...

The topic root is the platform's project name, medcea. The unit and zone segments are the codes as the Units tab shows them.

The sensors the SENSE template offers today:

SensorTags it publishes
Sensirion SCD40 / SCD41co2, air_temperature, air_humidity
Sensirion SCD30co2, air_temperature, air_humidity
DS18B20 substrate probeground_temperature
Analogue water level probewater_level

The CONTROL template describes an 8 or 16 channel relay board. Its equipment is the red, blue and UV grow lights, the air heater pad, the air cooler, the humidifier, the air flow fan, the CO2 fan, the CO2 flow steriliser and the substrate heater.

Slots

A unit is a physical chamber and a zone is one area inside it. Both are created in the Units tab of the Configuration UI before any board is onboarded. The onboarding wizard reads units and zones from the database and never creates them.

Each active zone has exactly two slots, one per role:

UNIT01 / ZONE01  ->  unit01-s-zone01   SENSE: reads the chamber
                     unit01-c-zone01   CONTROL: drives the chamber
  • A slot is free when no active device of that role is in the zone. Only free slots are offered.
  • A slot is taken when an active device of that role is in it. The wizard lists taken slots with their board, but you cannot pick them.
  • A slot is not offered when its unit and zone codes cannot make a legal board name. The wizard says why. See Device names.
  • Slots in an inactive unit or an inactive zone are left out.

This rule is read from the live device table on every run. To free a slot, mark its device Inactive in the Devices tab. Onboarding a board into a slot that already has a device record updates that record in place. It never creates a second one.

The one-SENSE, one-CONTROL rule also limits harm. A board can publish only under its own slot's topics, and a second board cannot quietly start driving a chamber that already has a controller.

Device names

A board has one name, built from its slot:

lower(unit code) - s|c - lower(zone code)

UNIT02 + CONTROL + ZONE02  ->  unit02-c-zone02

The same name is the board's DHCP hostname, its Hostname (DHCP) in the Devices tab, the device_dns field in every MQTT message, its broker user name, and the file name of its provisioning record. Lowercasing is the only change made to the codes, so the name stays readable and is the same every time the slot is onboarded. Unit codes are unique ignoring case, and zone codes are unique within their unit ignoring case, so two slots can never get the same name.

The codes must produce a legal hostname:

  • letters, digits and hyphens only, with no hyphen at the start or the end;
  • at most 32 characters, the longest hostname a MicroPython board accepts.

A slot whose codes break either rule is listed as not offered, with the reason, for example a code containing an underscore or a space. There is no fallback name. To use the slot, rename the unit or zone code in the Units tab. After the board boots, the run reads the hostname back from the board and warns if the board kept a different one.

A board onboarded with --unregistered is named cea-un-<mac6>, where <mac6> is the last six hex digits of its MAC address. The un shows at a glance that it has no slot.

The board does not answer .local names: it runs no mDNS responder. Use the IP address printed at the end of the run and kept in the provisioning record. A DHCP reservation on the router keeps that address stable.

The access policy (apps/iam/policy/defaults.yaml) gives these rights on boards:

The platform database enforces these rights (with IAM_DB_ROLES=true, as on this platform). The wizard reads and writes the platform database as the person who signed in. A person without onboarding rights can open the wizard and sign in, but the database refuses the registration. The wizard then reports that this role may not onboard boards. An administrator can also set EDGE_WIZARD_ROLE in config.env to require one realm role before anyone may use the wizard at all. It is empty by default.

Before the first onboarding

These are one-time tasks for the administrator of the platform host.

  1. Serial port access. The account that runs the wizard must be in the dialout group. ./deploy-infra.sh adds it. To do it by hand: 
    sudo usermod -aG dialout "$USER"
sudo systemctl restart "user@$(id -u)"
    The second command matters: the wizard service keeps its old group list until its user service manager restarts. Confirm with id -nG.
  2. The wizard service. ./install.sh and ./deploy-apps.sh --all run ./apps/edge-wizard/deploy.sh. It installs the cea-edge-wizard service on the host and publishes it at https://onboard-device.<domain>. If the service is not running, the Onboard Device button gives a connection error. ./health-check.sh checks that it answers.
  3. Sign-in. ./deploy-infra.sh creates the Keycloak client edge-wizard and writes EDGE_WIZARD_SECRET into config.env. Without it the wizard cannot sign anyone in.
  4. Units and zones. Create them in the Units tab, with codes that make legal names.
  5. Firmware. Nothing to do. edge/firmware/ may start empty: the run offers MicroPython images for the detected chip and downloads one on request.

The same tasks are in ./guide.sh under Edge devices: flash and register a board, show flash-device.sh's options, and install or update the browser wizard service.

The provisioning records in edge/provisioned/ hold each board's WiFi passphrase, WebREPL password and MQTT password in plain text. The files are readable by their owner only and are not in git. Keep them that way, and include the folder in host backups only if the backup is protected.

Onboarding from the browser

This is the normal way. Onboarding always happens over USB on the platform host: the cable proves the board is in your hands, and the sign-in says who you are.

  1. Plug the board into a USB port of the machine that runs the platform.
  2. Open the Configuration UI at https://config.<domain>, go to the Devices tab and press Onboard Device. It opens https://onboard-device.<domain> in a new tab.
  3. Sign in with your platform account.
  4. The page "Onboard a device" shows one tile per device type. Pick ESP32 / ESP32-S3. Tiles marked planned or unavailable cannot be started.
  5. Answer each question as the page shows it. The page also shows the live log and the current step. The questions are described in The steps of a run.
  6. At the end, read the summary card: IP address, hostname, unit and zone, role, broker, topics, and whether the device record was written. Copy the WebREPL password if you need it.
  7. Return to the Devices tab. The new board appears under its unit and zone.

The service runs one onboarding at a time. A second start while a run is in progress is refused with "a device is already being provisioned".

Do not use the Add Record button to add a board. It creates an inventory entry only, with no flash, no slot check and no broker credential.

Onboarding from a terminal

The same run works in a terminal on the platform host, for example over SSH:

./edge/flash-device.sh

Before it reads the free slots, the script shows a sign-in box:

This run reads and writes the platform database as you.
On any device with a browser open:  https://keycloak.<domain>/realms/medcea/device
and enter the code   XXXX-XXXX

Open that address on any phone or computer, sign in, and enter the code. The code expires after about ten minutes. Once you are signed in, the script prints "signed in as <name> (<user>, <role>)" and every database call in the run acts as you. Press Ctrl+C while it waits to stop without writing anything. The device code appears only in the terminal and is never shown on a web page.

Useful options (./edge/flash-device.sh --help lists all of them):

OptionEffect
--role SENSE or --role CONTROLSkip the role question.
--unit CODE, --zone CODELimit the slot menu to one unit or zone. Type the code exactly as the Units tab shows it; case matters. Only free slots are still offered.
--advancedAlso ask the parameters the template marks as advanced, such as I2C frequency and UART pins.
--port PATHUse this serial port instead of autodetecting.
--offlineUse only firmware already in edge/firmware/.
--no-eraseSkip the full erase. Only for a board you have already erased once.
--uiAlso serve this run as a web page and print its address. Use the printed link, which carries the run's token. It needs port 8088 free, so it cannot run while the wizard service is up; use the wizard service instead.
--no-registerFlash and configure the board for the slot, but do not write the device record. The slot stays free.
--unregisteredBench mode. See Bench mode.

With -y the script does not ask before erasing. It also refuses to move a board that is registered in another slot.

The steps of a run

The questions that only the person at the chamber can answer (role, slot, wiring) come first, before the board is touched, so a board is not left half onboarded because someone walked away. Two questions come later: the go-ahead to erase, and the WiFi network, which the board can only scan once it runs MicroPython. The browser page and the terminal ask the same questions in the same order.

  1. Sign in. In the browser you are already signed in. In a terminal, enter the device code. A run that is not registering a board (--unregistered) skips this.
  2. Role. "What is this board for?" Pick SENSE or CONTROL.
  3. Slot. "Which unit and zone is this board going into?" Only free slots of that role are listed, each with the name it will give the board. If there is exactly one, it is chosen for you. If none is free, the run stops and says to mark the existing device Inactive or add a zone.
  4. What is wired. For a SENSE board, "Which sensor is wired to this board?", one sensor at a time, then each sensor's pins, for example the 1-Wire data pin of a DS18B20. Pick Done when every sensor is listed. For a CONTROL board, the run shows the reference wiring, equipment against GPIO pin, and asks "Use this reference wiring?". Answer no to set the pins yourself or to remove equipment the chamber does not have. See The channel-map editor.
  5. Interval. For a SENSE board, the publish interval in seconds (30 by default). A CONTROL board's command poll interval (100 ms) is asked only with --advanced. The run then prints what it inferred without asking: broker address and port, topics and the board's name.
  6. Serial port. Detected automatically. If the account cannot open the port, the run says so and points at the dialout fix.
  7. Board check. The run reads the chip type and MAC address from the board. Two checks happen here, before anything is erased:
    • If this board is already registered in another slot, the run asks the move question. See Moving a board.
    • If the pin map was checked against a different chip than the one plugged in, the run checks it again against the real chip. If the map cannot drive that chip, the run stops and tells you which board type to pick.
  8. Firmware. The newest local image for this chip is the default. Images from micropython.org are offered for download. Only images that match the detected chip are listed.
  9. Erase and flash. "Erase and flash this board?" Yes wipes the whole chip, then writes MicroPython.
  10. WiFi. The board scans the air with its own radio. Pick a network, or enter a hidden one by name, then type the passphrase. A network missing from the list is usually 5 GHz only: these boards hear only 2.4 GHz.
  11. Files. The run generates a WebREPL password for this board only, writes the board's configuration file, its pin map (CONTROL) and the application, then restarts the board and waits for it to report an IP address.
  12. Registration. If the board came online, the run writes its device record, one component record per sensor (or one for the relay board), and the hash of its broker password. If the board never reported an IP address, it is not registered and the slot stays free.
  13. Record and summary. The run writes edge/provisioned/<name>.json and prints the summary.

If a registration is refused, the board is still flashed and running. Fix the cause and onboard the same slot again. The slot's record is updated in place.

The board in download mode: most boards reset themselves for flashing. If the run cannot talk to the board, hold BOOT, tap RESET, release BOOT, and try again.

The channel-map editor and the board check

When you answer no to the reference wiring in the browser, the page shows the channel map itself: a table of relay channels, every command the scheduler can send, and the pin map file being built as you type.

  • Board selector. It defaults to esp32s3, what this fleet runs. ESP32, S2, S3, C3, C6, H2 and P4 are offered. Changing it checks the map you have against that chip, without rewriting it.
  • Pin reference. Opens the table of every GPIO on the selected chip and what else already uses it.
  • Each row shows its pin's type as you type the number. Pins that cannot work (input-only pins, pins used by the SPI flash) are errors. Strapping, PSRAM, USB-JTAG and console pins are warnings.
  • Missing equipment. Clear the equipment the chamber does not have. Every command that needed it is then left out of the board's table, rather than shipped as a command that does nothing and still reports success.
  • Reset to reference wiring puts the reference layout back.

The page refuses to submit a map with errors. The run checks the map again when it gets it, and a third time against the real chip after probing, before the erase. In a terminal the same step asks for one GPIO per piece of equipment. Answer blank or - for equipment the chamber does not have.

The same editor exists as a standalone page for inspecting or correcting a map away from the platform:

./edge/tools/build-editor.sh        # writes edge/tools/actuator-config-editor.html
python3 edge/src/host/device_template.py pins CONTROL esp32c3   # the pin table in a terminal

Replacing a board

Use this when a board fails and a new board takes its place in the same slot. maintenance and engineer may do it.

  1. In the Devices tab, press Edit on the old board, set Status to Inactive and save. The slot becomes free, and within about 15 seconds the broker refuses the old board.
  2. Plug the new board into the platform host and start onboarding.
  3. Pick the same role and the now free slot. Wire it, flash it and let it register as usual.

The registration updates the slot's existing record in place. The record keeps its id, gets the new board's serial number, becomes Active again, and its components are replaced with the ones just chosen. The board gets the same name as before and a new broker password.

To re-flash the same board in its own slot (a firmware update, new pins), onboard it again without deactivating it. The run sees that the board is already in this slot and updates its record in place. The broker password changes.

Replacement is recorded in the slot history as replaced, with the old and the new serial number and the person who did it. Changing the serial number also deactivates the old board's broker credential.

Moving a board

A board's record follows the board, because its serial number (the MAC address) is unique. To move a board to another slot, start onboarding with the board plugged in and pick the new slot. When the run reads the board's MAC address, it finds the existing record and asks:

this board is already registered as unit01-s-zone01 - UNIT01 / ZONE01 (SENSE).
Move this board from unit01-s-zone01 to UNIT01 / ZONE02?
  • Yes moves the record to the new slot. The board takes the new slot's name, its components are replaced, and the old slot becomes free. If the new slot holds an older inactive record with the same name, that record is renamed <name>-<id> and kept inactive.
  • No stops the run before anything is erased or written.

The question comes after the board is probed and before the erase, because that is the first moment both the board and the target slot are known. A run started with -y never moves a board: it stops and asks you to onboard interactively.

maintenance may move a board only into a slot that already has an inactive record. Moving a board into a slot that never had one is an engineer's change.

A move is recorded in the slot history as moved, with the old and new zone, role and name.

MQTT credentials per board

The broker admits nobody anonymously. Each registered board has its own credential:

  • User name: the board's name, for example unit02-c-zone02.
  • Password: a fresh random password minted at every onboarding, so re-flashing a board changes it. The password goes onto the board and into its provisioning record. The platform database stores only its hash.
  • Access by role. The broker lets a SENSE board publish only under its own slot's sense/ topics. It lets a CONTROL board receive only its own slot's control/ topics and publish only its own control_setpoint/ topics.

A sidecar next to the broker rebuilds the broker's password and access files from the database every 15 seconds. Two things follow from that:

  • Deactivation revokes within about 15 seconds. When a device is marked Inactive, or its record is deleted, its credential drops out at the next rebuild. The broker then refuses its next connection and denies its publishes.
  • The first connections of a new board may be refused. The board boots before it is registered. Until the registration lands and the next rebuild picks it up, which takes up to about 15 seconds, the broker refuses the board. The board restarts after 10 seconds and tries again, so this clears by itself.

A board that is not registered (the run was refused, the board had no IP, or --no-register) has a password that the broker does not know, so it cannot publish. Onboard it again once the cause is fixed.

Boards flashed before broker authentication existed have no credential. Re-onboard them.

The WiFi passphrase and the MQTT password sit in plain text on the board's flash. Anyone holding the board can read them. WebREPL also stays on after onboarding: anyone who reaches port 8266 with the board's WebREPL password gets a full Python prompt and the board's files. Treat a lost board as a lost credential and mark it Inactive.

Slot history and what gets recorded

The database keeps an append-only history of where every board has been. A database trigger writes it on every change to a device record, whoever makes the change: onboarding, the Devices tab or a direct database change. Nobody can edit or delete the history, and it outlives a deleted device record.

EventWhen
placedA device record was created.
movedIts zone or role changed.
renamedOnly its name changed, for example after a unit or zone code was renamed and the slot re-onboarded.
replacedA different board (serial number) took over the record.
removedThe record was deleted.

Each event holds the board's serial number, the zone, role and name before and after, the time, and who made the change: their account, person id, name, platform role and source. A re-flash in place with no change of slot, name or board adds no event.

For each onboarding the platform records: the device record and its components, stamped with the person whose sign-in the run used; the slot history event; the board's credential hash; and on the host, edge/provisioned/<name>.json with the MAC address, chip, firmware file and its SHA-256, MicroPython version, tool versions, the IP at onboarding, the host login that flashed it and the Keycloak account that registered it. Every stored measurement is stamped with the zone its board was in when the reading arrived.

maintenance and engineer may read the slot history. auditor and qa may read it and export it from Database Management.

Adding a sensor type

The wizard's questions are data, not code. The SENSE questions come from edge/templates/esp32-sense.json and the CONTROL questions from edge/templates/esp32-control.json. Each sensor entry gives its name, the tags it publishes, and the parameters to ask, with the reference build's wiring as defaults. Neither flash-device.sh nor the wizard page changes when an entry is added.

A sensor also needs code on the board to read it: a reading function in the board application (edge/src/app/cea_sensors.py). If that function already exists, the template entry is all that is needed. A new kind of sensor needs a new reading function, which is a developer's change made through the normal review.

New device types in the onboarding page work the same way. Each tile is an entry in edge/catalog.json. An entry whose script is missing or not executable is shown as unavailable.

Bench mode

./edge/flash-device.sh --unregistered

This brings a board up on WiFi with no platform identity, for a bench with no platform deployed. It asks no slot, ships no application, writes nothing to the database and needs no sign-in. The board is named cea-un-<mac6> and has no MQTT credential, so it cannot connect to the broker. It joins WiFi and keeps WebREPL open, so the warning in MQTT credentials per board applies to it too. To give it a slot later, onboard it normally. Nothing has to be undone.

A registered run also offers to continue unregistered when the platform database does not answer or no sign-in is possible. If you accept, the board ends up the same as with --unregistered.

--no-register is different: it flashes the board for a slot with its application and pins, but does not write the device record. The slot still reads as free, and the broker refuses the board until it is onboarded again with registration.

When onboarding is refused

The wizard explains a refusal from the platform database in plain words:

The wizard saysWhat to do
this role may not onboard boards (permission denied)Ask an administrator for the engineer or maintenance role.
no platform role, or two own rolesAsk an administrator to fix the account in the User Manager.
anonymous request refused, or the sign-in token was refusedSign in again and re-run.
the token expired during the requestRe-run. The slot's record is updated in place.
config-api has no JWT keyAdministrator: run ./deploy-infra.sh, then ./apps/frontend/deploy.sh.
the code expired before the sign-in was finishedRe-run for a new code. If Keycloak said the account is disabled, the access request is still pending or the account was deactivated.
no free SENSE (or CONTROL) slotMark the existing device Inactive, or add a zone in the Units tab.
not offered: ... is not a legal hostnameRename the unit or zone code in the Units tab.

The run checks your sign-in again when it checks the board, just before the erase and just before the registration. If your session has ended (you signed out, or your account was deactivated), the run pauses and asks the same person to sign in again: the browser page sends you to the sign-in page, and a terminal run shows a new code. The run waits up to 15 minutes. If nobody signs in by then, a run that has not yet erased the board stops with "Nothing was erased".

If an administrator has set EDGE_WIZARD_ROLE and you no longer hold that role, the run stops before the erase. After the erase it skips the registration instead, and the board stays unregistered.
